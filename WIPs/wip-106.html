World ID Protocol

1. Abstract

This spec introduces the Authenticator Assertion Token (AAT): a short-lived statement, signed by an Authenticator Provider, about the integrity of the environment in which a single World ID Proof is generated. The Authenticator Provider checks platform integrity evidence (e.g. Apple App Attest) for every request and signs the result with a BabyJubJub-EdDSA-Poseidon2 key. The AAT is verified confidentially, typically inside a ZK circuit, bound to the Relying Party’s request through a blinded commitment, so the Authenticator Provider doesn’t need to learn which Relying Party the proof is for.

2. Motivation

Some use cases need information beyond the World ID Proof about where it was generated, typically when the Authenticator provides inputs the proof cannot verify itself (e.g. a live selfie compared in a ZK circuit). Relying Parties then need to know that a genuine Authenticator on a genuine device produced the proof.

3. Specification

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

  1. The definition of an Authenticator Provider is explicitly introduced into the Protocol. An Authenticator Provider is the publishing entity (e.g. a software company) of an Authenticator client.

  2. An Authenticator Provider MAY opt in to issuing AATs. An AAT is a statement only from the Authenticator Provider. Each Relying Party (RP) decides which Authenticator Providers and which security properties it accepts.

  3. The Field ($F$), the Curve (BabyJubJub), the hash function ($H_t$), the signature scheme (BabyJubJub-EdDSA-Poseidon2) and the PublicKey representation MUST follow WIP-100.

  4. An AAT MUST only be verified as a private input to a ZK circuit, or by a verifier outside a circuit that:

    • the RP trusts to report the verification results,
    • the Authenticator has authenticated through remote attestation (e.g. of a TEE) before sending the AAT, and
    • keeps aat_commitment, exp and sig confidential.

    Authenticator Providers and Authenticators MUST NOT share AATs raw with any other party.

3.2 Authenticator Provider Key

  1. An Authenticator Provider that issues AATs MUST have an authenticator_provider_key, the key that signs its AATs. The authenticator_provider_key MUST be a BabyJubJub-EdDSA-Poseidon2 key pair generated randomly.
  2. The authenticator_provider_key is identified by its kid, which MUST be the compressed wire encoding of its public key as specified in WIP-100 §4.
  3. Circuits identify it by authenticator_provider_key_hash = H_3(DS_KEY; x, y), over the affine coordinates of its public key.
  4. An authenticator_provider_key MUST be published in the Authenticator Metadata, with not_before and not_after, at least 24 hours before it signs its first AAT, so RPs with cached metadata recognize it.
  5. An authenticator_provider_key MUST NOT sign AATs for more than 180 days (not_after - not_before <= 15552000). Authenticator Providers SHOULD rotate keys every 90 days.
  6. To rotate, an Authenticator Provider MUST publish the next key per item 4 before the current key’s not_after, and MUST keep the outgoing key published for at least MAX_AAT_LIFETIME after its last AAT.
  7. The authenticator_provider_key private key SHOULD be generated and used only inside hardware-protected key storage (e.g. an HSM or a TEE), and SHOULD NOT be exportable.
  8. On suspected compromise, the Authenticator Provider MUST mark the key revoked immediately.

3.3 Request Commitment

The Authenticator binds an AAT to a single request through the request commitment aat_commitment:

aat_commitment = H_8(DS_REQ; aud, nonce, cdh, blind)

ValueDescription
audThe rpId of the ProofRequest.
nonceThe nonce of the ProofRequest.
cdhClient data hash. A commitment set by the Authenticator to bind the AAT to its upstream use (e.g. a user’s leaf_index). 0 is the nil value.
blindA blinding factor, generated by the Authenticator. MUST be a random element of $F$, fresh for every request.

The Authenticator MUST send only aat_commitment to the Authenticator Provider, never aud, nonce, cdh or blind.

Every specification that consumes an AAT MUST define what cdh commits to, or explicitly allow the nil value 0. The Authenticator MUST compute cdh exactly as that specification defines.

3.4 Authenticator Assertion Token

An AAT consists of the following values and a signature over them.

ValueTypeDescription
expuint32Expiration time, in seconds since the Unix epoch.
aat_commitmentField elementThe request commitment (see Request Commitment).
sec_flagsuint64Packed security attributes (see Security Flags).
sigSignatureBabyJubJub-EdDSA-Poseidon2 signature by the authenticator_provider_key over message.

The signed message is:

message = H_4(DS_AAT; exp, aat_commitment, sec_flags)

sig MUST follow WIP-100 §3.5, including its encoding.

3.4.1 Encoding

An AAT is transported as a CBOR Web Token (RFC 8392): an untagged COSE_Sign1 (RFC 9052) in deterministic CBOR (RFC 8949 §4.2.1).

  1. The protected header MUST contain only alg (label 1) with the value -65537. The unprotected header MUST be empty or contain only the kid (label 4) of the authenticator_provider_key, as an untrusted hint.
  2. The payload MUST contain exactly the following claims, in this order. nonce and eat_profile are the Entity Attestation Token claims of RFC 9711.
ClaimKeyValue typeValue length (bytes)
exp4uint, in $[2^{16}, 2^{32})$4
nonce10bstr: aat_commitment as a canonical big-endian field element32
eat_profile265tstr: EAT_PROFILE28
sec_flags-70000bstr, big-endian8

With CBOR headers the payload is always 89 bytes. sig is 64 bytes and the kid, if present, 32 bytes.

  1. The signature field MUST carry sig.
  2. The algorithm -65537 (Private Use) is allocated to BabyJubJub-EdDSA-Poseidon2 over an AAT. It does not sign the Sig_structure bytes (RFC 9052 §4.4). Instead it decodes exp, aat_commitment and sec_flags from the claims and signs message. The CWT bytes MUST be exactly the encoding above, and verifiers MUST reject any other encoding.
  3. An AAT is a syntactically valid CWT, but its signature is not over the CBOR bytes. Generic COSE/CWT libraries can decode an AAT but cannot verify it; only verifiers implementing algorithm -65537 as defined here can.

3.5.1 User Presence

user_presence is an assertion by the Authenticator Provider about the user during the proof generation, based on what the Authenticator reports. It SHOULD be covered by the platform integrity evidence.

ValueDefinition
0Undetermined
1User is not present
2User is present, verified by a liveness or biometric check during this request
3User was present within the last 7 days
4User was present within the last 30 days
  1. Values 5 to 7 are reserved and MUST be rejected.
  2. The Authenticator MUST report user_presence only from checks it performed itself. The Authenticator Provider MUST NOT sign a value the Authenticator did not report, or one its evidence contradicts.
  3. Values are identifiers, not an order, they MUST be lowered into the field following WIP-100.
  4. RPs MUST allowlist the exact values they accept.

3.6 Issuance

For every AAT, the Authenticator Provider:

  1. MUST verify platform integrity evidence whose challenge commits to aat_commitment before signing (e.g. an App Attest assertion with clientDataHash = SHA-256(aat_commitment)).
  2. MUST set sec_flags according to the evidence verified for this request, and MUST NOT set a sec_level the evidence does not support.
  3. MUST set exp such that exp - now <= MAX_AAT_LIFETIME at issuance.
  4. MUST set build_version from the evidence where the platform attests it (e.g. Play Integrity versionCode), and otherwise from the Authenticator’s report.
  5. MUST NOT retain a link between a device identifier and an issuance time beyond what abuse prevention requires.

3.7 Verification

AAT verification is specified below as a component embedded in other circuits (e.g. the Nullifier Proof). A verifier outside a circuit MUST perform the same checks, treat the Public values as its reported output and keep the Private values confidential. The component MUST introduce the following inputs.

InputVisibilityTypeDescription
authenticator_provider_key_hashPublicField elementHash of the Authenticator Provider’s key, supplied by the RP.
nowPublicuint32Current time, in seconds since the Unix epoch.
audPublicField elementThe rpId of the request.
noncePublicField elementThe nonce of the request.
platformPublicuint8See Security Flags.
sec_levelPublicuint8See Security Flags.
sec_metaPublicuint8See Security Flags.
user_presencePublicuint8See User Presence.
min_build_versionPublicuint32Minimum build_version the RP accepts.
authenticator_provider_keyPrivatePublicKeyThe key that signed the AAT.
expPrivateuint32From the AAT.
sec_flagsPrivateuint64From the AAT.
sigPrivateSignatureFrom the AAT.
cdhPrivateField elementSee Request Commitment.
blindPrivateField elementSee Request Commitment.

The circuit MUST implement the following constraints:

  1. Request binding. Compute aat_commitment = H_8(DS_REQ; aud, nonce, cdh, blind) from the public aud and nonce inputs and the private cdh and blind. The aud and nonce hashed here MUST be the same values as the public inputs, and this aat_commitment MUST be the one used in message. The circuit embedding the AAT MUST constrain cdh to its own inputs (e.g. recompute it from the leaf_index it proves), otherwise the AAT is not bound to its upstream use.
  2. Signature. Compute message as in Authenticator Assertion Token and verify sig over it under authenticator_provider_key per WIP-100 §3.5.1. H_3(DS_KEY; x, y) of that key MUST equal authenticator_provider_key_hash.
  3. Freshness. exp and now MUST be less than $2^{32}$. The circuit MUST enforce now < exp and exp - now <= MAX_AAT_LIFETIME, as comparisons over the full field $F$.
  4. Security flags. sec_flags MUST be less than $2^{54}$ and MUST equal platform + 2^8 * sec_level + 2^16 * build_version + 2^48 * sec_meta + 2^51 * user_presence, with each sub-field range-checked to its width.
  5. Nonce. nonce MUST NOT equal 0.
  6. User presence. user_presence MUST be less than 5.
  7. Build version. build_version >= min_build_version, as a comparison over the full field $F$. build_version MUST remain private.

A circuit MAY make AAT verification optional through a public boolean input has_aat. When has_aat = 0, constraints 1-4, 6 and 7 MUST NOT be enforced and authenticator_provider_key_hash, platform, sec_level, sec_meta and user_presence MUST equal 0.

exp MUST remain private: its exact value would let the Authenticator Provider link a proof to the AAT it issued.

3.8 Authenticator Metadata

  1. Each Authenticator Provider MUST expose a JSON metadata file over HTTPS at https://<FQDN>/.well-known/world-id-authenticator.json.
  2. The file MUST validate against the JSON Schema in Appendix A2. In summary:
FieldTypeDescription
versionintegerSchema version of this file. MUST be 1 for the format defined here.
provider_idstringStable identifier, which RPs MAY allowlist.
authenticator_provider_keysarrayEach entry: kid (hex), x, y (hex, the in-circuit PublicKey), status (active, retired or revoked), not_before and not_after (seconds since the Unix epoch).
sec_metaobjectMeaning of each sec_meta bit (see item 3).
  1. sec_meta is keyed by bit index ("0", "1", "2"). Each value is an object with name (string) and description (string). A bit without an entry is undefined, and the Authenticator Provider MUST NOT set it.
  2. authenticator_provider_key status values:
    • active: the key signs AATs.
    • retired: the key no longer signs AATs (e.g. after rotation). AATs it signed remain valid until they expire. Authenticator Providers MAY remove a retired key MAX_AAT_LIFETIME after its last AAT.
    • revoked: the key must no longer be trusted (e.g. it was compromised). RPs MUST reject every AAT signed by it.

4. Reference Verification

An RP accepts an AAT-carrying proof by performing the following validations, on the proof’s public inputs or on the values a verifier outside a circuit reports:

  1. authenticator_provider_key_hash is the hash of an authenticator_provider_key that belongs to an allowlisted Authenticator Provider, is active or retired (never revoked), and now is within its validity window.
  2. now is within 5 minutes of the RP’s local time (RECOMMENDED; RPs MAY be stricter).
  3. aud is the RP’s own rpId, and nonce is one the RP issued, has not expired and has not been used before.
  4. platform, sec_level, sec_meta and user_presence match values the RP allowlists.
  5. min_build_version is the RP’s own minimum.

5. Rationale

  1. A single provider-signed token. Verifying device-bound platform signatures (ECDSA P-256 over SHA-256) in-circuit dominates proving cost on mobile devices. Having the Authenticator Provider verify the platform evidence off-circuit reduces in-circuit verification to a single EdDSA signature over a Poseidon2 digest.
  2. Blinded request commitment. The Authenticator Provider must bind its signature to the request, but must not learn the RP or be able to link the proof back to the device. blind makes aat_commitment hiding, and the AAT stays a private input.
  3. CWT for transport only. The AAT is carried as a CWT, but its signature is over message rather than the CBOR bytes, so circuits verify it without parsing or hashing CBOR. Generic COSE libraries do not implement the private-use algorithm.
  4. User presence signed by the Authenticator Provider. The Authenticator runs the presence check, but the Authenticator Provider signs user_presence as part of sec_flags. It is accountable for the value like for every other claim, and can refuse values its evidence does not support.
  5. Verifiers outside a circuit. Some use cases may rely on a TEE that the RP trusts for other checks. Verifying the AAT there adds no new trust assumption and removes its cost from the circuit. Privacy is preserved as long as the verifier keeps aat_commitment, exp and sig confidential, which a TEE enforces through attestation even when the Authenticator Provider operates it. The circuit form in Verification stays the reference, so verification can move back into circuits as proving on mobile devices gets cheaper.
  6. Key hash as public value. A single field element keeps circuits embedding the AAT to one public input for the key, and lets a later key type keep the same interface. RPs compute it from the published x and y.

6. Alternatives Considered

  1. Device-signed AAT with a provider-signed key token. The Authenticator Provider attests a device-bound P-256 key once, and the device signs each AAT. Rejected: verifying P-256 ECDSA over SHA-256 in-circuit is too expensive for proving on mobile devices.
  2. Device-signed AAT with a ZK-friendly key. As above, but with a BabyJubJub device key. Rejected: platforms can not hold such keys in secure hardware, so a device owner can extract the key and sign assertions from any environment.
  3. Pre-fetched AATs. Authenticators obtain AATs ahead of requests to decouple issuance from proof timing. Rejected: an AAT would no longer attest the environment of a specific request, and cdh values that commit to per-request data can not be known in advance.

7. Security

  1. Assertions are Authenticator Provider statements. The Protocol verifies only that an AAT was signed by an authenticator_provider_key. It does not and can not verify the claims: sec_flags reflects only what the Authenticator Provider verified, and user_presence only what the Authenticator reported and the Authenticator Provider accepted. RPs MUST base their trust on the Authenticator Providers they allowlist.
  2. Issuance visibility. The Authenticator Provider observes every AAT issuance (device and time), but not the RP or the request. Issuance and proof times remain correlatable; short lifetimes limit this.
  3. Authenticator Provider key compromise. A leaked authenticator_provider_key lets an attacker mint AATs with arbitrary sec_flags. Revocation is through the Authenticator Metadata; AATs themselves are not revocable and rely on short lifetimes.
  4. Web environments. Browsers offer no remote attestation of the running code. Evidence from web Authenticators proves possession of a user credential only, hence sec_level = 10.
  5. User presence. user_presence is only as trustworthy as the Authenticator’s report and the Authenticator Provider’s checks. Use cases that need stronger guarantees SHOULD verify a signed statement from the check itself (e.g. a TEE face verifier) in-circuit.
  6. Availability. AAT issuance requires the Authenticator Provider to be online. Proofs without an AAT remain valid; RPs decide whether to accept them.

8. Future Considerations

The following may be considered for future versions of this spec.

  1. Integration into the Nullifier Proof and a ProofRequest attribute for requesting AATs.
  2. Delegated AATs (e.g. for agents).
  3. A standard-algorithm AAT profile (e.g. SHA-256 with Ed25519) for verifiers outside circuits, allowing KMS-hosted Authenticator Provider keys and verification with generic COSE libraries.

9. Backwards Compatibility

This WIP introduces new functionality; no existing functionality is affected.
