World ID Protocol

Note

This spec outlines a draft functionality for beta testing. Changes are expected.

1. Abstract

This spec defines the Flamingo Verifier (Verifier), a trusted execution environment (TEE) service. It runs one sandboxed biometric Engine release, provided by an Engine Provider. For a request, the Engine runs a pipeline’s checks, e.g. fraud detection, on some of the request’s entries, e.g. live frames, and compares entries, e.g. a live frame with a Credential image, under a requested match_strictness. If the Engine accepts, the Verifier signs a Flamingo Token over the Engine configuration, the compared entries, the public values of an Authenticator Assertion, if any, and the WIP-107 billing nullifier it checked, if the RP is billed. If a WIP-106 Trust Anchor Key Token (TAKT) and Authenticator Assertion Token (AAT) are provided, they are also verified. Consuming protocols such as WIP-202 use the Flamingo Token to prove the Verifier’s checks to a Relying Party (RP), optionally without revealing any entry.

2. Motivation

Many Proof-of-Human applications like deep fake prevention or human presence verification require A) running fraud detection models like presentation attack detection (PAD) on a set of input images and B) comparing images using embedding models, e.g., to verify that the person on a stream is the same as the one performing a liveness check on a phone.

Building a privacy preserving system for such image comparisons is very difficult. For example, running the models and comparisons locally on the user’s device is privacy-preserving but it has very low security guarantees: a mobile device’s output is not trustworthy, e.g., a jailbroken device could report that fraud detection and embedding comparison were performed, while simply running a spoofed client that does not perform them at all. Therefore, an RP cannot be sure that the claimed checks have actually been executed. Additionally, fraud detection models’ security relies on obscurity and obtaining the model weights, or even just the model architecture, opens up a wide range of attack vectors.

To achieve verifiability in a privacy-preserving way, this document introduces a general approach that runs fraud detection models and embedding models in an attested Trusted Execution Environment (TEE). This allows users to verify that the TEE operator is not able to access any biometric data, and a signature by the TEE proves to RPs that all claimed checks have been correctly executed. The Verifier image MUST be open source and reproducibly built, so anyone can check that its attested measurement matches the source and that no raw media or embeddings leave the TEE. Fraud detection models cannot be open, so the Verifier runs them as a closed Engine inside a kernel-enforced sandbox that has no network or storage access. The Verifier attests which Engine release it runs, and the RP accepts only releases the Engine Provider signed.

This section is non-normative. It sketches the parties and the one-shot verification flow.

Dashed arrows are set up once, except the Billing Contract’s logs, which the host keeps supplying (WIP-107). Numbered arrows are steps 1–6 of one verification; in step 7 the RP verifies the token locally:

  1. The Verifier attests its measurement and its loaded release, and sends that release’s manifest (Attestation and Channel) to the Authenticator. The Authenticator checks both and chooses a configuration. The results of this step can be cached and the attested channel can be re-used.
  2. The Authenticator seals a request to the Verifier. It carries the entries (images or embeddings) and names which of them the pipeline checks (pipeline_inputs) and which the Engine compares (compare) (Authenticator, Request and Response).
  3. The Verifier checks the request and passes it to the sandboxed Engine (Request Processing).
  4. The Engine runs the pipeline’s checks on the pipeline inputs and compares the selected entries (Request Processing).
  5. On a pass, the Verifier builds a Flamingo Token from the request and the loaded release, and signs it (Flamingo Token).
  6. The Authenticator passes the token, or a proof over it such as WIP-202, to the RP.
  7. The RP verifies it (Consuming Flamingo Tokens).

How the RP requests a Flamingo Token or a proof over it, and what it learns, is defined by the consuming protocol (Terminology).

Components and parties:

  • RP: requests and verifies the result, as its consuming protocol defines (Consuming Flamingo Tokens).
  • Authenticator: checks the attestation and the manifest before sending biometrics (Authenticator).
  • Verifier: open source; checks and forwards requests, enforces response timing and signs tokens. It runs one Engine release (Verifier).
  • Sandbox and Engine: closed source and closed weights; run fraud detection and comparison, with no way to export data (Engine, Sandboxed Engine).
  • Host and operator: run the enclave, relay its ciphertext and supply its WIP-107 billing state; trusted for availability, and for billing state where WIP-107 applies (Request Processing).
  • Engine Provider: signs Engine releases and publishes them (Release and Release Manifest, Engine Provider Metadata).
  • Authenticator Provider: decides which Verifier measurements its Authenticators accept and ships them, e.g. in the app release (Authenticator).

What each party is trusted for is in Trust Assumptions.

4. Specification

4.1 Terminology

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

  1. The Verifier is the TEE service this spec defines.
  2. The Engine is the sandboxed component of the Verifier that performs extraction, fraud detection and comparison. This spec defines the Engine’s interface (Engine), not its models or thresholds.
  3. The Engine Provider builds the Engine and signs its release manifests. It is identified by iss, an https URL without query or fragment (RFC 8414 §2, Rationale item 6). It MAY be the same organization as an Authenticator Provider.
  4. The Authenticator Provider is as defined in WIP-106.
  5. The host is the machine that runs the Verifier’s enclave and relays all its traffic, on AWS Nitro the parent EC2 instance. The operator runs the host. Neither is trusted beyond availability and the WIP-107 billing state the host supplies (Trust Assumptions).
  6. A pipeline is an Engine-defined set of pass/fail checks on its pipeline inputs, e.g. fraud detection such as presentation attack or deepfake detection.
  7. Match strictness levels say how similar compared entries must be to count as a match (Match Strictness Levels).
  8. A consuming protocol defines how a Flamingo Token is requested and used, e.g. a proof type such as WIP-202, or an RP that verifies tokens directly (Consuming Flamingo Tokens).
  9. The Field ($F$), the hash function ($H_t$), the signature scheme (BabyJubJub-EdDSA-Poseidon2) and the PublicKey representation MUST follow WIP-100. R(d) reads a 256-bit digest d as a big-endian integer modulo $q$.

4.3 Engine

An Engine is developed and released by an Engine Provider. It operates in a stateless request/response model. It encompasses the following high-level concepts:

  • Request entries. The Engine accepts requests that contain an array of entries. Each entry is one image or embedding with associated metadata (Request and response).
  • Pipeline. The request further specifies pipeline_id, to select the pipeline to run on a subset of entries. The subset is specified via a pipeline_inputs array that contains entry indices (Request Processing).
  • Comparisons. Similarly, an array of indices called compare specifies a subset of entries, possibly overlapping with pipeline_inputs, which are compared pair-wise using Engine-specific models at the requested match_strictness (Match Strictness Levels).
  • Response. The Engine only returns whether every check passed and every comparison matched (Request and response).
  • Releases. An Engine Provider publishes a signed release manifest for every Engine version. The manifest specifies the release’s pipelines, their inputs and response slots, and its match strictness levels (Release and Release Manifest, Release Versioning, Engine Provider Metadata).

4.3.1 Request and response

The Verifier passes the Engine request below to the Engine unchanged and passes nothing else. On the sandbox channel this WIP does not specify its encoding; in the Verifier request it is the payload map (Request and Response), and the types below are CBOR types (RFC 8949).

4.3.2 Match Strictness Levels

  1. Meaning. A match strictness level says how similar compared entries must be to count as a match. A request picks one with match_strictness. Internally, the Engine MAY use different similarity thresholds for a level depending on the inputs, e.g. their image type or quality, as long as the level keeps its documented meaning.
  2. Trade-off. A higher level lowers the chance of a false match, i.e. accepting entries that show different persons, but raises the chance of a false non-match, i.e. rejecting entries that show the same person.
  3. Rules. Levels are defined per release, as the manifest’s ascending match_strictness_levels. A level MUST mean the same whichever pipeline_id a request uses, and a higher level MUST be at least as strict for every two compared entries. The Engine Provider MUST document what each level means.

4.3.3 Request Processing

For each Engine request, in a reset instance (Sandboxed Engine), the Engine:

  1. Validates the request against its release: pipeline_id names one of its pipelines, match_strictness is listed, and the pipeline inputs match the pipeline’s inputs in count and media type. Otherwise it MUST return error.
  2. Checks the pipeline inputs: it MUST run the pipeline’s checks, e.g. presentation attack or deepfake detection, on the entries pipeline_inputs names, reading each entry’s meta as the pipeline defines. The checks MUST NOT depend on match_strictness.
  3. Compares the entries compare names: it extracts what the release compares, e.g. face embeddings, and MUST match every two of them at match_strictness (Match Strictness Levels).
  4. Responds: it MUST return Pass only if every check passed and every comparison matched, and error otherwise (Request and response).

4.3.4 Release and Release Manifest

A release is one version of an Engine: its bundle, i.e. code, model weights and configuration (Sandboxed Engine), and the release manifest that describes it. The manifest names the release’s pipelines and strictness levels, and its hash, release_hash, identifies the release. A Verifier runs one release. See Appendix A2 for an example manifest.

A release manifest is a JWS (RFC 7515) in compact serialization, signed with ES256 by the Engine Provider’s release key. Its protected header MUST contain alg = ES256, kid and typ = world-id-engine-manifest. Its payload is a JSON object:

  1. Release hash. release_hash is the SHA-256 of the manifest’s JWS Payload (RFC 7515 §2). It excludes the protected header and the signature, so re-signing a release keeps its release_hash.
  2. Signatures. RPs MUST verify a release manifest under an active release key of its iss (Engine Provider Metadata) before relying on it. The Verifier and Authenticators do not verify it.

4.3.5 Release Versioning

  1. version MUST be greater than the version of every earlier release of the same iss. Every change to the payload is a new release.
  2. A later release MUST NOT change a pipeline’s inputs, increase the number of its response_slots, or drop a match_strictness level; such a change uses a new pipeline_id value. A later release MAY drop a pipeline, but MUST NOT reuse its pipeline_id for different inputs.
  3. A later release MUST NOT give an existing match_strictness value a different meaning; a changed meaning uses a new value. It MAY change the Engine’s thresholds to keep a level’s meaning, e.g. for a new model.

4.3.6 Engine Provider Metadata

The Engine Provider MUST expose a JSON file over HTTPS at <iss>/.well-known/world-id-engine.json:

Metadata fields:

FieldTypeDescription
versionintegerMUST be 1.
release_keysarrayEach entry: jwk (a P-256 JWK with kid) and status (active, retired or revoked).
manifestsarrayThe release manifests the Engine Provider offers, each a compact JWS. Removing one withdraws its release.

A reader MUST NOT follow redirects to another origin, and MUST ignore manifests whose iss is not the one it fetched the file for. The Verifier never fetches the Engine Provider metadata. RPs compute the engine_config_hash values they accept from it, and SHOULD refresh it at least every 24 hours, so a withdrawn release or a revoked key stops being accepted.

4.4 Verifier

A Verifier is an open-source, reproducibly built AWS Nitro enclave image, run by an operator on a host. It runs one Engine release and serves requests from Authenticators. It encompasses the following high-level concepts:

  • Request and response. A request carries the RP’s aud and nonce, an expiry, the Engine request, and optionally an Authenticator Assertion. On a Pass, the Verifier builds a Flamingo Token from the request, the verified AAT and the loaded release, signs it and returns it (Request and Response, Flamingo Token).
  • Attestation. The Verifier attests its channel key together with the loaded release, and its token signing key, in Nitro attestation documents. Authenticators encrypt their requests to the attested channel key. The Verifier syncs its clock to each new attestation’s timestamp (Attestation and Channel).
  • Processing. The Verifier checks the request, rejects expired and replayed requests, verifies the Authenticator Assertion, and passes the Engine request to the Engine unchanged. Before signing, it checks billing against its own billing state, which its host keeps up to date. It releases each response only at fixed time slots, so its timing reveals little (Request Processing, Response Timing and Replay).
  • Sandboxed Engine. At start-up, the Verifier loads one Engine release and runs it in a sandbox that cannot export data (Sandboxed Engine).
  • Measurement. Anyone can rebuild the image from source and check its PCR values, which identify the Verifier to Authenticators and RPs (Build and Measurement).

4.4.1 Request and Response

The request is a deterministic CBOR map (RFC 8949 §4.2.1) with the fields below. The Authenticator encrypts the entire encoded map to the Verifier (Channel Encoding). Field elements are 32-byte byte strings, the canonical big-endian encoding.

payload is a CBOR byte string that contains the deterministic CBOR encoding (RFC 8949 §4.2.1) of the Engine request. It is carried as a byte string, so the Verifier checks the Authenticator Assertion against exactly the bytes it received and passes them to the Engine unchanged.

4.4.2 Attestation and Channel

  1. Keys. At boot, the Verifier MUST generate a channel key and a Flamingo Token signing key inside the enclave, from its hardware RNG, and MUST NOT export or persist either. It SHOULD replace its channel key frequently, e.g. at each refresh, and accept the previous key for MAX_REQUEST_LIFETIME afterwards.
  2. Documents. The Verifier MUST attest each key in its own Nitro attestation document, a COSE_Sign1 chaining to the AWS Nitro Root G1, with public_key and user_data as in the table below. A document’s timestamp is its creation time, in milliseconds since the Unix epoch.

Attestation documents:

Documentpublic_keyuser_dataUsed by
Channel attestationSHA-256(CHANNEL_KEY_DOMAIN || channel_key)The loaded release_hash.The Authenticator, to check the Verifier and encrypt a request; discarded afterwards.
signing_key_attestationThe Flamingo Token signing key (kid)—RPs, with every Flamingo Token.
  1. Manifest. The Verifier MUST set the channel attestation’s user_data to the release_hash it computed from the manifest it loaded (Sandboxed Engine), and MUST send that manifest, as received, with the attestation.
  2. Response. The Verifier MUST seal the padded response to response_key. Only the requester holds response_key, so the response is bound to its request; a Success is authenticated by its Flamingo Token.
  3. Refresh. The Verifier MUST re-attest its channel key and its signing key at least every MAX_ATTESTATION_AGE, and return its latest signing_key_attestation.
  4. Time. The Verifier MUST sync its clock to the timestamp of each new Nitro attestation and advance it on its monotonic clock in between. It MUST NOT use any other time source.

Channel Encoding. Both directions use the public-key encryption of WIP-100 §3.9.

  1. Info. info is CHANNEL_DOMAIN || 0x00 for a request and CHANNEL_DOMAIN || 0x01 for a response.
  2. Request plaintext. The first 1216 bytes are response_key, a fresh X-Wing encapsulation key; the rest is the Request and Response.
  3. Rejection. The Verifier MUST reject a request shorter than 1216 bytes or with an invalid response_key.

4.4.3 Request Processing

The host MAY drop requests above a size limit it chooses. For each sealed request it relays, the Verifier, in order:

  1. Checks. After decrypting (Channel Encoding), it MUST reject a request that does not meet the Verifier request (Request and Response) and Engine request (Request and response) formats, including their bounds and their references to the loaded release.
  2. Expiry and replay. It MUST reject an expired or replayed request (Response Timing and Replay).
  3. Authenticator Assertion. If aat_inputs is present, every check of WIP-106 §3.8 MUST hold, or it rejects the request. The TAKT, the AAT, the assertion_key and build_version MUST NOT leave the Verifier.
  4. Engine call. It MUST pass the Engine request to the sandboxed Engine unchanged, and nothing else (Sandboxed Engine).
  5. Billing. Before signing, it MUST check billing_nullifier as WIP-107 §4.7 requires, waiting for a registration as WIP-107 §4.8 allows, or it rejects the request. It MAY reject a request that cannot pass the check before the Engine call.
  6. Response. On Pass and a passed billing check, it signs a Flamingo Token (Flamingo Token). It then returns a Success or Failed response (Request and Response), released at a response slot (Response Timing and Replay).

4.4.4 Response Timing and Replay

The host sees when each response leaves the Verifier; slots and replay rejection bound what that reveals (Security item 9).

  1. Slots. Each pipeline’s response_slots list its release times in milliseconds after a request’s arrival (Release and Release Manifest).
  2. Release. The Verifier MUST hold each response until the first slot at or after the Engine’s finish, measured on its monotonic clock from the request’s arrival, and MUST NOT release it earlier, whatever the outcome. If the Engine has not finished by the last slot, the request fails and the Verifier MUST reset the Engine instance. Rejections before the Engine call MAY be released immediately; they do not depend on the entries.
  3. Choosing slots. Engine Providers SHOULD put the first slot at or above the pipeline’s fastest complete run and the last above its 99.9th-percentile run time, with slots in between following its run-time distribution.
  4. Expiry. The Verifier MUST reject a request whose expires_at has passed or is more than MAX_REQUEST_LIFETIME ahead of its time (Attestation and Channel).
  5. Replay. The Verifier MUST reject a request whose (aud, nonce) it has already processed (Security item 9). It keeps each pair until the request’s expires_at, so the set holds at most MAX_REQUEST_LIFETIME of requests. A reboot discards the set with the channel keys, so no older request can be opened.

4.4.5 Sandboxed Engine

  1. Loading. At start-up, the Verifier receives exactly one Engine bundle and its release manifest from the host. It MUST check that the bundle hashes to the manifest’s engine_hash and that the manifest is well-formed (Release and Release Manifest), without verifying its signature, and MUST NOT fetch anything else.
  2. Sandbox. The Verifier MUST run the Engine with no network access, no writable persistent storage, no process creation, no access to the Verifier’s keys, nothing outside its bundle, and only one bounded request-response channel. See the reference implementation’s sandbox for one way to meet these requirements.
  3. Per request. Before each request, the Verifier MUST reset the Engine to a state no earlier request has influenced, e.g. by starting a new instance or restoring one prepared before the first request. The reset MUST NOT depend on the Engine’s cooperation, e.g. the Verifier restarts the Engine process itself. It MUST bound the Engine’s memory, and MUST return an error if the Engine exceeds that bound, crashes, or returns anything other than an Engine response (Request and response). Its runtime is bounded by the last response slot (Response Timing and Replay).

4.4.6 Build and Measurement

The Verifier’s measurement MUST be verifiable from source:

  1. Publication. For each published Verifier measurement, an immutable reference to its source, e.g. a commit hash in a public repository, and its build instructions MUST be publicly available.
  2. Build. Building that source with the documented toolchain MUST produce a bit-identical Enclave Image File (EIF).
  3. Measurement. PCR0, PCR1 and PCR2 of that EIF, as AWS Nitro Enclaves computes them, are the Verifier’s measurement.
  4. Configuration. Everything that affects the Verifier’s behavior MUST be in the EIF. The host supplies only the Engine bundle, its release manifest (Sandboxed Engine), WIP-107 billing state updates and requests.

4.5 Flamingo Token

On a Pass, the Verifier builds a Flamingo Token from the request, the verified AAT, if any, and the loaded release, as specified below.

Envelope. A Flamingo Token is a CWT (RFC 8392) in an untagged COSE_Sign1, encoded as deterministic CBOR (RFC 8949 §4.2.1).

  1. The protected header MUST contain alg (label 1) = -65537 (Private Use, BabyJubJub-EdDSA-Poseidon2) and kid (label 4) = the compressed signing public key.
  2. The signature MUST be a BabyJubJub-EdDSA-Poseidon2 signature per WIP-100 over the signed digest below.

Claims. The payload MUST contain exactly these claims, in the bytewise order of their encoded keys.

ClaimKeyValue
eat_profile265EAT_PROFILE.
compared_entry_hash_k, k = 0..3-90000 - kR(SHA-256(data)) of the entry compare[k] names, over its data only, or 0 if compare has no position k.
aud-90004aud from the request.
nonce-90005nonce from the request.
trust_anchor_key_hash-90006WIP-106 hash of the trust_anchor_key that signed the verified TAKT, or 0 without an AAT.
aat_flags-90007Public TAKT and AAT values, packed as below; 0 without an AAT.
has_aat-900081 if the Verifier verified an AAT, otherwise 0.
now-90009The Verifier’s time when it signed the token, in Unix seconds.
engine_config_hash-90010The Engine configuration that ran; see below.
compare_sources-90011Which pipeline input each compared entry is; see below.
billing_nullifier-90012The WIP-107 billingNullifier the Verifier checked for a billed RP, or 0 for an RP that is not billed.
  1. aat_flags, has_aat, now and compare_sources are CBOR uints. All other claims except eat_profile are 32-byte byte strings, the canonical big-endian encoding of a field element.
  2. eat_profile is not in the signed digest and MUST be treated as an untrusted hint.
  3. Byte k of compare_sources, least significant first, is i + 1 if compare[k] is pipeline_inputs[i], and 0 otherwise, including when compare has no position k.
  4. engine_config_hash is H_4(DS_WIP_201_ENGINE; R(release_hash), pipeline_id, match_strictness) per WIP-100 §3.3.2, with $k = 3$.
  5. The Verifier MUST set billing_nullifier as WIP-107 §4.7 requires, whatever value the request carries.

aat_flags bits. aat_flags packs public values of two WIP-106 objects into one field element: the TAKT’s sec_flags layout (bits 0–51), with the public min_build_version in place of the private build_version, and the AAT’s authenticator_meta in bits WIP-106 leaves 0.

4.6 Authenticator

The Authenticator MUST accept only PCR0–2 values its Authenticator Provider ships with it, e.g. in the app release or as signed configuration. Before sending biometrics, it completes these steps in order, and MUST NOT send biometrics if one fails:

  1. Attestation. It MUST check that the channel attestation (Attestation and Channel):

    • is a valid COSE_Sign1 whose certificate chain leads to the AWS Nitro Root G1 and is valid at the current time;
    • does not have all-zero PCRs, which mark debug mode, and has PCR0–2 it accepts;
    • has public_key = SHA-256(CHANNEL_KEY_DOMAIN || channel_key) for the channel_key it encrypts to;
    • has user_data equal to the release_hash of the manifest the Verifier sent (Release and Release Manifest);
    • has a timestamp at most MAX_ATTESTATION_AGE old.

    It MAY reuse a checked attestation for later requests while these hold.

  2. Configuration. It MUST choose a pipeline the loaded release defines and whose inputs the device can produce, and a match_strictness the release lists, following the consuming protocol’s requirements or, where it sets none, the Authenticator Provider’s policy. It MUST build pipeline_inputs and compare so that they give the compare_sources the consuming protocol requires (Flamingo Token). If no pipeline and level qualify, it MAY use another Verifier instance.

  3. Response timing. It MUST NOT use a pipeline whose response_slots (Response Timing and Replay) list more release times than its configured maximum. The maximum SHOULD be at most 8, so a response’s timing reveals at most 3 bits (Security item 9).

  4. Seal. It MUST seal response_key || request to channel_key (Channel Encoding), send it, and open the response with response_key.

4.7 Consuming Flamingo Tokens

A consuming protocol (Terminology), e.g. WIP-202, defines how an RP requests and uses Flamingo Tokens. An RP MUST NOT accept a Flamingo Token, directly or through the protocol’s proof, unless every check below holds.

Checks. The checks use the Flamingo Token’s claims (Flamingo Token), with aat_flags unpacked into platform, sec_level, min_build_version, sec_meta and authenticator_meta, its signature sig, and the signing key verifier_key. A proof that hides the token MUST enforce checks 2, 3 and 8. For the other checks, it either reveals the values they need or takes the RP’s accepted sets as public inputs.

  1. Attestation. The signing_key_attestation:

    • chains to the AWS Nitro Root G1, with every certificate valid at its timestamp, and does not have all-zero PCRs, which mark debug mode;
    • has PCR0–2 the RP accepts;
    • attests verifier_key (kid is only a hint);
    • has a timestamp at most MAX_ATTESTATION_AGE old.

    An RP that receives the attestation MAY cache it by key; it identifies the Verifier instance, not the user.

  2. Signature. sig verifies under verifier_key per WIP-100 §3.5.1, over the signed digest computed from the values (Flamingo Token), with aat_flags = platform + 2^8 * sec_level + 2^16 * min_build_version + 2^48 * sec_meta + 2^52 * authenticator_meta.

  3. Well-formed values. has_aat is 0 or 1. The aat_flags sub-fields are range-checked to their widths, with the user_presence bits of authenticator_meta below 5. compare_sources < 2^32. With has_aat = 0, trust_anchor_key_hash and the aat_flags sub-fields are 0.

  4. Request. aud is the RP’s own; nonce is one the RP issued, has not expired and has not been used before; and now is recent by the RP’s clock.

  5. Authenticator Assertion. With has_aat = 0, the RP accepts tokens without an AAT. Otherwise min_build_version, trust_anchor_key_hash and the aat_flags sub-fields pass WIP-106 §4.

  6. Engine. engine_config_hash is the hash of a release, pipeline_id and match_strictness the RP accepts, from an active release manifest it verified under an active key of the manifest’s iss (Engine Provider Metadata), including the RP’s minimum version per iss. A circuit MAY take the hash’s components as private values and recompute it, to constrain them.

  7. Statement. The compared entries are the ones the consuming protocol’s statement depends on: compare_sources is the value it requires, e.g. 256, bytes [0, 1, 0, 0]: the entry compared at position 1 is pipeline input 0, and the others are references. Each compared_entry_hash the statement depends on is bound to the protocol’s own inputs, e.g. a Credential claim or the RP’s challenge.

  8. Billing. billing_nullifier is 0, or the consuming protocol binds it to the World ID the Flamingo Token is used for, as WIP-202 constraint 7 does.

5. Trust Assumptions

The protocol assumes the isolation, measurement and attestation of AWS Nitro Enclaves are sound. If they fail, neither privacy nor integrity holds. Support for other TEEs, so that AWS is not the only option, is a Future Consideration. Every party in the table below is trusted only for the listed parts, and a compromise of one only affects those parts, except AWS.

Parties:

AWS (Nitro Enclaves)Isolation, measurement and attestation of the enclave.Nothing: if this fails, neither privacy nor integrity holds.
Engine ProviderEngine correctness: fraud detection, matching, keeping each pipeline stable across releases, and documenting what each level means.Privacy: the sandbox keeps the Engine from exporting data.

Out of scope. Collusion between an RP and the user’s Authenticator, which can then produce any proof the RP accepts, and between an RP, an Engine Provider and the operator, which can only gather more than one response’s worth of timing information through requests the user consents to one by one. Collusion between an Engine Provider and the operator alone is in scope: Sandboxed Engine and Response Timing and Replay bound what they learn per request (Security item 9).

6. Rationale

  1. Match strictness instead of scores (Match Strictness Levels). A score’s meaning depends on the model and the pair, so an RP cannot pick a meaningful threshold, and scores are biometric signals. An ordered strictness survives model upgrades and keeps scores out of every Flamingo Token. Levels apply to comparisons, which every pipeline of a release shares, so the release defines them.
  2. A separate Engine Provider signs the Engine (Release and Release Manifest). Models may come from different parties, and trust in the models stays separate from trust in the capture environment. A pipeline keeps its meaning across an Engine Provider’s releases (Release Versioning).
  3. Only the RP checks manifest signatures (Release and Release Manifest). Who signed a release matters only for whether its results are trusted, which the RP decides; the sandbox protects privacy whoever wrote the Engine. So Authenticators need only accepted PCRs, and the Verifier image contains no Engine Provider keys, so one image serves every Engine Provider.
  4. SHA-384 for the Engine bundle (Release and Release Manifest). Only the Verifier computes engine_hash, over the bundle file, and AWS Nitro Enclaves measures images with SHA-384 too, so the Verifier’s measurement and its bundle check share one algorithm. Every other hash in this WIP is SHA-256, because it is reduced into the field with R(d) or is defined by another spec, e.g. cdh by WIP-106.
  5. Minimum versions and stable pipelines (Release Versioning). RPs accept a minimum version per iss instead of exact releases, so a new release reaches them without changing their requests, and Verifiers can move to it. A breaking change gets a new pipeline_id value, which RPs opt into. As with FIDO metadata’s authenticatorVersion and SUIT sequence numbers, the version is a plain integer that only orders releases.
  6. iss as the Engine Provider identifier (Engine Provider Metadata). As in JWT (RFC 7519) and OAuth metadata (RFC 8414), the signer is named by an https URL from which its metadata location follows. Each manifest repeats it, so a manifest stays bound to its provider wherever it is read.
  7. The AAT is verified in the Verifier (Request and Response). The Verifier is a WIP-106 §3.8 verifier: it keeps the Private inputs confidential and signs the Public values into the token, so RPs apply their WIP-106 §4 policy as usual. cdh covers the exact payload, so the AAT vouches for exactly the compared input.
  8. The AAT is optional (Request and Response). Not every Authenticator has an Authenticator Provider that issues AATs, and requiring one would exclude them. The RP decides per request whether it accepts a Flamingo Token without one.
  9. Opaque entries (Request Processing). The Verifier never decodes entries; only the Engine interprets them. A new capture method or image format then needs a new Engine release, not a new Verifier image, request or token format.
  10. Listed slots per pipeline (Response Timing and Replay). A list rather than a formula lets each Engine fit its slots to its run times, and in the signed manifest the latency trade-off is public. Slots are per pipeline because run times differ; shared slots would let a slow pipeline’s early exits stand out.
  11. Request expiry (Response Timing and Replay). Replay rejection needs a set of processed (aud, nonce) pairs, and the set has to stay bounded. An expires_at in the sealed request lets the Verifier forget each pair once its request expires. MAX_REQUEST_LIFETIME caps the expiry, because anyone can seal a request to the public channel key. The Verifier takes its time from its attestations, so it needs no clock the host sets.
  12. Hashes over the raw images (Flamingo Token). compared_entry_hash is the SHA-256 of the image bytes the Verifier received. Other parties can compute the same hash: the RP hashes its challenge image, and a PoH Credential already lists the SHA-256 of its face image. Embeddings wouldn’t work, because only the Engine can compute them.
  13. Signature over claim values, not CBOR bytes (Flamingo Token). The signature covers a Poseidon2 hash of the claim values, so a circuit verifies the Flamingo Token without parsing CBOR.
  14. Verifier time in the token (Flamingo Token). The Verifier checks the AAT at its own time and signs that time as now, so an Authenticator cannot pass off an expired TAKT or AAT by stating an old time. Every token carries it, so RPs can check a token’s age with or without an AAT; the single-use nonce still makes it fresh.
  15. Engine configuration hash (Flamingo Token). As in remote attestation (RFC 9334), the Verifier reports a measurement and the RP appraises it against reference values, here signed release manifests. One hash gives RPs exact control over accepted configurations, keeps the individual values private, and lets circuits constrain its components. Its release input hashes the manifest’s JWS Payload rather than the bundle, so the pipelines and slots the Verifier enforces are the ones the RP accepted, and re-signing a release keeps the hash stable.

7. Alternatives Considered

  1. Running the models in a ZK circuit. The Authenticator proves extraction and fraud detection in ZK. Rejected: proving these models is still computationally infeasible for most devices and most models, and the prover would need the model weights, while fraud detection relies on keeping them secret.
  2. MPC. Parties jointly run the models over secret-shared inputs and weights. Rejected: it runs the models orders of magnitude slower and adds the assumption that the parties don’t collude.
  3. Random or fixed response times. Random delays only lower the timing channel’s bandwidth, since repeated requests average the noise out. A single fixed response time removes the channel but makes every request wait for the worst case. Rejected in favor of quantized response times.
  4. Exact release_hash lists. The RP accepts only listed releases. Rejected: every release would require RPs to update their accepted sets, and Verifiers to keep old releases loaded until they do.
  5. Semantic versions. MAJOR.MINOR.PATCH with breaking changes in a new major. Rejected: the only boundary RPs need is “breaking or not”, which a new pipeline_id value expresses without range rules.

8. Security

  1. Post-quantum channel (Attestation and Channel). Biometrics don’t expire, so a party that records ciphertexts today (e.g. the host) MUST NOT be able to decrypt them with a future quantum computer. X-Wing combines ML-KEM-768 with X25519 and stays secure while either holds, assuming its SHA3 hash functions are secure.
  2. Classical token signatures (Flamingo Token). A quantum computer that recovers the Verifier’s signing key can forge Flamingo Tokens for unspent nonces, claiming comparisons no Engine ran. RPs MUST stop accepting BabyJubJub-EdDSA-Poseidon2 tokens before that becomes practical, and migrate to a post-quantum scheme.
  3. Authenticator integrity and missing AATs (Request and Response). A TAKT and an AAT show that a genuine Authenticator produced payload, which keeps modified or emulated Authenticators from injecting media. Without an AAT anyone can submit arbitrary media, and the verdict becomes an oracle for tuning attacks; RPs that accept has_aat = 0 accept that risk.
  4. Unchecked entries (Flamingo Token). An entry the pipeline did not check, e.g. a replayed photo, can be compared like any other. compare_sources shows which compared entries the pipeline checked, so a consuming protocol that requires a checked live capture rejects tokens where it was only compared.
  5. Unreviewed Engines (Release and Release Manifest). A host may load any Engine, and the channel attestation reveals which one. Authenticators do not check who signed it, so they may send biometrics to an unreviewed Engine; the sandbox still keeps it from exporting data (item 6), and its Flamingo Token carries an engine_config_hash no RP accepts. A leaked release key lets an attacker publish release manifests RPs accept until the Engine Provider marks the key revoked and RPs refresh its metadata (Engine Provider Metadata). RPs accept new releases unreviewed, so a leaked key or a faulty release reaches them at once; the Engine Provider withdraws a release by removing its manifest, and RPs MAY raise the minimum version they accept.
  6. Closed Engine (Sandboxed Engine). The Engine is not trusted with privacy. The sandbox removes its channels out, the per-request reset keeps one request’s data from the next, and debug_report reaches only the requester and is forwarded only with the user’s consent.
  7. Flamingo Token privacy (Consuming Flamingo Tokens). compared_entry_hash of a credential entry is constant per user, and a nonzero billing_nullifier per user, RP and billing period, so together with aud and nonce a Flamingo Token links a user to a specific RP request. Consuming protocols MUST keep Flamingo Tokens private, e.g. as private inputs to WIP-202.
  8. Verifier keys (Attestation and Channel). The Verifier generates its signing key inside the TEE at boot from the hardware RNG and never exports it, so a key in a valid signing_key_attestation was generated by that measurement and each boot uses a new key. A key cannot be revoked; RPs stop accepting a compromised measurement, and MAX_ATTESTATION_AGE bounds how long its attestation stays acceptable.
  9. Timing (Response Timing and Replay). The host sees when each response leaves the Verifier, and a malicious Engine can modulate its run time with the input. Releasing responses only at slots limits each request to revealing its slot, at most $\log_2 n$ bits for $n$ slots, a budget the Authenticator checks before sending biometrics (Authenticator). Replay rejection keeps the bound per request: otherwise the host could replay one request, and the Engine could leak a different part of the input on each run. An Engine that crashed the enclave could signal outside the slots, so the Verifier bounds the Engine’s memory and turns any Engine failure into an error released at a slot (Sandboxed Engine). Rejections before the Engine call depend only on the request’s structure, its expiry, the replay set, the AAT and the billing state, so they are released immediately. Waiting for a registration (WIP-107 §4.8) can move a response to a later slot, which reveals when the user registered, not the entries. With per-pipeline slots, timing may also reveal the release and pipeline. Microarchitectural side channels on shared hardware remain outside the guarantees of AWS Nitro Enclaves.
  10. Stale measurements (Authenticator). An Authenticator keeps accepting a compromised Verifier measurement until its Authenticator Provider removes it. Shipping the accepted PCRs as signed, expiring configuration, rather than only with app releases, shortens that window.

9. Future Considerations

  1. Other TEEs. Support for TEEs beyond AWS Nitro Enclaves, through attestation profiles that map each provider’s document, root and measurement to the rules of Attestation and Channel.
  2. Several Engines per Verifier. A Verifier that loads more than one release. As for pipelines today, the Authenticator would choose among them, and the RP accepts only the configurations it allows (Consuming Flamingo Tokens check 6).
  3. Published measurements. A standard format for publishing Verifier PCR values with a status, from which RPs and Authenticator Providers build their accepted sets.

10. Backwards Compatibility

This WIP introduces a new interface; no existing contracts or functionality are affected.
