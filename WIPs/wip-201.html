World ID Protocol

Note

This spec outlines a draft functionality for beta testing. Changes are expected.

1. Abstract

This spec defines the Flamingo Verifier (Verifier), a trusted execution environment (TEE) service. It receives up to eight images or embeddings, a pipeline and a match_strictness, and runs a sandboxed biometric Engine, provided by an Engine Provider, for fraud detection and comparison. If the Engine accepts, the Verifier signs a Flamingo Token over the Engine configuration, the compared entries and the public values of an Authenticator Assertion, if any. If a WIP-106 Trust Anchor Key Token (TAKT) and Authenticator Assertion Token (AAT) are provided, they are also verified. WIP-202 consumes the Flamingo Token to prove the comparison to a Relying Party (RP) without revealing any entry.

2. Motivation

Many Proof-of-Human applications like deep fake prevention or human presence verification require A) running fraud detection models like presentation attack detection (PAD) on a set of input images and B) comparing images using embedding models, e.g., to verify that the person on a stream is the same as the one performing a liveness check on a phone.

Building a privacy preserving system for such image comparisons is very difficult. For example, running the models and comparisons locally on the user’s device is privacy-preserving but it has very low security guarantees: a mobile device’s output is not trustworthy, e.g., a jailbroken device could report that fraud detection and embedding comparison were performed, while simply running a spoofed client that does not perform them at all. Therefore, an RP cannot be sure that the claimed checks have actually been executed. Additionally, fraud detection models’ security relies on obscurity and obtaining the model weights, or even just the model architecture, opens up a wide range of attack vectors.

To achieve verifiability in a privacy-preserving way, this document introduces a general approach that runs fraud detection models and embedding models in an attested Trusted Execution Environment (TEE). This allows users to verify that the TEE operator is not able to access any biometric data, and a signature by the TEE proves to RPs that all claimed checks have been correctly executed. The Verifier image MUST be open source and reproducibly built, so anyone can check that its attested measurement matches the source and that no raw media or embeddings leave the TEE. Fraud detection models cannot be open, so the Verifier runs them as a closed Engine inside a kernel-enforced sandbox that has no network or storage access. The Authenticator chooses the Engine by its hash, from a release manifest the Engine Provider signs.

3. Specification

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

  1. The Engine is the sandboxed component of the Verifier that performs extraction, fraud detection and comparison. This spec defines none of them.
  2. The Engine Provider builds the Engine and signs its release manifests. It MAY be the same organization as an Authenticator Provider (WIP-106).
  3. The host is the machine that runs the Verifier’s enclave and relays all its traffic, on AWS Nitro the parent EC2 instance. The operator runs the host. Neither is trusted beyond availability (Trust Assumptions).
  4. The Field ($F$), the hash function ($H_t$), the signature scheme (BabyJubJub-EdDSA-Poseidon2) and the PublicKey representation MUST follow WIP-100. R(d) reads a 256-bit digest d as a big-endian integer modulo $q$.

3.2 Request

The request is a deterministic CBOR map (RFC 8949 §4.2.1) with the fields below. The Authenticator encrypts the entire encoded map to the Verifier (Channel Encoding). Field elements are 32-byte byte strings, the canonical big-endian encoding.

payload is a CBOR byte string that contains a second deterministic CBOR map, the payload fields below. It is nested as bytes so that cdh commits to its exact encoding.

  1. The Verifier checks the payload’s shape and bounds, resolves release_hash, pipeline and match_strictness against the loaded release (Release Manifests), and hashes the entries compare names, in order, into compared_entry_hash (Claims). It interprets nothing else and forwards the payload to the Engine. Roles (Credential item, live frame, challenge) are fixed by pipeline through positions in compare.
  2. The Verifier MUST reject a request of any other shape, exceeding a bound, or whose compare repeats or names an out-of-range index. It MUST reject a sealed request larger than the largest max_request_bytes of its loaded releases before decrypting it, and one larger than its pipeline’s max_request_bytes after.

  2. error is implementation-defined and bounded in size; it comes from the Verifier or, passed through, from the Engine.
  3. debug_report is optional Engine output outside the Flamingo Token. The Verifier MUST NOT emit a report larger than MAX_DEBUG_REPORT. Clients MUST NOT forward it without the user’s explicit consent, and only to the Engine Provider. It SHOULD let the user inspect a report before forwarding it.
  4. The Verifier MUST emit a Flamingo Token only when the Engine returns Pass.

3.5 Engine

  1. Each pipeline defines the entry layout, how each entry’s meta is read, and which checks run. Each pipeline sets the match thresholds that meet each match_strictness level. Fraud detection is fixed by pipeline and does not vary with match_strictness.
  2. Each release manifest defines the match_strictness levels independently of pipeline: every pipeline MUST support every level, a level MUST mean the same in every pipeline, and a higher level MUST be at least as strict for every compared pair. The Engine MUST reject a match_strictness the release manifest does not define.
  3. Engine Provider. The Engine Provider builds the Engine and signs each release manifest (Release Manifests). A Verifier MAY load several Engines. It MUST reject a request unless it loaded the release named by release_hash.
  4. The Verifier MUST pass the payload fields to the Engine unchanged. The Engine MUST return Pass, meaning every check passed and every compared pair cleared match_strictness, or an error, either with an optional debug_report and never with scores. This WIP does not specify the encoding.

3.5.1 Isolation

The Engine sees raw biometrics and runs closed, injected models. The Verifier MUST give it no network access, no writable persistent storage, no process creation and no access to the Verifier’s keys, and only one bounded request-response channel. Each request MUST run in a fresh or reset Engine instance, so no data from one request reaches another. The Verifier MUST bound the Engine’s memory and return an error when it is exceeded. Response Timing bounds its runtime and the capacity of its timing channel to the host. See the reference implementation’s sandbox for one way to meet these requirements.

3.5.2 Release Manifests

A release manifest is a JWS (RFC 7515) in compact serialization, signed with ES256 by the Engine Provider’s release key. Its protected header MUST contain alg = ES256, kid and typ = world-id-engine-manifest. Its payload is a JSON object:

FieldTypeDescription
engine_hashstringSHA-256 of the Engine bundle, hex.
versionstringThe Engine Provider’s label for the release, unique per Engine Provider, for people and logs.
pipelinesarrayEach entry: pipeline (integer), description (string), which states its checks and the meaning of each compare position, response_slots (array of integers, release times in milliseconds; see Response Timing) and max_request_bytes (integer), the largest sealed request it accepts.
match_strictness_levelsarrayEach entry: match_strictness (integer) and description (string), ascending.

pipeline values MUST be unique within a manifest, and so MUST match_strictness values.

  1. Release hash. release_hash is the SHA-256 of the manifest’s JWS Payload (RFC 7515 §2). It excludes the protected header and the signature, so re-signing a release keeps its release_hash.
  2. Loading. The Engine bundle is everything the Engine runs: code, model weights and configuration. The host passes each bundle at start-up, as one artifact, together with its release manifest. The Verifier MUST check that the bundle hashes to the manifest’s engine_hash, that its pipeline and match_strictness values are unique, and that every response_slots is a non-empty, strictly ascending array of positive integers. It MUST NOT let an Engine load anything outside its bundle, and MUST run a request only on the release whose release_hash the request names, with a pipeline and match_strictness that release defines. It verifies no signature and fetches nothing.
  3. Signatures. RPs and Authenticators MUST verify a release manifest under an active release key of an Engine Provider they trust before relying on it.
  4. Engine Provider Metadata. The Engine Provider MUST expose a JSON file over HTTPS at https://<FQDN>/.well-known/world-id-engine.json:
FieldTypeDescription
versionintegerMUST be 1.
provider_idstringStable identifier, which RPs MAY allowlist.
release_keysarrayEach entry: jwk (a P-256 JWK with kid) and status (active, retired or revoked).
manifestsarrayThe release manifests the Engine Provider offers, each a compact JWS. Removing one withdraws its release.

The Verifier never fetches the Engine Provider metadata. RPs compute the engine_config_hash values they accept from it, and Authenticators read pipelines to lay out compare.

3.5.3 Engine Selection

  1. Offer. The RP lists the configurations it accepts as (release_hash, pipeline, match_strictness) tuples, in order of preference. How it conveys them is outside this WIP.
  2. Availability. The Verifier MUST advertise the release_hash values of its loaded releases to the Authenticator, alongside its channel attestation. The list is not covered by the attestation; a wrong list only makes requests fail.
  3. Choice. The Authenticator MUST choose the first offered tuple its device supports and the Verifier has loaded, and set release_hash, pipeline and match_strictness from it.
  4. Check. The RP accepts only the engine_config_hash of a tuple it offered (Reference Verification).

engine_config_hash = H_4(DS_WIP_201_ENGINE; R(release_hash), pipeline, match_strictness) identifies the chosen tuple. The Verifier signs it into the Flamingo Token, and the RP checks it against the tuples it offered.

3.5.4 Response Timing

  1. Slots. Each pipeline’s response_slots (Release Manifests) list its release times in milliseconds after a request’s arrival. With one slot, every response takes exactly that long.
  2. Release. The Verifier MUST release each response at the first slot of the request’s pipeline at which the Engine has finished, measured from the request’s arrival on its monotonic clock, whatever the outcome. A request whose Engine has not finished by the last slot fails; the Verifier MUST then terminate and reset the Engine instance.
  3. Choosing slots. Engine Providers SHOULD set the first slot at or above the pipeline’s fastest complete run, so early exits, e.g. a rejected input, are released together with completed runs, and the last slot above its 99.9th-percentile run time on the intended hardware, since slower requests fail. Between them, slots SHOULD follow the pipeline’s run-time distribution.
  4. Leakage budget. A response reveals at most $\log_2 n$ bits about its run time, for $n$ slots. Authenticators MUST refuse a release whose pipeline exceeds the slot count they accept before sending biometrics, and SHOULD accept at most 8.

3.6 Flamingo Token

The Flamingo Token is the primary output of a Verifier after a comparison. A Flamingo Token is a CWT (RFC 8392) in an untagged COSE_Sign1, encoded as deterministic CBOR (RFC 8949 §4.2.1).

  1. The protected header MUST contain alg (label 1) = -65537 (Private Use, BabyJubJub-EdDSA-Poseidon2) and kid (label 4) = the compressed signing public key.
  2. The signature MUST be a BabyJubJub-EdDSA-Poseidon2 signature per WIP-100 over the signed digest.

3.6.1 Claims

The payload MUST contain exactly these claims, in the bytewise order of their encoded keys.

ClaimKeyValue

compared_entry_hash_k, k = 0..3-90000 - kR(SHA-256(entries[compare[k]].data)), or 0 if compare has no position k.

nonce-90005nonce from the request.
trust_anchor_key_hash-90006WIP-106 hash of the trust_anchor_key that signed the verified TAKT, or 0 without an AAT.
aat_flags-90007platform + 2^8 * sec_level + 2^16 * min_build_version + 2^48 * sec_meta + 2^52 * authenticator_meta: the WIP-106 sec_flags layout with the public min_build_version in place of build_version, and authenticator_meta in bits 52-56; 0 without an AAT.

  2. eat_profile is not in the signed digest and MUST be treated as an untrusted hint.

3.6.2 Signed Digest

The signed message is not the COSE Sig_structure. It MUST be

H_16(DS_WIP_201; now,
     compared_entry_hash_0, compared_entry_hash_1, compared_entry_hash_2, compared_entry_hash_3,
     aud, nonce, trust_anchor_key_hash, aat_flags, has_aat, engine_config_hash)

per WIP-100 §3.3.2, with $k = 11$. A compared_entry_hash_k without a compared entry at position k is 0.

Four slots remain free.

3.7 Verifiability and Reproducible Builds

The Verifier runs as an AWS Nitro Enclaves image, and its measurement MUST be verifiable from source:

  1. Source. Each Verifier release MUST name its source by an immutable reference, e.g. a commit hash in a public repository.
  2. Build. Building that source with the documented toolchain MUST produce a bit-identical Enclave Image File (EIF).
  3. Measurement. PCR0, PCR1 and PCR2 of that EIF, as AWS Nitro Enclaves computes them, are the Verifier’s measurement.
  4. Publication. The Verifier operator MUST publish, per release, the source reference, the build instructions and PCR0–2.
  5. Acceptance. RPs and Authenticators MUST accept only PCR values they trust.

Engines are injected at runtime and bound by release_hash (Engine).

3.8 Attestation and Transport

The Verifier generates a channel key and a Flamingo Token signing key at boot and attests each in its own Nitro attestation document: a COSE_Sign1 chaining to the AWS Nitro Root G1. Its PCR0–2 are the measurement, its timestamp in milliseconds divided by 1000 is the attestation time, and its public_key binds the key below. A document with all-zero PCRs comes from debug mode and MUST be rejected.

Documentpublic_keyUsed by
Channel attestationSHA-256(CHANNEL_KEY_DOMAIN || channel_key)The Authenticator, to encrypt a request; discarded afterwards.
signing_key_attestationThe Flamingo Token signing key (kid)Consumers, with every Flamingo Token.

  1. Channel. Before sending a request, the Authenticator MUST check that the channel attestation:

    • is a valid COSE_Sign1 whose certificate chain leads to the AWS Nitro Root G1 and is valid at the current time;
    • does not have all-zero PCRs, and has PCR0–2 it accepts (Verifiability);
    • has public_key = SHA-256(CHANNEL_KEY_DOMAIN || channel_key) for the channel_key it encrypts to;
    • has a timestamp at most MAX_ATTESTATION_AGE old.

    It then seals response_key || request to channel_key (Channel Encoding), where response_key is a fresh X-Wing encapsulation key and request the plaintext of Request.

  2. Response. The Verifier MUST seal the padded response to response_key. Only the requester holds response_key, so the response is bound to its request; a Success is authenticated by its Flamingo Token.

  3. Replay. The Verifier MUST reject a request whose (aud, nonce) it has already processed under the same channel_key, before running the Engine. The channel_key MUST NOT be exported or persisted across boots, so an in-memory set suffices: a reset discards the key along with the set, and no other instance can open a request sealed to it.

  4. Refresh. The Verifier MUST re-attest its signing key at least every MAX_ATTESTATION_AGE and return its latest signing_key_attestation.

  5. Carrying. A proof or message that relies on a Flamingo Token MUST carry the Flamingo Token’s signing_key_attestation.

The Engine needs no attestation of its own: the measured Verifier signs its engine_config_hash into each Flamingo Token. One signing_key_attestation covers every Flamingo Token of a boot, so consumers MAY cache it by key. It identifies the Verifier instance, not the user.

3.8.1 Channel Encoding

Both directions use the public-key encryption of WIP-100 §3.9.

  1. Info. info is CHANNEL_DOMAIN || 0x00 for a request and CHANNEL_DOMAIN || 0x01 for a response.
  2. Request plaintext. The first 1216 bytes are response_key, an X-Wing encapsulation key; the rest is the request.
  3. Rejection. The Verifier MUST reject a request shorter than 1216 bytes or with an invalid response_key.

3.8.2 Authenticator Behavior

For each request, the Authenticator MUST, in order:

  1. Choose a configuration (Engine Selection).
  2. Verify its release manifest (Release Manifests), including its response_slots (Response Timing).
  3. Verify the channel attestation (Channel), including PCR0–2 it trusts (Verifiability).
  4. Seal and send the request (Channel Encoding), and open the response with its response_key.

It MUST NOT send biometrics if any step fails.

  2. Request binding. The Flamingo Token is for this request.
    • The digest uses the public aud and nonce.
  3. Authenticator Assertion. The Flamingo Token carries the AAT result, or none.

    • The digest uses the public engine_config_hash.
    • An embedding circuit MAY take its components as private inputs and recompute it, to constrain them.

The component returns compared_entry_hash. The embedding circuit MUST bind each hash its statement depends on to its own inputs (e.g. the Issuer’s claim or the RP’s challenge).

4. Trust Assumptions

The protocol assumes the isolation, measurement and attestation of AWS Nitro Enclaves are sound. If they fail, neither privacy nor integrity holds. Every party in the table below is trusted only for the listed parts, and a compromise of one only affects those parts, except AWS.

PartyTrusted forNot trusted for
AWS (Nitro Enclaves)Isolation, measurement and attestation of the enclave.Nothing: if this fails, neither privacy nor integrity holds.
Engine ProviderEngine correctness: fraud detection, matching, and accurate release manifest descriptions.Privacy: the sandbox keeps the Engine from exporting data.
Authenticator ProviderVerifying the Authenticator’s integrity, as stated in the TAKT.—
AuthenticatorThe source and freshness of the live capture.—
Host and operatorAvailability only.Privacy and integrity: they see only ciphertext, and the Verifier rejects replayed requests (Attestation and Transport).

Out of scope. Collusion between an RP and the user’s Authenticator, which can then produce any proof the RP accepts, and between an RP, an Engine Provider and the operator, which can only gather more than one response’s worth of timing information through requests the user consents to one by one. Collusion between an Engine Provider and the operator alone is in scope: Isolation and Response Timing bound what they learn per request, and Replay keeps them from repeating a request.

5. Reference Verification

A consumer accepts a Flamingo Token if:

  1. The signing_key_attestation:
    • chains to the AWS Nitro Root G1, with every certificate valid at its timestamp, and does not have all-zero PCRs;
    • has PCR0–2 the RP accepts (Verifiability);
    • attests the key that signed the Flamingo Token (kid is only a hint);
    • has a timestamp at most MAX_ATTESTATION_AGE old.
  2. The signature verifies under that key.
  3. The request matches:
    • aud is the RP’s own;
    • nonce is one the RP issued, has not expired and has not been used before.
  4. If has_aat = 0, the RP accepts requests without an AAT. Otherwise the public values pass WIP-106 §4: now, min_build_version, trust_anchor_key_hash and the aat_flags sub-fields.
  5. engine_config_hash is the hash of a tuple the RP offered (Engine Selection), from an active release manifest it verified under an active key of a trusted Engine Provider.

6. Rationale

  1. The Verifier interprets nothing. Roles, frame semantics and thresholds live in the Engine and the consumer. A new capture method or credential format never changes the request or Flamingo Token.
  2. The AAT is verified in the Verifier. WIP-106 §3.8 requires a verifier that keeps the Private inputs confidential and reports only the Public values; the attested Verifier is one. The Verifier already handles the media, and consumers save one signature verification. As cdh covers the exact payload, the AAT vouches for exactly the compared input.
  3. The AAT is optional. Not every Authenticator has an Authenticator Provider that issues AATs, and requiring one would exclude them. The RP decides per request whether it accepts a Flamingo Token without one.
  4. Public values as claims. The Flamingo Token carries the Public values of WIP-106 §3.8, so a consumer applies the same RP policy either way. Consumers read them directly; the Verifier is trusted to derive them from one request, as it is for the comparison. build_version stays private as WIP-106 requires; min_build_version takes its place.
  5. SHA-256 over received bytes. RPs and Issuers compute or check these hashes outside circuits, where SHA-256 is available everywhere. They cover the bytes the Verifier received, not embeddings derived from them, which no other party could reproduce.
  6. Signature over claim values, not CBOR bytes. The signature covers a Poseidon2 hash of the claim values, so a circuit verifies the Flamingo Token without parsing CBOR. Each claim keeps its own field element; the wider t=16 permutation costs less than unpacking packed claims in-circuit.
  7. No Verifier time. Most TEEs have no trusted clock, so the Verifier does not timestamp the Flamingo Token; the RP’s single-use nonce makes it fresh. The Authenticator states now for the AAT: the Verifier checks the AAT is valid at that now and signs it, and the RP checks now against its own clock (WIP-106 §4).
  8. Match strictness instead of scores. A score’s meaning depends on the model and the pair, so an RP cannot pick a meaningful threshold, and scores are biometric signals. An ordered strictness survives model upgrades and keeps scores out of every Flamingo Token.
  9. A separate Engine Provider signs the Engine. Models may come from different parties, and trust in the models stays separate from trust in the capture environment. Pipelines only have meaning relative to an Engine release manifest.
  10. Engine configuration hash. As in remote attestation (RFC 9334), the Verifier reports a measurement and the RP appraises it against reference values, here signed release manifests. One hash gives RPs exact control over accepted configurations, keeps the individual values private, and lets circuits constrain its components.
  11. Signatures outside the Verifier. The RP’s allowlist and the Authenticator’s release_hash give the protection a signature check in the TEE would, so one audited Verifier image serves every Engine Provider without trusted keys in its measurement.
  12. Quantized response times. The host sees when each response leaves, and an Engine’s execution time can depend on, or be modulated by, the biometric input. Releasing responses only at a few slots limits what that reveals to the slot index, at most $\log_2 n$ bits per request for $n$ slots, wherever the slots lie. Listing the slots rather than deriving them from a formula lets each Engine fit them to its run times, e.g. passes that cluster around two durations, and leaves no rounding for implementations to disagree on. The slots are in the signed manifest, so each Engine sets its latency trade-off in the open and Authenticators enforce their limit. A first slot no shorter than the fastest complete run keeps early exits from standing out, and the last slot bounds the Engine’s runtime. Rejecting replayed requests keeps the host from collecting several observations of the same request. Slots are per pipeline because run times differ by pipeline; shared slots would let early exits of a slow pipeline stand out.
  13. Release hash. The token commits to the signed release rather than to the bundle, so the pipelines and response slots the Verifier enforces are those the RP accepted. Hashing the JWS Payload instead of the JWS keeps the hash stable when a release is re-signed, e.g. after a key rotation, since ES256 signatures are randomized.

7. Alternatives Considered

  1. Running the models in a ZK circuit. The Authenticator proves extraction and fraud detection in ZK. Rejected: proving these models is still computationally infeasible for most devices and most models, and the prover would need the model weights, while fraud detection relies on keeping them secret.
  2. MPC. Parties jointly run the models over secret-shared inputs and weights. Rejected: it runs the models orders of magnitude slower and adds the assumption that the parties don’t collude.
  3. Random or fixed response times. Random delays only lower the timing channel’s bandwidth, since repeated requests average the noise out. A single fixed response time removes the channel but makes every request wait for the worst case. Rejected in favor of quantized response times.

8. Security

  1. Post-quantum channel. Biometrics don’t expire, so a party that records ciphertexts today (e.g. the host) MUST NOT be able to decrypt them with a future quantum computer. X-Wing combines ML-KEM-768 with X25519 and stays secure while either holds, assuming its SHA3 hash functions are secure. Flamingo Token signatures are not post-quantum; the single-use nonce only prevents replay of an existing token, not forgery of tokens for nonces not yet spent once BabyJubJub-EdDSA-Poseidon2 becomes forgeable (e.g. a quantum computer recovers the Verifier’s signing key), letting a forger claim a live comparison no Engine ever verified. RPs MUST stop accepting Flamingo Tokens signed with this scheme once it is considered forgeable (e.g. once a cryptographically relevant quantum computer is considered feasible), i.e. before forgery becomes practical, and migrate to a post-quantum signature scheme.
  2. Authenticator integrity and missing AATs. A TAKT and an AAT show that a genuine Authenticator produced payload, which keeps modified or emulated Authenticators from injecting media. Without an AAT anyone can submit arbitrary media, and the verdict becomes an oracle for tuning attacks; RPs that accept has_aat = 0 accept that risk.
  3. Unreviewed Engines. A host may load any Engine, but an honest request reaches only the Engine whose hash the Authenticator chose, bound by cdh, and a Flamingo Token from another Engine carries an engine_config_hash no RP accepts. A leaked release key lets an attacker publish release manifests RPs and Authenticators accept until the Engine Provider marks the key revoked. Even a malicious Engine cannot export data directly (item 4).
  4. Closed Engine. The Engine is not trusted with privacy. The sandbox removes its channels out, the per-request reset keeps one request’s data from the next, and debug_report reaches only the requester and is forwarded only with the user’s consent.
  5. Flamingo Token privacy. compared_entry_hash of a credential entry is constant per user, so together with aud and nonce a Flamingo Token links a user to a specific RP request. Consumers MUST keep Flamingo Tokens private, e.g. as private inputs to WIP-202.
  6. Verifier keys. The Verifier generates its signing key inside the TEE at boot from the hardware RNG and never exports it, so a key in a valid signing_key_attestation was generated by that measurement and each boot uses a new key. A key cannot be revoked; RPs stop accepting a compromised measurement, and MAX_ATTESTATION_AGE bounds how long its attestation stays acceptable.
  7. Timing. Each response reveals which slot of its pipeline it was released in (Response Timing), at most $\log_2 n$ bits per request for $n$ slots, a budget the Authenticator checks before sending biometrics; with per-pipeline slots, timing may also reveal the release and pipeline. Microarchitectural side channels on shared hardware remain outside the guarantees of AWS Nitro Enclaves.

9. Future Considerations

  1. Other TEEs. Support for TEEs beyond AWS Nitro Enclaves, through attestation profiles that map each provider’s document, root and measurement to the rules of Attestation and Transport.
