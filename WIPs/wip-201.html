World ID Protocol

Note

This spec outlines a draft functionality for beta testing. Changes are expected.

1. Abstract

This spec defines the Flamingo Verifier (Verifier), a trusted execution environment (TEE) service. It runs one sandboxed biometric Engine release, provided by an Engine Provider. An Engine is a program of biometric models, e.g. presentation attack detection and face matching, that takes a request’s entries and returns pass or fail; its code and weights can stay private. A release has one or more pipelines, each identified by its pipeline_id, and its release manifest describes them all. Consuming protocols define a pipeline type, an EIP-712-inspired string that names the input roles and their counts, and what a pass of such a pipeline means. The Verifier checks every request against the type. Each input has a role from the type, and its entry is opaque bytes that only the Engine parses. A type can let a role take a variable number of inputs, e.g. frames for a custom liveness check. If the Engine passes, the Verifier signs a Flamingo Token over the type’s hash, the Engine configuration, and the SHA-256 hash of each entry whose role the type marks with #. Consuming protocols use these hashes to bind entries to other data, e.g. that the reference image the Engine compared is the one committed in a Credential. The Authenticator can also provide a WIP-106 Trust Anchor Key Token (TAKT) and Authenticator Assertion Token (AAT) committing to the engine request, which are verified by the Verifier. If the RP is billed, the Authenticator also provides a WIP-107 billing nullifier, which is verified against the on-chain billing state. The public WIP-106 values and the billing nullifier are then also included in the Flamingo Token. Consuming protocols such as WIP-202 use the token to prove the result to a Relying Party (RP), optionally without revealing any entry.

2. Motivation

Many Proof-of-Human applications, like deepfake prevention or human presence verification, need biometric checks on images, e.g. presentation attack detection (PAD), liveness or face matching. They also need to bind the result to other data, e.g. that the face on a stream matches the thumbnail in a user’s Credential.

Running these models on the user’s device is private but not trustworthy: a jailbroken device can report checks it never ran. Fraud detection also relies on obscurity, so its models and weights cannot be published.

This WIP runs the models in an attested TEE instead. The TEE’s attestation shows users that the Operator cannot access biometric data, and its signature shows RPs that the checks ran. The Verifier image is open source and reproducibly built, so anyone can check that its measurement matches the source and that no raw media or embeddings leave the TEE. The closed Engine runs inside a kernel-enforced sandbox with no network or storage access. The Verifier attests which Engine release it runs, and the RP accepts only the Engine configurations it allowlists, from releases the Engine Provider signed.

What a pipeline checks differs per use case, so this WIP does not define it. A consuming protocol defines a pipeline type, and the token binds which type ran. The token holds only hashes of entries, so a consuming protocol can prove the result to the RP without revealing any entry, e.g. with a zero-knowledge proof as in WIP-202.

  2. The Authenticator seals a request to the Verifier: the pipeline, the strictness and one entry per pipeline input, in input order.
  3. The Verifier checks the request against the pipeline and passes it to the sandboxed Engine.
  4. The Engine runs the pipeline and returns Pass or error.
  5. On Pass, the Verifier signs a Flamingo Token over the pipeline’s type, the hashes of the entries the type commits to, and the other claims.
  6. The Authenticator passes the token, or a proof over it such as WIP-202, to the RP.
  7. The RP verifies it, as its consuming protocol defines.

4. Specification

4.1 Terminology

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

  1. The Verifier is the TEE service this spec defines.
  2. The Engine is the sandboxed component of the Verifier that runs pipelines. This spec defines its interface, not its models or thresholds.
  3. The Engine Provider builds the Engine and signs its release manifests. It is identified by iss, an https URL without query or fragment (RFC 8414 §2). It MAY be the same organization as an Authenticator Provider.
  4. The Authenticator Provider is as defined in WIP-106.
  5. The Host is the machine that runs the Verifier’s enclave and relays all its traffic, on AWS Nitro the parent EC2 instance. The Operator runs the Host.
  6. A pipeline is an Engine-defined computation over its inputs that passes or fails, e.g. presentation attack detection on a live capture and a face match with a Credential image.
  7. A type names what a pipeline’s inputs are and what its pass means. A consuming protocol defines it.
  8. A role is what one input is to the type, e.g. live. A label is what it is to the Engine, e.g. unlit_frame.
  9. The strictness is a pipeline parameter the request picks, e.g. how strictly faces must match. Its meaning comes from the type.
  10. A consuming protocol defines one or more types and how a Flamingo Token is requested and used, e.g. a proof type such as WIP-202.
  11. The field F, the hash functions H_t and H_var, the signature scheme (BabyJubJub-EdDSA-Poseidon2) and the PublicKey representation MUST follow WIP-100. R(d) reads a 256-bit digest d as a big-endian integer modulo q.
  12. Field types in tables of CBOR structures (the Engine and Verifier requests, the response and the Flamingo Token) are CBOR types (RFC 8949). Those of JSON structures (the release manifest and the Engine Provider metadata) are JSON types. A Field element is a 32-byte byte string, the canonical big-endian encoding.

4.3 Consuming protocols

A consuming protocol, e.g. WIP-202, builds on Flamingo Tokens. It defines the types that pipelines implement, what their results mean, and how an RP asks for a token or a proof over it. This spec defines the Verifier request and the checks every token must pass.

4.3.1 Types

A type string names a pipeline shape. Grammar, in ABNF (RFC 5234):

type   = name "<" levels ">" "(" member *("," member) ")"
name   = segment *("/" segment)
segment = 1*(%x41-5A / DIGIT / "-")
levels = "0" / %x31-39 *2DIGIT
member = role ["#"] ["?" / "*" / "+"]
role   = %x61-7A *(%x61-7A / DIGIT / "_")
  1. Form. A type string is ASCII, at most MAX_TYPE_BYTES long, with no whitespace. Its roles MUST be distinct.
  2. Name. A type’s name MUST be unique among consuming protocols and SHOULD follow the WIP-100 label convention with a version, WORLD-ID/WIP-<number>/FLAMINGO-TYPE/V<version>, e.g. WORLD-ID/WIP-202/FLAMINGO-TYPE/V1.
  3. Cardinality. A member without a suffix takes exactly one input. ? takes exactly one input whose entry a request MAY leave absent. * takes any number of inputs and + at least one; the pipeline fixes the number.
  4. Commitment. # marks a committed role: the Flamingo Token (4.6) carries the hash of its entry. Only a member without * or + MAY carry #, and a type has at most MAX_COMMITTED of them. The committed roles, in type order, are committed roles 0 to 3.
  5. Hash. pipeline_type = R(SHA-256(TYPE_DOMAIN || type string)), over the string’s bytes.

Example. EXAMPLE<2>(reference#,``live#,evidence*``) has three roles:

  • reference# and live#: exactly one input each, committed in entry_hash_0 and entry_hash_1.
  • evidence*: any number of inputs, fixed by the pipeline, with no hash in the token.
  • <2>: strictness levels 1 and 2.

entry_hash_2 and entry_hash_3 are 0. A pipeline of this type runs liveness and fraud checks on live and evidence, then matches live against reference at strictness. Appendix A2 uses this type in a full release.

4.3.2 Strictness

  1. Values. A strictness is a uint below 2^8. A type’s <n> fixes its strictness levels, with n at most 255. With n = 0 the type has none, and every request uses strictness 0. Otherwise its levels are 1 to n.
  2. Order. A higher level is at least as strict as a lower one. Generally, a higher strictness lowers the false acceptance rate and raises the false rejection rate, i.e. it favors security over UX.
  3. Meaning. The consuming protocol defines what each level means, e.g. how strictly faces must match or how strict a liveness check is, and how a request’s level is chosen (4.3.3).
  4. Use. A request picks one level its pipeline lists, and the Flamingo Token’s strictness claim says which level ran (4.6).

4.3.3 What a consuming protocol defines

A consuming protocol MUST:

  1. Types. Fix each of its type strings byte for byte, and say what each role is and what a Pass of a pipeline of that type means. A published type string MUST keep its meaning: a protocol that changes what a role, a Pass or a strictness level means MUST define a new type string, e.g. by incrementing its version (4.3.1).
  2. Strictness levels. Say what each strictness level of its types means, e.g. how strictly faces must match.
  3. Selection. Say how the strictness level is chosen, e.g. by the RP in its request.
  4. Nonce. Say how nonce is bound to the RP’s request.
  5. Delivery. Say how the RP obtains the Flamingo Token or a proof over it.
  6. Bindings. Say what each committed role’s entry_hash_k is bound to, e.g. a Credential claim or the RP’s challenge.
  7. Billing. Bind a nonzero WIP-107 billing_nullifier to the World ID the token is used for and to the RP aud, as WIP-107 §4.7 requires.
  8. Disclosure. Say which token values and entries the RP learns.
  9. Checks. Say, for each check of Consuming Flamingo Tokens, whether the RP or the protocol’s proof enforces it (4.8).

4.4 Engine

An Engine is developed and released by an Engine Provider. It is stateless: each request names a pipeline of its release, a strictness, and one entry per pipeline input. It returns only whether the pipeline passed. Each pipeline implements a type a consuming protocol defines (4.3). Each release is described by a signed manifest that lists its pipelines with their types, strictness levels, inputs and response slots.

4.4.1 Request and response

The Verifier passes the Engine request below to the Engine unchanged and passes nothing else. On the sandbox channel this WIP does not specify its encoding; in the Verifier request it is the payload map.

Engine request fields:

FieldTypeBoundsDescription

strictnessuint< 2^8A strictness level of that pipeline, chosen by the Authenticator.
entriesarrayexactly the pipeline’s inputs countentries[i] is the pipeline’s inputs[i]: bytes holding an encoded image or embedding, or null for an absent entry.

Appendix A2 has an example Engine request.

Engine response variants:

debug_report is defined in 4.4.6.

4.4.2 Request Processing

For each Engine request, in a reset instance, the Engine:

  1. Validates the request against its release: pipeline_id names one of its pipelines, strictness is one of that pipeline’s strictness levels, entries fits the pipeline’s inputs as the Engine request (4.4.1) and the release (4.4.3) define. Otherwise it MUST return error.
  2. Runs the pipeline on the entries at strictness, as the pipeline’s type requires.
  3. Responds: it MUST return Pass only if the pipeline passed, and error otherwise.

4.4.3 Release and release manifest

A release is one version of an Engine: its bundle, i.e. code, model weights and configuration, and the release manifest that describes it. The manifest’s hash, release_hash, identifies the release. A Verifier runs one release. Appendix A2 has an example manifest.

A release manifest is a JWS (RFC 7515) in compact serialization, signed with ES256 by the Engine Provider’s release key. Its protected header MUST contain alg = ES256, kid and typ = world-id-engine-manifest. Its payload is a JSON object:

Manifest payload fields:

FieldTypeDescription
issstringThe Engine Provider.
engine_hashstringSHA-384 of the Engine bundle, 96 lowercase hex digits.
versionintegerSee Release Versioning.
pipelinesarrayNon-empty; see below. pipeline_id values MUST be nonzero and unique within a manifest.
errorsobjectMap from each Engine error code, as 4 lowercase hex digits from 0001 to fffe, to a human-readable message the Authenticator MAY display. The Engine MUST return only listed codes. 0000 and ffff are reserved for the Verifier (4.5.1).

Pipeline fields:

FieldTypeDescription
pipeline_idintegerThe pipeline identifier, < 2^16.
typestringThe pipeline’s type string.
strictness_levelsarray of integersNon-empty, strictly ascending, each < 2^8.
inputsarray1 to 255 items; see below.

Input fields:

FieldTypeDescription
rolestringA role of the pipeline’s type.
labelstringNon-empty. What the input is to the Engine, e.g. unlit_frame. It has no protocol meaning; the Engine Provider documents it.
media_typesarray of stringsAccepted media types, e.g. image/jpeg. Non-empty.
  1. Conformance. A pipeline’s type MUST be a valid type string, every input’s role MUST be a member of it, and each member’s inputs MUST number as its cardinality says. Its strictness_levels MUST be levels of its type (4.3.2). Two inputs of a pipeline MUST NOT have the same role and label, so every input is named without its position.
  2. Strictness. For each strictness level a pipeline lists, the Engine Provider MUST document how the pipeline meets the meaning its type’s consuming protocol defines (4.3.2). Internal thresholds MAY vary, e.g. per input quality.
  3. Release hash. release_hash is the SHA-256 of the manifest’s JWS Payload (RFC 7515 §2). Re-signing a release keeps its release_hash.
  4. Signatures. RPs MUST verify a release manifest under an active release key of its iss before relying on it. The Verifier and Authenticators do not verify it.

4.4.4 Release Versioning

  1. version MUST be greater than the version of every earlier release of the same iss. Every change to the payload is a new release.
  2. A later release MUST NOT change a pipeline’s type or inputs; such a change uses a new pipeline_id. A later release MAY drop a pipeline, but MUST NOT reuse its pipeline_id.

4.4.5 Engine Provider Metadata

The Engine Provider MUST expose a JSON file over HTTPS at <iss>/.well-known/world-id-engine.json:

FieldTypeDescription
versionintegerMUST be 1.
release_keysarrayEach entry: jwk (a P-256 JWK with kid) and status (active, retired or revoked).
manifestsarrayThe release manifests the Engine Provider offers, each a compact JWS. Removing one withdraws its release.

A reader MUST NOT follow redirects to another origin, and MUST ignore manifests whose iss is not the one it fetched the file for. The Verifier never fetches the metadata. RPs compute the engine_config_hash values they accept from it, and SHOULD refresh it at least every 24 hours.

4.4.6 Debug Report

An Engine response MAY carry a debug_report.

  1. Content. Opaque bytes the Engine Provider defines, e.g. which check failed, to help debug failures. It is not part of the Flamingo Token and has no protocol meaning. Engine Providers SHOULD keep it to what debugging needs, since it helps anyone probing the Engine (7).
  2. Size. The Verifier MUST NOT emit a debug_report larger than MAX_DEBUG_REPORT.
  3. Delivery. The Verifier MUST return it only in the sealed, padded response to the Authenticator (4.5.1), and MUST NOT expose it to the Engine Provider, the Operator or the Host.
  4. Forwarding. The Authenticator MAY forward it only to the Engine Provider, and only with the user’s explicit consent. It MUST offer the user a way to inspect it, but MAY forward it without an inspection.

4.5 Verifier

A Verifier is any implementation of this section built as an open-source, reproducibly built AWS Nitro enclave image. Each image has its own measurements (PCRs), and Authenticator Providers and RPs choose which implementations they trust by allowlisting them. A Verifier is run by an Operator on a Host. It runs one Engine release and serves requests from Authenticators. It checks each request against the pipeline it names, verifies the Authenticator Assertion, checks billing, passes the Engine request to the sandboxed Engine unchanged, and on a Pass signs a Flamingo Token. It releases each response only at fixed time slots.

4.5.1 Request and Response

The request is a deterministic CBOR map (RFC 8949 §4.2.1) with the fields below. The Authenticator encrypts the entire encoded map to the Verifier. payload is a byte string holding the deterministic CBOR encoding of the Engine request, so the Verifier checks the Authenticator Assertion against exactly the bytes it received and passes them on unchanged.

  2. The Verifier MUST handle debug_report as 4.4.6 requires.

4.5.2 Attestation and Channel

  1. Keys. At boot, the Verifier MUST generate a channel key and a Flamingo Token signing key inside the enclave, from its hardware RNG, and MUST NOT export or persist either. It SHOULD replace its channel key frequently and accept the previous key for MAX_REQUEST_LIFETIME afterwards.
  2. Documents. The Verifier MUST attest each key in its own Nitro attestation document, a COSE_Sign1 chaining to the AWS Nitro Root G1. The channel attestation has public_key = SHA-256(CHANNEL_KEY_DOMAIN || channel_key) and user_data = the loaded release_hash; the signing_key_attestation has public_key = the token signing key. A document’s timestamp is its creation time, in milliseconds since the Unix epoch.
  3. Release manifest. The Verifier MUST send the release manifest (4.4.3) of the Engine release it loaded, as received, with the channel attestation.
  4. Response. The Verifier MUST seal the padded response to response_key.
  5. Refresh. The Verifier MUST re-attest both keys at least every MAX_ATTESTATION_AGE.
  6. Time. The Verifier MUST sync its clock to the timestamp of each new attestation, advance it on its monotonic clock in between, and MUST NOT move it backward. It MUST NOT use any other time source.

Channel Encoding. Both directions use the public-key encryption of WIP-100 §3.9. info is CHANNEL_DOMAIN || 0x00 for a request and CHANNEL_DOMAIN || 0x01 for a response. The first 1216 bytes of a request’s plaintext are response_key, a fresh X-Wing encapsulation key; the rest is the request. The Verifier MUST reject a request shorter than 1216 bytes or with an invalid response_key.

4.5.3 Request Processing

The Host MAY drop requests above a size limit it chooses. For each sealed request it relays, the Verifier, in order:

  1. Checks. After decrypting, it MUST reject a request that does not meet the Verifier request and Engine request formats, or whose pipeline_id, strictness or entries do not fit the loaded release as Request Processing item 1 of the Engine says, apart from media types.
  2. Expiry and replay. It MUST reject an expired or replayed request.
  3. Authenticator Assertion. If aat_inputs is present, every check of WIP-106 §3.8 MUST hold. The TAKT, the AAT, the assertion_key and build_version MUST NOT leave the Verifier.
  4. Billing. Before the Engine call, it MUST check billing_nullifier as WIP-107 §4.7 requires. It MUST NOT check billing again afterward.
  5. Engine call. It MUST pass the Engine request to the sandboxed Engine unchanged, and nothing else.
  6. Response. On Pass, it signs a Flamingo Token. It returns a Success or EngineError response, released at a response slot.

4.5.4 Response Timing and Replay

  1. Release. The Verifier MUST hold each response until the first of the pipeline’s response_slots at or after the Engine’s finish, measured on its monotonic clock from the request’s arrival, whatever the outcome. If the Engine has not finished by the last slot, the request fails and the Verifier MUST reset the Engine instance. Rejections before the Engine call MAY be released immediately.
  2. Choosing slots. Engine Providers SHOULD put the first slot at or above the pipeline’s fastest complete run and the last above its 99.9th-percentile run time.
  3. Expiry. The Verifier MUST reject a request whose expires_at has passed or is more than MAX_REQUEST_LIFETIME ahead of its time.
  4. Replay. The Verifier MUST reject a request whose (aud, nonce) it has already processed or is processing. It MUST keep each pair until the request’s expires_at has passed and MAY drop it after. While the set is full, it MUST reject every request.

4.5.5 Sandboxed Engine

  1. Loading. At start-up, the Verifier receives exactly one Engine bundle and its release manifest from the Host. It MUST check that the bundle hashes to the manifest’s engine_hash and that the manifest is well-formed, including Conformance, without verifying its signature, and MUST NOT fetch anything else.
  2. Sandbox. The Verifier MUST run the Engine with no network access, no writable persistent storage, no process creation, no access to the Verifier’s keys, nothing outside its bundle, and only one bounded request-response channel.
  3. Per request. Before each request, the Verifier MUST reset the Engine to a state no earlier request has influenced, without relying on the Engine’s cooperation. It MUST bound the Engine’s memory, and MUST return an error if the Engine exceeds it, crashes, or returns anything other than an Engine response.

4.5.6 Build and Measurement

  1. Publication. For each published Verifier measurement, an immutable reference to its source and its build instructions MUST be publicly available.
  2. Build. Building that source with the documented toolchain MUST produce a bit-identical Enclave Image File (EIF).
  3. Measurement. PCR0, PCR1 and PCR2 of that EIF are the Verifier’s measurement.
  4. Configuration. Everything that affects the Verifier’s behavior MUST be in the EIF. The Host supplies only the Engine bundle, its manifest, WIP-107 billing state updates and requests.

4.6 Flamingo Token

On a Pass, the Verifier builds a Flamingo Token from the request, the verified AAT, if any, and the loaded release.

Envelope. A Flamingo Token is a CWT (RFC 8392) in an untagged COSE_Sign1, encoded as deterministic CBOR. The protected header MUST contain alg (label 1) = -65537 (Private Use, BabyJubJub-EdDSA-Poseidon2) and kid (label 4) = the compressed signing public key. The signature MUST be a BabyJubJub-EdDSA-Poseidon2 signature per WIP-100 over the signed digest below.

Claims. The payload MUST contain exactly these claims, in the bytewise order of their encoded keys.

4.7 Authenticator

The Authenticator MUST accept only PCR0–2 values its Authenticator Provider ships with it, e.g. in the app release or as signed configuration. Before sending biometrics, it completes these steps in order, and MUST NOT send biometrics if one fails:

  1. Attestation. It MUST check that the channel attestation is a valid COSE_Sign1 whose chain leads to the AWS Nitro Root G1 and is valid now; does not have all-zero PCRs and has PCR0–2 it accepts; has public_key = SHA-256(CHANNEL_KEY_DOMAIN || channel_key) for the key it encrypts to; has user_data equal to the release_hash of the manifest the Verifier sent; and is at most MAX_ATTESTATION_AGE old. It MAY reuse a checked attestation while these hold.
  2. Configuration. It MUST choose a pipeline of the loaded release whose type is one its consuming protocol requires and whose inputs it can produce, as their labels describe, and a strictness the consuming protocol requires and the pipeline lists. Among qualifying pipelines, it follows the consuming protocol or, where it sets none, the Authenticator Provider’s policy. It fills entries in input order and leaves an entry absent only where the consuming protocol allows it. If no pipeline qualifies, it MAY use another Verifier instance.
  3. Response timing. It MUST NOT use a pipeline whose response_slots list more release times than its configured maximum. The maximum SHOULD be at most 8, so a response’s timing reveals at most 3 bits.
  4. Seal. It MUST seal response_key || request to channel_key, send it, and open the response with response_key.
  5. Retries. To retry, it MUST send a new request with a fresh nonce and response_key, and a new AAT. Authenticator Providers SHOULD rate-limit attempts.

4.8 Consuming Flamingo Tokens

A consuming protocol defines its types and how an RP requests and uses Flamingo Tokens. An RP MUST NOT accept a Flamingo Token, directly or through the protocol’s proof, unless every check below holds. A proof that hides the token MUST enforce checks 2, 3, 7 and 8; for the others it reveals the values they need or takes the RP’s accepted sets as public inputs.

  1. Attestation. The signing_key_attestation chains to the AWS Nitro Root G1, with every certificate valid at its timestamp; does not have all-zero PCRs and has PCR0–2 the RP accepts; attests verifier_key (kid is only a hint); and is at most MAX_ATTESTATION_AGE old.
  2. Signature. sig verifies under verifier_key per WIP-100 §3.5.1 over the signed digest computed from the values, with aat_flags = platform + 2^8 * sec_level + 2^16 * min_build_version + 2^48 * sec_meta + 2^52 * authenticator_meta.
  3. Well-formed values. has_aat is 0 or 1. The aat_flags sub-fields are range-checked to their widths, with the user_presence bits of authenticator_meta below 5. With has_aat = 0, trust_anchor_key_hash and the aat_flags sub-fields are 0.
  4. Request. aud is the RP’s own; nonce is bound, as the consuming protocol defines, to a request the RP issued that has not expired and has not been used before; and now is recent by the RP’s clock. The RP MUST accept at most one proof per request.
  5. Authenticator Assertion. With has_aat = 0, the RP accepts tokens without an AAT. Otherwise min_build_version, trust_anchor_key_hash and the aat_flags sub-fields pass WIP-106 §4.
  6. Engine. engine_config_hash is the hash of a release, pipeline_id and strictness the RP accepts, from an active manifest it verified under an active key of its iss, at or above the RP’s minimum version per iss.
  7. Type. pipeline_type is the hash of a type string the consuming protocol defines, and each entry_hash_k its statement depends on is bound to the protocol’s own inputs, e.g. a Credential claim or the RP’s challenge.
  8. Strictness. strictness is a level the consuming protocol accepts for this request, e.g. the level the RP requested.
  9. Billing. billing_nullifier is 0, or the consuming protocol binds it to the World ID the token is used for, as WIP-202 constraint 7 does.

5. Trust Assumptions

The protocol assumes the isolation, measurement and attestation of AWS Nitro Enclaves are sound. If they fail, neither privacy nor integrity holds. Every party below is trusted only for the listed parts.

PartyTrusted forNot trusted for
AWS (Nitro Enclaves)Isolation, measurement and attestation of the enclave.Nothing: if this fails, neither privacy nor integrity holds.
Engine ProviderEngine correctness: each pipeline does what its type requires, keeps doing so across releases, and meets each strictness level it lists.Privacy: the sandbox keeps the Engine from exporting data.
Authenticator ProviderVerifying the Authenticator’s integrity, as stated in the TAKT, and the Verifier measurements its Authenticators accept.—
AuthenticatorThe source and freshness of the entries it sends, e.g. that a capture is live.—
Host and OperatorAvailability, and the WIP-107 billing state they supply.Privacy, and every other token claim: they see only ciphertext, and the Verifier rejects replayed requests.

Out of scope. Collusion between an RP and the user’s Authenticator, which can then produce any proof the RP accepts, and between an RP, an Engine Provider and the Operator, which can only gather more timing information through requests the user consents to one by one. Collusion between an Engine Provider and the Operator alone is in scope: the sandbox and response slots bound what they learn per request.

6. Rationale

  1. Typed pipelines. What a pass means differs per use case, so the consuming protocol defines it and WIP-201 only fixes the shape. The release fixes each input’s role and processing, so a requester cannot relabel an entry.
  2. The type in the token. The consuming protocol checks pipeline_type against a constant, so a pipeline of another shape fails even if an RP’s allowlist names it by mistake, e.g. after a reused pipeline_id or a hand-copied hash.
  3. Explicit commitment. # makes the type string say what the token hashes. A single role without #, e.g. a depth map, stays possible.
  4. Roles and labels. A role is the protocol’s, so several Engines can serve one type; a label is the Engine’s, so it can tell inputs apart.
  5. Strictness levels in the type. Scores depend on the model and the pair and are biometric signals, so a request names a level whose meaning the consuming protocol defines. Putting n in the type lets the Verifier reject a release with levels the protocol does not define at load, as it does for roles. Levels 1 to n need no list.
  6. The strictness in the token. The protocol can check the level that ran against the one it expects, e.g. the RP’s request, instead of relying on the RP’s engine_config_hash allowlist alone.
  7. Only the RP checks manifest signatures. Who signed a release only matters for trusting its results, which the RP decides, so the Verifier image holds no Engine Provider keys.
  8. SHA-384 for the bundle. It matches how Nitro measures images; every other hash is SHA-256.
  9. Minimum versions. RPs accept a minimum version per iss, so new releases reach them without changes; a breaking change takes a new pipeline_id.
  10. The AAT in the Verifier, and optional. The Verifier keeps WIP-106’s private inputs and signs the public values; RPs decide whether they accept tokens without an AAT.
  11. Hashes over raw bytes. The RP and the Credential can compute the same SHA-256; embeddings only the Engine can compute.
  12. Signature over claim values. A circuit verifies the token without parsing CBOR.
  13. Verifier time. The Verifier checks the AAT at its own time and signs it, so an expired TAKT or AAT cannot pass.
  14. Engine configuration hash. One hash over the manifest’s JWS Payload, pipeline and strictness gives RPs exact control and keeps the values private.
  15. **Numeric engine **error codes. A uint16 keeps responses one size, gives Authenticators a stable code to act on, and keeps free text out of the response. The release’s errors map gives each code a message and shows reviewers every error an Engine can return.
  16. Debug reports only to the Authenticator. A report may describe the user’s biometrics, so only the user’s device receives it, and it reaches the Engine Provider only with the user’s consent.
  17. AWS Nitro. Nitro Enclaves have no persistent storage or external network, measure the whole image with reproducible PCRs, and sign attestations with a public root, which is what Authenticators and RPs need to check the Verifier.
  18. Two attestations. The channel key and the signing key are attested separately, so the channel key can be replaced frequently while the signing key, which RPs check tokens against, stays for the whole boot.
  19. Post-quantum channel. Biometrics don’t expire, so a recorded request must stay confidential even if it is decrypted years later. The channel therefore uses the X-Wing hybrid KEM.
  20. The Verifier fetches nothing. The Host supplies the bundle, the manifest and billing state, and the Verifier checks them. No network dependency enters the measured image, and its behavior follows from the measurement alone.
  21. Fixed-length responses. Every response is padded to the largest possible size, so the Host learns neither the outcome nor the report size from the ciphertext.
  22. Response slots. Random delays average out over repeated requests, and one fixed time makes every request wait for the worst case. A few slots per pipeline bound what timing reveals per request (7) while keeping fast pipelines fast.

7. Security

  1. Channel confidentiality. Requests and responses stay confidential while ML-KEM-768 or X25519 holds. It does not cover a compromised enclave.
  2. Missing AATs. Without an AAT anyone can submit arbitrary media, and the verdict becomes an oracle for tuning attacks; RPs that accept has_aat = 0 accept that risk.
  3. Pipelines that do not meet their type. The type fixes the shape, not what the Engine does. Only the Engine Provider and the release audit stand behind it, so RPs accept releases per iss and per pipeline.
  4. Unreviewed Engines. A Host may load any Engine; its tokens carry an engine_config_hash no RP accepts, and the sandbox keeps it from exporting data. A leaked release key works until it is revoked and RPs refresh.
  5. Closed Engine. The sandbox removes the Engine’s channels out, and the per-request reset keeps one request’s data from the next.
  6. Token privacy. A committed Credential hash and a nonzero billing_nullifier link a user to an RP request, so consuming protocols MUST keep tokens private, e.g. as private proof inputs.
  7. Verifier keys. The signing key never leaves the TEE; RPs stop accepting a compromised measurement, and MAX_ATTESTATION_AGE bounds its attestation.
  8. Timing. Slots limit each request to at most log2(n) bits for n slots, replay rejection keeps that bound per request, and any Engine failure becomes an error at a slot. Per-pipeline slots may reveal the pipeline.
  9. Stale measurements. An Authenticator accepts a compromised measurement until its provider removes it; signed, expiring configuration shortens that window.
  10. Engine as an oracle. Anyone can seal a request, so a modified Authenticator can query the Engine without bound. Operators SHOULD rate-limit at the Host, and Engine Providers SHOULD keep debug_report small.

8. Future Considerations

  1. Other TEEs, through attestation profiles for each provider’s document, root and measurement.
  2. Several Engines per Verifier. The Authenticator would choose among them, and RPs accept per engine_config_hash as today.
  3. Published measurements. A standard format for publishing Verifier PCRs with a status.
  4. Bounded Engine queries. A per-key attempt limit, keyed by the RP’s signed request or the AAT’s assertion key.
  5. Committed multi-valued roles. # on a * or + member, with an H_var commitment over that role’s entry hashes.
  6. Nested types. Grouping roles, e.g. a live capture and its evidence, as an EIP-712-style struct, once a second protocol needs it.

9. Alternatives Considered

  1. Running the models in a ZK circuit. Rejected: proving these models is still infeasible for most devices, and the prover would need the secret weights.
  2. MPC. Rejected: orders of magnitude slower, and it adds a non-collusion assumption.
