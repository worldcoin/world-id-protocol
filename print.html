Abstract

The World ID v4.0 release introduces account abstraction at its core, transforming a World ID from a single secret into an abstract record in a public registry (called WorldIDRegistry) with multiple authorized keys. This fundamental change enables several key improvements:

  1. Multi-key support: Users can generate proofs using multiple valid authenticators (such as across multiple devices, multiple platforms or multiple applications) while maintaining the same identity.
  2. Improved Protocol Resilience: Multi-key support reduces likelihood of loss of all keys, key rotation and revocation are natively supported, and the user can (optionally) define a World ID Recovery Agent (e.g. such as biometric authentication).
  3. Web-based authenticator provider: A reference web authenticator provider simplifies World ID usage directly in browsers, improving user experience and adoption potential.
  4. Improved privacy: The protocol enforces one-time use of nullifiers for longer-term actions, preventing tracking while maintaining proof integrity.

These changes collectively increase security, privacy, and usability while enabling more sophisticated applications of human verification in the Age of AI. For more details on what is changing from a technical standpoint, please see Summary: What is Changing?.

Product Specs

At a high level, this release of the Protocol is about Account Abstraction. A World ID is no longer tied to a single secret, and instead is an abstract record created in the public WorldIDRegistry with a defined set of authorized keys which allow the user to interact with their World ID (a similar mental model is how passkeys authorize accounts for specific websites or how smart contract wallets work in the Ethereum ecosystem).

Stemming from the enablement of other Authenticators to exist, a reference open-source, web-based Authenticator will be published which will reduce some of the overhead for using a World ID and simplifies the user experience. The enhanced user experience will enable simpler and more widespread adoption of the Protocol.

Definitions

  • Authenticator: A software or hardware agent (e.g., app, device, web client, or service) that controls a set of authorized keypairs for a World ID Account and is functionally capable of interacting with the Protocol, and is therefore permitted to act on that account’s behalf. An Authenticator is the agent of users/holders. Each Authenticator is registered in the WorldIDRegistry through their authorized keypairs.
  • OPRF Nodes: The OPRF Nodes are a multi-party set (MPC) of nodes responsible for enabling the nullifier generation which users present to RPs to prove uniqueness.
  • Recovery Agent: A party designated by the user which has a special permission to recover their World ID Account in case of loss of all Authenticators. The party may be a set of entities represented with abstract rules (e.g. through a smart contract). This designation is optional and done on-chain.
  • Action: Maintains definition from previous Protocol version.
  • Nullifier: Maintains definition from previous Protocol version. A nullifier is a one-time use identifier that guarantees an action can only be taken once. It’s analogous to a one-time use ticket, a user generates a nullifier through a Proof, and presents it to an RP. A nullifier will always be the same for the same user and the same RP+Action.
  • Uniqueness Proof: A statement where a user proves they are performing an action once and they own a particular credential (e.g. I’m a unique person with a PoH credential voting on this proposal once). These proofs cannot be cryptographically associated with any other proof (e.g. not across RP, or even to the same RP).
  • Session Proofs: Used with a sessionId provided by an Authenticator and subsequently provided by an RP to receive a statement that cryptographically guarantees the same World ID is being used (e.g. I have an account with an RP and I want to prove I now have a new Credential). These proofs cannot be associated across RPs, across sessions with the same RP, or with any other proof.

Key Product Functionality

This notes the key new features or functionality for this release of World ID (v4.0):

  • Multi-key support: A World ID is not bound to a single key. A user can generate proofs on multiple valid authenticators (e.g. devices, platforms). With the important exception of security properties of the Authenticator, a proof proves the same thing to an RP regardless of which authenticator was used.
    • A user can add or remove different valid authenticators to manage their World ID (Portability).
    • Motivation: Allowing multiple authenticators serves to the Decentralization of the Protocol, with no reliance on a single actor (such as a single Authenticator provider, e.g. World App). Furthermore, abstracting a World ID into a conceptual record vs. a single secret enables the secure and practical existence of multiple Authenticators as well as enabling Recovery in case of loss and rotation in case of compromise.
  • Recovery: Regain access to the same World ID through Recovery Agents.
    • Motivation: Recovery is a fundamental building block of a Proof-of-Human Protocol (see Whitepaper on why). While we expect authenticator providers to offer robust backup mechanisms, the user must be able to recover their World ID and related state in a contingency scenario.
  • Web-based Authenticator Provider: A limited authenticator that allows usage of World ID in the web browser. This serves both as a reference of an authenticator and also for improved UX for certain RP flows. Functionality is limited as enrollment of credentials is out of the scope for this initial release.
    • Motivation: A lightweight web-based authenticator enables simpler usage of World ID which provides a better user experience and will enable more growth as interacting with RPs will be significantly simpler.
  • Trusted RPs. An authenticator can identify a request comes from a valid RP.
    • Motivation: Authenticators need to be able to identify that they’re generating proofs for the right recipient to reduce potential for proof phishing (e.g. a malicious actor asking you for a proof meant for a different RP to know if you’ve performed that action). In addition, this enables future introduction of Protocol fees.

Non-Functional Requirements

  • Privacy.
    • Assuming non-collusion of nodes of each multi-party system, the user’s privacy cannot be compromised by any single party, neither correlation of multiple actions nor direct identification of a user. For example, it’s impossible to know that a specific user performed a specific action (identification) or that two different Actions were performed by the same user (correlation).
    • Addressing the attack vector of collusion of a threshold (or all) nodes is covered in the Other Risk Considerations section.
    • Strict requirements for the identifiers handed off by the Protocol are introduced. See details in Tech Specs.
    • No human super-cookies. Permanent state or linkable state is as privacy-preserving as possible and is protocol-enforced. Privacy preserving in this context means that it’s not possible to identify a single person, even pseudonymously, across a long period of time without ongoing consent. Any exposed long-living / constant IDs should be protected as secrets.
  • Security.
    • A World ID is not a single secret that needs to be shared or can’t be rotated.
    • A World ID cannot be recovered or an authenticator added without verifiable user intent (through knowledge of a secret key of an authorized authenticator).
    • Collusion of all nodes with an multi-party system (MPC) does not allow performing actions on the user’s behalf.
    • User Auditability — each user needs to be able to see account management events that have been authorized with their World ID, for example things like adding / removing of authenticators.
  • Migration Path.
    • There needs to be a clear migration path for all currently active and relevant use cases to the new version of the Protocol.

Technical Specs

Tip

Please note these are the high level technical specifications at the time of introduction of World ID 4.0. The most up-to-date technical documentation reflecting the current state of the Protocol can always be found in the developer documentation and the Protocol repository.

Summary: What is Changing?

  • A World ID is now a record on an on-chain registry and more importantly a single World ID can have multiple public keys.
    • This also means identity commitments (identityCommitment) no longer exist. Instead, the identification mechanism is the knowledge of a secret key corresponding to a public key registered in a specific leaf index in the WorldIDRegistry.
    • Also implies that the on-chain trees of identity commitments is gone in favor of a single WorldIDRegistry.
  • Creating a World ID now occurs through on-chain registration (vs. as an offline keypair generation previously), and issuing Credentials is now done without on-chain interaction. Credentials are now issued by the Issuer signing them. Previously, the Issuer would add the user’s identity commitment to the relevant on-chain tree.
  • Nullifiers are enforced one-time use. Previously there was no enforcement of nullifiers being one-time use and they could become pseudonymous identifiers for an RP, now Authenticators will not issue a nullifier more than once.
  • [For RPs only]. When RPs require users to prove they are still the same World ID that originally performed an action, they will be able to store an identifier (a sessionId) and provide it to the user for subsequent proofs. With Proof of Human, this allows RPs to establish they are interacting with the same World ID, potentially with different credentials too. See Session Proofs for further details.
  • [For Issuers only]. Authentication based on using nullifiers from ZKPs as identifiers is no longer supported. A new authentication mechanism is introduced for issuers.
  • Access to a World ID can be recovered. A user can designate a Recovery Agent for their account which will allow for recovery in case of access to all Authenticators is lost.
    • [Recovery Agent Scope]. Users may designate the PoH AMPC system as their Recovery Agent to recover their World ID. In the future, other Recovery Agents are expected to be available.

High level overview

Diagram of components for the World ID 4.0 Protocol.

  1. The World ID Registry is introduced. This public contract is the source of truth for World IDs, a World ID conceptually becomes an account, represented in a leaf of the Merkle tree in this contract. Each account is identified with its index in the tree. The registry also contains a list of authenticator public keys authorized to act on behalf of the holder. The OPRF Nodes, as well as RPs use this to verify proofs (through an Merkle inclusion proof within the ZKPs).

  2. Similarly, a Relying Party Registry is introduced. This registry contains a list of authorized Relying Parties with their accompanying authorized public keys. The registry permits RPs to authenticate requests for proofs to Authenticators.

  3. The multi-party set of OPRF Nodes is introduced. This set of nodes are now responsible for generating the nullifiers that users present to RPs to prove uniqueness. The nullifiers are generated through a Verified Threshold Oblivious Pseudorandom Function (vOPRF) with participation of the OPRF nodes. Nodes verify requests for nullifiers are properly validated by both RPs and users (see Uniqueness Proofs), and only then will generate the required output to compute the user’s nullifier. The users then construct the final nullifier and prove its computation in the proof they present to RPs.

    1. A multi-party OPRF is necessary because it prevents nullifiers from being guessable, i.e. nullifiers are deterministic but appear random (recall that PRF outputs under a uniformly random key are computationally indistinguishable from a uniformly random function). This could theoretically be accomplished with a regular hash function, but then nullifiers could be brute forced by computing the hash for all possible leafIndexes (which are public on-chain). To prevent this, secret entropy is required (in World ID ≤ 3.0, the user provided this entropy). Since this is not available anymore, the entropy now comes from the OPRF nodes.
    2. Additionally, to prevent brute forcing even with involvement of OPRF nodes, OPRF nodes require authentication before computing each hash. They authenticate the user through a ZKP that proves knowledge of an Authenticator secret key authorized in the WorldIDRegistry for the particular leafIndex for which they are generating a nullifier.
    3. Importantly, the OPRF nodes compute the keyed-hash function $H_k(x’)$ on a blinded input, hence they cannot learn which user is actually performing a request. Furthermore, the OPRF nodes output a proof that attests to the proper computation of $H_k$ given a committed $k_{pk}$, so neither users nor RPs need to blindly trust the OPRF nodes.
    4. Similar to how OPRF Nodes are used to generate the nullifiers presented to RPs, these nodes also generate a blinding factor for each credential so there cannot be correlation of World IDs from malicious issuers.
    5. More information on the OPRF Nodes can be found in the paper: “A Nullifier Protocol based on a Verifiable, Threshold OPRF”.
    6. Details about the nature, number, and diversity requirements of OPRF nodes must be established before the production network is live.

Technical Details

Uniqueness Proofs

A Uniqueness Proof is how a user primarily proves they are performing an action once and they own a Credential that meets the RP’s requirements (e.g. the user has a unique government-issued document). While fundamentally the user is proving uniqueness per World ID Account when performing an action, if the request is not bound to a Credential that offers a measure of uniqueness (e.g. PoH or unique government-issued document), the proof will lack value.

  • The nullifier is computed by the OPRF Nodes. Computing it requires output from a threshold number of nodes to be valid.

    • Importantly, the input to the OPRF Nodes is blinded so that no OPRF node can see the raw leafIndex (i.e. OPRF nodes only know that the request is from an authorized authenticator).
    • Importantly, the nullifier is credential independent, so the action can only be performed once regardless of which credentials are available at the time.
    • Further information on how the nullifier is computed can be found in the TACEO OPRF Whitepaper.

  • Nullifiers have the following properties, which in combination make them amenable for use by an RP to enforce anonymous per-action uniqueness:

    PropertyDescription
    DeterministicGiven the same context (leafIndex [blinded], rpId, action), the nullifier is always the same. Assuming honest behavior of OPRF nodes never rotating their base key. Note that the credential is intentionally not included in this context. This means that the action can be performed only once, regardless of which credentials are available at the time.
    UnguessableFor a fixed context, the nullifier output is uniformly distributed over the output space. Even with the full set of possible users, computing candidate nullifiers is infeasible without collusion of a threshold of OPRF nodes such that the OPRF key is known.
    AuthenticatedIt’s probabilistically impossible to claim ownership over a nullifier if you don’t know a secret value (a secret key whose public counterpart is registered in the WorldIDRegistry).
    AnonymousA nullifier hides which user generated it. To preserve anonymity, each nullifier must only be used once (otherwise repeated use makes it pseudonymous). This is the responsibility of Authenticators.
    UnlinkableFor any two nullifiers with different contexts, the probability that an adversary can correctly distinguish whether they were derived from the same user is at most negligibly better than random guessing.
    Pre-image resistanceFor any given nullifier, and knowing the public context (rpId, action), it is computationally infeasible to find the pre-image or the leafIndex.

  • The authenticator generates two types of different zero-knowledge proofs to be able to deliver a Uniqueness Proof to an RP,

    • The query proof $\pi_1$ which proves to the OPRF Nodes that the request is properly authorized by the user. This ZKP proves the request is signed by a public key which is registered for the particularly provided blinded leafIndex in the WorldIDRegistry.
    • A final Uniqueness Proof $\pi_2$ which ensures at least the following constraints:
      • The same constraints of the query proof are evaluated.
      • Correct OPRF evaluation on leafIndex, i.e. the generated nullifier is correct for the committed public keys from each OPRF node.
      • Request is signed by a public key that is registered for the leafIndex in the WorldIDRegistry (user authentication).
      • The Credential was issued for this World ID, i.e. the Credential’s sub matches the blinded leafIndex of the user.
      • The Credential used in the proof is signed by the Issuer (through the committed key in the CredentialSchemaIssuerRegistry).
      • Credential is not expired.
      • Credential meets the minimum genesis_issued_at constraint provided by the RP.
      • Signal and nonce provided by the RP as public inputs are committed.
      • Potential future constraints may include: integrity attestation of device, enforcing the expiration of actions, credential specific checks, etc.

  • Oblivious Nullifier Pool. The Oblivious Nullifier Pool is a separate service which offers Private Intersection Retrieval and keeps track of used nullifiers. Its function is simply to keep a flat list of used nullifiers such that an authenticator can query if a nullifier has been used before sharing it (and the related $\pi_2$) with an RP if it has been used before. The list is flat (as the nullifier is already unique per-RP-per-action-per-user) relying on the collision-resistance property of the hash function used in the Protocol.

    • This system ensures that nullifiers can’t be misused to create long running identifiers. As their name suggests, a nullifier is one-time use.
    • The term oblivious is used to refer to the fact that this map is queried in a way where the servers serving such requests cannot learn which records where accessed and hence be able to compromise the user’s privacy.
    • The main limitation of the nullifier pool is performance at scale. One option is to shard the pool, making trade-offs of anonymity set size vs. performance. This is still in research.
    • Initially, this pool will only be used for actions that have a running period longer than a predefined threshold. This is to solve for scaling issues as this system grows.

  • Blinded subjects. To prevent correlation of users even among issuers, or in case of leaked credentials, the subjects of the credentials are blinded.

    • When requesting a new credential from an issuer, the user generates a blinding factor using the OPRF nodes, $\texttt{subjectBlindingFactor}=H_k(\texttt{issuerSchemaId} \mid\mid \texttt{leafIndex})$.
    • The user then hashes the blinding factor with their leafIndex to compute the sub claim of the credential. This value is what issuers include in the credential.
    • When a proof is presented, the subjectBlindingFactor is used within the Uniqueness Proof circuit to ensure the credential is issued to the right user. The blinding factor acts as entropy to prevent correlation, but the right leafIndex as provided in the circuit input must match correctly.

Registries

  • World ID Registry
    • Each user can grant access to multiple different keys to interact with their World ID. The Authenticator proves control inside a ZKP to prevent long-lived identifiers.
    • In order to not leak the user, this needs to be in some structure that allows inclusion proofs. This is accomplished with Incremental Merkle Trees.
    • Each Authenticator registers two keys in the registry. This is done to enable performant operations both on-chain and on zero-knowledge circuits.
      • An on-chain key which is an elliptic curve key on the secp256k1 curve is used to authorize on-chain operations on the contract (e.g. adding an authenticator, removing an authenticator, etc.). The public key is simply represented as an Ethereum address.
      • An off-chain key which is an elliptic curve key on the BabyJubJub curve is used to sign requests for zero-knowledge proofs. The public key (represented as a curve point) is emitted on-chain and committed to in the contract.
  • Relying Party Registry
    • Each RP needs to commit to their authorized public key on the public registry, such that this can be verified in the request proof $\pi_1$ by each queried OPRF node.
    • Registering an RP is a public action that anyone can take, but this requires paying a one-time registration fee (see Registration Fees below).
    • In order to allow for decentralized application creation and registration, the RP Registry will be extended and restrictions further lifted in the future, but for this initial version the following applies:
      • At launch, only one authorized key is allowed per RP. This will be extended in the future.
  • Credential Schema Issuer Registry
    • It’s a simple registry where Issuers register for each of their credential types a schema and an authorized signatory and get issued an issuerSchemaId. This ID represents the combination of an (issuer, schema). For example: (Tools For Humanity, Orb credential).
    • The issuerSchemaId is included in the credential and is verified as part of all Proofs. When generating and verifying proofs, the signature of a credential is verified against the public key registered in the contract.
    • Registering an Issuer Schema also requires paying a one-time registration fee (see Registration Fees below).

Registration Fees

Both the Relying Party Registry and the Credential Schema Issuer Registry charge a one-time registration fee. The fee infrastructure serves as a permissionless rate-limiting mechanism — an alternative to restricting registration to authorized callers — ensuring that registration remains open to anyone while preventing abuse.

Why the fee exists. Registering an RP or an Issuer Schema triggers the initialization of an OPRF key via a multi-round distributed key generation ceremony across the OPRF Nodes. This is a computationally expensive operation with real infrastructure cost. The registration fee is sized to cover the cost of OPRF key generation and storage for at least approximately one year.

How it works.

  • The fee is paid in a configurable ERC-20 token via safeTransferFrom at the time of registration, before OPRF key generation begins.

Future: per-request fees. The registration fee described here covers only the one-time cost of onboarding. A separate per-request fee — enforced by OPRF Nodes as a proof-of-payment requirement during nullifier generation — may be introduced in a future Protocol release (4.1 or 4.2). See Future Proofing Notes for details.

Recovery

Recovery is introduced for the case where access to all authenticators (or their keys) is lost. Recovery enables users to gain back control of their World ID by registering a new Authenticator and revoking lost ones. A Recovery Agent may be designated by each user, with a special role to perform the recoverAccount operation. This special role can recover a user’s World ID and nothing else, and conversely only these agents can perform a recoverAccount operation.

Important

This section defines Recovery as a Protocol primitive. Each Recovery Agent will provide its own set of specifications for how they provide World ID recovery.

  1. A recoverAccount operation is a function defined in the WorldIDRegistry contract which receives a signed message from the Recovery Agent with a new authenticator public key. The operation results in the new authenticator being registered and all the old authenticators being revoked. The historical state of authenticators is naturally available on-chain.
  2. The signed message supports ERC-1271, which means it can come from a smart contract that sets its own rulesets for how recovery can be performed. For example, a Recovery Agent may require signatures from multiple parties to allow a recovery. Furthermore, this enables that a Recovery Agent can be defined as an abstract entity governed by its own smart contract.
  3. Importantly, recovery will only be possible for users in the new Protocol. Fundamentally, there’s no way to recover previously lost World IDs because it’s a secret that has been lost. Some fallbacks are being introduced to mitigate this, see Migration Considerations for details.
  4. Designating a Recovery Agent is entirely optional and can be updated at any time.
  5. Once a World ID account has been recovered, new Credentials can be requested to each relevant Issuer. Each Issuer can define their own set of rules for what is needed to recover their Credential.
  6. Future Consideration. In the future, a new feature could be introduced where a World ID is used as a signer on something else. For example, a World ID signature could be used as a factor for recovering a cryptocurrency wallet. While this functionality builds on top of the Recovery primitive, it is independent of this primitive and not in its scope.

Session Proofs

RPs can create sessions for their app to ensure that it’s still the same World ID interacting with them across multiple interactions. Session Proofs intentionally allow the RP to link multiple interactions in their app to the same World ID. Sessions require the RP to store a sessionId. A sessionId can be created as part of a request for a Uniqueness Proof (see Binding Uniqueness Proofs to a Session), which binds the sessionId to a nullifier, or standalone without uniqueness binding. Potential use cases include:

  • Credential upgrade: A user verified previously with one credential and now wants to prove using another one (e.g. unlocking additional benefits). Important Note. While this can be used to prove a new Credential belongs to the same World ID, the implications must be carefully considered when it comes to uniqueness. Uniqueness sets are independent, e.g. users may have both a PoH and a government document Credential, but this doesn’t mean that by accepting both as an RP you can get guarantees that only a single human is behind each. A user may choose to obtain a PoH Credential and a document Credential in different World IDs.
  • Credential expiration check: A user previously enrolled with one Credential; periodically,the RP wants to make sure the user’s Credential is still valid (for example not expired).
  • (Future). RP-level Face Auth: Currently, Face Auth only ensures that the whoever produces the proof is the same person that received the Credential. However, for some applications an RP may want to make sure the same person is behind multiple interactions.

Session Proofs use the same zero-knowledge circuits as Uniqueness Proofs, but authenticators MUST clearly distinguish them to users since they involve a reusable identifier that can link interactions. Instead of a nullifier, Session Proofs return a sessionNullifier which is required for verification but does not provide the same uniqueness guarantee (see below on sessionNullifier). Session Proofs without uniqueness binding work in the following manner:

  • An RP requests an authenticator to create a session.
  • The authenticator provides a sessionId, together with an initial session proof that proves that the sessionId is well formed. A unique identifier bound to the user’s World ID for that RP.
  • The RP stores this sessionId alongside their account for the user.
  • For subsequent interactions, the RP includes the sessionId in proof requests. The user can then generate a Session Proof to prove they have the same World ID. Different proofs over time with the same sessionId may use different credentials.

The OPRF call to derive r and the OPRF call to derive the nullifier can be made in parallel.

Session Nullifiers

  • A sessionNullifier is used for verifying Session Proofs. It must be passed to the verification contract. Internally, the sessionNullifier implements custom encoding on the Authenticator and on the WorldIDVerifier contract.
  • The raison d’être is simply to allow usage of the same ZK circuit as for Uniqueness Proofs. Reducing the number of circuits is currently a priority because of the size of the circuits needed to be bundled in Authenticator clients. As World ID moves to a different proving system, this type will no longer be required.
  • Session Proofs use a randomized action as circuit input. This randomized action ensures the circuit’s nullifier output is unique per proof, preserving the one-time use property. It is verified internally within the circuit. It does not affect r derivation.

Binding Uniqueness Proofs to a Session

  • A Uniqueness Proof request may set the sessionId field to "create" to atomically mint a session and bind the proof to it. The protocol verifies in-circuit that the session and the nullifier belong to the same World ID. The flow is outlined below. Binding a Uniqueness Proof to an already existing sessionId is not supported. A session is either created together with the uniqueness proof, or it carries no uniqueness binding at all.
  • The blinding factor r of the minted sessionId is returned to the Authenticator for caching; as for session proofs it can always be re-derived from the oprf_seed.
  • Verifiers MUST check bound proofs against the session’s commitment. With the session commitment set to 0 the proof is valid but unbound. On-chain, the dedicated verifyWithSession() entry point does this (it rejects sessionId == 0). The convenience verify() entry point pins the signal to 0 and rejects bound proofs, so binding is explicit in both directions.
  • Binding one sessionId to Uniqueness Proofs under different actions intentionally links those actions to the same World ID; Authenticators MUST clearly surface this to users.

Other Risk Considerations

  • Loss of State. The OPRF nodes work with an m-of-n threshold. If $n-m+1$ nodes loses their keys, the state of the Protocol will be lost, there won’t be a way to generate the correct nullifiers and the state of “consumed” or performed actions will be lost.
  • Censoring by OPRF nodes. OPRF nodes could reject generating nullifiers for users. It’s difficult for this to be a targeted attack because the leafIndex is blinded, but they could censor specific RPs or actions.
  • Compromised OPRF nodes. Should a threshold of nodes’ key materials be compromised, or a threshold of nodes collude maliciously, users’ past and/or ongoing activity could be compromised, i.e. these nodes could arbitrary compute any nullifier because the leafIndexes are known and the domain space is relatively low. To be useful, this would require matching nullifiers to actual usage with RPs, or knowing a user’s leafIndex, at least the second not being straightforward. This is a risk that will be progressively mitigated, and the following strategies are being researched for upcoming minor Protocol version updates:
    1. Provable secure environments for OPRF nodes. Running OPRF nodes in attestable secure environments backed by secure hardware where the key material is securely stored and the execution provable. Given the nature of the computations of OPRF nodes, it is quite feasible that a plurality of enviroments and hardware providers could be supported. Authenticators would be able to verify attestations from OPRF nodes on every proof request.
    2. Increase on the number of OPRF nodes. Increasing the number of OPRF nodes and the threshold required to generate nullifiers reduces the risk of compromise. It is also very feasible to significantly extend the number of nodes over time. The cost of running a node is relatively low.
    3. Strict key management policies. RPs will be able to specify their policies for action duration such that keys are destroyed after their utility period has elapsed.
  • Authenticator Risk. Aside from having access to the user’s credentials, an Authenticator must learn of a user’s raw leafIndex to be able to generate Proofs. A malicious Authenticator can misuse this to track the user, even though that tracking cannot be correlated to nullifiers provided to RPs on its own. Different strategies to mitigate Authenticator risk are being explored.
  • Recovery Agent Risk. Should a user designate a Recovery Agent, this entity has a special permission that allows it to gain access to the user’s World ID, which could be misused. Beyond the explicit risk of a malicious Recovery Agent compromising a user’s World ID, users need to consider the different risks associated with different Recovery Agents based on how they perform authentication.

Future Proofing Notes (World ID 4.x future releases and beyond)

This is not a comprehensive list, but it outlines general topics that may be the target of upcoming Protocol releases which are not currently covered on this release.

  • Face Auth. The signature on the credential by the issuer will allow for the introduction of a provable (still with camera sensor trust) FaceAuth check during proof generation.
  • Authenticator policies and permission set. In this release, the WorldIDRegistry contains only a flat list of public keys, but this could be upgraded to be a more complex data structure that codifies explicit permissions for each key such that each authenticator can have a different policy for each action (e.g. add an authenticator vs. generating a proof), and this can be publicly verified.
  • Client-side proving. With the introduction of client-side proving and later potentially other types of proofs (e.g. age attestation), it will be possible to combine Uniqueness Proofs with additional attestations.
  • Issuers having the ability to revoke Credentials.
  • Establishing trust between protocol parties (e.g. identifying a trustworthy Authenticator).
  • Ability to merge multiple World IDs, which translates into an ability to rotate identifiers with each Issuer.
  • On the RP registry. In the future, the RP trust could also be anchored in other existing mechanisms, such as their domain name (DNS). Furthermore, actions could also be publicly registered for auditability and enforcement.
  • World ID as signer (or biometric recovery). Similar to how recovering a World ID is possible because PoH AMPC allows for the addition of a new authenticator, it’ll be conceptually possible that a World ID could be a recovery signer for other accounts.
  • Man-in-the-middle (MITM) proof phishing protection. While the attack vector of proof phishing is reduced with the introduction of the RP registry, it may still be possible to MITM proofs. Further protection mechanisms are required to mitigate this.
  • In the future, credentials could be authenticator-specific, where issuers sign them for use with a specific authenticator only.
  • Per-request fee gates may be introduced in the future (targeting 4.1 or 4.2) such that the OPRF Nodes receive a proof of payment as part of the request to generate a nullifier. This is distinct from the one-time registration fee already in place (see Registration Fees).
  • Supporting cryptographic operations that enables secrets that can live in secure hardware and never be exported.

WIP-100: Cryptographic Primitives for World ID Protocol

1. Abstract

This spec establishes the default cryptographic primitives used throughout the World ID Protocol (the “Protocol”) such as the default elliptic curve, field, signature scheme and hashing. It includes particularly important constraints and validations which are security-critical. It also specifies the circuit components that World ID circuits share: World ID authentication, Credential verification and session commitments.

2. Motivation

The Protocol is heavily reliant on different cryptographic primitives to uphold privacy and security. The correct definition and implementation of such primitives is essential for the Protocol operation. Furthermore, the spec documentation permits multiple implementations to exist in an interoperable way.

3. Specification

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

3.3.1 Domain separators

Unless otherwise specified, new domain separator labels MUST use WORLD-ID/WIP-<number>/<purpose>, where <number> is the defining WIP’s decimal number and <purpose> is an uppercase alphanumeric ASCII identifier for the construction within that WIP. For example, WORLD-ID/WIP-111/SIGN identifies WIP-111’s authenticator authorization message. This convention applies to both fixed-arity and variable-length hash labels. Existing explicitly specified labels retain their values.

A domain separator ds is the $F_q$ element derived from an ASCII label by big-endian octet-string-to-integer conversion, reduced mod $q$. Labels MUST be at most 31 bytes, so that distinct labels cannot collide under the reduction.

Each label MUST be bound to exactly one (construction, $t$, $k$) triple. For example, EdDSA Signature is allocated to the challenge hash at $t = 8$, $k = 5$, giving

$$\texttt{ds}_{\texttt{EdDSA Signature}} = 360302137480307891234917541314130533$$

3.3.2 Fixed-arity hash $H_t$

$H_t$ is the hash used wherever the number of inputs is known in advance. For a domain separator ds and inputs $m_1, \dots, m_k$ with $k \le t - 1$:

$$H_t(\texttt{ds}; m_1, \dots, m_k) := P_t([\texttt{ds}, m_1, \dots, m_k, 0, \dots, 0])[1]$$

That is, ds MUST occupy the capacity element at state index 0, the inputs occupy state indices 1..k, any remaining state elements are zero, and the digest is state element 1 of the permutation output.

$k$ MUST be constant for a given ds. The zero padding is not length-encoded, so $H_t(\texttt{ds}; m_1)$ and $H_t(\texttt{ds}; m_1, 0)$ are the same digest; binding $k$ to ds is what prevents cross-arity collisions. A construction whose input count varies at runtime MUST NOT use $H_t$.

Caution

For emphasis, failing to follow the requirement on a constant $k$, or failing to place a fixed ds at state index 0 is catastrophic. A varying $k$ gives trivial collisions and second pre-images. An input-controlled state index 0 allows an attacker to invert the permutation and produce pre-images for any digest.

3.3.3 Variable-length hash $H_\text{var}$

$H_\text{var}$ is the hash used for byte strings whose length is not fixed, where $H_t$ cannot be applied. It is a sponge over $P_{16}$: rate 15 across state indices 0..14, capacity at index 15, squeezing from index 0. Note this is the opposite convention to $H_t$, which places the capacity at index 0; $H_\text{var}$ places it last to follow SAFE.

The input is split into 31-byte chunks, each converted to an integer in big-endian order (the final chunk is not padded); the chunks are absorbed 15 at a time, applying $P_{16}$ after each group. The capacity is initialized with a SHA3-256 tag over the domain separator label and the input and output lengths, following SAFE. Because the length is bound into the capacity, inputs of different lengths cannot collide by padding, the weakness $H_t$ avoids by fixing $k$ instead.

3.4 Hash to Curve

Some constructions, in particular the OPRF evaluation of the OPRF paper, require a map $H_1: F_q \mapsto E$ that takes a field element to a curve point whose discrete logarithm with respect to $G$ is unknown. The Protocol follows RFC 9380 (“Hashing to Elliptic Curves”) instantiated for BabyJubJub, with the RFC’s expand_message step replaced by Poseidon2.

The default is $\mathrm{EncodeToCurve}$, RFC 9380’s encode_to_curve. Its output lies in the prime-order subgroup and has unknown discrete logarithm, but is not uniformly distributed in that subgroup: Elligator 2 reaches only about half of the curve points. This is sufficient wherever the requirement is an unknown discrete logarithm rather than uniformity, which covers every present use in the Protocol.

$\mathrm{EncodeToCurve}$ composes four steps, each defined below:

$$\mathrm{EncodeToCurve}(x) := \mathrm{ClearCofactor}\bigl(\mathrm{RationalMap}\bigl(\mathrm{Elligator2}\bigl(\mathrm{HashToField}(x)\bigr)\bigr)\bigr)$$

3.4.1 Notation

$\texttt{sgn0}$ is RFC 9380 §4.1 sgn0: the least significant bit of the canonical integer representative of its argument. $\texttt{inv0}$ is RFC 9380 §4 inv0: $\texttt{inv0}(0) = 0$ and $\texttt{inv0}(y) = y^{-1}$ otherwise. $\texttt{isSquare}$ is RFC 9380 §4 is_square and is true for zero. $\texttt{sqrt}$ returns an arbitrary one of the two roots; the sign is fixed explicitly in step 19 of Elligator 2, so implementations MUST NOT rely on $\texttt{sqrt}$ selecting a canonical root. $\texttt{CMOV}(f, g, c)$ returns $g$ if the condition $c$ holds and $f$ otherwise.

$E_M$ is the Montgomery form of BabyJubJub from EIP-2494, birationally equivalent to $E$:

K\,t^2 = s^3 + J\,s^2 + s, \qquad J = \frac{2(a+d)}{a-d} = 168698, \qquad K = \frac{4}{a-d} = 1

Since $K = 1$, the RFC’s constants reduce to $c_1 = J/K = 168698$ and $c_2 = 1/K^2 = 1$, and the final scalings by $K$ are no-ops. Implementations MAY drop them.

3.4.2 Hash to field

The label OPRF_HashToField_BabyJubJub is allocated to this construction at $t = 3$, $k = 1$. Writing $\texttt{ds}_\text{H2F}$ for the resulting domain separator,

$$\texttt{ds}_\text{H2F} = 32627786498498119128812045057993354633158048678109587794777765218$$

$$\mathrm{HashToField}(x) := H_3(\texttt{ds}_\text{H2F};\ x)$$

RFC 9380 §5 obtains a field element by expanding to $\lceil (\log_2 q + k)/8 \rceil$ bytes and reducing mod $q$, to bound the distance from uniform. Poseidon2 is a permutation over $F_q$, so $H_3$ already outputs an $F_q$ element with no modular bias, and the oversampling step is omitted.

3.4.3 Map to curve (Elligator 2)

$\mathrm{Elligator2}: F_q \mapsto E_M$ is RFC 9380 §6.7.1 with $Z = 5$, the value returned by the RFC’s find_z_ell2 for $F_q$ (RFC 9380 App. H.3). $Z$ is a non-square in $F_q$.

Given $u$, return $(s, t)$:

\begin{aligned}
&1..2.\ \ &&\texttt{tv1} = Z \cdot u^2 \\
&3..4.   &&\texttt{tv1} = \texttt{CMOV}(\texttt{tv1},\ 0,\ \texttt{tv1} = -1) \\
&5..7.   &&x_1 = -c_1 \cdot \texttt{inv0}(\texttt{tv1} + 1) \\
&8..11.  &&g_{x_1} = \bigl((x_1 + c_1)\,x_1 + c_2\bigr)\,x_1 \\

&15..16. &&x = \texttt{CMOV}(x_2,\ x_1,\ e_2), \quad y^2 = \texttt{CMOV}(g_{x_2},\ g_{x_1},\ e_2) \\
&17..19. &&y = \texttt{sqrt}(y^2), \quad y = \texttt{CMOV}(y,\ -y,\ e_2 \oplus \texttt{sgn0}(y)) \\
&20..22. &&(s, t) = (x \cdot K,\ y \cdot K)
\end{aligned}

Step 3 handles $\texttt{tv1} = -1$, for which $x_1$ is undefined; steps 14–16 select the branch that yields a square.

3.4.4 Rational map

$\mathrm{RationalMap}: E_M \mapsto E$ is RFC 9380 App. D.1. Given $(s, t)$, return $(v, w)$:

\texttt{tv} = \texttt{inv0}\bigl((s+1)\,t\bigr), \qquad v = \texttt{tv} \cdot (s+1) \cdot s, \qquad w = \texttt{CMOV}\bigl(\texttt{tv} \cdot t \cdot (s-1),\ 1,\ \texttt{tv} = 0\bigr)

The $\texttt{tv} = 0$ branch maps the exceptional points of the rational map to the identity $(0, 1)$ of $E$, so the map is total.

3.4.5 Clear cofactor

$$\mathrm{ClearCofactor}(Q) := h \cdot Q = 8 \cdot Q$$

Implementations SHOULD compute this as three doublings. The result lies in the prime-order subgroup, and the output of $\mathrm{EncodeToCurve}$ MAY therefore be consumed by templates that require a subgroup element without a further subgroup check.

Note that $\mathrm{ClearCofactor}$ can return the identity — for the $\mathrm{RationalMap}$ exceptional points above, and for any $Q$ of order dividing 8. Callers for which the identity is not an acceptable $H_1$ output MUST reject it explicitly.

3.5 Signatures

The default signature scheme for the World ID Protocol is an Edwards-curve Digital Signature Algorithm (EdDSA) over the twisted Edwards form $E$ of BabyJubJub, referred to as BabyJubJub-EdDSA-Poseidon2. It is the scheme given in the OPRF paper.

It follows the structure of RFC-8032 but is not an RFC 8032 ciphersuite: RFC 8032 defines only Ed25519 and Ed448, each with a fixed curve and a fixed hash function, and this scheme replaces both.

  1. BabyJubJub-EdDSA-Poseidon2 uses:
    1. $F_q$ as its finite field;
    2. $E$ as its elliptic curve;
    3. the base point $G$ as defined in Curve, of order $r$;
    4. Poseidon2 as its challenge hash, as defined in Hashing;
    5. BLAKE3 in XOF mode for the derivation of the secret scalar $sk$ and for deterministic nonce derivation. Implementations MUST NOT substitute Poseidon2 here, nor SHA-512 as RFC 8032 would prescribe. Implementors SHOULD follow the recommendations in RFC 8032 for key generation.
  2. Message. Messages are elements of $F_q$. A message not natively encodable in $F_q$ MUST first be lowered to $F_q$ with a construction from Hashing.
  3. Challenge. $e = H_8(\texttt{ds}_{\texttt{EdDSA Signature}}; R_x, R_y, pk_x, pk_y, M)$, where $pk$ is the signer’s public key. $e$ MAY be used as a full-field scalar without reduction, since reduction mod $r$ is a no-op on the prime-order subgroup in which $pk$ is required to lie.
  4. Signature. The signature is $\sigma = (R, s)$. $R$ is $r’ \cdot G$, where $r’$ is RECOMMENDED to be derived by hashing the deterministic nonce concatenated by the message as in RFC 8032, and $s = r’ + e * sk$.
  5. Public Key. The public key $pk$ is derived as $sk \cdot G$.

3.5.1 Verification

A signature $\sigma = (R, s)$ on a message $M$ under a public key $pk$ is valid iff all of the following hold.

  1. Canonical encoding. $pk$ and $R$ MUST decode from canonical field elements, per Public Key Representation.
  2. Canonical Scalar. All $s$ scalars MUST fulfill $s \in \{0, \dots, r-1\}$ to prevent signature malleability (i.e. a reduced scalar).
  3. $pk$ in the prime-order subgroup. $pk$ MUST satisfy the curve equation, MUST lie in the prime-order subgroup, and MUST NOT be the identity. This also rejects the small-order points.
  4. $R$ on curve. $R$ MUST be a point satisfying the BabyJubJub curve equation because addition is only complete for on-curve points. The point is NOT REQUIRED to lie in the prime-order subgroup for security, although conforming clients MUST produce points that lie in the prime-order subgroup.
  5. Cofactored verification equation. The signature MUST meet the cofactored verification equation $h\left(sG - R - e \cdot pk\right) = \mathcal{O}$, with $h = 8$. See Chalkias, K. et al.. Cofactorless verification MUST NOT be used; the two accept different sets of signatures.

3.5.2 Encoding

A signature is encoded as 64 bytes: $R$ in the compressed point encoding of Public Key Representation, followed by $s$ as a canonical little-endian $F_r$ element.

3.6 Discrete Logarithm Equality Proof

A discrete logarithm equality (DLogEq) proof is a Chaum–Pedersen sigma protocol, made non-interactive by the Fiat–Shamir transform with Poseidon2 as the challenge hash. It is the scheme given in the OPRF paper.

It proves knowledge of a scalar $x \in F_r$ such that

$$A = x \cdot D \quad\text{and}\quad C = x \cdot B$$

for public points $A, B, C, D \in E$, without revealing $x$. This is what gives the OPRF public verifiability: the OPRF node publishes $A = x \cdot D$ as its public key and proves that the same $x$ produced the evaluation $C = x \cdot B$ on the client’s blinded query $B$.

$D$ is a parameter of the scheme, not fixed by it. Every present use in the Protocol instantiates $D = G$, and an implementation MAY hard-code it, but the challenge hash MUST bind $D$ regardless, so that a prover cannot move the statement to a different base.

3.6.1 Proving

Given the witness $x$ and the base $B$, the prover:

  1. samples a nonce $\rho \in F_r$ uniformly at random;
  2. computes the commitments $R_1 = \rho \cdot D$ and $R_2 = \rho \cdot B$;
  3. computes the challenge $e$ as defined in Challenge;
  4. computes the response $s = \rho + e \cdot x \in F_r$.

The proof is $\pi = (e, s)$. $\rho$ MUST be freshly sampled per proof and MUST NOT be reused or derived from public data: two proofs over distinct statements that share a $\rho$ reveal $x$.

3.6.2 Challenge

The label DLOG Equality Proof is allocated to this construction at $t = 16$ with $k = 12$ inputs, giving

$$\texttt{ds}_{\texttt{DLOG Equality Proof}} = 1523098184080632582082867317389990410064981862$$

$$e = H_{16}(\texttt{ds}{\texttt{DLOG Equality Proof}};\ A_x, A_y,\ B_x, B_y,\ C_x, C_y,\ D_x, D_y,\ R{1,x}, R_{1,y},\ R_{2,x}, R_{2,y})$$

The operand order is normative: the four statement points as $A, B, C, D$, then the two commitments as $R_1, R_2$, each point contributing $x$ then $y$.

$e$ is an element of $F_q$. As in Signatures, it MAY be used as a full-field scalar without reduction, since reduction mod $r$ is a no-op on the prime-order subgroup in which all four points are required to lie.

3.6.3 Verification

A proof $\pi = (e, s)$ for the statement $(A, B, C, D)$ is valid iff all of the following hold.

  1. Canonical Scalar. $s \in \{0, \dots, r-1\}$, as in Signatures.
  2. Statement points in the prime-order subgroup. Each of $A$, $B$, $C$, $D$ MUST satisfy the curve equation, MUST lie in the prime-order subgroup, and MUST NOT be the identity.
  3. Recomputed commitments. $R_1 = s \cdot D - e \cdot A$ and $R_2 = s \cdot B - e \cdot C$.
  4. Non-degenerate commitments. Neither $R_1$ nor $R_2$ is the identity.
  5. Challenge. $e$ equals the challenge recomputed over $(A, B, C, D, R_1, R_2)$ per Challenge, compared as $F_q$ elements.

A verifier MAY discharge check 2 for a given point outside the proof system, and a circuit implementing this verification MAY therefore omit it for a point that is a public input of the enclosing proof. In that case the check becomes an obligation on the enclosing verifier and MUST be documented as such at the circuit boundary.

3.7.1 Groth16 Proof Encoding

A Groth16 proof is three BN254 points $(A, B, C)$, with $A, C \in G_1$ and $B \in G_2$. Their coordinates use BN254’s base field $F_p$, distinct from the circuit field $F_q$ in Field:

$$p = 21888242871839275222246405745257275088696311157297823662689037894645226208583$$

Write a $G_2$ coordinate as $x_0 + x_1 i$, where $i^2 = -1$. The canonical Solidity encodings are fixed-length sequences of 32-byte unsigned big-endian words, preserving leading zero bytes:

FormWord orderSize
Uncompressed[A.x, A.y, B.x1, B.x0, B.y1, B.y0, C.x, C.y]8 words / 256 bytes
Compressed[a, B.x1, b, c]4 words / 128 bytes

For non-infinity points, a = (A.x << 1) | sA, c = (C.x << 1) | sC, and b = (B.x0 << 2) | (hB << 1) | sB. The low bits carry square-root selection information:

  • For $G_1$, s = 0 selects $y = (x^3 + 3)^{(p+1)/4} \bmod p$; s = 1 selects its negation.
  • For $G_2$, hB is the square-root hint and sB selects whether to negate the recovered $y$ coordinate. Both MUST follow compress_g2 / decompress_g2 in the reference verifier. These bits are not parity bits or the BabyJubJub sign convention.
  • Infinity is all-zero coordinates when uncompressed, and 0 for $G_1$ or [0, 0] for $G_2$ when compressed.

Encoders MUST match the reference verifier’s compressProof output, including the imaginary-before-real order of the $G_2$ words. This is the Solidity BN254 compression scheme, not arkworks’ CanonicalSerialize compressed encoding. Coordinates MUST be canonical integers less than $p$; verifiers MUST reject invalid points and enforce the Groth16 group and pairing checks. Successful decoding alone does not establish proof validity.

3.7.2 World ID Proof Envelope

The ZeroKnowledgeProof type used for Uniqueness and Session Proofs appends the Merkle root to the compressed proof: [a, B.x1, b, c, merkle_root]. This is exactly 160 bytes, or Solidity uint256[5]. The root is a public input in $F_q$, MUST be less than $q$, and is not a fourth proof point. Other public inputs are supplied separately.

The JSON representation is the lowercase hexadecimal encoding of these 160 bytes: 320 characters, without a 0x prefix.

3.9 Public-key Encryption

By default, the Protocol SHOULD use the following mechanism for use cases requiring public-key encryption where encryption is intended as anonymous. Anyone with a recipient’s public key can encrypt a message, and the recipient uses the matching secret key to open it. Its ciphersuite is Hybrid Public Key Encryption (HPKE) from RFC 9180, in Base mode.

Implementations of this ciphersuite MUST use the following algorithms:

PartAlgorithmPurpose
Key encapsulation (KEM)X-WingEstablishes a shared secret for each message.
Key derivation (KDF)HKDF-SHA-256Derives the encryption key and nonce from that secret.
Authenticated encryption (AEAD)ChaCha20-Poly1305Encrypts data and detects tampering.

X-Wing combines ML-KEM-768 (quantum resistance) with X25519 (conventional EC). The hybrid design protects the shared secret as long as at least one of these two components remains secure. The encryption also depends on the security of the KDF and AEAD.

The HPKE algorithm identifiers MUST be 0x647A for X-Wing, 0x0001 for HKDF-SHA-256, and 0x0003 for ChaCha20-Poly1305.

The sealed-message format defined below is version 2. Each message MUST use a fresh HPKE Base context with cryptographically secure randomness and exactly one encryption at sequence number zero, as in RFC 9180 §6.1. Base mode does not authenticate the sender.

Applications MAY supply context bytes through HPKE’s info input. Both sides MUST use the same bytes; when no context is specified, info MUST be empty. These bytes are not included in the sealed message, so the enclosing protocol MUST define them if used.

3.9.1 Key Encoding

Encryption keys MUST use the X-Wing byte encodings. The recipient’s public key is exactly 1216 bytes: the 1184-byte ML-KEM-768 public key followed by the 32-byte X25519 public key. A serialized secret key is the 32-byte X-Wing seed from which both component keys are derived.

When represented as text, the public key MUST use the standard Base64 alphabet from RFC 4648 §4, without = padding, whitespace, or a prefix.

3.9.2 Sealed-message Encoding

A sealed message MUST be the following concatenation of raw bytes, with no length prefixes or separators:

header || enc || ct

Offsets below count bytes from zero.

OffsetSize (bytes)Field
07Header, defined below.
71120enc: X-Wing encapsulated key.
1127All remaining bytes, at least 16ct: encrypted message and authentication tag.

enc MUST contain the 1088-byte ML-KEM-768 ciphertext followed by the 32-byte ephemeral X25519 public key, in that order, using the X-Wing encodings.

ct MUST be the HPKE encryption output: the encrypted plaintext followed by the 16-byte Poly1305 tag, as defined in RFC 8439 §2.8. The nonce is derived by HPKE and is not transmitted separately. The total sealed-message length is the plaintext length plus 1143 bytes; an empty plaintext is allowed and produces a 1143-byte sealed message.

3.9.3 Header

The header MUST contain exactly these fields and values. The two-byte identifiers MUST be unsigned integers in big-endian order.

OffsetSize (bytes)FieldRequired value

02 64 7a 00 01 00 03

The header is not encrypted. These exact seven bytes MUST be supplied as HPKE’s associated data (aad) for both encryption and decryption, so the authentication tag also protects the header.

Receivers MUST reject messages shorter than 1143 bytes, any header that differs from the one above, and any failed KEM decapsulation or AEAD authentication. They MUST NOT release plaintext unless authentication succeeds.

4. Public Key Representation

The PublicKey type is introduced to represent public keys of used elliptic curves. Two representations are defined and MUST NOT be conflated:

  1. In-circuit: an affine point, i.e. a structure with two Field elements $(x, y)$. Both coordinates MUST be carried explicitly; a circuit MUST NOT decompress a point.
  2. Wire: a compressed point of 32 bytes, holding $y$ as a canonical little-endian $F_q$ element with the sign of $x$ in the most significant bit of the final byte. The sign bit is set when $x > -x$, comparing canonical integer representatives. Note: This is not equivalent to sgn0.

Decompression recovers $x$ from $y$ via the curve equation and selects the root indicated by the sign bit. Deserialization MUST reject a non-canonical $y$, i.e. one that is not less than $q$. The identity point of the used BabyJubJub curve is (0,1) and is represented using the above rules.

This compressed encoding is not the iden3 BabyJubJub packing, and the two are not interchangeable.

5. Merkle Inclusion Proof

The Protocol uses Merkle trees to store membership and prove inclusion. The most important use of it is to store World ID account membership in the WorldIDRegistry. An account’s position in the tree is its leaf index.

5.1 Parameters

ParameterValue
Arity2
Depth30
Node compression$\mathrm{Compress}$, below
Empty leaf$0$

Leaf index 0 is reserved and MUST NOT be assigned.

5.2 Node compression

Nodes MUST be combined with the Davies–Meyer compression function

$$\mathrm{Compress}(x_L, x_R) := P_2([x_L, x_R])[0] + x_L$$

$t = 2$ leaves no state element free for a capacity, so $\mathrm{Compress}$ carries no domain separator and is an exception to Domain separators. $\mathrm{Compress}$ MUST NOT be used outside a fixed-depth Merkle tree; see Security.

5.3 Inclusion proof

An inclusion proof for a leaf at index $i$ consists of $i$ together with the 30 sibling nodes $s_0, \dots, s_{29}$, ordered from the leaf level upwards. The root is recomputed as

v_0 = \mathrm{leaf}, \qquad
v_{j+1} = \begin{cases}
  \mathrm{Compress}(v_j,\ s_j) & \text{if bit } j \text{ of } i \text{ is } 0 \\
  \mathrm{Compress}(s_j,\ v_j) & \text{otherwise}
\end{cases}

where bit $j$ is the $j$-th least significant bit of $i$. The proof is valid if and only if $v_{30}$ equals the tree root. Verifiers MUST apply exactly 30 compressions and ensure the depth of the Merkle tree is 30 and $\forall i$, $0 < i < 2^{30}$ MUST hold.

6. Circuit Components

Circuit components are building blocks that World ID proof circuits share. Each is specified once here, and other specs use it by reference.

  1. A component is a constrained function over the parameters listed for it. It proves only the relation its checks enforce.
  2. A circuit composes components into one proof. Each of its inputs is public, known to the verifier, or private, known only to the prover.
  3. A consuming specification defines which parameters are public and how the others are derived, following Composition.

6.4 Composition

  1. A consuming circuit MUST pass the same leaf_index to World ID Authentication and every other component, and MUST keep it private.
  2. A consuming circuit MUST compute message with a domain separator of its own, allocated per Domain separators.

6.5 Reference Verification

An RP accepts the public parameters a consuming circuit exposes if:

  1. merkle_root is a root the WorldIDRegistry accepts and has not expired.
  2. cred_pk is a trusted Issuer key for issuer_schema_id, and genesis_issued_at_min and now meet the RP’s policy.
  3. If the RP needs a proof to concern the same World ID as another proof, session_id is nonzero and equals that proof’s session commitment.

7. Security

  1. Poseidon2 in compression mode. For a security argument of using Poseidon2 with state size 2 as a 2-1 compression mode, we refer to both section 3.1 of the Poseidon2 paper as well as the treatment of the construction in section 4.2 of the Griffin paper.
  2. Security Target. The Protocol defines a target security of 128 bits. BabyJubJub is the binding constraint, with $r \approx 2^{251}$. Poseidon2 and BLAKE3 are both parameterized for 128 bits.
  3. Assumptions. The discrete logarithm problem is hard in the order-$r$ subgroup of $E$; Poseidon2 over $F_q$, at the widths in Hashing, is collision- and preimage-resistant and behaves as a random oracle under Fiat–Shamir; BLAKE3 is a secure pseudorandom function and extendable-output function.
  4. Fixed tree depth. $\mathrm{Compress}$ carries no domain separator, so nothing in a node marks its tree level. Requiring exactly 30 compressions fixes each node’s level, so an inclusion proof can not end at an inner node or mix levels.
  5. Leaf-index binding. Without the shared leaf_index of Composition, a proof can combine one World ID’s Authenticator with another World ID’s Credential or session.
  6. Message separation. Two circuits that sign the same message format accept each other’s Authenticator signatures. A domain separator per circuit prevents this.

8. Backwards Compatibility

This spec is introduced after the initial release of the World ID 4.0 protocol, it is documenting design decisions previously defined in the 4.0 Specs and from the OPRF Whitepaper, so it’s not breaking backwards compatibility. From adoption onwards, the definitions in this spec become binding for the Query Proof and Nullifier Proof used in the World ID Protocol.

Circuit Components restate the logic the Query Proof, Uniqueness Proof and WIP-103 already enforce, with one exception: fixed Merkle depth (breaking for WIP-103). The components fix the tree depth to 30, so the Proof of Ownership no longer takes depth as a public input. Its verifiers stop passing one, and proofs from the earlier circuit don’t verify against the new keys.

WIP-101: RP Request Authorization Method for Smart Contracts

1. Abstract

This spec introduces a method to verify Relying Party (RP) proof requests in the World ID Protocol through on-chain smart contracts. As some RPs may not have a backend and be simply a contract, this allows OPRF Nodes to answer “Does the RP authorize this request?” in order to process relevant OPRF requests such as for nullifier generation.

2. Motivation

Context: Proof requests from Relying Parties in the World ID Protocol MUST be signed in order to be recognized. This serves to ensure proofs are authorized for the intended recipient and reduce the attack surface in post-compromise scenarios for Authenticators.

A Relying Party MAY be a Smart Contract without a backend. When this is the case, having a private key to sign the request is impractical or even impossible in a secure way. Hence, we need a way for Relying Parties to authorize the request in a way compatible with Smart Contracts.

3. Specification

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

In this document, “contract” and “smart contract” are used interchangeably.

This specification introduces both concerns of “Authorization” and “Validation” of Relying Party (RP) Proof requests. When an RP requests a proof without a smart contract, they construct the proof request and sign the data they constructed. If the RP does not have a backend or other trusted environment, they cannot control the inputs to the Proof request. Hence, the contract SHOULD implement validation rules for the request. For example, an RP should determine what is the maximum expiration period they should allow for Proof requests and enforce it during verification.

3.1 Contract Interface

  1. To be compatible with signature verification, a contract acting as an RP MUST conform to the IWIP101 interface below. verifyRpRequest MUST NOT modify state (declared view for solc > 0.5) and MUST allow external calls.
  2. On a valid request, verifyRpRequest MUST return the bytes4 magic value 0x35dbc8de (the function selector for verifyRpRequest). Reverts otherwise.
  3. The contract (implementer) MUST also adhere to ERC-165 and return true from supportsInterface for type(IWIP101).interfaceId.
/**
 * @dev Interface of the WIP-101 standard for World ID,
 *   RP Request Authorization Method for Smart Contracts.
 */
interface IWIP101 is IERC165 {
    /**
     * @dev The RP request is not valid. The code may be used to provide additional debugging information.
     */
    error RpInvalidRequest(uint256 code);

    /**
     * @notice Verifies a World ID Proof Request is authorized by the RP.
     * @dev Should return whether the RP request is valid and should be honored. The `rpId` is implicit in this request,
     *  any contract implementing this interface will be pointed to in the `RpRegistry`.
     * @param version The version determines the format of the request.
     * @param nonce Unique nonce for this request
     * @param createdAt Creation timestamp of the request
     * @param expiresAt Expiration timestamp specified for the request
     * @param action Provided action for the request. Importantly, this is already a hashed
     *  action as a field element.
     * @param data Arbitrary data useful for the verification.
     * @return magicValue The expected magic value when the request is valid. Reverts otherwise.
     *
     * MUST return the bytes4 magic value 0x35dbc8de when function passes (function selector for verifyRpRequest).
     * MUST NOT modify state (view modifier for solc > 0.5)
     * MUST allow external calls
     */
    function verifyRpRequest(
        uint8 version,
        uint256 nonce,
        uint64 createdAt,
        uint64 expiresAt,
        uint256 action,
        bytes calldata data
    ) external view returns (bytes4 magicValue);
}

3.2 Request Validation and Errors

  1. If the request is not authorized, verifyRpRequest MUST revert.
  2. When a request is invalid, implementers SHOULD revert with the explicit RpInvalidRequest error.
  3. Callers MUST treat any return value other than the magic value 0x35dbc8de as an invalid request.
  4. RPs MAY define any number of codes in RpInvalidRequest. These codes are intended only for RP debugging, hence the RP can establish any format/definition for this attribute.
  5. It is RECOMMENDED implementers ensure that any upgrades to validation logic are backwards-compatible for the duration of the maximum expiresAt window.

3.3 OPRF Node Behavior

The verifyRpRequest method will be used by OPRF Nodes to verify an incoming proof request before generating the required output to construct a nullifier. When a contract compliant with this spec is deployed, its address can be set as a signer in the RpRegistry contract (e.g. through the updateRp function).

  1. OPRF Nodes MUST use this spec (WIP-101) verification if the signer in the RpRegistry implements ERC-165 for type(IWIP101).interfaceId.
  2. Following the main threat model of this spec, OPRF Nodes MUST pass to verifyRpRequest the same action value that will be used as input to the OPRF computation.
  3. On an explicit RpInvalidRequest revert, OPRF Nodes MUST return the inner code to the requester (for debugging purposes).
  4. OPRF Nodes MAY enforce a timeout on the resolution of verifyRpRequest.
  5. Implementers SHOULD NOT rely on computationally expensive validation logic, so a call resolves within any node-enforced timeout.
  6. OPRF Nodes MAY check whether a contract is deployed at the registered signer address, and MAY return a specific error code if a deployed contract is not WIP-101 compliant.
  7. OPRF Nodes are NOT REQUIRED to verify signature via ECDSA if there is a contract deployed at the signer address.

3.4 Signer Caching

  1. OPRF Nodes MAY cache an RP’s signer for performance. This cache may include the consideration on whether the signer is WIP-101 compliant or not.
  2. A cached signer entry MUST NOT exceed a 30-day TTL.
  3. OPRF Nodes MUST invalidate the signer cache on any RpUpdated event emission from the RpRegistry.

3.5 Request Field Constraints

  1. The maximum length of data is 8192 bits (1024 bytes); the data field MUST NOT exceed this length.
  2. OPRF Nodes MAY enforce this maximum length and reject requests which exceed it.

3.6 Deployment

  1. Implementations of WIP-101 MUST be deployed on World Chain Mainnet (Chain ID: 480).
  2. OPRF Nodes MUST only verify contract execution on chain ID 480.

Note: For RPs using other chains, proof verification MAY occur elsewhere, it’s only the request authorization that MUST happen on World Chain.

3.7 Additional Context (non-normative)

Version.

The version of the ProofRequest which is passed as version attribute to the verifyRpRequest function is currently defined in the RequestVersion enum.

Invalidating Signer Cache.

Note that RPs can trigger a cache invalidation of the signer by doing a no-op (or an actual) update with the updateRp method in the RpRegistry (see §3.4). This is useful if for example the signer is an ERC-1967 proxy and the implementation was updated in a way material to determine compliance or non-compliance with this spec (e.g. a bug in the implementation of the ERC-165 interface).

Authorizing Sessions.

Implementers may also authorize requests for Session Proofs or starting a session. For these scenarios, the action value will have the relevant prefix. For example, requests for a Session Proof will have a prefix of 0x02 in the most significant byte of the action, i.e. uint8(action >> 248) == uint8(2). More details on the different prefixes can be found in the SessionId definition.

Implementers MAY encode different handling depending on the type of request. For example:

  • If the RP does not support sessions, reject proofs if the prefix does not equal 0x00.
  • If the RP supports sessions, the actions are randomly generated, so as long as the prefix matches one of the expected values (e.g. 0x01, 0x02), the action check can be considered fulfilled.

4. Rationale

The verifyRpRequest allows an RP to verify all the inputs that would otherwise be signed, so any rules that an RP would normally use when constructing an off-chain request can be encoded in the RP’s contract for pure on-chain interactions.

The rationale behind the arbitrary data is that the action is passed to this function already hashed into the field so nothing on the pre-image can be validated. Validating the content of the pre-image is something particularly important because it scopes the uniqueness space, i.e. it’s an input to the nullifier of a proof. An example of this is data could include the pre-image of the action in order to perform validations over the raw action data.

This spec is inspired by ERC-1271.

5. Reference Implementation

contract WIP101Example is IWIP101, ERC165 {
    // bytes4(keccak256("verifyRpRequest(uint8,uint256,uint64,uint64,uint256,bytes)"))
    bytes4 internal constant MAGICVALUE = 0x35dbc8de;
    
    /**
    * @dev The RP request is not valid. The code may be used to provide additional debugging information.
    */
    error RpInvalidRequest(uint256 code);

    /// @inheritdoc IWIP101
    function verifyRpRequest(
        uint8 version,
        uint256 nonce,
        uint64 createdAt,
        uint64 expiresAt,
        uint256 action,
        bytes calldata data
    ) external view returns (bytes4 magicValue) {
        if (version > 1) {
            revert RpInvalidRequest(0);
        }
        
        if (createdAt > block.timestamp || createdAt < block.timestamp - 15 minutes) {
            revert RpInvalidRequest(1);
        }

        if (expiresAt < block.timestamp || expiresAt > block.timestamp + 15 minutes) {
            revert RpInvalidRequest(2);
        }
        
        if (uint8(action >> 248) != uint8(0)) {
            // This RP does not support Session Proofs
            revert RpInvalidRequest(3);
        }
        
        // note the bitshift by 8 for the action to fit into the field; this is the same
        // method as in `FieldElement::from_arbitrary_raw_bytes` which is used in common SDKs
        uint256 expected_action = uint256(keccak256(abi.encodePacked("vote"))) >> 8;

        if (action != expected_action) {
            revert RpInvalidRequest(4);
        }

        return MAGICVALUE;
    }

    /// @inheritdoc ERC165
    function supportsInterface(bytes4 interfaceId) public view virtual override(ERC165, IERC165) returns (bool) {
        return interfaceId == type(IWIP101).interfaceId || super.supportsInterface(interfaceId);
    }
}

6. Recommended Validations

It is RECOMMENDED to implement the following validations for a Proof request:

  1. Reject a request which version is larger than the maximum known, as future version changes MAY be incompatible with previous versions.
  2. createdAt is not in the future and close to the current time.
  3. expiresAt is not in the past and is not too far in the future. While “too far” is relative to each RP’s use case, it’s unlikely that a Proof request should be valid for more than 15 minutes. Note that sub-minute precision SHOULD generally NOT be relied upon on-chain.
  4. nonce has not been used before. This is RECOMMENDED, however OPRF Nodes will still enforce a nonce is only used once. Nonce tracking within verifyRpRequest is not possible due to the view constraint. Implementers relying on nonce uniqueness SHOULD track used nonces in a separate transaction (e.g., when the proof is consumed on-chain). The rationale for this is that a nonce isn’t considered “consumed” until the proof is verified. Furthermore, each OPRF Node will call the verifyRpRequest function independently, so it’s not a good place to enforce non re-use.
  5. action hash is the expected value for Uniqueness Proofs.
  6. If the RP does not support Session Proofs, the first 8 bits of the action must all equal 0.

7. Security

  1. The main threat model protected with this spec is authorization of RP Requests such that an authenticator (malicious or not) cannot generate nullifiers (or other OPRF outputs) for use with an RP without that RP’s authorization. This for example helps protect users in post-compromise scenarios. If an RP implements proper authorization logic, even with a compromised authenticator, an attacker would be unable to compute a user’s nullifier. Binding the OPRF input to the verified action (§3.3) is what anchors this guarantee.
  2. Implementers are solely responsible for the security of their validation logic. A verifyRpRequest that unconditionally returns the magic value is equivalent to having no authorization and exposes the RP to unbounded nullifier generation for any action as well as users in a post-compromise scenario.

WIP-102: Simplified Optimistic Recovery Agent Update

1. Abstract

This spec proposes replacing the current Recovery Agent update mechanism (initiateRecoveryAgentUpdate, cancelRecoveryAgentUpdate, executeRecoveryAgentUpdate), that always requires two transactions, with a new flow (updateRecoveryAgent, revertRecoveryAgentUpdate) that only requires a second transaction when the update needs to be reverted. The proposal preserves the security delay through a revert window.

2. Motivation

In the current contract implementation the user has to first call initiateRecoveryAgentUpdate. This initiates a configurable (e.g. 14 days) period during which the update operation can be cancelled (with a cancelRecoveryAgentUpdate call). After the period is over anyone can call a permissionless executeRecoveryAgentUpdate transaction to finalize the update.

This introduces the following issues:

  1. The updater has to remember to execute the call after the delay, or someone needs to develop and maintain an auto-executing service.
  2. The new Recovery Agent isn’t set on-chain until the delay elapses, which can be problematic e.g. if the user wants to register a Recovery Agent after registering their World ID. The Recovery Agent cannot be sure this has been set up properly for a World ID.

3. Specification

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

3.1 Method Changes

The existing 3 methods are replaced with 2 new methods:

initiateRecoveryAgentUpdateupdateRecoveryAgent
cancelRecoveryAgentUpdaterevertRecoveryAgentUpdate
executeRecoveryAgentUpdateremoved

3.2 Mechanism

Instead of delaying the Recovery Agent update on-chain, the updateRecoveryAgent function updates the address immediately, records the previous Recovery Agent in a mapping, and sets a delay on the account. During this delay period an account MUST NOT yet be recoverable with the new Recovery Agent.

  • The previous Recovery Agent remains valid until invalidAfter elapses and the user MAY revert the update during this window, restoring the previous Recovery Agent. This is to maintain the security mechanism when updating a Recovery Agent to mitigate takeover attacks.
  • The new Recovery Agent SHALL NOT be used until after invalidAfter. Once invalidAfter elapses without a revert, the previous Recovery Agent becomes invalid and the new Recovery Agent becomes the sole valid Recovery Agent.

3.3 Storage

This change requires storing the previousRecoveryAgent address and an invalidAfter timestamp per leafIndex in the WorldIDRegistry. The data stored is equivalent to what is currently stored in the contract but with inverted semantics:

Current:

When recoverAccount is called, any active Recovery Agent update (i.e. invalidAfter has not yet elapsed) MUST be cleared automatically. This handles the attack scenario where an attacker compromises an authenticator, removes the user’s authenticators to lock them out, and initiates a Recovery Agent update. 4. Rationale

This solution preserves the original security properties while enabling better ergonomics and user experience. Notably:

  1. No follow-up transaction required. The update takes effect immediately, removing the need for an execution step after the delay period.
  2. Equivalent security. The revert window ensures that an attacker who compromises an authenticator cannot immediately replace the Recovery Agent. Any Admin Authenticator retains the ability to revert the change during the delay period.

WIP-103: Proof of Ownership

1. Abstract

This spec introduces a new ZK circuit (“Ownership Proof”) to the World ID Protocol that allows a user to prove they own a specific registered leaf without revealing their leaf_index or any private key material to the verifier. The circuit takes a domain-separated commitment, H(domain_separator, leaf_index, commitment_blinder), and proves that the user controls a secret key registered in the WorldIDRegistry for that leaf, without exposing the commitment_blinder value (e.g. a credential blinding factor) as a public input. The initial use case is Issuer Authentication, where a user proves ownership of a credential sub to an Issuer for operations like re-issuance, renewal, or deletion.

2. Motivation

There are use cases that require users to prove ownership for their World ID and a specific commitment. At the time of writing there is a well-known use case for Issuer Authentication.

2.1 Issuer Authentication

Issuers may require users to authenticate with their World ID. Some examples of such use cases:

  • Re-issuance. Allowing the user to get a new copy of their credential due to loss.
  • Status information. Providing the user with information on their current enrollment state.
  • Cancellation/deletion/unregistration. Allowing the user to unregister, delete or cancel their existing credential.

For the cases above, Issuers need to know the legitimate owner of a Credential is requesting the operation. Issuers do not know the user’s leaf_index by design, so a mechanism to authenticate based on the Credential’s subject (sub) is required.

3. Specification

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

The terms Authenticator, Issuer and Credential are as defined in the World ID Protocol.

This specification introduces a new circuit to the Protocol: “Ownership Proof”. The Ownership Proof is a new circuit which allows users to prove ownership (as defined below) using a specific commitment.

A non-normative high-level description of what the circuit proves:

  1. It proves the user’s leaf_index hashed with a commitment_blinder and a specific domain separator produces an expected_commitment. An example, is the Credential’s blinded sub.
  2. It proves the user’s leaf_index is validly registered in the WorldIDRegistry and the user can produce a signature with a secret key ($sk$) registered as an authenticator for the particular leaf_index.
  3. It proves the user authorized the operation through a signature with a registered authenticator secret key and that such operation is only valid for a specific nonce and context provided.

The Ownership Proof circuit MUST introduce the following inputs. The circuit MUST NOT introduce any additional public inputs which are not specified in this or a future spec.

3.2 Circuit constraints

The Ownership Proof circuit MUST implement the following constraints (order is not relevant):

  1. Expected commitment. Compute the commitment as: H_3(domain_separator, leaf_index, commitment_blinder). The computed commitment MUST equal the expected_commitment. The domain_separator is dependent on the Use Case and all possible domain separators MUST be hardcoded in the circuit.
  2. Authorization message. Compute message = H_4(DS_WIP_103, expected_commitment, nonce, context). Constraint 3 verifies the Authenticator’s signature over it, which authorizes the particular nonce and context.
  3. World ID Authentication. The circuit MUST enforce WIP-100 World ID Authentication over message, with user_pk, pk_index, leaf_index, siblings and (sig_r, sig_s) as its inputs. This selects pk = user_pk[pk_index] with pk_index < NUM_KEYS, rejects the neutral element $O = (0,1)$ used for inactive slots, proves inclusion of the MERKLE_LEAF_DS key-set commitment at leaf_index under merkle_root with 0 < leaf_index < 2^30, and verifies the signature.
  4. Leaf-index binding. The leaf_index hashed into the commitment in constraint 1 and the leaf_index of constraint 3 MUST be the same witness. The circuit MUST NOT accept two independent values. This binding is essential, otherwise the circuit is only proving the prover knows the sk of some leaf, not the one being proven in the expected_commitment.
  5. Verifier-supplied input validation. The nonce and context MUST NOT equal 0. These are usually intended as sentinel values and could surface an incorrect use of them.

3.3 Nonce

The nonce is a security mechanism to prevent replay attacks. Recipients of an Ownership Proof (also called “verifiers” in this spec) are responsible for its generation and verification.

  1. Provenance. Verifiers MUST generate and provide the nonce. Authenticators MUST NOT generate nonces.
  2. Single Use. Verifiers MUST enforce that a nonce may only be used one time. Verifiers MUST invalidate any nonce after first use.
  3. Entropy. Verifiers MUST generate the nonce from a uniformly random distribution using a CSPRNG over the whole field $F$.
  4. Expiration. Nonces MUST have a defined TTL and not be valid after expiration. Verifiers MAY define the mechanism to accomplish this.
  5. The 0 element is NOT a valid nonce.

3.4 Context

The context is the mechanism by which a verifier binds a specific proof to a specific requested operation. The verifier MUST constrain the use of Ownership Proofs to specific operations and assign such operations with a unique context. For example, renewing a credential and deleting a credential are two different contexts. The verifier MUST provide the context when requesting a proof and MUST verify the provided context is valid for the explicit operation being executed.

It is RECOMMENDED that Verifiers use contexts shorter than 31 bytes or use a hash function to avoid collisions.

The 0 element is NOT a valid context.

3.5 Verification requirements

  1. Enrollment. Verifiers SHOULD verify a Proof of Ownership when enrolling a sub (i.e. seeing it for the first time). This recommendation depends on what enrollment does at the Verifier. For example, providing an invalid sub for ordinary credential issuance only yields an unusable credential. In any case, an unverified sub MUST NOT authorize any operation by itself.
  2. Root Freshness. Verifiers MUST check that the provided public input merkle_root is valid and non-expired. Verifiers MAY check WorldIDRegistry.isValidRoot(merkle_root) on every verification or cache a valid result until the root’s actual expiration (e.g. from WorldIDRegistryV2.getRootExpiration). The configured getRootValidityWindow() is not the root’s remaining lifetime and MUST NOT, by itself, determine the cache duration. A getRootExpiration result of 0 denotes the latest root, not an unlimited cache lifetime. Cache access MUST NOT extend the expiration.
  3. Proving System. Ownership Proofs MUST use the ProveKit proving system. Verifiers MUST NOT use verification artifacts supplied by the prover.

4. Use Cases

  1. Authenticators MUST restrict Ownership Proofs subject only to the use cases outlined in this spec or a future spec which references this one.
  2. If future use cases are added, the commitment_blinder IS REQUIRED to always be a high entropy value to prevent finding a user’s leaf_index. Unless otherwise noted, it should be randomly generated from a CSPRNG uniformly distributed over the entire $F$.

Please note that after World ID Recovery, a Proof of Ownership can still be used to prove a sub, as the original leafIndex is preserved.

4.1 WIP-103-001: Issuer Authentication

  • Use case: Authenticating to an Issuer where the Issuer has a sub as identifier.
  • Domain Separator: b"H_CS(id, r)" named DS_CREDENTIAL_SUB.
  • commitment_blinder value: The credential’s blinding factor as stored (or re-derived) by the Authenticator.
  • Use conditions: Can only be used to prove ownership with the specific Issuer for which the sub was generated. The Authenticator MUST ensure this proof is only provided to the Issuer it corresponds. The Authenticator knows this from the blinding factor used as the commitment_blinder input. Furthermore, providing this proof MUST come from a user initiated action and SHALL NOT be requested by Issuers. Acceptable examples include: when a user requests a Credential re-issuance, when a user requests a Credential renewal, when a user requests a Credential deletion.
  • Verification: Issuers MUST ensure the expected_commitment public input of the circuit matches the expected identifier (i.e. Credential’s sub).

5. Rationale

A keen observer would notice the Ownership Proof circuit is very similar to the Query Proof circuit. Using this circuit is not an option because the verifying party would need to learn the commitment_blinder being verified to ensure the hash validity (it’s a public input). For example, an Issuer does not need to learn the credential blinding factor, which would defeat the purpose of the blinding factor because the leaf_index could be easily brute forced.

6. Reference Verification

An Issuer will be able to know a specific user is the legitimate owner of a sub by performing the following validations:

  1. Ensuring the received zero-knowledge proof verifies according to Proving system.
  2. The root hash satisfies Root freshness at verification time.
  3. The expected_commitment public input matches the expected sub being verified. This value MAY also be used for lookups when the sub is not known in advance.
  4. The nonce public input is one the Issuer itself generated, has not expired, and has not been used before. The nonce MUST be invalidated at this point. See Nonce.
  5. The context public input is the context the Issuer assigns to the operation it is about to execute. A proof carrying any other context MUST be rejected, even if every other check passes. See Context.

Validations 4 and 5 are what make the proof unreplayable and single-purpose. The circuit constrains the nonce and context to be bound in the authenticator’s signature, but it cannot know which values the verifier intended, so a verifier that accepts the values supplied alongside the proof without comparing them to its own gains no replay or cross-context protection.

7. Security

  1. commitment_blinder is never revealed. Unlike the Query Proof circuit, the commitment_blinder value is a private input. For Issuer Authentication (WIP-103-001), this means the credential blinding factor is never exposed to the Issuer. If it were, the Issuer could brute-force the leaf_index (the domain of possible values is small) and break the unlinkability property of the blinding factor.
  2. Domain separation prevents cross-context replay. Each use case defines its own domain separator, and the domain_separator is committed inside the hash. A proof generated for one use case cannot be replayed in another context. Authenticators MUST enforce that only domain separators defined in this spec or a referencing spec are used.
  3. Authenticator-gated usage. Authenticators MUST restrict generation of Ownership Proofs to user-initiated actions for the defined use cases. Issuers SHALL NOT be able to request this proof; the Authenticator must initiate it. This prevents an Issuer from using the proof as an oracle to test whether a given sub belongs to a particular user.
  4. Nonce and context are bound into the signed message. The signature verified by the circuit is over nonce, context and expected_commitment, not only over the bare commitment. This means every Ownership Proof requires a fresh signature from the authenticator signing key for that specific (nonce, context) tuple (in addition to the expected_commitment), anchoring proof generation to an active signing event by the Authenticator.
  5. For note, proofs for the same expected_commitment (e.g. the same sub) are linkable because they use the same public input. This is intended as the expected_commitment is what its getting proven. This proof however prevents cross-verifier linking as the commitment_blinder differs.

8. Backwards Compatibility

This World Improvement Proposal (WIP) introduces a new interface; no existing contracts or other previously existing functionality is affected.

Adopting the WIP-100 Circuit Components removed the public depth input and added the leaf_index != 0 constraint. This changes the circuit’s public inputs and its proving and verification artifacts, so provers and verifiers MUST upgrade together.

WIP-104: Proving and Admin Authenticators with Fixed Permission Sets

1. Abstract

This spec introduces a distinction between two classes of Authenticators in the World ID Protocol: Proving Authenticators and Admin Authenticators. A Proving Authenticator holds only an off-chain public key and is limited to proof generation and presentation. An Admin Authenticator additionally holds an on-chain management key (represented as an address registered in _authenticatorAddressToPackedAccountData) and can perform all management operations on the World ID. The authenticator type is encoded in the existing pubkey bitmap of the WorldIDRegistry. In addition, this spec deprecates the updateAuthenticator method.

2. Motivation

Prior to this spec, every authenticator registered for a World ID was required to have a corresponding on-chain management key. This means every authenticator has equal permissions and can perform all management operations (inserting, removing or updating other authenticators, initiating recovery agent updates, etc.). There are multiple use cases where a user may want to have an authenticator capable of generating proofs on their behalf but not managing their World ID. An example of this is when delegating proof generation to some CLI tools, agents or non fully-featured authenticators.

Requiring a management key for authenticators that don’t need it expands the attack surface (and additionally increases storage costs on-chain). Separating the two roles allows:

  1. A smaller attack surface for Proving Authenticators, limiting the blast radius in case of compromise.
  2. Reduced storage costs for authenticators that only generate proofs.
  3. Flexibility for future authenticator form factors that lack the ability to hold an Ethereum key pair.

3. Specification

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

The terms Authenticator, Issuer and Credential are as defined in the World ID Protocol.

3.1 Terminology

This spec introduces the following explicit terminology:

  1. Signing Key: This is an EdDSA over BabyJubJub keypair which authenticators use to sign operations off-chain related to proof generation. The signatures from this key are used in ZK circuits (e.g. Query Circuit or WIP-103 Proof of Ownership). Previously this may have been referred to as off-chain signer.
  2. Management Key: An ECDSA over secp256k1 keypair (curve used by World Chain) used to sign operations on-chain that change the state of a World ID in the WorldIDRegistry. The public key is represented as an Ethereum address. Previously this may have been referred to as on-chain signer.
  3. Management Operations: Any operation which results in a state change to a user’s World ID in the WorldIDRegistry. Examples: inserting an authenticator, removing an authenticator, initiating a Recovery Agent update.

3.2 Authenticator Classes

A distinction is introduced between two classes of Authenticators:

  1. Proving Authenticator: Holds only a Signing Key and is capable of proof generation and presentation. A Proving Authenticator SHALL NOT perform any management operations on the World ID, i.e. it cannot perform any state changes on the WorldIDRegistry for the user. A Proving Authenticator has no entry in _authenticatorAddressToPackedAccountData.
  2. Admin Authenticator: Holds both an Signing Key and a Management Key. An Admin Authenticator is capable of all operations for a user’s World ID, including management operations and proof generation.

Prior to the introduction of this spec, all registered authenticators MUST be considered Admin Authenticators.

3.3 Bitmap Encoding

The WorldIDRegistry stores a 96-bit pubkey bitmap per account in _leafIndexToRecoveryAddressPacked. This spec splits the bitmap into two halves:

  • Bits [0-47]: Occupancy. Bit n is set if pubkeyId n is in use.
  • Bits [48-95]: Authenticator Class. Bit 48 + n is set if pubkeyId n is a Proving Authenticator.

An occupied slot with its class bit clear is an Admin Authenticator. An occupied slot with its class bit set is a Proving Authenticator. The state (occupancy=0, class=1) is unused and MUST NOT occur; an unoccupied slot MUST have both bits clear.

As a consequence of this encoding, the effective hard limit on authenticators per account is reduced from 96 to 48. This limit MUST be exposed as a separate constant, MAX_AUTHENTICATORS_V2_HARD_LIMIT, and the registry MUST reject setMaxAuthenticators calls with a value greater than it.

3.4 insertAuthenticator

The insertAuthenticator function MUST accept address(0) as the newAuthenticatorAddress parameter. When address(0) is provided:

  1. The occupancy bit for the given pubkeyId MUST be set.
  2. The class bit MUST be set, marking the slot as a Proving Authenticator.
  3. No entry SHALL be written to _authenticatorAddressToPackedAccountData.
  4. Address validation (_validateNewAuthenticatorAddress) MUST be skipped.

When a non-zero address is provided, the function behaves as in V1 (occupancy bit set, class bit clear, address mapping written).

The operation MUST be authorized by an existing Admin Authenticator (no changes).

3.5 removeAuthenticator

The removeAuthenticator function MUST use the bitmap class bit to determine the removal path:

  1. If the class bit is set (Proving Authenticator), the caller MUST pass address(0) as authenticatorAddress. No address mapping validation or cleanup is performed. Both the occupancy and class bits MUST be cleared.
  2. If the class bit is clear (Admin Authenticator), the caller MUST pass the correct non-zero authenticatorAddress. Full V1 validation applies: the address mapping is checked for leaf index, pubkeyId, and recovery counter consistency, then deleted. Both the occupancy and class bits MUST be cleared.

If an incorrect authenticatorAddress is passed for the authenticator class being removed (non-zero for a Proving Authenticator, or zero for an Admin Authenticator) the call MUST revert with AuthenticatorClassMismatch.

The operation MUST be authorized by an existing Admin Authenticator (no changes).

3.6 updateAuthenticator

The updateAuthenticator function is deprecated in this version. Calls MUST revert with MethodUnsupported. Key rotation can be accomplished with a removeAuthenticator followed by insertAuthenticator.

3.7 Account Creation

Account creation (_registerAccount) is unaffected. _registerAccount rejects address(0), so every new account starts with at least one Admin Authenticator.

3.8 Manageability Invariant

An Admin Authenticator MUST NOT be removed if it is the only Admin Authenticator remaining on the account. Such a call MUST revert with UnmanageableNotAllowed. This guarantees that an account always retains at least one Admin Authenticator capable of managing it.

4. Rationale

Introducing two classes of authenticators allows users to have more control over the permissions they assign to different authenticators. This follows common security practices of least privilege.

4.1 Split bitmap over separate storage

The authenticator class could be stored in a separate mapping (e.g. mapping(uint64 => uint256)), but this would add a new cold SSTORE (20k gas) per account on first use. The split-bitmap approach reuses the existing 96-bit bitmap with no additional storage cost. The trade-off is halving the maximum authenticator count from 96 to 48, which is acceptable given practical account sizes.

4.2 updateAuthenticator disabled

Supporting all type of transitions in a single function adds significant surface area. The same outcomes are achievable via removeAuthenticator + insertAuthenticator. Furthermore, these operations are expected to seldom occur.

4.3 Authorization model

Proving Authenticators cannot sign management operations because they have no entry in _authenticatorAddressToPackedAccountData, which is required by _recoverAccountDataFromSignature. This is enforced structurally rather than with an explicit permission check, and the structural check covers every call site that resolves a signer through _recoverAccountDataFromSignature (e.g. insertAuthenticator, removeAuthenticator, initiateRecoveryAgentUpdate, cancelRecoveryAgentUpdate).

5. Security

  1. Proving Authenticators cannot escalate privileges. The lack of an _authenticatorAddressToPackedAccountData entry means _recoverAccountDataFromSignature will always revert for a Proving Authenticator’s address. There is no code path through which a Proving Authenticator can authorize a management operation.
  2. Class enforcement on removal. The bitmap class bit determines the required removal path. A caller cannot use address(0) to remove an Admin Authenticator (which would leave its mapping stale) or a non-zero address to remove a Proving Authenticator.
  3. Bitmap backward compatibility. V1 accounts have all type bits at zero, correctly classifying existing authenticators as Admin. This holds because _maxAuthenticators was never set above 48 in V1. The setMaxAuthenticators override enforces this new hard limit going forward.
  4. Account creation unchanged. The _registerAccount function retains its V1 check that rejects address(0), ensuring every new account starts with at least one Admin Authenticator.

6. Backwards Compatibility

  • All existing authenticators are classified as Admin Authenticators (class bit defaults to 0). No migration is required.
  • The maximum authenticator count per account is reduced from 96 to 48. Accounts with authenticators at pubkeyId >= 48 are incompatible.
  • updateAuthenticator is disabled. Callers relying on this function MUST switch to removeAuthenticator + insertAuthenticator.

7. Alternatives Considered

With the introduction of this spec, we also considered completely decoupling Signing Keys from Management Keys, which means that each key is treated independently and there is no explicit concept of an Authenticator encoded in the WorldIDRegistry. This was eventually dismissed. Implementing such a system requires one of two options.

A general note applies to both options: practical accounts are expected to hold a small number of authenticators (the V1 default for _maxAuthenticators is 7 and has never been raised), so the 48-slot cap imposed by the chosen encoding is not a binding constraint. While at this time the use of Management-only keys does not have an application it is quite likely the the future direction is for Management Keys to exist on alternative constructs (examples: passkeys, zkLogin alternatives, etc). These constructs could provide recovery alternatives to users. Not pursued with this spec because at this time there are off-protocol mechanisms (e.g. authenticator-managed backups) which address most of the same user pain points.

Option 1: New storage layout. This would truly reflect the separation between each key, but changing the storage layout requires the introduction of at least a new mapping (to store the separate Management Keys) which would cost at least 20,000 additional gas per account on first use, plus a migration path or lazy-init logic for V1 accounts, both of which expand the surface area. The runtime gain (decoupled lifecycles) does not justify these costs given the manageability invariant already binds at least one Management Key to each account.

Option 2: Re-structured bitmap. This entails reusing the same 96-bit bitmap but claiming the unused (occupancy=0, class=1) state to mean a Management-only Authenticator (a slot with a Management Key but no Signing Key). The main concrete benefit is that inserting or removing a Management Key would not require updating the Merkle tree, but this operation is rarely expected to occur. In exchange, the bitmap encoding becomes a four-state enum (instead of a flag on an occupied slot) and removeAuthenticator must distinguish three classes. The added complexity is not justified.

WIP-105: Authenticator Message Format

1. Abstract

This spec defines a CBOR wire format for World ID authenticators to exchange requests, responses and notifications. The method field MUST use underscore-separated camelCase segments prefixed with worldid. Other WIPs define the methods and their payloads.

It also defines worldid:// deeplinks, which SHOULD follow a namespace, version and action structure. The details of individual deeplinks are defined by the protocols that use them.

2. Motivation

World ID supports authenticators from different providers and on different platforms. A shared message and deeplink format lets them communicate over different transports.

3. Specification

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

3.1 Message format

3.1.1 Encoding

Messages MUST be encoded using CBOR (RFC 8949). Each transport message MUST contain exactly one CBOR map: a request, response or notification. Receivers MUST reject trailing bytes and validate the whole message before executing the request, including the duplicate-key and resource checks below.

The transport defines message boundaries, routing, authentication and encryption.

Envelope field names are case-sensitive CBOR text strings. Binary payloads MUST use CBOR byte strings. Each method’s defining WIP specifies its parameter and result schemas.

Senders MUST NOT emit maps with duplicate keys. Receivers MUST reject a message in which any key they interpret, including envelope fields and fields of the method’s parameter or result schema, appears more than once in the same map. Receivers MAY accept duplicates of keys they ignore.

Each transport specification MUST set a maximum encoded message size and define what happens when it is exceeded. Implementations MUST limit nesting depth and resource use. Receivers MAY drop messages that exceed these limits or fail transport authentication without replying.

3.1.2 Requests and notifications

Either peer MAY send a request. For each request, the sender is the caller and the receiver is the responder.

A notification is a valid request without an id field. The responder MUST NOT reply to a valid notification, even if execution fails, the method is unknown or its arguments are invalid. A malformed request without an id is not a notification.

A request is a map with these fields:

FieldRequiredTypeMeaning
versionYesText stringMUST be "1.0", the envelope version defined by this WIP.
methodYesText stringMethod name following §3.2.
paramsNoAny CBOR valueArguments conforming to the method’s parameter schema.
idNoText stringID used to match the response to the request. Omit for notifications.

Request IDs MUST NOT be null. Callers MUST NOT reuse an ID while waiting for the response to that ID from the same peer in the same session.

For a valid request with an id, the responder MUST return one response with the same ID value.

Omitting params means no arguments were supplied. A present value, including null, MUST conform to the method’s parameter schema. Requests MUST NOT contain fields other than those in the table. Receivers MUST reject unknown envelope fields.

3.1.3 Responses

A response is a map with these fields:

FieldRequiredTypeMeaning
versionYesText stringMUST be "1.0".
idYesText string or nullThe request ID, or null for an uncorrelated error as defined in §3.1.4.
resultOn successAny CBOR valueThe method-defined result, including null when allowed by its schema.
errorOn failureMapFailure details as defined below.

A response MUST contain exactly one of result or error. A success always has a non-null ID. An error always includes its id field, even when null. A null error ID MUST NOT be matched to a pending request. Receivers MUST reject unknown response envelope fields.

The failure details map has these fields:

FieldRequiredTypeMeaning
codeYesText stringStable, case-sensitive failure code.
messageYesText stringShort human-readable explanation.
dataNoAny CBOR valueAdditional details defined by the method or error code. A present null value is distinct from omission.

Unknown fields in the error map MUST be ignored. Callers MUST match responses to requests by id, not arrival order. They MUST NOT reply to invalid or unmatched responses, or accept them as successful results. Implementations SHOULD report these as local protocol errors.

3.1.4 Errors

The following error codes are shared by all methods:

CodeMeaning
parse_errorThe message does not follow the CBOR encoding rules in §3.1.1.
invalid_requestThe request is malformed, or its envelope version is unsupported.
method_not_foundThe requested method is not available.
invalid_paramsThe arguments do not match the method’s parameter schema.
internal_errorThe responder could not complete the call because of an internal error.

Method-specific error codes MUST be defined by the method’s WIP and MUST NOT reuse the codes above. Callers MUST use code, not message, to identify an error.

Whether to reply to a parse error is transport-defined. If a parse error response is sent, it MUST use id: null. For an invalid request, the responder MUST copy its ID into id if it can read a single, unambiguous text string ID; otherwise it MUST use null. Error responses MUST use version: "1.0". Responders MUST NOT send errors in reply to notifications or responses.

3.1.5 Examples

These examples show CBOR diagnostic notation. h'0102ff' represents the three bytes 01 02 ff.

Request with an inline binary argument:

{
  "version": "1.0",
  "method": "worldid_example_v1_process",
  "params": {"payload": h'0102ff'},
  "id": "request-1"
}

Successful response with an inline binary result:

{"version": "1.0", "id": "request-1", "result": h'0304'}

Failure response:

{
  "version": "1.0",
  "id": "request-1",
  "error": {"code": "invalid_params", "message": "Unexpected payload length"}
}

Successful response with a nullable result:

{"version": "1.0", "id": "request-1", "result": null}

Uncorrelated parse error:

{"version": "1.0", "id": null, "error": {"code": "parse_error", "message": "bad"}}

Notification (no response, including on failure):

{"version": "1.0", "method": "worldid_example_v1_process", "params": {"payload": h'0102ff'}}

3.2 Methods

The method field MUST consist of camelCase segments joined by underscores _. The first segment MUST be worldid. For example worldid_auth_v1_register.

The method, params, result and error fields MUST be defined in a WIP. This spec does not introduce specific methods.

3.3 Deeplinks

Deeplinks MUST be URIs (RFC 3986) with the scheme worldid. They SHOULD have the form:

worldid://{namespace}/{version}/{action}?{parameters}

namespace is the protocol area, version is v followed by a positive integer, and action is the operation the deeplink starts. For example worldid://auth/v1/register.

Authenticators SHOULD register the worldid scheme with the operating system where the platform allows.

Deeplinks MUST be defined in a WIP. This spec does not introduce specific deeplinks.

4. Backwards Compatibility

This WIP defines a new message format and deeplink format. It does not modify existing protocol behavior, contracts or stored data, and implementations that do not exchange authenticator messages are unaffected. Existing worldid URIs that are not defined by a WIP are not affected.

WIP-106: Authenticator Assertions

1. Abstract

This spec introduces two tokens that attest the integrity of the environment in which a World ID Proof is generated. The Trust Anchor Key Token (TAKT) is a statement by an Authenticator Provider that a device-bound assertion_key belongs to a genuine Authenticator on a genuine device. The Authenticator Assertion Token (AAT) is signed by that assertion_key for a single request. Both are CBOR Web Tokens: the TAKT is signed with BabyJubJub-EdDSA-Poseidon2, so circuits verify it cheaply, and the AAT with ES256, which device hardware supports. They are verified in a privacy-preserving manner, so the Relying Party learns only the security properties it asked for, never the device key or the tokens themselves.

2. Motivation

Some use cases need information beyond the World ID Proof about where it was generated, typically when the Authenticator provides inputs the proof cannot verify itself (e.g. a live selfie compared in a ZK circuit). Relying Parties then need to know that a genuine Authenticator on a genuine device produced the proof.

3. Specification

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

  1. The definition of an Authenticator Provider is explicitly introduced into the Protocol. An Authenticator Provider is the publishing entity (e.g. a software company) of an Authenticator client.
  2. An Authenticator Provider MAY opt in to issuing TAKTs. A TAKT, and every AAT signed by the key it attests, is a statement only from the Authenticator Provider. Each Relying Party (RP) decides which Authenticator Providers and which security properties it accepts.
  3. The TAKT attests an assertion_key; the AAT is signed by that assertion_key. The two tokens are bound only by this shared key.
  4. The Field ($F$), the Curve (BabyJubJub), the hash function ($H_t$), the signature scheme (BabyJubJub-EdDSA-Poseidon2) and the PublicKey representation MUST follow WIP-100.
  5. TAKTs and AATs MUST only be verified in environments that provably guarantee privacy, as specified in Verification. Authenticators MUST NOT share TAKTs or AATs when this cannot be guaranteed.

3.2 Token Format

Both tokens are CBOR Web Tokens (RFC 8392): untagged COSE_Sign1 (RFC 9052) in deterministic CBOR (RFC 8949 §4.2.1).

  1. The payload MUST contain exactly the claims listed for the token, in deterministic CBOR key order, each with the value width given. Verifiers MUST reject any other encoding.
  2. Claims that carry a field element MUST encode a value less than the field order, as a 32-byte big-endian byte string. Verifiers MUST reject larger values rather than reduce them.

3.3 Trust Anchor Key

  1. An Authenticator Provider that issues TAKTs MUST have a trust_anchor_key, the key that signs its TAKTs. The trust_anchor_key MUST be a BabyJubJub-EdDSA-Poseidon2 key pair generated randomly.
  2. The trust_anchor_key is identified by its kid, which MUST be the compressed wire encoding of its public key as specified in WIP-100 §4.
  3. Circuits and RPs identify it by trust_anchor_key_hash = H_3(DS_KEY; x, y), over the affine coordinates of its public key.
  4. A trust_anchor_key MUST be published in the Authenticator Metadata, with not_before and not_after, before it signs its first TAKT. It SHOULD be published at least 24 hours before, so RPs with cached metadata recognize it.
  5. A trust_anchor_key MUST NOT sign TAKTs for more than 180 days (not_after - not_before <= 15552000). Authenticator Providers SHOULD rotate keys every 90 days.
  6. To rotate, an Authenticator Provider MUST publish the next key per item 4 before the current key’s not_after, and MUST keep the outgoing key published for at least MAX_TAKT_LIFETIME after its last TAKT.
  7. The trust_anchor_key private key SHOULD be generated and used only inside hardware-protected key storage (e.g. an HSM or a TEE), and SHOULD NOT be exportable.
  8. On suspected compromise, the Authenticator Provider MUST mark the key revoked immediately.

3.4 Trust Anchor Key Token (TAKT)

A TAKT attests that an assertion_key belongs to a genuine Authenticator on a genuine device, with the security properties in sec_flags.

  1. The protected header MUST contain exactly alg (label 1) with the value -65537 and the kid (label 4) of the trust_anchor_key, so the Authenticator knows which key signed the TAKT (e.g. during a key rotation). The unprotected header MUST be empty.
  2. The payload MUST contain the following claims:
ClaimKeyValue typeDescription
exp4uint, in $[2^{16}, 2^{32})$ (4 bytes)Expiration time, in seconds since the Unix epoch.
cnf8map {1: COSE_Key}The attested assertion_key (RFC 8747 §3.1), an EC2 P-256 COSE_Key (RFC 9053 §7.1): {1: 2, -1: 1, -2: x, -3: y}, with x and y as 32-byte byte strings.
eat_profile265tstr: EAT_PROFILE_TAKT
sec_flags-70000bstr, big-endian (8 bytes)Packed security attributes of the assertion_key (see Security Flags).

  1. The algorithm -65537 (Private Use) is allocated to BabyJubJub-EdDSA-Poseidon2 over a TAKT. It does not sign the Sig_structure bytes (RFC 9052 §4.4). Instead it decodes exp, cnf and sec_flags from the claims and signs

    message = H_8(DS_TAKT; exp, x_hi, x_lo, y_hi, y_lo, sec_flags)

    where x_hi and x_lo are the high and low 128 bits of the assertion_key’s x, read big-endian, and likewise for y.

  2. The signature field MUST carry the signature over message per WIP-100 §3.5, including its encoding. Generic COSE/CWT libraries can decode a TAKT but cannot verify it.

  3. The protected header is authenticated implicitly: alg is fixed by this specification and bound to the signature through DS_TAKT, and kid MUST equal the compressed wire encoding of the key the signature verifies under. Verifiers MUST reject a TAKT whose protected header differs from these values.

  4. An Authenticator Provider MUST NOT issue TAKTs with differing platform, sec_level or sec_meta for the same assertion_key. build_version MAY differ, so an updated Authenticator can renew its TAKT.

  5. A TAKT’s exp MUST NOT be later than the not_after of the trust_anchor_key that signs it.

3.5 Authenticator Assertion Token (AAT)

An AAT binds a single request to an assertion_key attested by a TAKT.

  1. The assertion_key is a P-256 key pair held by the Authenticator. It SHOULD be generated inside, and bound to, the device’s secure hardware (e.g. the Secure Enclave or StrongBox), so the private key is not exportable.
  2. The AAT MUST be signed with ES256 (RFC 9053 §2.1) over the Sig_structure of RFC 9052 §4.4, with an empty external_aad. The protected header MUST contain only alg (label 1) with the value -7. The unprotected header MUST be empty.
  3. The payload MUST contain the following claims:
ClaimKeyValue typeDescription
aud3bstr, big-endian (8 bytes)The rpId of the ProofRequest. This deviates from RFC 8392, which types aud as a string; verifiers MUST reject any other type.
exp4uint, in $[2^{16}, 2^{32})$ (4 bytes)Expiration time, in seconds since the Unix epoch.

eat_profile265tstr: EAT_PROFILE_AAT

  2. The Authenticator MUST set exp such that exp - now <= MAX_AAT_LIFETIME, and MUST sign a fresh AAT for every request.
  3. This spec does not define how the TAKT is conveyed together with the AAT (RFC 8747 §3.5). The binding depends only on the shared assertion_key.

3.7 Issuance

For every TAKT, the Authenticator Provider:

  1. MUST verify platform integrity evidence that commits to the assertion_key before signing (e.g. an App Attest assertion with clientDataHash = SHA-256 of the COSE_Key, or an Android Key Attestation certificate chain for the assertion_key itself).
  2. MUST set sec_flags according to that evidence, and MUST NOT set a sec_level the evidence does not support.
  3. MUST set exp such that exp - now <= MAX_TAKT_LIFETIME at issuance.
  4. MUST set build_version from the evidence where the platform attests it (e.g. Play Integrity versionCode), and otherwise from the Authenticator’s report.
  5. MUST NOT retain a link between a device identifier and an assertion_key beyond what abuse prevention requires.

The Authenticator SHOULD request a new TAKT after an update, so build_version stays current.

3.8 Verification

A verifier checks a TAKT and an AAT together, against the following inputs. The verifier MUST keep the Private inputs confidential and reveal only the Public inputs.

A verifier is acceptable only if the Authenticator can establish, before sending it a TAKT or an AAT, that the verifier enforces every check below and reveals only the Public values. This holds for:

  1. a zero-knowledge proof the Authenticator generates itself, with the Private values as private inputs, or
  2. a trusted execution environment (TEE) whose remote attestation the Authenticator verifies against a code measurement it trusts. The RP MUST authenticate the TEE’s results, e.g. through a signature by a key that attestation binds.

Every specification that consumes TAKTs and AATs MUST name its verifier and how the Authenticator authenticates it.

  2. TAKT signature. The TAKT’s signature over message verifies under trust_anchor_key per WIP-100 §3.5.1, and the TAKT’s kid is the compressed wire encoding of that key. H_3(DS_KEY; x, y) of that key MUST equal trust_anchor_key_hash.

  7. Authenticator meta. The AAT’s authenticator_meta has no reserved bits set, its user_presence is less than 5, and it equals the public input.
  8. Build version. build_version >= min_build_version. build_version MUST remain private.

4. Reference Verification

An RP accepts a proof that carries an Authenticator Assertion by performing the following validations on the Public values of Verification:

  1. trust_anchor_key_hash is the hash of a trust_anchor_key that belongs to an allowlisted Authenticator Provider, is active or retired (never revoked), and now is within its validity window.
  2. now is within 5 minutes of the RP’s local time. RPs MAY be stricter.
  3. aud is the RP’s own rpId, and nonce is one the RP issued, has not expired and has not been used before.
  4. platform, sec_level, sec_meta and authenticator_meta match values the RP allowlists.
  5. min_build_version is the RP’s own minimum.

5. Rationale

  1. Device-bound assertion key. The Authenticator signs each AAT on the device, so the Authenticator Provider does not need to be online for every proof and does not observe when proofs are generated.
  2. Two tokens bound by a key. The TAKT carries the expensive platform attestation once per assertion_key; the AAT is a cheap per-request signature. The cnf claim is the standard confirmation mechanism of RFC 8747.
  3. ES256 for the AAT, BabyJubJub for the TAKT. Secure hardware on iOS and Android supports P-256, so the device-held assertion_key signs with ES256. The Authenticator Provider can hold any key, so the TAKT uses a signature native to $F$ and a circuit verifies only one ES256 signature. That remaining SHA-256 and P-256 verification is still costly to prove on mobile devices today, so verifiers other than a zero-knowledge proof (Verification) remain the practical choice until proving systems close that gap.
  4. CWT for transport. The TAKT is carried as a CWT, but its signature is over message rather than the CBOR bytes, so circuits verify it without hashing CBOR with SHA-256.
  5. Key hash as public value. A single field element keeps circuits to one public input for the key. RPs compute it from the published x and y.
  6. Fixed-width encodings. Constant claim offsets let a verifier, including an in-circuit one, read the claims without a general CBOR parser.
  7. User presence signed by the Authenticator. Presence is checked per request, after the TAKT is issued, so only the assertion_key can sign it. The TAKT’s sec_level states how far the Authenticator’s integrity, and with it this claim, can be trusted.

6. Alternatives Considered

  1. A single provider-signed token per request. The Authenticator Provider verifies platform evidence and signs a token native to $F$ for every proof. Rejected: the Authenticator Provider must be online for every proof and observes every issuance.
  2. An ES256 trust_anchor_key. It could live in a standard HSM or KMS and verify with generic COSE libraries. Rejected: a circuit would need SHA-256 and non-native P-256 arithmetic a second time, roughly doubling the cost of verifying both tokens in a circuit.
  3. An assertion_key native to $F$. Rejected: platforms cannot hold such keys in secure hardware, so a device owner can extract the key and sign assertions from any environment.
  4. JWT for the TAKT. Rejected: one envelope format for both tokens keeps verifiers simple, and CBOR has fixed-width encodings JSON lacks.

7. Security

  1. Assertions are Authenticator Provider statements. The Protocol verifies only that a TAKT was signed by a trust_anchor_key and that the attested assertion_key signed the AAT. It does not and can not verify the claims. RPs MUST base their trust on the Authenticator Providers they allowlist.
  2. The assertion_key is a device pseudonym. It is stable for the lifetime of its TAKT. Revealing it, or the TAKT, would link all proofs of the device. Hence verification MUST keep both private.
  3. The TAKT is not covered by the AAT signature. It is authenticated by its own signature and bound to the AAT only through the cnf key. Authenticator Providers MUST NOT attest the same assertion_key with differing platform, sec_level or sec_meta, so a TAKT can not be swapped for one with other security properties.
  4. Trust anchor compromise. A leaked trust_anchor_key lets an attacker attest arbitrary keys with arbitrary sec_flags. Revocation is through the Authenticator Metadata and reaches every RP within its 24-hour refetch interval; TAKTs themselves are not revocable and rely on MAX_TAKT_LIFETIME.
  5. Assertion key compromise. An assertion_key extracted from a device signs AATs from any environment until its TAKT expires. sec_level states how well the key is protected.
  6. User presence. user_presence is only as trustworthy as the Authenticator that reports it. Use cases that need stronger guarantees SHOULD verify a signed statement from the check itself (e.g. a face verifier).
  7. Web environments. Browsers offer no hardware-backed remote attestation. A browser integrity verdict rests on signals the Authenticator Provider evaluates heuristically, so web Authenticators receive at most sec_level = 3, and sec_level = 10 without such a verdict.

WIP-107: Experimental Fees Per-Period

1. Abstract

This spec introduces a protocol fee that Relying Parties (RPs) pay in order to authorize proofs for specific World ID(s). Paid users (World ID holders) must provide a valid proof of the RP’s payment in order to present proofs to the RP in a given billing period. During a billing period, a paid World ID can perform any number of proofs.

Important

This spec is introduced as an experiment, and it applies only to select RPs and only to Proofs of Embedding Similarity (WIP-202). Other Proofs and other RPs keep their existing behavior. This spec is expected to be updated based on experimentation results, and may inform the billing mechanics introduced throughout the World ID Protocol. Accordingly, no organization or individual is making a commitment, promise, or obligation to develop, implement, or make available any feature, product, or functionality described in this spec, and there is no guarantee that they will ever exist or perform as described in the future.

2. Motivation

Fees are charged to RPs receiving proofs, not individual end users making proofs, because RPs can more easily estimate the value generated by World ID and compare it to the fees charged for using World ID. It also follows that RPs usually pay fees for services they use.

Monthly per-World ID billing lets an RP budget for distinct users without paying for each repeat proof. They make it easier for RPs to trade off per-monthly-user value against fees compared to per-proof fees. Repeated Embedding Similarity comparisons motivate this design. The World ID protocol is uniquely able to support such a fee mechanism because it exposes “unique human” as a protocol primitive.

3. High-Level Overview

This section introduces a non-normative high-level description of the billing mechanism.

  1. This spec is experimentally introduced. This means that it will apply only to a specific set of RPs and only to Embedding Similarity Proofs. The administrator selects these RPs through an allowlist in the Billing Contract. This is likely to be extended in the future with a spec update.
  2. An RP must pay for fees during a billing period in order to request proofs from a user.
  3. Each calendar month is valid from 00:00:00 UTC+14:00 on its first day until 00:00:00 Anywhere on Earth (AoE, UTC−12:00) on the next month’s first day. Periods overlap by 26 hours.
  4. Billing is done through a smart contract (the “Billing Contract”).
  5. Registration capacity is priced in USD and purchased with WLD.
  6. Capacity is purchased for one RP and one billing period. Each unit permits one distinct World ID to register. A capacity of 2 means that the RP can receive proofs from two distinct World IDs during that period.
  7. When an RP requests a proof from a user (see ProofRequest), the RP signs the request with its own action, whose first byte marks the request as a billed proof. The same signature also authorizes usage of a capacity of at most one.
  8. A user generates a Uniqueness Proof for the billing action corresponding to the current period using their Proof of Human (PoH) Credential. The billing action is derived from the RP and the period; the RP does not directly sign it. This proof results in a special type of nullifier denominated the billingNullifier, which is submitted once to the Billing Contract with the RP’s authorization to claim capacity. The Authenticator caches the nullifier and its private OPRF output for the billing period.
  9. Billing for Proofs of Embedding Similarity is enforced by TEE Verifiers (WIP-201) where a valid proof of payment (through a billingNullifier) must be presented. If a proof is not presented, the Verifier rejects the request. The Verifier signs the checked billingNullifier into the Flamingo Token, and the Embedding Similarity circuit (WIP-202) proves that it belongs to the World ID making the proof.
  10. An RP may purchase or top up registration capacity for the current AoE month and the next calendar month. Current-month purchases are prorated by seconds left in the AoE month. Future months are paid in full. Capacity cannot move between RPs or periods.
  11. Unused capacity receives no rebate and does not roll over.
  12. Users do not pay for fees; only RPs (or an entity acting on an RP’s behalf) pay.
  13. Fees are set per World ID and period in the Billing Contract. An administrator may update the USD fee amount on-chain. Payments settle in WLD; earlier purchases remain unchanged. An oracle price is used to convert between USD and WLD.

4.3 Billing Context

Every RP uses the same AoE calendar months. periodStart is 00:00:00 AoE on the month’s first day (12:00:00 UTC). periodEnd is 00:00:00 AoE on the next month’s first day and is exclusive. The active interval is [periodStart - PERIOD_OVERLAP, periodEnd), clipped at Unix timestamp zero. Months overlap by PERIOD_OVERLAP (§4.1). Either active context MUST be accepted. Capacity, registrations and billing actions remain separate for each period. Nonces are consumed per RP across periods.

A periodStart is canonical if and only if it equals getBillingPeriod(periodStart).periodStart, i.e. it is 00:00:00 AoE on a month’s first day. The Billing Contract and billing verifiers MUST reject a noncanonical periodStart. getBillingPeriod returns the AoE month containing timestamp and its exclusive end; months beginning before Unix timestamp zero MUST be rejected. Clients MUST use the selected context’s active interval for registration and proof acceptance. getActivePeriods(timestamp) returns the periodStart of the month containing timestamp and, while timestamp is within PERIOD_OVERLAP of the next month’s start, that next periodStart (otherwise zero); the Contract’s registration check uses the same rule. Purchases and top-ups remain limited to the purchase window in §4.2; the overlap does not permit purchases after periodEnd. Any future configurable-period extension MUST expose its boundaries on-chain and preserve already purchased periods.

4.5 RP Authorization

The RP’s normal ProofRequest authorizes registration. The RP signs nothing extra, keeps its own action, and does not need to know whether the user is registered. An Authenticator without a cached registration for the active context (§4.6) registers with that request before proving.

The request’s action is the RP’s own action, and its most significant byte MUST be BILLED_ACTION_PREFIX (§4.1). Only Proof of Embedding Similarity requests carry such an action (WIP-202 §4.3). The RP signature does not cover the proof type, so the prefix is what marks a request as one that may consume capacity. The RP signs the RP signature message with that action as usual: version || nonce || createdAt || expiresAt || signedAction, 81 bytes. This is the packed message, not the SHA-256 value returned by ProofRequest::digest_hash. A request without an action cannot authorize registration.

To reiterate from the original specs, it is strongly RECOMMENDED that RPs always generate fresh private keys from a cryptographically-secure randomness source for signing keys and store it in secure environments (e.g. HSMs). If an RP registers a signing key that someone else possesses, or a smart contract that someone else controls, that party can consume capacity on the RP’s behalf.

The registration proof always uses billingAction (§4.3) as the action for the OPRF Query and subsequently the nullifier computation. A valid RP signature over signedAction authorizes exactly two actions for the same rpId: a proof for the signedAction itself (which is processed out of the scope of this spec), and billing authorization for the current active billing context. It MUST NOT authorize any other action. Billing authorization requires signedAction to carry BILLED_ACTION_PREFIX; a signature over any other action, e.g. a Uniqueness Proof’s (most significant byte 0x00), MUST NOT authorize registration.

RegistrationAuthorization copies the request’s version, nonce, timestamps, OPRF key ID, action (as signedAction), signature and WIP-101 data. The request’s rp_id and oprf_key_id MUST match scope.rpId and the context’s pinned key (§4.4.2). The Contract MUST reject a version it does not support.

  • Contract: register MUST reject a signedAction whose most significant byte is not BILLED_ACTION_PREFIX. It MUST verify the authorization as OPRF nodes verify RP requests, with signedAction as the action, and MUST verify the proof with billingAction as the action. A registered signer without code is verified by EIP-191 recovery, and wip101Data MUST be empty. A signer with code MUST support IWIP101 through ERC-165 and is verified through WIP-101 verifyRpRequest with signedAction, with wip101Data of at most 1024 bytes.
  • OPRF nodes: Nodes MUST accept a billing query: an OPRF query whose action is billingAction, carrying scope and the RP’s signedAction as signature verification data, as session create-and-bind queries carry the uniqueness action. Nodes MUST verify the RP signature over signedAction, and MUST recompute billingAction from scope and check that scope.chainId and scope.billingContract match their configuration, scope.rpId matches the request, and scope.periodStart is canonical and active (§4.3). Billing queries MUST use a dedicated nonce scope, so one RP request authorizes at most one application query and one billing query. Nodes MUST reject a billing query for any action other than the recomputed billingAction, or whose signedAction does not carry BILLED_ACTION_PREFIX. They MUST accept such a signedAction as signature verification data on session-seed queries, so that a Proof of Embedding Similarity can re-derive its session.
  • Freshness: The Contract MUST check freshness as OPRF nodes do, with now the block timestamp: now < expiresAt, |now - createdAt| <= maxRequestAge and expiresAt - createdAt <= maxRequestLifetime. Accepting a createdAt up to maxRequestAge in the future tolerates RP clock skew; with a strict createdAt <= now, an RP whose clock runs ahead would get requests the nodes accept and the Contract rejects. The uint64 limits MUST agree with the OPRF nodes: maxRequestAge with their createdAt tolerance in both directions, and maxRequestLifetime with their maximum expiresAt - createdAt.

Unsigned request fields MUST NOT be treated as RP-authenticated.

4.6 Authenticator Cache

The Authenticator MUST:

  • Cache the billing nullifier, billingAction and the unblinded OPRF output of the billing query by account, BillingContext, and the RP’s OPRF key ID and OPRF public key. The Proof of Embedding Similarity needs no other OPRF witness (§4.7).
  • Keep OPRF witnesses, credential witnesses and query authorization inputs private. Together with the public billingNullifier, the cached OPRF output reveals the account’s leaf index to a search over leaf indices.
  • Decide whether to register from isBilledRp. A Verifier rejecting a request with billing_nullifier_required (§4.7) means that read was stale; re-read it, register with the same RP request and retry (WIP-201 §4.6).
  • Choose the context for a request in this order: a cached registration for any active context (§4.3); otherwise the next period, if it is active and getPeriodCapacity shows capacity left; otherwise the current period. During the overlap, a registration under the next period covers the rest of the overlap and the whole next period with one unit of capacity. An Authenticator that lost its cache cannot tell whether it is registered for the current period, and each RP request authorizes only one billing query (§4.5). So during the overlap it may register under the next period while already registered for the current one. That uses one unit of the next period’s capacity early, a unit the World ID needs anyway if it returns in that period.
  • After registering, wait until the registration is included in a block before sending the Verifier request (§4.8).
  • On billing_unregistered (§4.7), retry with backoff while the RP request has not expired (WIP-201 §4.6). The registration may not have reached the Verifier yet. If attempts keep failing, drop the entry, e.g. after a reorganization (§6), and register again with a later RP request.
  • Refresh account membership, RP authorization and credential verification inputs before generating a new registration proof.
  • Expire entries at period end.
  • Recover lost entries, including after switching Authenticators, through a fresh authorized query for the same World ID and BillingContext under the same pinned key. The nullifier MUST remain unchanged. An existing registration remains valid and recovery MUST NOT consume more capacity.
  • Not apply single-use nullifier replay protection to billingNullifier within its BillingContext, so that retries after a failed register and recovery remain possible. Before exempting a nullifier, the Authenticator MUST recompute billingAction for a trusted Billing Contract and a canonical, active periodStart.

Without a cached registration for the active context, the Authenticator makes a billing query for billingAction from the same RP request, in addition to any query the RP’s own proof needs. A Proof of Embedding Similarity needs one only to re-derive a session.

The TEE Verifier MUST use the billing state of the Billing Contract it is configured with, on its configured chain (CHAIN_ID in production, §4.1). The sealed request names neither, and the Verifier MUST NOT take chain targets from it. Before the Engine call, it MUST look up aud, the RP’s rpId (WIP-201), in its billing state (§4.8), and then:

  • RP not billed. Sign billing_nullifier = 0, whatever the request carries.

When it rejects a request for billing, the error of its Failed response (WIP-201 §4.4.1) MUST be one of these, so Authenticators can react (§4.6):

billing_nullifier_requiredThe RP is billed and the request carries billing_nullifier = 0.
billing_unregisteredThe RP is billed and the billing state holds no registration of billing_nullifier for aud in an active context. The Verifier did not run the Engine, so the Authenticator MAY retry (WIP-201 §4.6).

The Verifier does not verify the RP’s signature. Capacity is consumed only by register, which does (§4.5), and the RP checks its own nonce when it verifies the proof (WIP-201 §4.7).

The Verifier never sees the Proof of Embedding Similarity, which is produced after the Flamingo Token and verified by the RP. The RP is the billed party, so billing MUST NOT depend on any check the RP performs. Instead, the Proof of Embedding Similarity (WIP-202 constraint 7) MUST prove that a nonzero billing_nullifier belongs to the World ID it proves, for the RP aud. With billingAction and the cached OPRF output R (§4.6) as private inputs, it constrains

billing_nullifier = H_4(DS_NULLIFIER; H_4(DS_QUERY; leaf_index, rp_id, billingAction), R.x, R.y)

with rp_id the request’s aud, DS_QUERY and DS_NULLIFIER as in WIP-100 §3.8, and with the same leaf_index as its Merkle inclusion proof. This is the UniquenessNullifier of §4.3. The registration proof already verified R under the pinned key (§4.4), and only registered nullifiers reach the Flamingo Token, so the circuit does not verify the OPRF evaluation again and takes no billing public inputs. The cached output does not depend on a Merkle root, so the proof uses its own fresh root and WIP-202 Root Freshness is unchanged.

4.8 Billing State

The TEE Verifier keeps its own billing state and checks requests against it. Its host reads the Billing Contract and keeps that state up to date; the Verifier makes no chain reads.

The host MUST:

  • Read the Contract’s BilledRpUpdated logs from its deployment, and its Registered logs from the start of the earliest active context’s interval (§4.3), at the provider’s latest block, not at finality (§6).
  • Supply every change to the Verifier in block order as soon as it reads it, and the removal of every change a reorganization drops.

TEE Verifiers MUST:

  • Hold the billed RPs and the registrations of active contexts, each billingNullifier with its rpId and periodStart. Bound the registrations they hold, and expire each at its period’s end.
  • Report not ready, and serve no request, until the host has supplied the state up to the block at which it started reading.
  • Use the Verifier’s time (WIP-201 §4.4.2) as now for the active period (§4.3). Block timestamps MUST NOT serve as the Verifier’s time.
  • Fail closed when the bound is reached: reject every request, including for RPs that are not billed, since the state may be missing registrations.

Host read failures MUST NOT fail process liveness. While they last, the Verifier keeps the state it has: an RP billed in the meantime stays unbilled, and the kill switch takes effect once the host catches up. Operators SHOULD alert on how far the host’s state trails the chain. Hosts SHOULD combine a log subscription with polling from the last block they supplied, so a dropped subscription delays changes but never loses them.

4.9 Fees

Fees are configured in USD per World ID per period and paid in WLD. Each unit of registration capacity permits one distinct World ID to register.

The RP approves the Billing Contract’s WLD allowance, then calls purchaseCapacity. The contract transfers WLD from the payer to the designated protocol fee address and adds capacity atomically (§4.2). Approval alone does not pay the fee.

For example, a purchase with 10 days left in a 30-day AoE month costs 10/30, about 33.33% of the full-month price. duration is the AoE month’s own length: 28, 29, 30 or 31 days.

Charges are in WLD base units. The contract MUST use checked USD totals and full-precision conversion.

The price source MUST be an on-chain adapter for the Chainlink WLD/USD Data Stream. A report submitter obtains a signed report and submits it to the adapter. The adapter MUST verify it through the configured Chainlink verifier, require the configured feed ID, and normalize its price to USD scaled by 10^18. It MUST expose only verified usdPerWld and observedAt values to the Billing Contract. Unverified reports MUST NOT update the stored rate.

quotePurchase and purchaseCapacity read that verified rate; a getter alone does not obtain or authenticate a report. The charge MUST NOT exceed the payer’s maxWldAmount. Zero, future-dated, stale or unavailable prices MUST reject the purchase without affecting existing capacity. The feed ID, verifier, adapter, report format, source scale and maxPriceAge MUST be selected and tested before release (§8).

Unused capacity receives no refund and does not roll over. Top-ups and later parameter changes MUST NOT alter earlier purchases.

Warning

OPRF key rotation is not currently supported. A rotation that replaces an RP’s pinned key before period end invalidates that period’s billingNullifiers without refund, and the Contract rejects every registration for that period until it ends.

5. Rationale

  • Billing nullifier: Counts one World ID across credentials without publishing its account leaf index.
  • Cached OPRF output: Avoids repeated billing OPRF queries. With billingAction, it is all the Proof of Embedding Similarity needs.
  • Nullifier in the Flamingo Token: The RP is the billed party, so the nullifier the Verifier checked reaches the proof through the Verifier’s signature, not through the RP. It stays private in the proof, which keeps proofs unlinkable within a period.
  • No OPRF verification in the Embedding Similarity circuit: Registration already verified the OPRF output. A preimage of the registered nullifier binds it to the World ID and RP at a fraction of the cost (WIP-202 §5).
  • Allowlist in the Billing Contract: Authenticators and Verifiers use the same state, and changing it needs no new enclave measurement.
  • Latest block instead of finality: On World Chain, the finalized block trails the latest by about 15–20 minutes, longer than an RP request lives. Any confirmation depth would add its latency to every user’s first proof for an RP in a period, while a reorganization of unfinalized blocks remains possible at any depth (§6).
  • No RP signature in the Verifier: Billing depends only on registrations, and register already verifies the RP’s signature. Checking it again in the Verifier would add fields to the sealed request, a registry read and a freshness check, for no billing guarantee.
  • No bound on the state’s age: The host is trusted for billing state and could withhold updates whatever the Verifier checks, so a bound on their age would only catch a broken host, at the cost of rejecting every request during a provider outage. Detecting a stalled host is left to the operator’s monitoring (§4.8).
  • Failing closed at the bound: A full state may be missing the registration a request needs, so the Verifier rejects every request instead of treating an RP as not billed. Every RP is expected to be billed eventually.
  • Host-supplied billing state: Reading the chain inside the enclave needs a TLS client, certificate roots and network egress in the measured image. The host already relays all of the Verifier’s traffic, so it supplies the state instead. That trusts it for billing, whose cost falls on the fee recipient (§6). No request triggers a read, so no provider learns when a nullifier is used.
  • Checking before the Engine: The host supplies the billing state and is not trusted with privacy. A check after the Engine would let it flip the outcome of a run by adding or withholding a registration mid-run, learning when the Engine finished, and force retries that rerun the Engine on the same capture. Checked before, a billing rejection depends only on the billing state and runs no Engine. An Authenticator that registered right before its request, whose registration has not reached the Verifier yet, retries with a new request for the same RP request; the Verifier keeps no retry state.
  • Registration capacity: One unit covers one distinct World ID for one RP and period, matching the RP’s monthly user budget.
  • Overlapping months: Capacity covers the calendar month in every time zone. Preferring the next period for registrations during the overlap means a user first seen there who returns next month uses one unit of capacity, not two.
  • Prorating: An RP that starts or tops up mid-month pays only for the time left in the AoE month.
  • No rebate or rollover: Keeps each month’s capacity and revenue independent and avoids refund or carry-forward accounting.
  • Reusing the RP request: The RP cannot know whether a user is already registered, so its normal request must be enough to register.
  • Derived billing action: Deriving billingAction instead of having the RP sign it keeps the RP’s action free for its own proof. Proofs of Embedding Similarity do not use the RP’s action, but Uniqueness Proofs do, so this keeps billing extensible to other proof types.
  • Reserved action prefix: The RP signature does not cover the proof type. Without the prefix, a Uniqueness Proof request would also authorize registration, and a modified Authenticator could spend a billed RP’s capacity on users who never made a Proof of Embedding Similarity. A prefix in the signed action marks the request type at no extra signing cost. OPRF nodes already reject Uniqueness queries whose action is not 0x00-prefixed, so an embedding request cannot authorize a Uniqueness Proof either.

6. Security

An RP request is bearer authorization until bound to a holder. Consuming the nonce limits registrations but does not bind authorization to the intended holder.

Any RP-signed request whose action carries BILLED_ACTION_PREFIX can authorize one registration in an active context of that RP, once per nonce. It yields only the billingNullifier in addition to the nullifier for the signed action. OPRF nodes and the Contract MUST treat the recomputed billingAction as the only additional action a signature authorizes; accepting any other derived action would let a signature over one action yield nullifiers for actions the RP never approved.

The registration and the application proof share the RP’s nonce, which is public in register calldata. An observer who also sees the application proof’s nonce can link the application proof to the billingNullifier.

A paid-state lookup alone does not prove that the prover owns the registered World ID. The Verifier signs the checked nullifier into the Flamingo Token, and the Embedding Similarity circuit binds it to the prover (§4.7). This holds against a modified Authenticator, which can neither obtain a Flamingo Token for a billed RP without a registered nullifier nor prove with one that is not its own.

It does not hold against an RP that colludes with the user’s Authenticator. Together they can verify the Flamingo Token outside the circuit and skip WIP-202 constraint 7, or use a Verifier measurement that skips billing. WIP-201 places this collusion out of scope, and so does this experiment, although its cost falls on the fee recipient rather than on the RP.

Hosts read registrations at the latest block rather than at finality (§4.8). Blocks not yet posted to L1 can still be reorganized, e.g. on a sequencer failover or a batcher failure. The chance of such a reorganization is low, and this experiment accepts it. If a registration is reorganized out after a Verifier admitted it, Flamingo Tokens were issued without consumed capacity. The host supplies the removal and the Verifier drops the registration (§4.8), so this is limited to requests admitted before the reorganization. The sequencer usually re-includes the transaction; if it then fails, e.g. on exhausted capacity, the Verifier rejects the next request and the Authenticator registers again (§4.6).

The host is trusted for billing state (§4.8). An operator that drops a BilledRpUpdated log enabling an RP keeps that RP free, and one that supplies a registration the Contract never recorded lets that World ID skip registration. Either way the cost falls on the fee recipient: the host still sees only ciphertext, and the Proof of Embedding Similarity still binds the nullifier to the prover, so users’ privacy and RPs’ integrity are unaffected. A host that cannot read the chain has the same effect until it catches up, without anyone acting maliciously. Removing this trust requires the Verifier to verify the logs itself, e.g. over TLS to a provider or against the sequencer’s block signatures.

Registrations are linkable within their billing context. The Proof of Embedding Similarity keeps billing_nullifier private, so only the proof whose request registered is linkable to it, through the nonce. Implementations MUST NOT log credentials, private witnesses or sealed payloads.

7. Backwards Compatibility

This spec is additive. It adds the Billing Contract and a billing check for select RPs’ Proofs of Embedding Similarity. OPRF nodes gain a billing query mode and nonce scope (§4.5) and need the Billing Contract’s chain and address configured; existing queries are unchanged. The Flamingo Token gains a billing_nullifier claim under a new digest label (WIP-201), and the Proof of Embedding Similarity a constraint (WIP-202); Verifiers, Authenticators and RPs MUST upgrade together. Other proof types, RPs and contracts are unchanged.

The billing action encoding and pinned keys MUST remain fixed for active periods. Rollout, rollback and pauses MUST preserve purchased capacity and registrations.

8. Experimental Release

Before enablement:

  • Select RPs, deployment addresses, the proxy administrator, designated protocol fee address, initial USD price and request limits. Select the Chainlink feed, verifier, adapter, report format, scale and price-age limit (§4.9).
  • The contract and OPRF nodes MUST adopt the billing authorization of §4.5. OPRF nodes supporting billing queries MUST be deployed before enablement. WIP-202 requests MUST carry an action, including with a session_id (WIP-202 §4.3), and Verifiers MUST sign the Flamingo Token’s billing_nullifier claim (§4.7).
  • Add each selected RP through setBilledRp only once it has capacity for the active period; until then, its users’ proofs fail. Calling setBilledRp(rpId, false) is the kill switch: Verifiers stop billing the RP as soon as the host supplies the change, which waits for the host to read the chain.
  • WIP-101 contract-backed RPs are excluded until OPRF nodes support signature verification data for them.

The proxy owner updates pricePerWorldID and other billing settings through the authorized on-chain setters. Changing the price does not require a node software release and MUST preserve earlier purchases.

TEE operators deploy compatible verifier images. Authenticators and RPs approve the accepted attestation measurements and keys under WIP-201. The Engine Provider signs engine releases; the RP’s engine policy decides which releases to accept. Operators MUST NOT treat an unsigned or unapproved release as accepted.

OPRF operators deploy compatible node software and keep pinned period keys available through period end. Clients verify OPRF proofs against the registry-authorized public keys, including the pinned key for an active billing context. Before enablement, record the operators, policy owners and contract upgrade owner and agree on compatible versions and key retention.

9. Rejected Alternatives

  • Per-proof charging: Rejected for this experiment because it charges repeated comparisons and makes monthly costs less predictable. Any future per-proof scheme requires a separate proposal defining pre-purchase and expiry rules.
  • Credential-specific registration: Charges one World ID more than once across credentials or renewals.
  • Off-chain-only billing: Rejected for this experiment because capacity and registration would depend on a billing operator.
  • RP signs billingAction directly: Works only when the RP’s action is unused, as in Proofs of Embedding Similarity. It prevents billing Uniqueness Proofs, which need the RP’s own action, and makes RPs compute a period-dependent action for every request.
  • Arbitrary registration action: The billing unit would become one World ID per action, so a changing or random action would bill per proof. It would also publish the RP’s application nullifier on-chain and make it linkable across periods.

WIP-109: Authenticator Registration

1. Motivation

World ID 4.0 supports multiple authenticators per account. Registering a new authenticator requires an existing Admin Authenticator (WIP-104) to authorize an InsertAuthenticator operation on WorldIDRegistry, and the new authenticator needs the account’s leaf_index, its assigned pubkey_id, and the user’s credentials to generate proofs. This requires:

  1. An interoperable, end-to-end encrypted channel between two authenticators across devices and providers.
  2. Explicit, informed user approval on the Approving Authenticator.
  3. Out-of-band authentication via a short pairing code typed into the Approving Authenticator, so possession of the Pairing URI alone cannot authorize a request or forge a response.

2. Summary

  1. The Requesting Authenticator generates a random pairing_secret, a 6-letter pairing_code, and an ephemeral X-Wing response_pubkey keypair. It signs a commitment (registration_digest) to its keys, encrypts a WIP-105 worldid_auth_v1_register request under a key derived from pairing_secret and pairing_code, publishes the ciphertext to the message-bridge, and displays a worldid://auth/v1/register Pairing URI (as a QR code or deeplink).
  2. The Approving Authenticator opens the Pairing URI, fetches the single-use encrypted request from the bridge, and prompts the user to enter pairing_code (which the Requesting Authenticator reveals once the bridge reports the request was retrieved).
  3. Using pairing_code, the Approving Authenticator decrypts and validates the request, checks the account state, and asks the user for explicit approval (showing which credentials will be transferred).
  4. Upon approval, the Approving Authenticator submits InsertAuthenticator on WorldIDRegistry (unless the key is already registered as requested), waits for finality, and returns the assigned (leaf_index, pubkey_id) and optional vault and attachments sealed to response_pubkey and authenticated under the transport key.
  5. The Requesting Authenticator decrypts and unseals the response, verifies on-chain that its key is registered at (leaf_index, pubkey_id), imports the vault, and handles each attachment by its kind.

3. Specification

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

Authenticator roles and keys follow WIP-104. Messages MUST conform to WIP-105.

3.1 Terminology

  • Requesting Authenticator: The new authenticator to be registered.
  • Approving Authenticator: An existing Admin Authenticator registered on the user’s World ID.
  • Bridge: An untrusted message-bridge deployment that relays encrypted requests and responses.
  • Pairing Secret: 32 random bytes generated per attempt by the Requesting Authenticator and carried in the Pairing URI.
  • Pairing Code: A 6-letter random code generated per attempt by the Requesting Authenticator, displayed after the bridge reports retrieved, and manually entered into the Approving Authenticator.

3.3 Pairing Secret, Pairing Code and Derived Values

For each registration attempt, the Requesting Authenticator MUST generate a fresh 32-byte pairing_secret, pairing_code, and response_pubkey keypair using a CSPRNG. The pairing_code MUST be sampled uniformly from six-letter uppercase ASCII strings (A–Z) and revealed only after the bridge status becomes retrieved.

HKDF denotes HKDF-SHA256 (RFC 5869) with an empty salt and 32-byte output. Argon2id (RFC 9106) uses version 0x13, memory m = 65536 KiB (64 MiB), iterations t = 3, parallelism p = 4, empty secret and associated data, and a 32-byte output:

request_id       = HKDF(pairing_secret, info = "WORLD-ID/WIP-109/REQUESTID")
code_key         = Argon2id(password = pairing_secret || ASCII(pairing_code), salt = request_id,
                            m = 65536, t = 3, p = 4, version = 0x13, output_length = 32)
transport_secret = HKDF(pairing_secret || code_key, info = "WORLD-ID/WIP-109/TRANSPORTSECRET")

Here request_id is 32 bytes (encoded as lowercase_hex(request_id) in bridge URLs and message id fields), and password is the 32-byte pairing_secret concatenated with the 6-byte ASCII pairing_code (38 bytes).

3.3.1 Registration Digest

The Requesting Authenticator commits to the registration parameters in the Pairing URI over a fixed-width binary layout:

registration_digest = SHA-256(
    "WORLD-ID/WIP-109/REGISTER"     // ASCII
 || request_id                      // 32 bytes
 || new_authenticator_pubkey        // 32 bytes, WIP-100 §4 wire encoding
 || new_authenticator_address       // 20 bytes; 20 zero bytes for a Proving Authenticator
 || response_pubkey                 // 1216 bytes, X-Wing encapsulation key
)

All fields except name (an unauthenticated display label), supported_issuer_schema_ids, supported_attachment_kinds, and registration_sig are covered.

3.3.2 Registration Signature

The Requesting Authenticator proves possession of new_authenticator_pubkey by hashing registration_digest into a field element and signing it with EdDSA (WIP-100 §3.5):

d_hi, d_lo       = registration_digest[0..16], registration_digest[16..32]    // big-endian integers
m                = H_3(ds("WORLD-ID/WIP-109/REGSIG"); d_hi, d_lo)             // WIP-100 §3.3.2
registration_sig = EdDSA-Sign(signing_key, m)                                 // 64 bytes, WIP-100 §3.5.2

3.5 Transport

Requests and responses are exchanged through the message-bridge under lowercase_hex(request_id) (§3.3) and follow the bridge’s session lifetime.

  • Outer encryption: Both directions use AES-256-GCM under transport_secret with a fresh random 12-byte nonce (iv, standard padded base64) and ciphertext with its 16-byte tag (payload, standard padded base64). A nonce MUST NOT be reused under the same key.
  • Request: Apply outer encryption to the CBOR-encoded request with AAD ASCII("WORLD-ID/WIP-109/REQUEST") || request_id.
  • Response: First seal the CBOR-encoded response (success or error) to response_pubkey using WIP-100 §3.9 with info = "WORLD-ID/WIP-109/RESPONSE". Then apply outer encryption to the sealed bytes with AAD ASCII("WORLD-ID/WIP-109/RESPONSE") || request_id.

The encoded CBOR plaintext MUST NOT exceed 4 KiB for a request and 15 MiB + 4 KiB for a response (covering vault, attachments, and envelope overhead). Receivers MUST enforce corresponding size bounds before decryption and MUST authenticate the outer AES-GCM envelope before parsing a request or unsealing a response.

Note

transport_secret authenticates both directions because unauthenticated HPKE base mode allows anyone holding response_pubkey to seal a message. The inner WIP-100 §3.9 layer provides post-quantum confidentiality for the vault even if the pairing secret and code are later compromised.

3.7 Approving Authenticator Procedure

  1. Fetch and decrypt:
    • Parse the Pairing URI (§3.4), derive request_id (§3.3), and fetch GET /request/:request_id before prompting for pairing_code (this single-use read sets the bridge status to retrieved).
    • Prompt the user for pairing_code, derive code_key and transport_secret (§3.3), and decrypt the request (§3.5). Because GET /request/:request_id is single-use, the Approving Authenticator MUST retain the ciphertext locally if it allows retrying a mistyped code, and SHOULD limit the number of attempts.
    • Validate the CBOR request (id == lowercase_hex(request_id), method == "worldid_auth_v1_register", and §3.6.1 schema), verify that the recomputed registration_digest matches d from the URI, and verify registration_sig against new_authenticator_pubkey. On failure, send an error response (if a valid response_pubkey is available) or abort locally.
  2. Check account state:
    • Refresh account state and verify that the Approving Authenticator is an Admin Authenticator of the account; otherwise respond not_authorized.
    • Already registered: If new_authenticator_pubkey is already registered on the account, verify that the slot’s class and (for an Admin Authenticator) management address match the request; otherwise respond authenticator_conflict. User approval (step 3) is still required, after which step 4 skips InsertAuthenticator and returns the existing leaf_index and pubkey_id.
    • Otherwise, if new_authenticator_address is already registered, respond authenticator_conflict.
    • Otherwise, select the lowest free pubkey_id below getMaxAuthenticators(); if none is free, respond max_authenticators_reached.
  3. Approve:
    • Show an explicit consent screen displaying the requested class (Proving vs Admin), the untrusted name (if present), a warning only to approve trusted authenticators, and which credentials will be transferred (noting if they or their attachments contain biometric data and that without them the new authenticator cannot generate proofs for existing credentials). The consent screen SHOULD also show which attachments are included. The Approving Authenticator MAY let the user change which credentials are transferred.
    • If the request includes supported_issuer_schema_ids, the Approving Authenticator SHOULD NOT transfer credentials whose issuer schema ID is not listed. If supported_issuer_schema_ids is absent, the Approving Authenticator MAY transfer all credentials.
    • The Approving Authenticator MUST NOT send an attachment whose kind is not listed in supported_attachment_kinds, and sends no attachments when supported_attachment_kinds is absent. Attachments tied to a credential are sent only when that credential is transferred.
    • If no credentials are transferred, omit vault and any attachments tied to a credential.
    • The Approving Authenticator SHOULD require local user verification (e.g. device biometric or PIN) before signing InsertAuthenticator or exporting the vault and attachments. If the user declines, respond user_rejected.
  4. Submit and respond:
    • Unless already registered, sign and submit InsertAuthenticator (passing the zero address for a Proving Authenticator per WIP-104) and wait for finality. Do not submit another insertion while one is in flight. If the operation definitively fails, respond operation_failed (or authenticator_conflict on an address conflict); if the outcome is not known in time, respond outcome_unknown.
    • Seal and encrypt the response (§3.5), and send it via PUT /response/:request_id.

3.8 Requesting Authenticator Procedure

  1. Reuse the same authenticator key(s) and class across retries of the same registration so a retry after a lost response hits the already-registered case (§3.7 step 2) instead of inserting a second slot.
  2. Encrypt the request (§3.5) and publish it via POST /request before showing the Pairing URI.
  3. Display the Pairing URI and poll GET /response/:request_id:
    • While initialized, keep the Pairing URI visible.
    • Once retrieved, replace the Pairing URI with pairing_code and instructions to enter it only on the intended Approving Authenticator.
    • Once completed, proceed to step 4.
  4. Authenticate and decrypt the outer response, unseal the inner HPKE payload (§3.5), and validate the CBOR response (id == lowercase_hex(request_id) and §3.6 schema).
  5. On result, verify against on-chain/indexer state that new_authenticator_pubkey is registered at (leaf_index, pubkey_id) with the requested class and management address before completing registration or importing vault, and validate imported credentials against the account before use. Handling of attachments is implementation-specific. If the response contains an attachment whose kind was not listed in its supported_attachment_kinds, the Requesting Authenticator SHOULD ignore that attachment. On error, surface the error (and offer a retry on outcome_unknown).

Both authenticators MUST discard pairing_secret, pairing_code, derived keys, and the ephemeral response private key when the attempt ends, and MUST NOT log or send the Pairing URI or pairing_code to analytics or link-preview services.

4. Rationale

  • Message-bridge transport: Reuses the existing off-chain relay without contract changes or new endpoints, keyed by a single request_id derived from pairing_secret to keep the QR code compact.
  • Out-of-band pairing code with Argon2id: Entering pairing_code after the request is fetched binds the session to the user’s intended device. Argon2id (salted with request_id and keyed with pairing_secret) raises the cost of offline guessing without allowing precomputation.
  • Dual-layer response encryption: The outer AES-GCM layer under transport_secret authenticates both success and error responses, while the inner WIP-100 §3.9 X-Wing seal provides forward and post-quantum confidentiality for the credential vault.
  • Attachment kinds: Keeps auxiliary data (such as biometric or authenticator-specific data) out of the vault format, so each kind is defined and versioned on its own, and authenticators without support for a kind still import the credential.
  • Declared capabilities: supported_issuer_schema_ids and supported_attachment_kinds let the Approving Authenticator avoid sending credentials and attachments the Requesting Authenticator cannot use.

5. Security

  • Untrusted bridge and URI interception: The bridge sees metadata (request_id, sizes, timing, IPs) and can drop messages or spoof retrieved, and any QR scanner or worldid:// handler can read the Pairing URI. Without pairing_code, an interceptor cannot decrypt the request or forge a valid response, though it can consume the single-use request or response slot and force a retry.
  • Offline code guessing: The 6-letter pairing_code has 26^6 (~28 bits of entropy) possibilities. Argon2id slows offline brute-force against captured ciphertexts, and the inner X-Wing seal keeps vault confidential even if transport_secret is eventually recovered.
  • Phishing and malicious handlers: A user tricked into scanning an attacker’s URI and entering the attacker’s code will be prompted to register the attacker’s key, and a malicious app intercepting worldid:// could spoof the code-entry screen. Explicit consent and verifying the target app remain essential.
  • Attachments and declared capabilities: attachments receive the same two-layer confidentiality as vault. Requesting Authenticators MUST treat all attachment data as untrusted input. supported_issuer_schema_ids and supported_attachment_kinds are self-reported and are not an authorization boundary.

6. Backwards Compatibility

This WIP requires no changes to existing bridge endpoints or contracts. Proving Authenticator registration requires WorldIDRegistryV2 (WIP-104). Authenticators that do not implement this WIP are unaffected.

WIP-113: Uniqueness Identifiers

1. Abstract

This spec lets Authenticators disclose a nullifier more than once, but only to Relying Parties (RPs) that the Authenticator Provider whitelists. A whitelisted RP can then use the nullifier as a uniqueness identifier: a stable per-user account key that both enforces one account per user and recognizes a returning user, for example to authenticate them, from a single Uniqueness Proof.

2. Motivation

RPs that need to use World ID for authentication require a stable per-user identifier that every Authenticator can reproduce without client state. The nullifier already is one: it is deterministic in (leaf_index, rp_id, action) and bound to the user by the Uniqueness Proof. Authenticators refuse to disclose it twice, so today an RP can’t use it to log a user in again. They refuse because a nullifier disclosed repeatedly becomes a pseudonymous identifier that links all of a user’s proofs to the same RP, which is dangerous for standard RPs.

The protocol doesn’t enforce one-time use. Contracts don’t store nullifiers and OPRF Nodes don’t track them. Each Authenticator keeps a local replay guard, which other Authenticators of the same World ID don’t share. Users therefore already trust their Authenticator Provider to keep nullifiers one-time use. That trust can also cover a small set of RPs the provider lets reuse them.

3. Specification

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

3.1 Proof Request

The ProofRequest and ProofResponse formats are unchanged. A whitelisted RP requests a reusable nullifier with a standard uniqueness request.

3.2 RP Whitelist

  1. Authenticators MUST only disclose a nullifier more than once to RPs that are explicitly whitelisted by the Authenticator Provider. The distribution of this whitelist is out of scope and up to the Authenticator Provider. It could e.g. be distributed as part of an app release.
  2. Authenticators MUST be transparent about the members of the whitelist and SHOULD allow users to remove RPs from the whitelist they do not trust.
  3. Authenticators MUST NOT let users add RPs to the whitelist without a warning that the RP will be able to recognize them.
  4. When handling a request from a whitelisted RP, Authenticators MUST show a distinct UI that tells the user the RP can recognize them. They MUST NOT present the proof as anonymous.

3.3 Authenticator Flow

  1. The Authenticator runs the nullifier query for every request. It MUST NOT reuse a cached OPRF output unless it verifies the RP signature and request expiry itself, because otherwise only OPRF Nodes check them (see §5).
  2. If the RP is not whitelisted, the Authenticator MUST refuse a nullifier it already disclosed.
  3. If the RP is whitelisted, the Authenticator skips the replay guard check and builds the proof.
  4. The Authenticator SHOULD record the nullifier in the replay guard for whitelisted RPs too, so that removing an RP from the whitelist makes its nullifiers one-time use again.

3.4 RP Guidance

  1. Uniqueness identifier. A whitelisted RP MAY use the nullifier as a uniqueness identifier, i.e. as the key of the user’s account. The value and the nullifier field are unchanged; the term only names this use.
  2. Registration and authentication. The RP sends a uniqueness request with a fixed action. If the uniqueness identifier is unknown, it creates an account under it. If it is known, it logs the user into that account. One request covers both cases.
  3. Nonce. The RP MUST check that the proof’s nonce is the one it issued for this login and MUST NOT accept a nonce twice. Otherwise a captured proof logs in anyone who replays it.
  4. Action choice. The RP SHOULD keep one fixed action per purpose. Changing the action gives every user a new uniqueness identifier.
  5. Non-whitelisted Authenticators. An RP MUST NOT assume every Authenticator whitelists it. A user whose Authenticator doesn’t whitelist the RP can register but can’t log in again with a Uniqueness Proof.

4. Rationale

  1. Reuse the nullifier instead of a new identifier. The nullifier is already deterministic across Authenticators and bound to the user by the circuit. The id_commitment of a seeded session isn’t proven to derive from the seed, so it needs a Uniqueness Proof next to it for sybil resistance. A reusable nullifier gives both in one proof.
  2. One request, one round trip. Seeded sessions need a uniqueness request to register and a session request to authenticate, and bound uniqueness proofs add a proof type to merge them. Here the RP always sends the same uniqueness request.
  3. No wire format change. RPs, OPRF Nodes, contracts and circuits stay unchanged. Only Authenticators change their replay guard.
  4. Naming. A nullifier is the value a verifier records to void a one-time right. That still describes its use for duplicate checks, but not for authentication, where nothing is voided. This spec keeps the nullifier field and names the authentication use “uniqueness identifier”. Renaming the field would touch circuits, contracts, SDKs and RP integrations, and would suggest two different values.

5. Security

  1. Tracking within an RP. A uniqueness identifier is a stable per-RP identifier. All Uniqueness Proofs a user gives a whitelisted RP for one action are linkable. This is why §3.2 requires a whitelist and a distinct UI. Nullifiers for different RPs stay unlinkable.
  2. The whitelist is enforced by Authenticators only. It protects users from RPs. A modified Authenticator that ignores it only exposes its own user.
  3. Proof replay. A proof works as a login credential for a whitelisted RP. The RP’s nonce check (§3.4) is what stops replays.
  4. OPRF key rotation for an RP changes all of its nullifiers, and users lose access to their accounts.
  5. Forged requests. The nonce is not bound to the OPRF output, so a cached output yields a valid proof for any request. Without the RP signature check, a party impersonating a whitelisted RP would learn the user’s uniqueness identifier for that RP. Logging in still needs a nonce issued by the RP (§3.4).

6. Backwards Compatibility

The change is additive. Authenticators that don’t implement this spec refuse the second request as a replay. RPs, OPRF Nodes, contracts and circuits need no changes. The World ID 4.0 spec statement that Authenticators never disclose a nullifier more than once becomes: except to whitelisted RPs.

WIP-201: Flamingo Verifier

Note

This spec outlines a draft functionality for beta testing. Changes are expected.

1. Abstract

This spec defines the Flamingo Verifier (Verifier), a trusted execution environment (TEE) service. It runs one sandboxed biometric Engine release, provided by an Engine Provider. An Engine is a program of biometric models, e.g. presentation attack detection and face matching, that takes a request’s entries and returns pass or fail; its code and weights can stay private. A release has one or more pipelines, each identified by its pipeline_id, and its release manifest describes them all. Consuming protocols define a pipeline type, an EIP-712-inspired string that names the input roles and their counts, and what a pass of such a pipeline means. The Verifier checks every request against the type. Each input has a role from the type, and its entry is opaque bytes that only the Engine parses. A type can let a role take a variable number of inputs, e.g. frames for a custom liveness check. If the Engine passes, the Verifier signs a Flamingo Token over the type’s hash, the Engine configuration, and the SHA-256 hash of each entry whose role the type marks with #. Consuming protocols use these hashes to bind entries to other data, e.g. that the reference image the Engine compared is the one committed in a Credential. The Authenticator can also provide a WIP-106 Trust Anchor Key Token (TAKT) and Authenticator Assertion Token (AAT) committing to the engine request, which are verified by the Verifier. If the RP is billed, the Authenticator also provides a WIP-107 billing nullifier, which is verified against the on-chain billing state. The public WIP-106 values and the billing nullifier are then also included in the Flamingo Token. Consuming protocols such as WIP-202 use the token to prove the result to a Relying Party (RP), optionally without revealing any entry.

2. Motivation

Many Proof-of-Human applications, like deepfake prevention or human presence verification, need biometric checks on images, e.g. presentation attack detection (PAD), liveness or face matching. They also need to bind the result to other data, e.g. that the face on a stream matches the thumbnail in a user’s Credential.

Running these models on the user’s device is private but not trustworthy: a jailbroken device can report checks it never ran. Fraud detection also relies on obscurity, so its models and weights cannot be published.

This WIP runs the models in an attested TEE instead. The TEE’s attestation shows users that the Operator cannot access biometric data, and its signature shows RPs that the checks ran. The Verifier image is open source and reproducibly built, so anyone can check that its measurement matches the source and that no raw media or embeddings leave the TEE. The closed Engine runs inside a kernel-enforced sandbox with no network or storage access. The Verifier attests which Engine release it runs, and the RP accepts only the Engine configurations it allowlists, from releases the Engine Provider signed.

What a pipeline checks differs per use case, so this WIP does not define it. A consuming protocol defines a pipeline type, and the token binds which type ran. The token holds only hashes of entries, so a consuming protocol can prove the result to the RP without revealing any entry, e.g. with a zero-knowledge proof as in WIP-202.

4.3 Consuming protocols

A consuming protocol, e.g. WIP-202, builds on Flamingo Tokens. It defines the types that pipelines implement, what their results mean, and how an RP asks for a token or a proof over it. This spec defines the Verifier request and the checks every token must pass.

4.3.1 Types

A type string names a pipeline shape. Grammar, in ABNF (RFC 5234):

type   = name "<" levels ">" "(" member *("," member) ")"
name   = segment *("/" segment)
segment = 1*(%x41-5A / DIGIT / "-")
levels = "0" / %x31-39 *2DIGIT
member = role ["#"] ["?" / "*" / "+"]
role   = %x61-7A *(%x61-7A / DIGIT / "_")
  1. Form. A type string is ASCII, at most MAX_TYPE_BYTES long, with no whitespace. Its roles MUST be distinct.
  2. Name. A type’s name MUST be unique among consuming protocols and SHOULD follow the WIP-100 label convention with a version, WORLD-ID/WIP-<number>/FLAMINGO-TYPE/V<version>, e.g. WORLD-ID/WIP-202/FLAMINGO-TYPE/V1.
  3. Cardinality. A member without a suffix takes exactly one input. ? takes exactly one input whose entry a request MAY leave absent. * takes any number of inputs and + at least one; the pipeline fixes the number.
  4. Commitment. # marks a committed role: the Flamingo Token (4.6) carries the hash of its entry. Only a member without * or + MAY carry #, and a type has at most MAX_COMMITTED of them. The committed roles, in type order, are committed roles 0 to 3.
  5. Hash. pipeline_type = R(SHA-256(TYPE_DOMAIN || type string)), over the string’s bytes.

Example. EXAMPLE<2>(reference#,``live#,evidence*``) has three roles:

  • reference# and live#: exactly one input each, committed in entry_hash_0 and entry_hash_1.
  • evidence*: any number of inputs, fixed by the pipeline, with no hash in the token.
  • <2>: strictness levels 1 and 2.

entry_hash_2 and entry_hash_3 are 0. A pipeline of this type runs liveness and fraud checks on live and evidence, then matches live against reference at strictness. Appendix A2 uses this type in a full release.

4.3.2 Strictness

  1. Values. A strictness is a uint below 2^8. A type’s <n> fixes its strictness levels, with n at most 255. With n = 0 the type has none, and every request uses strictness 0. Otherwise its levels are 1 to n.
  2. Order. A higher level is at least as strict as a lower one. Generally, a higher strictness lowers the false acceptance rate and raises the false rejection rate, i.e. it favors security over UX.
  3. Meaning. The consuming protocol defines what each level means, e.g. how strictly faces must match or how strict a liveness check is, and how a request’s level is chosen (4.3.3).
  4. Use. A request picks one level its pipeline lists, and the Flamingo Token’s strictness claim says which level ran (4.6).

4.3.3 What a consuming protocol defines

A consuming protocol MUST:

  1. Types. Fix each of its type strings byte for byte, and say what each role is and what a Pass of a pipeline of that type means. A published type string MUST keep its meaning: a protocol that changes what a role, a Pass or a strictness level means MUST define a new type string, e.g. by incrementing its version (4.3.1).
  2. Strictness levels. Say what each strictness level of its types means, e.g. how strictly faces must match.
  3. Selection. Say how the strictness level is chosen, e.g. by the RP in its request.
  4. Nonce. Say how nonce is bound to the RP’s request.
  5. Delivery. Say how the RP obtains the Flamingo Token or a proof over it.
  6. Bindings. Say what each committed role’s entry_hash_k is bound to, e.g. a Credential claim or the RP’s challenge.
  7. Billing. Bind a nonzero WIP-107 billing_nullifier to the World ID the token is used for and to the RP aud, as WIP-107 §4.7 requires.
  8. Disclosure. Say which token values and entries the RP learns.
  9. Checks. Say, for each check of Consuming Flamingo Tokens, whether the RP or the protocol’s proof enforces it (4.8).

4.4 Engine

An Engine is developed and released by an Engine Provider. It is stateless: each request names a pipeline of its release, a strictness, and one entry per pipeline input. It returns only whether the pipeline passed. Each pipeline implements a type a consuming protocol defines (4.3). Each release is described by a signed manifest that lists its pipelines with their types, strictness levels, inputs and response slots.

  1. Conformance. A pipeline’s type MUST be a valid type string, every input’s role MUST be a member of it, and each member’s inputs MUST number as its cardinality says. Its strictness_levels MUST be levels of its type (4.3.2). Two inputs of a pipeline MUST NOT have the same role and label, so every input is named without its position.
  2. Strictness. For each strictness level a pipeline lists, the Engine Provider MUST document how the pipeline meets the meaning its type’s consuming protocol defines (4.3.2). Internal thresholds MAY vary, e.g. per input quality.
  3. Release hash. release_hash is the SHA-256 of the manifest’s JWS Payload (RFC 7515 §2). Re-signing a release keeps its release_hash.
  4. Signatures. RPs MUST verify a release manifest under an active release key of its iss before relying on it. The Verifier and Authenticators do not verify it.

4.4.4 Release Versioning

  1. version MUST be greater than the version of every earlier release of the same iss. Every change to the payload is a new release.
  2. A later release MUST NOT change a pipeline’s type or inputs; such a change uses a new pipeline_id. A later release MAY drop a pipeline, but MUST NOT reuse its pipeline_id.

4.4.5 Engine Provider Metadata

The Engine Provider MUST expose a JSON file over HTTPS at <iss>/.well-known/world-id-engine.json:

A reader MUST NOT follow redirects to another origin, and MUST ignore manifests whose iss is not the one it fetched the file for. The Verifier never fetches the metadata. RPs compute the engine_config_hash values they accept from it, and SHOULD refresh it at least every 24 hours.

4.4.6 Debug Report

An Engine response MAY carry a debug_report.

  1. Content. Opaque bytes the Engine Provider defines, e.g. which check failed, to help debug failures. It is not part of the Flamingo Token and has no protocol meaning. Engine Providers SHOULD keep it to what debugging needs, since it helps anyone probing the Engine (7).
  2. Size. The Verifier MUST NOT emit a debug_report larger than MAX_DEBUG_REPORT.
  3. Delivery. The Verifier MUST return it only in the sealed, padded response to the Authenticator (4.5.1), and MUST NOT expose it to the Engine Provider, the Operator or the Host.
  4. Forwarding. The Authenticator MAY forward it only to the Engine Provider, and only with the user’s explicit consent. It MUST offer the user a way to inspect it, but MAY forward it without an inspection.

4.5 Verifier

A Verifier is any implementation of this section built as an open-source, reproducibly built AWS Nitro enclave image. Each image has its own measurements (PCRs), and Authenticator Providers and RPs choose which implementations they trust by allowlisting them. A Verifier is run by an Operator on a Host. It runs one Engine release and serves requests from Authenticators. It checks each request against the pipeline it names, verifies the Authenticator Assertion, checks billing, passes the Engine request to the sandboxed Engine unchanged, and on a Pass signs a Flamingo Token. It releases each response only at fixed time slots.

The Authenticator encrypts the entire encoded map to the Verifier. payload is a byte string holding the deterministic CBOR encoding of the Engine request, so the Verifier checks the Authenticator Assertion against exactly the bytes it received and passes them on unchanged.

4.5.2 Attestation and Channel

  1. Keys. At boot, the Verifier MUST generate a channel key and a Flamingo Token signing key inside the enclave, from its hardware RNG, and MUST NOT export or persist either. It SHOULD replace its channel key frequently and accept the previous key for MAX_REQUEST_LIFETIME afterwards.
  2. Documents. The Verifier MUST attest each key in its own Nitro attestation document, a COSE_Sign1 chaining to the AWS Nitro Root G1. The channel attestation has public_key = SHA-256(CHANNEL_KEY_DOMAIN || channel_key) and user_data = the loaded release_hash; the signing_key_attestation has public_key = the token signing key. A document’s timestamp is its creation time, in milliseconds since the Unix epoch.
  3. Release manifest. The Verifier MUST send the release manifest (4.4.3) of the Engine release it loaded, as received, with the channel attestation.
  4. Response. The Verifier MUST seal the padded response to response_key.
  5. Refresh. The Verifier MUST re-attest both keys at least every MAX_ATTESTATION_AGE.
  6. Time. The Verifier MUST sync its clock to the timestamp of each new attestation, advance it on its monotonic clock in between, and MUST NOT move it backward. It MUST NOT use any other time source.

Channel Encoding. Both directions use the public-key encryption of WIP-100 §3.9. info is CHANNEL_DOMAIN || 0x00 for a request and CHANNEL_DOMAIN || 0x01 for a response. The first 1216 bytes of a request’s plaintext are response_key, a fresh X-Wing encapsulation key; the rest is the request. The Verifier MUST reject a request shorter than 1216 bytes or with an invalid response_key.

4.5.3 Request Processing

The Host MAY drop requests above a size limit it chooses. For each sealed request it relays, the Verifier, in order:

  1. Checks. After decrypting, it MUST reject a request that does not meet the Verifier request and Engine request formats, or whose pipeline_id, strictness or entries do not fit the loaded release as Request Processing item 1 of the Engine says, apart from media types.
  2. Expiry and replay. It MUST reject an expired or replayed request.
  3. Authenticator Assertion. If aat_inputs is present, every check of WIP-106 §3.8 MUST hold. The TAKT, the AAT, the assertion_key and build_version MUST NOT leave the Verifier.
  4. Billing. Before the Engine call, it MUST check billing_nullifier as WIP-107 §4.7 requires. It MUST NOT check billing again afterward.
  5. Engine call. It MUST pass the Engine request to the sandboxed Engine unchanged, and nothing else.
  6. Response. On Pass, it signs a Flamingo Token. It returns a Success or EngineError response, released at a response slot.

4.5.4 Response Timing and Replay

  1. Release. The Verifier MUST hold each response until the first of the pipeline’s response_slots at or after the Engine’s finish, measured on its monotonic clock from the request’s arrival, whatever the outcome. If the Engine has not finished by the last slot, the request fails and the Verifier MUST reset the Engine instance. Rejections before the Engine call MAY be released immediately.
  2. Choosing slots. Engine Providers SHOULD put the first slot at or above the pipeline’s fastest complete run and the last above its 99.9th-percentile run time.
  3. Expiry. The Verifier MUST reject a request whose expires_at has passed or is more than MAX_REQUEST_LIFETIME ahead of its time.
  4. Replay. The Verifier MUST reject a request whose (aud, nonce) it has already processed or is processing. It MUST keep each pair until the request’s expires_at has passed and MAY drop it after. While the set is full, it MUST reject every request.

4.5.5 Sandboxed Engine

  1. Loading. At start-up, the Verifier receives exactly one Engine bundle and its release manifest from the Host. It MUST check that the bundle hashes to the manifest’s engine_hash and that the manifest is well-formed, including Conformance, without verifying its signature, and MUST NOT fetch anything else.
  2. Sandbox. The Verifier MUST run the Engine with no network access, no writable persistent storage, no process creation, no access to the Verifier’s keys, nothing outside its bundle, and only one bounded request-response channel.
  3. Per request. Before each request, the Verifier MUST reset the Engine to a state no earlier request has influenced, without relying on the Engine’s cooperation. It MUST bound the Engine’s memory, and MUST return an error if the Engine exceeds it, crashes, or returns anything other than an Engine response.

4.5.6 Build and Measurement

  1. Publication. For each published Verifier measurement, an immutable reference to its source and its build instructions MUST be publicly available.
  2. Build. Building that source with the documented toolchain MUST produce a bit-identical Enclave Image File (EIF).
  3. Measurement. PCR0, PCR1 and PCR2 of that EIF are the Verifier’s measurement.
  4. Configuration. Everything that affects the Verifier’s behavior MUST be in the EIF. The Host supplies only the Engine bundle, its manifest, WIP-107 billing state updates and requests.

4.7 Authenticator

The Authenticator MUST accept only PCR0–2 values its Authenticator Provider ships with it, e.g. in the app release or as signed configuration. Before sending biometrics, it completes these steps in order, and MUST NOT send biometrics if one fails:

  1. Attestation. It MUST check that the channel attestation is a valid COSE_Sign1 whose chain leads to the AWS Nitro Root G1 and is valid now; does not have all-zero PCRs and has PCR0–2 it accepts; has public_key = SHA-256(CHANNEL_KEY_DOMAIN || channel_key) for the key it encrypts to; has user_data equal to the release_hash of the manifest the Verifier sent; and is at most MAX_ATTESTATION_AGE old. It MAY reuse a checked attestation while these hold.
  2. Configuration. It MUST choose a pipeline of the loaded release whose type is one its consuming protocol requires and whose inputs it can produce, as their labels describe, and a strictness the consuming protocol requires and the pipeline lists. Among qualifying pipelines, it follows the consuming protocol or, where it sets none, the Authenticator Provider’s policy. It fills entries in input order and leaves an entry absent only where the consuming protocol allows it. If no pipeline qualifies, it MAY use another Verifier instance.
  3. Response timing. It MUST NOT use a pipeline whose response_slots list more release times than its configured maximum. The maximum SHOULD be at most 8, so a response’s timing reveals at most 3 bits.
  4. Seal. It MUST seal response_key || request to channel_key, send it, and open the response with response_key.
  5. Retries. To retry, it MUST send a new request with a fresh nonce and response_key, and a new AAT. Authenticator Providers SHOULD rate-limit attempts.

4.8 Consuming Flamingo Tokens

A consuming protocol defines its types and how an RP requests and uses Flamingo Tokens. An RP MUST NOT accept a Flamingo Token, directly or through the protocol’s proof, unless every check below holds. A proof that hides the token MUST enforce checks 2, 3, 7 and 8; for the others it reveals the values they need or takes the RP’s accepted sets as public inputs.

  1. Attestation. The signing_key_attestation chains to the AWS Nitro Root G1, with every certificate valid at its timestamp; does not have all-zero PCRs and has PCR0–2 the RP accepts; attests verifier_key (kid is only a hint); and is at most MAX_ATTESTATION_AGE old.
  2. Signature. sig verifies under verifier_key per WIP-100 §3.5.1 over the signed digest computed from the values, with aat_flags = platform + 2^8 * sec_level + 2^16 * min_build_version + 2^48 * sec_meta + 2^52 * authenticator_meta.
  3. Well-formed values. has_aat is 0 or 1. The aat_flags sub-fields are range-checked to their widths, with the user_presence bits of authenticator_meta below 5. With has_aat = 0, trust_anchor_key_hash and the aat_flags sub-fields are 0.
  4. Request. aud is the RP’s own; nonce is bound, as the consuming protocol defines, to a request the RP issued that has not expired and has not been used before; and now is recent by the RP’s clock. The RP MUST accept at most one proof per request.
  5. Authenticator Assertion. With has_aat = 0, the RP accepts tokens without an AAT. Otherwise min_build_version, trust_anchor_key_hash and the aat_flags sub-fields pass WIP-106 §4.
  6. Engine. engine_config_hash is the hash of a release, pipeline_id and strictness the RP accepts, from an active manifest it verified under an active key of its iss, at or above the RP’s minimum version per iss.
  7. Type. pipeline_type is the hash of a type string the consuming protocol defines, and each entry_hash_k its statement depends on is bound to the protocol’s own inputs, e.g. a Credential claim or the RP’s challenge.
  8. Strictness. strictness is a level the consuming protocol accepts for this request, e.g. the level the RP requested.
  9. Billing. billing_nullifier is 0, or the consuming protocol binds it to the World ID the token is used for, as WIP-202 constraint 7 does.

5. Trust Assumptions

The protocol assumes the isolation, measurement and attestation of AWS Nitro Enclaves are sound. If they fail, neither privacy nor integrity holds. Every party below is trusted only for the listed parts.

6. Rationale

  1. Typed pipelines. What a pass means differs per use case, so the consuming protocol defines it and WIP-201 only fixes the shape. The release fixes each input’s role and processing, so a requester cannot relabel an entry.
  2. The type in the token. The consuming protocol checks pipeline_type against a constant, so a pipeline of another shape fails even if an RP’s allowlist names it by mistake, e.g. after a reused pipeline_id or a hand-copied hash.
  3. Explicit commitment. # makes the type string say what the token hashes. A single role without #, e.g. a depth map, stays possible.
  4. Roles and labels. A role is the protocol’s, so several Engines can serve one type; a label is the Engine’s, so it can tell inputs apart.
  5. Strictness levels in the type. Scores depend on the model and the pair and are biometric signals, so a request names a level whose meaning the consuming protocol defines. Putting n in the type lets the Verifier reject a release with levels the protocol does not define at load, as it does for roles. Levels 1 to n need no list.
  6. The strictness in the token. The protocol can check the level that ran against the one it expects, e.g. the RP’s request, instead of relying on the RP’s engine_config_hash allowlist alone.
  7. Only the RP checks manifest signatures. Who signed a release only matters for trusting its results, which the RP decides, so the Verifier image holds no Engine Provider keys.
  8. SHA-384 for the bundle. It matches how Nitro measures images; every other hash is SHA-256.
  9. Minimum versions. RPs accept a minimum version per iss, so new releases reach them without changes; a breaking change takes a new pipeline_id.
  10. The AAT in the Verifier, and optional. The Verifier keeps WIP-106’s private inputs and signs the public values; RPs decide whether they accept tokens without an AAT.
  11. Hashes over raw bytes. The RP and the Credential can compute the same SHA-256; embeddings only the Engine can compute.
  12. Signature over claim values. A circuit verifies the token without parsing CBOR.
  13. Verifier time. The Verifier checks the AAT at its own time and signs it, so an expired TAKT or AAT cannot pass.
  14. Engine configuration hash. One hash over the manifest’s JWS Payload, pipeline and strictness gives RPs exact control and keeps the values private.
  15. **Numeric engine **error codes. A uint16 keeps responses one size, gives Authenticators a stable code to act on, and keeps free text out of the response. The release’s errors map gives each code a message and shows reviewers every error an Engine can return.
  16. Debug reports only to the Authenticator. A report may describe the user’s biometrics, so only the user’s device receives it, and it reaches the Engine Provider only with the user’s consent.
  17. AWS Nitro. Nitro Enclaves have no persistent storage or external network, measure the whole image with reproducible PCRs, and sign attestations with a public root, which is what Authenticators and RPs need to check the Verifier.
  18. Two attestations. The channel key and the signing key are attested separately, so the channel key can be replaced frequently while the signing key, which RPs check tokens against, stays for the whole boot.
  19. Post-quantum channel. Biometrics don’t expire, so a recorded request must stay confidential even if it is decrypted years later. The channel therefore uses the X-Wing hybrid KEM.
  20. The Verifier fetches nothing. The Host supplies the bundle, the manifest and billing state, and the Verifier checks them. No network dependency enters the measured image, and its behavior follows from the measurement alone.
  21. Fixed-length responses. Every response is padded to the largest possible size, so the Host learns neither the outcome nor the report size from the ciphertext.
  22. Response slots. Random delays average out over repeated requests, and one fixed time makes every request wait for the worst case. A few slots per pipeline bound what timing reveals per request (7) while keeping fast pipelines fast.

7. Security

  1. Channel confidentiality. Requests and responses stay confidential while ML-KEM-768 or X25519 holds. It does not cover a compromised enclave.
  2. Missing AATs. Without an AAT anyone can submit arbitrary media, and the verdict becomes an oracle for tuning attacks; RPs that accept has_aat = 0 accept that risk.
  3. Pipelines that do not meet their type. The type fixes the shape, not what the Engine does. Only the Engine Provider and the release audit stand behind it, so RPs accept releases per iss and per pipeline.
  4. Unreviewed Engines. A Host may load any Engine; its tokens carry an engine_config_hash no RP accepts, and the sandbox keeps it from exporting data. A leaked release key works until it is revoked and RPs refresh.
  5. Closed Engine. The sandbox removes the Engine’s channels out, and the per-request reset keeps one request’s data from the next.
  6. Token privacy. A committed Credential hash and a nonzero billing_nullifier link a user to an RP request, so consuming protocols MUST keep tokens private, e.g. as private proof inputs.
  7. Verifier keys. The signing key never leaves the TEE; RPs stop accepting a compromised measurement, and MAX_ATTESTATION_AGE bounds its attestation.
  8. Timing. Slots limit each request to at most log2(n) bits for n slots, replay rejection keeps that bound per request, and any Engine failure becomes an error at a slot. Per-pipeline slots may reveal the pipeline.
  9. Stale measurements. An Authenticator accepts a compromised measurement until its provider removes it; signed, expiring configuration shortens that window.
  10. Engine as an oracle. Anyone can seal a request, so a modified Authenticator can query the Engine without bound. Operators SHOULD rate-limit at the Host, and Engine Providers SHOULD keep debug_report small.

8. Future Considerations

  1. Other TEEs, through attestation profiles for each provider’s document, root and measurement.
  2. Several Engines per Verifier. The Authenticator would choose among them, and RPs accept per engine_config_hash as today.
  3. Published measurements. A standard format for publishing Verifier PCRs with a status.
  4. Bounded Engine queries. A per-key attempt limit, keyed by the RP’s signed request or the AAT’s assertion key.
  5. Committed multi-valued roles. # on a * or + member, with an H_var commitment over that role’s entry hashes.
  6. Nested types. Grouping roles, e.g. a live capture and its evidence, as an EIP-712-style struct, once a second protocol needs it.

9. Alternatives Considered

  1. Running the models in a ZK circuit. Rejected: proving these models is still infeasible for most devices, and the prover would need the secret weights.
  2. MPC. Rejected: orders of magnitude slower, and it adds a non-collusion assumption.

WIP-202: Proof of Embedding Similarity

Note

This spec outlines a draft functionality for beta testing. Changes are expected.

1. Abstract

This spec introduces a ZK circuit (“Proof of Embedding Similarity”) which proves that a WIP-201 Flamingo Verifier matched a live capture and an optional challenge to the image committed in a user’s PoH Credential. The proof reveals no image, no Flamingo Token and no Credential.

The circuit neither extracts embeddings nor compares them. It verifies the Flamingo Token, binds its compared entries to the Credential image and, if present, the RP’s challenge, and checks the Issuer’s Credential and an Authenticator’s authorization of the result. For an RP billed under WIP-107, it also proves that the billing nullifier the Verifier checked belongs to the proving World ID. This first iteration supports only the PoH Credential; it shall be generalized to other Credentials in the future (Future Considerations).

2. Motivation

Deepfakes make it hard to know who is on the other side of a video call or behind an online interaction in general. An RP that can capture an image of that party, the challenge, wants to know whether the image stems from a verified real human.

A WIP-201 Flamingo Verifier can be used to compare a live capture and the challenge with the face image of a user with a valid Orb Credential, and run fraud detection models on the live capture images. Its Flamingo Token alone does not answer the RP’s question:

  1. No Credential. The Flamingo Verifier compares any images, so the token does not show the compared image is the one in an issued (Orb) Credential.
  2. No owner. It does not show that the user controls the World ID the Credential was issued to.
  3. Linkable. The Credential image’s hash is the same in every token of a user, so revealing tokens would link all their proofs.

This proof closes those gaps in zero knowledge. It binds the compared image to the Issuer’s PoH Credential and the RP’s challenge, and the result to a registered Authenticator. It reveals only values the RP sets or already knows, the Flamingo Verifier’s key and time, the Flamingo configuration and the AAT values. An optional session lets the RP check that a later proof comes from the same World ID.

The proof combines a WIP-201 Flamingo Verifier with checks in the circuit to show that:

  1. Liveness. A live capture passed the fraud checks of a Flamingo pipeline, e.g. presentation attack and deepfake detection.
  2. Match. The live capture matches the RP’s challenge image, if it sets one, e.g. a frame from a meeting stream, and the Orb thumbnail, the image captured at Orb sign-up that the PoH Credential commits to (Supported Credentials).
  3. Trusted Flamingo Verifier. An attested Flamingo Verifier, running an Engine configuration the RP accepts, signed the result for this RP’s request (rp_id, and a nonce bound to the RP’s).
  4. Credential ownership. The World ID creating the proof is registered, holds a valid PoH Credential from a trusted Issuer that commits to the thumbnail, and authorizes the result and the RP’s signal.
  5. Untampered Authenticator (optional). If the RP requires it, the live capture came from an untampered Authenticator, by the WIP-106 assertion the Flamingo Verifier checks.
  6. Session (optional). The proof concerns the World ID of a session the RP names (Session Proofs).
  7. Billing (optional). For an RP billed under WIP-107, the billing nullifier the Flamingo Verifier checked belongs to the proving World ID.

This lets an RP verify that the person it sees, e.g. on a video stream, is a verified human who was in front of the Authenticator when the proof was made. The optional session_id also lets it verify that the same human comes back across verifications.

  1. Request. The RP requests a proof with its nonce and an optional signal and session_id (Proof Request). It may add a challenge, an image it captured of the party it interacts with, e.g. a frame of a video call, as challenge_hash = R(SHA-256(challenge)), and set return_live_capture to receive the live capture.
  2. Session and Billing (if needed). If the RP named a session and the Authenticator has not cached its blinding, it re-derives it through the OPRF nodes. This can run in parallel with steps 3 and 4. If the RP bills and the Authenticator has no cached registration, it makes a billing query and registers its billing nullifier first, since the Flamingo request carries it (Proof Generation).
  3. Flamingo Verification (Liveness and Comparison). The user’s Authenticator sends the WIP-201 Flamingo Verifier one or more live captures as pipeline inputs, the face thumbnail from the user’s PCP and the optional challenge, with an Authenticator Assertion if it has one. The Flamingo Verifier’s Engine checks the live captures for liveness and fraud, e.g. deepfakes, and compares the first live capture with the thumbnail and, if present, the challenge (Flamingo Request and Entry Layout). After a failed capture or a billing rejection, the Authenticator can retry within the same RP request (Proof Generation).
  4. Flamingo Token. On a match, the Flamingo Verifier signs a Flamingo Token with the SHA-256 of each image and the Engine configuration that ran (Flamingo Request and Entry Layout).
  5. Proof. The Authenticator proves the statements above in zero knowledge (Proof Generation, Circuit Constraints).
  6. Verification. The RP verifies the proof and checks (Reference Verification):
    • its policy: the Flamingo Verifier’s attestation, the Engine configuration, the time and the AAT values;
    • its request: the challenge, the signal and, if it named one, the session;
    • the delivered live capture, if it requested one.

The RP learns that a live person who holds an Orb-verified World ID matches its challenge, if it set one, and, with a session_id, that it is the session’s World ID holder. It does not learn which World ID, and sees no Flamingo Token, Credential or image other than a live capture it requested.

4. Specification

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in this document are to be interpreted as described in RFC 2119.

4.1 Supported Credentials

This first iteration supports only the PoH Credential, comparing the PCP’s thumbnail.png:

  1. Personal Custody Package (PCP). At verification, the Orb packages the user’s images and stores them on the user’s device (World implements Personal Custody). The package includes hashes.json, which the Orb signs: a JSON object mapping each file name, e.g. thumbnail.png for the face thumbnail, to the lowercase hex SHA-256 of the file, plus a version. orb-core writes it as compact JSON (no insignificant whitespace) with sorted keys; constraint 3 relies on this format.
  2. PoH Credential. The PoH Credential commits in claim 0 to the Orb-signed hashes.json as $H_\text{var}$ with label CLAIMS_HASH_V1. This chain lets the circuit bind the compared image to the Issuer’s Credential without hashing the image.

4.4 Proof Generation

The Authenticator makes a proof for an RP’s request as follows. If a step fails, it MUST NOT send a proof. Step 1 MAY run in parallel with steps 2–5. Step 2 MUST complete before step 3.

  1. Session. If the request names a session_id, the Authenticator uses its cached session_id_r for the session’s oprf_seed. Without one, it re-derives session_id_r through the session-seed OPRF query, which carries action as RP signature verification data, and SHOULD cache it. Either way, session_id_r MUST open session_id for its leaf_index (constraint 5).
  2. Billing. If the RP is billed (WIP-107 Billing Contract), the Authenticator obtains its billing nullifier for rp_id as WIP-107 Authenticator Cache requires, from its cache or through a billing query and registration. Otherwise, billing_nullifier is 0.
  3. Flamingo request. It sends a Flamingo request built per Flamingo Request and Entry Layout.
  4. Retries. After a failed capture or a billing rejection (WIP-107 Billing Verification), it MAY send a new Flamingo request with a fresh nonce_salt within the same RP request (WIP-201 Authenticator item 5). It reacts to billing rejections as WIP-107 Authenticator Cache requires.
  5. Token check. It SHOULD check that the Flamingo Token’s claims match the Flamingo request it sent, so that a faulty Flamingo Verifier fails before proving.
  6. Authorization. It signs message = H_8(DS_WIP_202_AUTH; digest, flamingo_verifier_key.x, flamingo_verifier_key.y, signal_hash), with digest the Flamingo Token’s signed digest, using a key registered for its World ID (constraint 4).
  7. Circuit inputs. It builds the Circuit Inputs from the request, the Flamingo Token, its account, the PoH Credential, the signature of step 6, session_id_r from step 1, and billing_action and billing_oprf_output from its WIP-107 cache.
  8. Proof. It proves the Circuit Constraints and sends the proof to the RP. If return_live_capture is true, it sends with it the exact bytes of the compared live capture, pipeline_inputs[0], it gave the Flamingo Verifier for the token it proved with, and otherwise no image. The Credential image is never sent. The channel is outside this WIP.

4.6 Circuit Constraints

The circuit MUST enforce the following constraints. They hold jointly; the numbering only groups them. Every inequality (<, <=) is over integers range-checked to the stated width.

  1. Flamingo Token Verification

    1. Derive the token’s nonce.
      • flamingo_nonce = H_3(DS_WIP_202_NONCE; nonce, nonce_salt).
    2. Verify the token.
      • Enforce checks 2 (Signature) and 3 (Well-formed values) of WIP-201 Consuming Flamingo Tokens, with nonce = flamingo_nonce, compared_entry_hash_0 = R(credential_digest), compared_entry_hash_1 = live_capture_hash, compared_entry_hash_2 = challenge_hash, compared_entry_hash_3 = 0, compare_sources = 256 (bytes [0, 1, 0, 0]: only the live capture is a pipeline input) and min_build_version = 0, yielding its signed digest.

  2. Optional Challenge and Disclosure

    • challenge_hash is not constrained beyond item 1.2: 0 means the token compared no challenge (Entry Layout). The RP checks it against its request (Reference Verification item 5).
    • disclosed_live_capture_hash * (disclosed_live_capture_hash - live_capture_hash) == 0: the proof discloses the live capture’s hash, or 0.

  3. Credential Image Binding

    1. hashes.json is the Credential’s.
      • MIN_HASHES_JSON_BYTES <= hashes_json_len <= MAX_HASHES_JSON_BYTES, and the chunks beyond hashes_json_len are zero.
      • claims[CLAIM_INDEX] equals $H_\text{var}$ (WIP-100 §3.3.3) with label CLAIMS_HASH_V1 over the first hashes_json_len bytes. The capacity tag binds hashes_json_len, not MAX_HASHES_JSON_BYTES; the last chunk holds only the remaining bytes, and only the $\lceil$hashes_json_len/31$\rceil$ chunks are absorbed.
      • Only the chunks around digest_offset are split into bytes; other chunks with the same commitment would be a Poseidon2 collision.
    2. Extract the image digest.
      • 18 <= digest_offset and digest_offset + 64 < hashes_json_len.
      • The 64 bytes at digest_offset are lowercase hexadecimal digits, followed by ", all within the first hashes_json_len bytes.
      • The 17 bytes before digest_offset are "thumbnail.png":", and the byte before them is { or ,.
      • The digits decode as the 32-byte big-endian digest credential_digest.

  4. World ID Authentication

    • Compute message = H_8(DS_WIP_202_AUTH; digest, flamingo_verifier_key.x, flamingo_verifier_key.y, signal_hash), with digest from item 1.
    • Enforce WIP-100 World ID Authentication over message, yielding leaf_index.

  5. Session Commitment

    • Enforce WIP-100 Session Commitment. session_id = 0 means no session.

  6. Credential Verification

    • Enforce WIP-100 Credential Verification at now, yielding claims.
    • Range-check expires_at_min as 64-bit and constrain expires_at_min < cred_expires_at.

  7. Billing Nullifier Ownership

    • Compute billing_query = H_4(DS_QUERY; leaf_index, rp_id, billing_action).
    • billing_nullifier * (billing_nullifier - H_4(DS_NULLIFIER; billing_query, billing_oprf_output[0], billing_oprf_output[1])) == 0.
    • This makes billing optional: billing_nullifier = 0 means the RP is not billed, and any other value MUST be this World ID’s billing nullifier for rp_id. The Flamingo Verifier sets it (WIP-107 §4.7). With 0, billing_action and billing_oprf_output are unconstrained and SHOULD be 0.

Items 4–7 MUST use the same leaf_index per WIP-100 Composition, which binds the Credential, the session and the billing nullifier to the World ID whose Authenticator authorized the result.

4.7 Verification Requirements

  1. Root Freshness. Verifiers MUST check that the provided public input merkle_root is valid and non-expired. Verifiers MAY check WorldIDRegistry.isValidRoot(merkle_root) on every verification or cache a valid result until the root’s actual expiration (e.g. from WorldIDRegistryV2.getRootExpiration). The configured getRootValidityWindow() is not the root’s remaining lifetime and MUST NOT, by itself, determine the cache duration. A getRootExpiration result of 0 denotes the latest root, not an unlimited cache lifetime. Cache access MUST NOT extend the expiration.
  2. Proving System. Proofs of Embedding Similarity MUST use the ProveKit proving system. Verifiers MUST NOT use verification artifacts supplied by the prover.

4.8 Reference Verification

An RP accepts a proof if the following hold. It MUST check items 2–8 before verifying the proof (item 1).

  1. The proof verifies according to Proving System.
  2. The Flamingo Token values pass checks 1 and 4–6 of WIP-201 Consuming Flamingo Tokens, check 4 on the public nonce, to which constraint 1.1 binds the token’s; constraints 1–3 cover check 7 together with the RP’s Engine policy for the accepted release and pipeline: the pipeline’s input 0 is a live capture, and in compare_kinds byte 0 is a kind the release documents for Orb face thumbnails, byte 1 a live capture kind the RP accepts, byte 2 a challenge kind the RP accepts, or 0 if and only if challenge_hash is 0, and byte 3 is 0. Constraint 7 covers check 8.
  3. now is within 5 minutes of the RP’s own clock.
  4. The World ID and Credential are trusted:
    • merkle_root satisfies Root Freshness at verification time;
    • cred_pk is a trusted Issuer key for issuer_schema_id, for the PoH Credential.
  5. The request matches:
    • genesis_issued_at_min and expires_at_min are the RP’s own;
    • challenge_hash equals the RP’s own challenge_hash, or is 0 if its request had none;
    • signal_hash is the hash of the RP’s own signal, or 0 if its request had none.
  6. If the RP needs this proof to concern the same World ID as another proof, session_id is nonzero and equals that proof’s session commitment.
  7. AAT values. If has_aat = 1, trust_anchor_key_hash, platform, sec_level, sec_meta and authenticator_meta are within the RP’s own policy (WIP-106 §4), whether or not its request stated them. If has_aat = 0, the RP accepts proofs without an AAT.
  8. Delivered live capture. If the RP’s return_live_capture is true, the RP received an image and R(SHA-256(image)) over its exact bytes equals disclosed_live_capture_hash; a proof that withholds the hash fails this, since no image hashes to 0. The RP MUST NOT use the image before items 1–8 hold.

5. Rationale

  1. Authenticator authorization in the circuit. As in other World ID proofs, a signature by a registered Authenticator key shows the prover controls the World ID the Credential was issued to. A copy of the Credential and hashes.json alone cannot produce a proof, revoking an Authenticator stops its proofs, and even a compromised Flamingo Verifier cannot authorize results for a World ID whose Authenticators it does not control. The signature is bound to this result: digest fixes the RP, the RP’s nonce through the token’s derived nonce, and the live capture, and flamingo_verifier_key fixes the Verifier instance. A signature that reaches a prover or leaks with a witness cannot authorize another proof.

  2. Binding the compared image to the PoH Credential. The PoH Credential commits to hashes.json, which lists the SHA-256 of the face thumbnail under thumbnail.png. The circuit reads that digest at a prover-supplied offset and uses it as compared_entry_hash[0] in the token’s digest, so the live capture and challenge were compared with the Credential image. The offset is safe because in the compact format orb-core writes (Supported Credentials) the checked pattern occurs only once.

  3. Fixed entry layout in the Flamingo Token. Positions and compare_sources bind entries to roles without parsing the Engine release manifest in the circuit. Kinds are Engine-specific, so the circuit exposes compare_kinds and the RP checks it with the rest of its Engine policy; a relabeled entry fails that check.

  4. Optional session ID. An RP can check that a later proof comes from the same World ID as an earlier one, e.g. so a different person cannot take over an account. It is optional so proofs stay unlinkable by default.

  5. Credential verification. The circuit verifies the Issuer’s signature, so the RP knows the World ID holds a valid Orb-verified PoH Credential.

  6. Signal in the authorization message. The signal binds the proof to the RP’s context, e.g. an account or a transaction, so a relayed proof cannot be reused for another one. Signing it with the Authenticator key binds the public input to a constraint; an unconstrained public input could be malleable.

  7. Exposed image hashes. The proof exposes at most two image hashes, each only when the RP’s request calls for it: challenge_hash, so the RP can check that the proof concerns its own challenge, and disclosed_live_capture_hash, so it can check a live capture it receives. The Credential image’s hash is constant per user and would link all their proofs, so it is never exposed. A live capture’s hash differs for every capture, so exposing it links no proofs. The combinations serve different uses:

    • No challenge, no live capture: re-authenticating the World ID of a session_id, e.g. a step-up login. The proof exposes no image hash.
    • No challenge, live capture: obtaining a matched live capture as a reference image for later face checks, e.g. during a video call.
    • Challenge, no live capture: matching a party the RP sees, e.g. a frame of a video call.
    • Challenge and live capture: matching that party and keeping a fresh reference image of them.

    Without a challenge, rp_id and the derived nonce still bind the proof to the RP’s request.

  8. Billing nullifier without OPRF verification. Every registered billingNullifier passed a Uniqueness Proof that verified its OPRF output under the RP’s pinned key (WIP-107 §4.4), and the Flamingo Verifier signs only a registered one. Constraint 7 opens it to this proof’s leaf_index and rp_id; by the collision resistance of Poseidon2, which also makes nullifiers unique, they are the registered World ID and RP. A wrong billing_oprf_output only yields an unregistered nullifier, which the Flamingo Verifier never signs. Verifying the OPRF evaluation again would add no guarantee, and would cost a hash-to-curve, several scalar multiplications and the pinned OPRF key as a public input.

  9. Private billing nullifier. The billing nullifier is constant per World ID, RP and billing period, so a public one would let the RP link all of a user’s proofs within a period. The RP needs no billing value: it is the billed party, so billing is enforced by the Flamingo Verifier and constraint 7, not by checks of the RP.

  10. Private issuer_version. As in Uniqueness and Session Proofs, the circuit accepts any issuer_version signed under the trusted cred_pk and keeps it private, so the RP needs no version policy and learns no version. The PoH Issuer therefore keeps claim 0 a hashes.json commitment in every version of issuer_schema_id.

  11. Derived Flamingo nonce. A Flamingo Verifier processes each (aud, nonce) only once (WIP-201), so with the RP’s nonce in the Flamingo request, one failed capture or billing rejection would use up the RP’s request. A fresh nonce per attempt lets the Authenticator retry without a new RP request, while constraint 1.1 keeps the token bound to the RP’s nonce; an RP-supplied challenge_hash binds it to the RP’s request as well.

6. Alternatives Considered

  1. Comparing embeddings in the circuit. Rejected: extraction and fraud detection would still run outside, and the circuit would need fixed-point arithmetic, a fixed embedding dimension and a hash per embedding.
  2. Verifying the AAT in the circuit. Rejected: verification in the Flamingo Verifier per WIP-201 saves the TAKT’s EdDSA verification and the AAT’s ES256 verification on the device, which circuits cannot do efficiently yet.
  3. Verifying more in the Flamingo Verifier. EdDSA verifications dominate the circuit’s cost, so moving more of them into the TEE is tempting. Rejected: World ID authentication there would reveal the leaf index, a permanent identifier, to the TEE, require the Authenticator key to leave the device, and remove the check a compromised Flamingo Verifier cannot forge. Credential verification there would reveal the Credential and tie the Flamingo Verifier to one Credential format, while it currently compares any images.
  4. Disclosing an RP-chosen entry. The RP could name a position whose hash the proof discloses, e.g. the live capture. Rejected: it needs a public index next to the disclosed hash, while the RP knows every other image it wants matched, e.g. a profile picture, and can send it as its challenge.

7. Security

  1. Privacy. The proof hides the media, the Flamingo Token, the Credential, hashes.json and the billing nullifier. Public are the values the RP chose (rp_id, nonce, challenge_hash, signal_hash, session_id, expires_at_min and the Credential policy), disclosed_live_capture_hash if the RP requested the live capture, now, engine_config_hash, compare_kinds, the AAT’s public values and flamingo_verifier_key; an uncommon combination can narrow the set of possible users. flamingo_verifier_key is the same for every token of one Flamingo Verifier boot, so it groups proofs by Verifier instance, not by user.
  2. No uniqueness. An Embedding Similarity Proof provides no uniqueness guarantees by design. Its use case is different. An RP that needs uniqueness MUST also request a Uniqueness Proof with the same nonzero session_id.
  3. Binding to the RP’s counterparty. A proof shows that the compared images match the Credential’s subject. It does not show that the RP’s challenge is unmodified, e.g. a frame of a video stream, or that the interaction is not relayed. Without a challenge, it does not tie the live capture to the party the RP interacts with at all; an RP that uses the capture as a reference MUST establish that binding by its own checks.
  4. Billing. WIP-107 billing holds against a modified Authenticator, which can neither obtain a Flamingo Token for a billed RP without a registered billing nullifier nor prove with one that is not its own. It does not hold against an RP that colludes with the user’s Authenticator, which WIP-201 places out of scope (WIP-107 §6).

8. Future Considerations

  1. Other Credentials. The circuit shall be generalized to other Credentials, likely through a circuit-friendly, general format for Credentials and custody packages.
  2. Build version floors. Build numbers are per Authenticator Provider, so the RP cannot state one useful minimum. A later version may let RPs require a minimum build per Authenticator Provider, e.g. keyed by trust_anchor_key_hash, which would make min_build_version a circuit input again.

9. Backwards Compatibility

This WIP introduces a new interface; no existing contracts or functionality are affected. disclosed_live_capture_hash and compare_kinds add public inputs, so they change the circuit’s verification key.
