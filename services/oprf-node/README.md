# World ID OPRF Node

The World ID OPRF Node is the protocol's OPRF service implementation. The
workspace package for the service is `world-id-oprf-node`.

## Releases

`world-id-oprf-node` is released independently from the published Rust crates. Releases are
triggered by pushing a `world-id-oprf-node-vX.Y.Z` tag that points to a commit on `main`.

1. Bump `version` in `services/oprf-node/Cargo.toml` to the desired version and refresh the
   lockfile (`cargo update -p world-id-oprf-node`). The Docker build runs with `--locked`, so
   the lockfile must be up to date.
2. Commit the version bump to `main` via a PR.
3. After the PR is merged, tag the merge commit and push the tag:
   ```sh
   git tag world-id-oprf-node-vX.Y.Z <commit-sha>
   git push origin world-id-oprf-node-vX.Y.Z
   ```
4. The `Release OPRF Node` workflow will:
   - Build the Docker image reproducibly (see below) and push it to GHCR
     (`ghcr.io/worldcoin/world-id-protocol/world-id-oprf-node`).
   - Cut a GitHub release with release notes generated by git-cliff, scoped to commits under
     `services/oprf-node/` since the previous `world-id-oprf-node-v*` tag.
   - No staging deploy is triggered (that happens separately in the deploy repo).

Tags with a pre-release suffix (e.g. `world-id-oprf-node-v2.0.0-rc.1`) are published as
pre-releases on GitHub and do not receive the `latest` Docker tag.

## Reproducible Docker image

The image is built from `services/oprf-node/Dockerfile` on [StageX](https://stagex.tools), a
full-source-bootstrapped, digest-pinned musl/LLVM toolchain. The image manifest digest is a pure
function of the git commit: the `Build OPRF Node Docker Image` workflow builds the image on two
independent runners with no cache, refuses to push unless both digests match, and pushes the OCI
layout as-is with `crane` so the registry digest equals the locally computed one.

To reproduce a published image, use the run summary of the workflow run that built it: it contains
the agreed digest, a `docker buildx create` command for the pinned BuildKit, and a copy-paste
rebuild command including the OCI labels, which are part of the image config and therefore of
the digest.

To compare two local builders without those labels (linux/amd64, BuildKit v0.33.1):

```sh
SOURCE_DATE_EPOCH=$(git log -1 --pretty=%ct) docker buildx build \
  --platform linux/amd64 --provenance=false --sbom=false --no-cache \
  --build-arg GIT_HASH=$(git rev-parse HEAD) \
  --output type=oci,dest=out,tar=false,rewrite-timestamp=true,force-compression=true,oci-mediatypes=true \
  -f services/oprf-node/Dockerfile .
jq -r '.manifests[0].digest' out/index.json
```

A build without the labels yields a different manifest digest than the published image but
identical layers.
