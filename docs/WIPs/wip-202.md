## 1. Abstract

This spec introduces a ZK circuit ("Proof of Embedding Similarity") which proves that a [WIP-201][wip-201] Flamingo Verifier matched a live capture, and optionally an RP-supplied challenge, to the image committed in a user's [Credential][credential]. The proof reveals no image, no Flamingo Token and no Credential.

The circuit neither extracts embeddings nor compares them. It verifies the Flamingo Token, binds its compared entries to the Credential image and the RP's challenge, and checks the Issuer's Credential and the World ID account's authorization of the result. This first iteration supports only the PoH Credential; it shall be generalized to other Credentials in the future ([Future Considerations](#10-future-considerations)).

## 2. Motivation

Proving that you are a particular person online is becoming increasingly important, e.g. to combat deepfakes. Credentials that attest to a user's biometrics, such as their face, make this possible. This spec binds a comparison to a Credential image and, optionally, a challenge image, so a challenger can check it interacts with the right person, e.g. in a video call or a social network conversation.

## 3. Background

This section is non-normative.

1. **Personal Custody Package (PCP).** At verification, the Orb packages the user's images and stores them on the user's device ([World implements Personal Custody](https://world.org/blog/announcements/world-implements-personal-custody)). The package includes `hashes.json`, which the Orb signs: a JSON object mapping each file name, e.g. `thumbnail.png` for the face thumbnail, to the lowercase hex `SHA-256` of the file, plus a `version`.
2. **PoH Credential.** The [PoH Credential](https://docs.world.org/world-id/credentials/1) commits in claim 0 to the Orb-signed `hashes.json` as `H_var(CLAIMS_HASH_V1; hashes.json)`. This chain lets the circuit bind the compared image to the Issuer's Credential without hashing the image.

### 4.1 Supported Credential

This first iteration supports only the [PoH Credential](https://docs.world.org/world-id/credentials/1). The compared Credential image is the PCP's `thumbnail.png`, and `claims[CLAIM_INDEX]` commits to its `hashes.json` ([Background](#3-background)).

### 4.3 Entry Layout

The circuit binds compared entries by their position in the [WIP-201][wip-201] request's `compare`:

| Position | Role | Bound to |
| --- | --- | --- |
| `0` | `"credential"` | The Credential image, through [Manifest Opening](#45-manifest-opening). |
| `1` | `"live"` | The live capture, through the AAT's `cdh` in the Verifier. |
| `2` | `"challenge"` | The public `challenge_hash`, or absent without a challenge. |

1. Every pipeline in `policy` MUST have the roles `["credential", "live"]` or `["credential", "live", "challenge"]`.
2. `challenge_hash` is `R(SHA-256(challenge))` over the exact challenge bytes, or `0` without a challenge.

### 4.5 Manifest Opening

`hashes_json` is a byte buffer of `MAX_HASHES_JSON_BYTES` bytes. Its first `hashes_json_len` bytes are the Issuer-committed file; the remaining bytes MUST be zero.

1. The prefix MUST be valid UTF-8 JSON with one top-level object, unique keys and exactly one top-level `thumbnail.png` key, whose value is a string of 64 lowercase hexadecimal digits.
2. `thumbnail_offset` is only a hint: the circuit MUST prove it locates that top-level key and its complete value within the prefix.
3. The circuit MUST decode the value as a 32-byte big-endian digest `d`.

### 4.6 Circuit Constraints

Every ordering comparison is over integers range-checked to the stated width.

**Flamingo Token**

1. **Flamingo Token verification.** Enforce [WIP-201 Flamingo Token Verification](wip-201.md#39-flamingo-token-verification), yielding its signed digest and `compared_entry_hash`.
2. **Challenge.** `compared_entry_hash[2] == challenge_hash` and `compared_entry_hash[3] == 0`.
3. **Credential image.** Enforce [Manifest Opening](#45-manifest-opening) over exactly `hashes_json[0:hashes_json_len]`, with `0 < hashes_json_len <= MAX_HASHES_JSON_BYTES`, and constrain `compared_entry_hash[0] == R(d)`.

**Account**

4. **Key selection.** Range-check `pk_index` as 3-bit, constrain `pk_index < NUM_KEYS` and select `pk = user_pk[pk_index]`. Inactive slots are the identity $(0,1)$, which WIP-100 signature verification rejects.
5. **Registry inclusion.** Compute `H_16(MERKLE_LEAF_DS; user_pk[0].x, user_pk[0].y, …, user_pk[6].x, user_pk[6].y)` and prove its inclusion at `leaf_index` under `merkle_root`, per WIP-100, with depth 30 and `0 < leaf_index < 2^30`.
6. **Authorization.** Verify `(auth_r, auth_s)` by `pk` over `H_4(DS_WIP_202_AUTH; digest, verifier_key.x, verifier_key.y)`, where `digest` and `verifier_key` are those of constraint 1.

**Credential**

7. **Claims binding.** `H_var(CLAIMS_HASH_V1; hashes_json[0:hashes_json_len]) == claims[CLAIM_INDEX]`, over the same prefix as constraint 3.
8. **Credential signature.** Compute `sub = H_3(DS_CREDENTIAL_SUB; leaf_index, cred_sub_blinding_factor)` and `claims_hash`, the Poseidon2 $t=16$ permutation over `[claims[0], …, claims[14], 0]` with output element `1`. Range-check `cred_id` as 64-bit and compute `cred_id_packed = cred_id + issuer_version * 2^64`. Verify `(cred_r, cred_s)` by `cred_pk` over `H_8(DS_CREDENTIAL_V1; issuer_schema_id, sub, cred_genesis_issued_at, cred_expires_at, claims_hash, cred_associated_data_hash, cred_id_packed)`.
9. **Credential validity.** Range-check `now` as 32-bit and the Credential times as 64-bit. Constrain `now < cred_expires_at` and `genesis_issued_at_min <= cred_genesis_issued_at`.
10. **Session commitment.** `session_id * (session_id - H_3(DS_SESSION_COMMITMENT; leaf_index, session_id_r)) == 0`.

Constraints 5, 8 and 10 MUST use the same `leaf_index`, which binds the Credential to the account that authorized the result.

### 4.7 Reference Verification

An RP accepts a proof if:

1. The proof verifies under the verification key the RP pinned for this circuit.
2. The Flamingo Token inputs pass [WIP-201 Reference Verification](wip-201.md#5-reference-verification), with every `policy` entry acceptable to the RP and following [Entry Layout](#43-entry-layout).
3. `now` is within 5 minutes of the RP's own clock.
4. `merkle_root` is a root the `WorldIDRegistry` accepts, and `cred_pk` is a trusted Issuer key for `issuer_schema_id` and `issuer_version`, for the [PoH Credential](https://docs.world.org/world-id/credentials/1).
5. `genesis_issued_at_min` and `challenge_hash` match the RP's request.
6. If the RP needs this proof to concern the same World ID as another proof, `session_id` is nonzero and equals that proof's session commitment.

## 5. Trust Assumptions

This spec adds two parties to the [WIP-201 Trust Assumptions](wip-201.md#4-trust-assumptions):

| Party | Trusted for |
| --- | --- |
| Issuer | That the Credential image depicts the Credential's subject. |
| `WorldIDRegistry` | The account's registered keys. |

## 6. Use Cases

1. **RP-supplied challenge.** The RP captures a frame of the party it interacts with and requests a proof against it. A valid proof shows the Verifier matched the live capture, the challenge and the Credential image pairwise. It does not establish that a video stream is unmodified or prevent a relayed interaction.
2. **Presence.** Without a challenge, a valid proof shows the Verifier matched the live capture to the Credential image, without revealing either to the RP.

## 7. Rationale

1. **Account authorization in the circuit.** The account signs the Flamingo Token digest and `verifier_key`, and the circuit binds that account to the Credential. A compromised Verifier can invent results, but cannot authorize them for an account it does not control.
2. **Opening the manifest.** The Credential commits to `hashes.json`, which holds the image's SHA-256 digest. Opening it binds the compared image to the Issuer's claim without hashing the image in the circuit.
3. **Fixed entry layout.** Positions bind entries to roles without parsing the Engine release in the circuit.
4. **One `now`.** The Flamingo Token's `now` and the Credential's validity use the same public time, which the RP checks once.
5. **No nullifier.** Similarity is not uniqueness. A use case that needs uniqueness requests a Uniqueness Proof as well.

## 8. Alternatives Considered

1. **Comparing embeddings in the circuit.** Rejected: extraction and fraud detection would still run outside, and the circuit would need fixed-point arithmetic, a fixed embedding dimension and a hash per embedding.
2. **Verifying the AAT in the circuit.** Rejected: the Verifier already verifies it per [WIP-201][wip-201], which saves an EdDSA verification on the device.

## 9. Security

1. **A Verifier key does not authorize an account.** Without the account's authorization over the Flamingo Token digest, no proof exists for that account. A holder of an authorization can still present that result; the RP MUST consume the `nonce`.
2. **Privacy.** The proof hides the media, the Flamingo Token, the Credential and `hashes.json`. The AAT's public values, `policy`, `challenge_hash` and `now` are public; an uncommon `policy` can narrow the set of possible users.
3. **No uniqueness.** An RP that needs uniqueness MUST also request a Uniqueness Proof with the same nonzero `session_id`.

## 10. Future Considerations

1. **Other Credentials.** This first iteration supports only the PoH Credential. The circuit shall be generalized to other Credentials, likely through a circuit-friendly, general format for Credentials and custody packages.

This WIP introduces a new interface; no existing contracts or functionality are affected.
