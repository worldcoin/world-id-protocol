## 1. Abstract

This spec introduces a ZK circuit ("Proof of Embedding Similarity") which proves that a [WIP-201][wip-201] Flamingo Verifier matched a live capture and an RP-supplied challenge to the image committed in a user's [Credential][credential]. The proof reveals no image, no Flamingo Token and no Credential.

The circuit neither extracts embeddings nor compares them. It verifies the Flamingo Token, binds its compared entries to the Credential image and the RP's challenge, and checks the Issuer's Credential and an Authenticator's authorization of the result. This first iteration supports only the PoH Credential; it shall be generalized to other Credentials in the future ([Future Considerations](#8-future-considerations)).

## 2. Motivation

Proving that you are a particular person online is becoming increasingly important, e.g. to combat deepfakes. Credentials that attest to a user's biometrics, such as their face, make this possible. This spec binds a comparison to a Credential image and a challenge image, so a challenger can check it interacts with the right person, e.g. in a video call or a social network conversation.

## 3. Background

This section is non-normative.

1. **Personal Custody Package (PCP).** At verification, the Orb packages the user's images and stores them on the user's device ([World implements Personal Custody](https://world.org/blog/announcements/world-implements-personal-custody)). The package includes `hashes.json`, which the Orb signs: a JSON object mapping each file name, e.g. `thumbnail.png` for the face thumbnail, to the lowercase hex `SHA-256` of the file, plus a `version`.
2. **PoH Credential.** The [PoH Credential](https://docs.world.org/world-id/credentials/1) commits in claim 0 to the Orb-signed `hashes.json` as `H_var(CLAIMS_HASH_V1; hashes.json)`. This chain lets the circuit bind the compared image to the Issuer's Credential without hashing the image.

### 4.3 Entry Layout

The circuit binds compared entries by their position in the [WIP-201][wip-201] request's `compare`:

| Position | Role | Bound to |
| --- | --- | --- |
| `0` | Credential image | The Credential image, through [constraint 3](#45-circuit-constraints). |
| `1` | Live capture | Not bound in the circuit; the AAT, if present, vouches for it through `cdh`. |
| `2` | Challenge | The public `challenge_hash`. |

1. The RP MUST accept only `engine_config_hash` values whose verified release manifest describes `pipeline` with the Credential image, the live capture and the challenge at `compare` positions 0, 1 and 2.
2. `challenge_hash` is `R(SHA-256(challenge))` over the exact challenge bytes.

### 4.5 Circuit Constraints

Every ordering comparison is over integers range-checked to the stated width.

**Flamingo Token**

1. **Flamingo Token verification.** The Verifier signed this Flamingo Token.
   - Enforce [WIP-201 Flamingo Token Verification](wip-201.md#39-flamingo-token-verification), yielding its signed digest and `compared_entry_hash`.
2. **Challenge.** The Engine compared the challenge image the RP checked.
   - `challenge_hash != 0`.
   - `compared_entry_hash[2] == challenge_hash`.
3. **Credential image.** The Engine compared the image the Credential commits to.
   - `MIN_HASHES_JSON_BYTES <= hashes_json_len <= MAX_HASHES_JSON_BYTES`, and the bytes beyond `hashes_json_len` are zero.
   - The byte before `thumbnail_offset` is `{` or `,`.
   - The 17 bytes at `thumbnail_offset` are `"thumbnail.png":"`, followed by 64 lowercase hexadecimal digits and `"`, all within the first `hashes_json_len` bytes.
   - The digits decode as the 32-byte big-endian digest `d`, and `compared_entry_hash[0] == R(d)`.

**World ID Authentication**

1. **Key selection.** One of the World ID's registered Authenticator keys signed the authorization.
   - Range-check `pk_index` as 3-bit and constrain `pk_index < NUM_KEYS`.
   - Select `pk = user_pk[pk_index]`. Inactive slots are the identity $(0,1)$, which WIP-100 signature verification rejects.
2. **Registry inclusion.** That key set is registered for a World ID in the `WorldIDRegistry`.
   - Compute `H_16(MERKLE_LEAF_DS; user_pk[0].x, user_pk[0].y, …, user_pk[6].x, user_pk[6].y)`.
   - Prove its inclusion at `leaf_index` under `merkle_root`, per WIP-100, with depth 30 and `0 < leaf_index < 2^30`.
3. **Authorization.** An Authenticator of that World ID authorized this exact result from this Verifier.
   - Verify `(auth_r, auth_s)` by `pk` over `H_4(DS_WIP_202_AUTH; digest, verifier_key.x, verifier_key.y)`, with `digest` and `verifier_key` from constraint 1.

4. **Session commitment.** `session_id`, if set, identifies this World ID.
   - `session_id * (session_id - H_3(DS_SESSION_COMMITMENT; leaf_index, session_id_r)) == 0`.

**Credential**

1. **Claims binding.** The opened `hashes.json` is the one the Credential commits to.
   - `H_var(CLAIMS_HASH_V1; hashes_json[0:hashes_json_len]) == claims[CLAIM_INDEX]`, over the same bytes as constraint 3.
2. **Credential signature.** The Issuer issued the Credential to this World ID.
   - Compute `sub = H_3(DS_CREDENTIAL_SUB; leaf_index, cred_sub_blinding_factor)`.
   - Compute `claims_hash`, the Poseidon2 $t=16$ permutation over `[claims[0], …, claims[14], 0]` with output element `1`.
   - Range-check `cred_id` as 64-bit and compute `cred_id_packed = cred_id + issuer_version * 2^64`.
   - Verify `(cred_r, cred_s)` by `cred_pk` over `H_8(DS_CREDENTIAL_V1; issuer_schema_id, sub, cred_genesis_issued_at, cred_expires_at, claims_hash, cred_associated_data_hash, cred_id_packed)`.
3. **Credential validity.** The Credential is valid at `now` and meets the RP's minimum first-issuance time.

- Range-check `now` as 32-bit and the Credential times as 64-bit.
- `now < cred_expires_at` and `genesis_issued_at_min <= cred_genesis_issued_at`.

Constraints 5, 7 and 9 MUST use the same `leaf_index`, which binds the Credential to the World ID whose Authenticator authorized the result.

### 4.6 Reference Verification

An RP accepts a proof if:

1. The proof verifies under the verification key the RP pinned for this circuit.
2. The Flamingo Token inputs pass [WIP-201 Reference Verification](wip-201.md#5-reference-verification), with an `engine_config_hash` that follows [Entry Layout](#43-entry-layout).
3. `now` is within 5 minutes of the RP's own clock.
4. The World ID and Credential are trusted:
   - `merkle_root` is a root the `WorldIDRegistry` accepts;
   - `cred_pk` is a trusted Issuer key for `issuer_schema_id` and `issuer_version`, for the [PoH Credential](https://docs.world.org/world-id/credentials/1).
5. The request matches:
   - `genesis_issued_at_min` is the RP's own;
   - `challenge_hash` is `R(SHA-256(challenge))` of a challenge image the RP checked against the party it interacts with.
6. If the RP needs this proof to concern the same World ID as another proof, `session_id` is nonzero and equals that proof's session commitment.

## 5. Rationale

1. **Authenticator authorization in the circuit.** As in other World ID proofs, a signature by a registered Authenticator key shows the prover controls the World ID the Credential was issued to. A copy of the Credential and `hashes.json` alone cannot produce a proof, revoking an Authenticator stops its proofs, and even a compromised Verifier cannot authorize results for a World ID whose Authenticators it does not control.
2. **Opening `hashes.json`.** The Credential commits to `hashes.json`, which holds the image's SHA-256 digest. Opening it binds the compared image to the Issuer's claim without hashing the image in the circuit. A prover-chosen offset suffices: Orb-produced files are compact JSON with unique file-name keys and hex or version values, so the checked pattern occurs only at the one `thumbnail.png` entry.
3. **Fixed entry layout.** Positions bind entries to roles without parsing the Engine release manifest in the circuit.
4. **Optional Session ID** Allows RP to verify that they verified the same human again. E.g., useful to prevent real humans to steal accounts of other real humans.

## 6. Alternatives Considered

1. **Comparing embeddings in the circuit.** Rejected: extraction and fraud detection would still run outside, and the circuit would need fixed-point arithmetic, a fixed embedding dimension and a hash per embedding.
2. **Verifying the AAT in the circuit.** Rejected: the Verifier already verifies it per [WIP-201][wip-201], which saves an EdDSA verification on the device.

## 7. Security

1. **Privacy.** The proof hides the media, the Flamingo Token, the Credential and `hashes.json`. The AAT's public values, `engine_config_hash`, `challenge_hash` and `now` are public; an uncommon combination can narrow the set of possible users.
2. **No uniqueness.** An RP that needs uniqueness MUST also request a Uniqueness Proof with the same nonzero `session_id`.
3. **Relay and stream integrity.** A proof shows the challenge image matches the Credential's subject. It does not establish that a video stream is unmodified or prevent a relayed interaction.

## 8. Future Considerations

1. **Other Credentials.** The circuit shall be generalized to other Credentials, likely through a circuit-friendly, general format for Credentials and custody packages.

## 9. Backwards Compatibility

This WIP introduces a new interface; no existing contracts or functionality are affected.
