## 1. Abstract

This spec defines the **Flamingo Verifier** (**Verifier**), a trusted execution environment (TEE) service. It receives up to eight images or embeddings, a `pipeline` and a `match_strictness`, and runs a sandboxed biometric Engine, provided by an Engine Provider, for fraud detection and comparison. If the Engine accepts, the Verifier signs a **Flamingo Token** over the Engine configuration, the compared entries and the AAT's public values, if any. If a [WIP-106][wip-106] Authenticator Assertion Token (AAT) is provided, it is also verified. [WIP-202][wip-202] consumes the Flamingo Token to prove the comparison to a Relying Party (RP) without revealing any entry.

## 2. Motivation

Many Proof-of-Human applications like deep fake prevention or human presence verification require A) running fraud detection models like presentation attack detection (PAD) on a set of input images and B) comparing images using embedding models, e.g., to verify that the person on a stream is the same as the one performing a liveness check on a phone.

Building a privacy preserving system for such image comparisons is very difficult. For example, running the models and comparisons locally on the user's device is privacy-preserving but it has very low security guarantees: a mobile device's output is not trustworthy, e.g., a jailbroken device could report that fraud detection and embedding comparison were performed, while simply running a spoofed client that does not perform them at all. Therefore, an RP cannot be sure that the claimed checks have actually been executed. Additionally, fraud detection models' security relies on obscurity and obtaining the model weights, or even just the model architecture, opens up a wide range of attack vectors.

To achieve verifiability in a privacy-preserving way, this document introduces a general approach that runs fraud detection models and embedding models in an attested Trusted Execution Environment (TEE). This allows users to verify that the TEE operator is not able to access any biometric data, and a signature by the TEE proves to RPs that all claimed checks have been correctly executed. The Verifier image MUST be open source and reproducibly built, so anyone can check that its attested measurement matches the source and that no raw media or embeddings leave the TEE. Fraud detection models cannot be open, so the Verifier runs them as a closed Engine inside a kernel-enforced sandbox that has no network or storage access. The Authenticator chooses the Engine by its hash, from a release manifest the Engine Provider signs.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

1. The **Engine** is the sandboxed component of the Verifier that performs extraction, fraud detection and comparison. This spec defines none of them.
2. The **Engine Provider** builds the Engine and signs its release manifests. It MAY be the same organization as an Authenticator Provider ([WIP-106][wip-106]).
3. The **host** is the machine that runs the Verifier's enclave and relays all its traffic, on AWS Nitro the parent EC2 instance. The **operator** runs the host. Neither is trusted beyond availability ([Trust Assumptions](#4-trust-assumptions)).
4. The Field ($F$), the hash function ($H_t$), the signature scheme (`BabyJubJub-EdDSA-Poseidon2`) and the `PublicKey` representation MUST follow [WIP-100][wip-100]. `R(d)` reads a 256-bit digest `d` as a big-endian integer modulo $q$.

| `DS_WIP_201_ENGINE` | `8362622191109606222205468683123474433460185506268139077` (`b"WORLD-ID/WIP-201/ENGINE"`) | Domain separator for `engine_config_hash`. |
| `MAX_ATTESTATION_AGE` | `86400` | Maximum age of a `signing_key_attestation` at verification, in seconds. |

| `CHANNEL_DOMAIN` | `WORLD-ID/WIP-201/CHANNEL` | Domain of the request channel. |

### 3.2 Request

The request is a deterministic CBOR map ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)) with the fields below. The Authenticator encrypts the entire encoded map to the Verifier ([Channel Encoding](#381-channel-encoding)). Field elements are 32-byte byte strings, the canonical big-endian encoding.

`payload` is a CBOR byte string that contains a second deterministic CBOR map, the payload fields below. It is nested as bytes so that `cdh` commits to its exact encoding.

| Field | Type | Description |
| --- | --- | --- |
| `version` | `uint` | MUST be `1`. |
| `payload` | bytes | The encoded payload map; see below. |
| `aud` | Field element | The `rpId` of the request. |
| `nonce` | Field element | The RP's nonce for the request, sampled uniformly from the nonzero elements of $F$ with a CSPRNG. |
| `aat_inputs` | map, optional | Inputs for verifying an AAT ([Authenticator Assertion](#33-authenticator-assertion)). |

| `payload` field | Type | Bounds | Description |
| --- | --- | --- | --- |
| `pipeline` | `uint` | `1..2^16` | Engine-defined pipeline, chosen by the Authenticator among the configurations the RP offers ([Engine Selection](#353-engine-selection)). |
| `match_strictness` | `uint` | `< 2^8` | Matching strictness level, defined by the Engine Provider for all pipelines. |
| `hints` | bytes | ≤ 1 KiB | Request-level Engine hints, e.g. experiment flags. MUST NOT change any security assumptions or weaken `match_strictness`; anything that changes the verdict belongs in `pipeline`. |
| `entries` | array of maps | `1..=MAX_ENTRIES` | Inputs to the Engine, each `{ data, meta }`. |
| `entries[i].data` | bytes | | An encoded image or an embedding. |
| `entries[i].meta` | bytes | ≤ 256 bytes | How the Engine reads `data`, e.g. which frame of a capture it is. |
| `compare` | array of `uint` | `2..=MAX_COMPARED` distinct indices into `entries` | Ordered; the Engine compares every pair. |
| `engine_hash` | bytes | 32 bytes | `SHA-256` of the Engine bundle, taken from the RP's offer ([Engine Selection](#353-engine-selection)). The Authenticator MUST verify its release manifest under a trusted Engine Provider key before sending biometrics to it. |

1. The Verifier interprets none of the `payload` fields and forwards them to the Engine. Roles (Credential item, live frame, challenge) are fixed by `pipeline` through positions in `compare`.
2. The Verifier MUST reject a request of any other shape, exceeding a bound, or whose `compare` repeats or names an out-of-range index. It MAY impose further byte limits on `entries[].data`.

### 3.3 Authenticator Assertion

`aat_inputs` is OPTIONAL. Authenticators without an Authenticator Provider that issues AATs omit it. If present, it is a map with the fields marked `aat_inputs.` below, and the Verifier obtains every input of [WIP-106 §3.7][wip-106] as follows:

| WIP-106 §3.7 input | Type | Source |
| --- | --- | --- |
| `authenticator_provider_key` | `PublicKey` | `aat_inputs.authenticator_provider_key` |
| `authenticator_provider_key_hash` | Field element | Computed from `authenticator_provider_key`. |
| `exp` | uint32 | `aat_inputs.exp` |
| `sec_flags` | uint64 | `aat_inputs.sec_flags` |
| `sig` | Signature | `aat_inputs.sig` |
| `blind` | Field element | `aat_inputs.blind` |
| `now` | uint32 | `aat_inputs.now` |
| `min_build_version` | uint32 | `aat_inputs.min_build_version`, the RP's minimum; `0` sets no minimum. |
| `aud`, `nonce` | Field element | The request's `aud` and `nonce`. |
| `cdh` | Field element | Computed as `R(SHA-256(payload))`. |
| `platform`, `sec_level`, `sec_meta`, `user_presence` | uint8 | Unpacked from `sec_flags`. |

1. **Verification.** If `aat_inputs` is present, every check of [WIP-106 §3.7][wip-106] MUST hold before the Verifier calls the Engine; otherwise it rejects the request.
2. **Outputs.** The public inputs reach the Flamingo Token as `authenticator_provider_key_hash`, `now` and `aat_flags` ([Claims](#361-claims)); `aud` and `nonce` as themselves. `exp`, `sec_flags`, `sig`, `blind` and the derived `aat_commitment` and `build_version` MUST NOT leave the Verifier, and `aat_inputs` MUST NOT be passed to the Engine.
3. **Without an AAT.** The Verifier MUST set `has_aat` to `1` if it verified an AAT and to `0` otherwise. With `has_aat = 0`, `now`, `authenticator_provider_key_hash` and `aat_flags` MUST be `0`, as in WIP-106's `has_aat = 0` case.

### 3.4 Response

| Variant | Contents |
| --- | --- |
| `Success` | `token` ([Flamingo Token](#36-flamingo-token)), `signing_key_attestation` ([Attestation and Transport](#38-attestation-and-transport)), `debug_report` (optional) |
| `Failed` | `error`, `debug_report` (optional) |

1. The response MUST be encrypted to the requester and MUST be padded to a fixed length, hiding the outcome and the report size.
2. `error` is implementation-defined and bounded in size; it comes from the Verifier or, passed through, from the Engine.
3. `debug_report` is optional Engine output outside the Flamingo Token. The Verifier MUST NOT emit a report larger than `MAX_DEBUG_REPORT`. Clients MUST NOT forward it without the user's explicit consent, and only to the Engine Provider. It SHOULD let the user inspect a report before forwarding it.
4. The Verifier MUST emit a Flamingo Token only when the Engine returns `Pass`.

### 3.5 Engine

1. Each `pipeline` defines the entry layout, how each entry's `meta` is read, and which checks run. Each pipeline sets the match thresholds that meet each `match_strictness` level. Fraud detection is fixed by `pipeline` and does not vary with `match_strictness`.
2. Each release manifest defines the `match_strictness` levels independently of `pipeline`: every pipeline MUST support every level, a level MUST mean the same in every pipeline, and a higher level MUST be at least as strict for every compared pair. The Engine MUST reject a `match_strictness` the release manifest does not define.
3. **Engine Provider.** The Engine Provider builds the Engine and signs each release manifest ([Release Manifests](#352-release-manifests)). A Verifier MAY load several Engines. It MUST reject a request unless it loaded an Engine whose bundle hashes to `engine_hash`.
4. The Verifier MUST pass the `payload` fields to the Engine unchanged. The Engine MUST return `Pass`, meaning every check passed and every compared pair cleared `match_strictness`, or an error, either with an optional `debug_report` and never with scores. This WIP does not specify the encoding.

#### 3.5.1 Isolation

The Engine sees raw biometrics and runs closed, injected models. The Verifier MUST give it no network access, no writable persistent storage, no process creation and no access to the Verifier's keys, and only one bounded request-response channel. Each request MUST run in a fresh or reset Engine instance, so no data from one request reaches another. The Verifier MUST bound the Engine's runtime and memory and return an `error` when they are exceeded. See the [reference implementation's sandbox](https://github.com/worldcoin/flamingo/tree/main/verifier/sandbox-client) for one way to meet these requirements.

#### 3.5.2 Release Manifests

A release manifest is a JWS ([RFC 7515](https://www.rfc-editor.org/rfc/rfc7515)) in compact serialization, signed with `ES256` by the Engine Provider's release key. Its protected header MUST contain `alg` = `ES256`, `kid` and `typ` = `world-id-engine-manifest`. Its payload is a JSON object:

| Field | Type | Description |
| --- | --- | --- |
| `engine_hash` | string | `SHA-256` of the Engine bundle, hex. |
| `version` | string | The Engine Provider's label for the release, unique per Engine Provider. It is for people and logs and is not part of `engine_config_hash`. |
| `pipelines` | array | Each entry: `pipeline` (integer) and `description` (string), which states its checks and the meaning of each `compare` position. |
| `match_strictness_levels` | array | Each entry: `match_strictness` (integer) and `description` (string), ascending. |

1. **Loading**. The Engine bundle is everything the Engine runs: code, model weights and configuration. The host passes bundles at start-up, each as one artifact. The Verifier MUST hash each bundle, MUST NOT let an Engine load anything outside its bundle, and MUST run a request only on a bundle that hashes to the request's `engine_hash`. It reads no release manifest, verifies no signature and fetches nothing.
2. **Signatures**. RPs and Authenticators MUST verify a release manifest under an active release key of an Engine Provider they trust before relying on it.
3. **Configuration hash**. `engine_config_hash = H_4(DS_WIP_201_ENGINE; R(engine_hash), pipeline, match_strictness)`.
4. **Metadata**. The Engine Provider MUST expose a JSON file over HTTPS at `https://<FQDN>/.well-known/world-id-engine.json`:

| Field | Type | Description |
| --- | --- | --- |
| `version` | integer | MUST be `1`. |
| `provider_id` | string | Stable identifier, which RPs MAY allowlist. |
| `release_keys` | array | Each entry: `jwk` (a P-256 JWK with `kid`) and `status` (`active`, `retired` or `revoked`). |
| `manifests` | array | Each entry: `manifest` (the compact JWS) and `status` (`active`, `retired` or `revoked`). |

The Verifier never fetches the metadata. RPs compute the `engine_config_hash` values they accept from it, and Authenticators read `pipelines` to lay out `compare`.

#### 3.5.3 Engine Selection

1. **Offer.** The RP lists the configurations it accepts as (`engine_hash`, `pipeline`, `match_strictness`) tuples, in order of preference. How it conveys them is outside this WIP.
2. **Availability.** The host MUST serve the `engine_hash` values of the loaded Engines alongside the channel attestation. The list is unauthenticated; a wrong list only makes requests fail.
3. **Choice.** The Authenticator MUST choose the first offered tuple its device supports and the Verifier has loaded, and set `engine_hash`, `pipeline` and `match_strictness` from it.
4. **Check.** The RP accepts only the `engine_config_hash` of a tuple it offered ([Reference Verification](#5-reference-verification)).

### 3.6 Flamingo Token

The Flamingo Token is the primary **output** of a Verifier after a comparison. A Flamingo Token is a CWT ([RFC 8392](https://datatracker.ietf.org/doc/html/rfc8392)) in an untagged `COSE_Sign1`, encoded as deterministic CBOR ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)).

1. The protected header MUST contain `alg` (label `1`) = `-65537` (Private Use, `BabyJubJub-EdDSA-Poseidon2`) and `kid` (label `4`) = the compressed signing public key.
2. The signature MUST be a `BabyJubJub-EdDSA-Poseidon2` signature per [WIP-100][wip-100] over the [signed digest](#362-signed-digest).

#### 3.6.1 Claims

The payload MUST contain exactly these claims, in the bytewise order of their encoded keys.

| Claim | Key | Value |
| --- | --- | --- |
| `eat_profile` | `265` | `EAT_PROFILE`. |
| `compared_entry_hash_k`, `k = 0..3` | `-90000 - k` | `R(SHA-256(entries[compare[k]].data))`, or `0` if `compare` has no position `k`. |
| `aud` | `-90004` | `aud` from the request. |
| `nonce` | `-90005` | `nonce` from the request. |
| `authenticator_provider_key_hash` | `-90006` | [WIP-106][wip-106] hash of the `authenticator_provider_key` that verified the AAT, or `0` without an AAT. |
| `aat_flags` | `-90007` | `platform + 2^8 * sec_level + 2^16 * min_build_version + 2^48 * sec_meta + 2^51 * user_presence`, the [WIP-106][wip-106] `sec_flags` layout with the public `min_build_version` in place of `build_version`; `0` without an AAT. |
| `has_aat` | `-90008` | `1` if the Verifier verified an AAT, otherwise `0`. |
| `now` | `-90009` | `now` of the verified AAT, or `0` without an AAT. |
| `engine_config_hash` | `-90010` | The Engine configuration that ran ([Release Manifests](#352-release-manifests)). |

1. `aat_flags`, `has_aat` and `now` are CBOR uints. All other claims except `eat_profile` are 32-byte byte strings, the canonical big-endian encoding of a field element.
2. `eat_profile` is not in the signed digest and MUST be treated as an untrusted hint.

#### 3.6.2 Signed Digest

The signed message is **not** the COSE `Sig_structure`. It MUST be

```
H_16(DS_WIP_201; now,
     compared_entry_hash_0, compared_entry_hash_1, compared_entry_hash_2, compared_entry_hash_3,
     aud, nonce, authenticator_provider_key_hash, aat_flags, has_aat, engine_config_hash)
```

per [WIP-100][wip-100] §3.3.2, with $k = 11$. A `compared_entry_hash_k` without a compared entry at position `k` is `0`.

Four slots remain free.

### 3.7 Verifiability and Reproducible Builds

The Verifier runs as an [AWS Nitro Enclaves](https://aws.amazon.com/ec2/nitro/nitro-enclaves/) image, and its measurement MUST be verifiable from source:

1. **Source.** Each Verifier release MUST name its source by an immutable reference, e.g. a commit hash in a public repository.
2. **Build.** Building that source with the documented toolchain MUST produce a bit-identical Enclave Image File (EIF).
3. **Measurement.** PCR0, PCR1 and PCR2 of that EIF, as AWS Nitro Enclaves computes them, are the Verifier's measurement.
4. **Publication.** The Verifier operator MUST publish, per release, the source reference, the build instructions and PCR0–2.
5. **Acceptance.** RPs and Authenticators MUST accept only PCR values they trust.

Engines are injected at runtime and bound by `engine_hash` ([Engine](#35-engine)).

### 3.8 Attestation and Transport

The Verifier generates a channel key and a Flamingo Token signing key at boot and attests each in its own Nitro attestation document: a `COSE_Sign1` chaining to the [AWS Nitro Root G1](https://aws-nitro-enclaves.amazonaws.com/AWS_NitroEnclaves_Root-G1.zip). Its PCR0–2 are the measurement, its `timestamp` in milliseconds divided by 1000 is the attestation time, and its `public_key` binds the key below. A document with all-zero PCRs comes from debug mode and MUST be rejected.

| Document | `public_key` | Used by |
| --- | --- | --- |
| Channel attestation | `SHA-256(CHANNEL_KEY_DOMAIN \|\| channel_key)` | The Authenticator, to encrypt a request; discarded afterwards. |
| `signing_key_attestation` | The Flamingo Token signing key (`kid`) | Consumers, with every Flamingo Token. |

1. **Channel**. Before sending a request, the Authenticator MUST check that the channel attestation:
   - is a valid `COSE_Sign1` whose certificate chain leads to the AWS Nitro Root G1 and is valid at the current time;
   - does not have all-zero PCRs, and has PCR0–2 it accepts ([Verifiability](#37-verifiability-and-reproducible-builds));
   - has `public_key = SHA-256(CHANNEL_KEY_DOMAIN || channel_key)` for the `channel_key` it encrypts to;
   - has a `timestamp` at most `MAX_ATTESTATION_AGE` old.

   It then seals `response_key || request` to `channel_key` ([Channel Encoding](#381-channel-encoding)), where `response_key` is a fresh X-Wing encapsulation key and `request` the plaintext of [Request](#32-request).
2. **Response**. The Verifier MUST seal the padded response to `response_key`. Only the requester holds `response_key`, so the response is bound to its request; a `Success` is authenticated by its Flamingo Token.
3. **Replay**. The host can replay a request. That yields at most another Flamingo Token for the same `nonce`, which the RP rejects as reused.
4. **Refresh**. The Verifier MUST re-attest its signing key at least every `MAX_ATTESTATION_AGE` and return its latest `signing_key_attestation`.
5. **Carrying**. A proof or message that relies on a Flamingo Token MUST carry the Flamingo Token's `signing_key_attestation`.

The Engine needs no attestation of its own: the measured Verifier signs its `engine_config_hash` into each Flamingo Token. One `signing_key_attestation` covers every Flamingo Token of a boot, so consumers MAY cache it by key. It identifies the Verifier instance, not the user.

#### 3.8.1 Channel Encoding

Both directions use the public-key encryption of [WIP-100][wip-100] §3.9.

1. **Info**. `info` is `CHANNEL_DOMAIN || 0x00` for a request and `CHANNEL_DOMAIN || 0x01` for a response.
2. **Request plaintext**. The first 1216 bytes are `response_key`, an X-Wing encapsulation key; the rest is the request.
3. **Rejection**. The Verifier MUST reject a request shorter than 1216 bytes or with an invalid `response_key`.

### 3.9 Flamingo Token Verification

Flamingo Token verification is specified as a component for circuits (e.g. [WIP-202][wip-202]); a consumer outside a circuit MUST perform the same checks ([Reference Verification](#5-reference-verification)). The component MUST introduce these inputs.

| Input | Visibility | Type | Description |
| --- | --- | --- | --- |
| `verifier_key` | **Public** | `PublicKey` | The Verifier's signing key, checked against its `signing_key_attestation`. |
| `now` | **Public** | uint32 | Current time, in seconds since the Unix epoch. With an AAT it is the AAT's `now`, see [WIP-106 §3.7][wip-106]. |
| `aud`, `nonce` | **Public** | Field element | The RP's request. |
| `has_aat` | **Public** | bool | Whether the Flamingo Token carries an AAT result. |
| `authenticator_provider_key_hash` | **Public** | Field element | Hash of an allowlisted Authenticator Provider key. |
| `platform`, `sec_level`, `sec_meta`, `user_presence` | **Public** | uint8 | AAT sub-fields, see [WIP-106 §3.5][wip-106]. |
| `min_build_version` | **Public** | uint32 | Minimum `build_version` the RP accepts. |
| `compared_entry_hash` | Private | [Field element; 4] | From the Flamingo Token. |
| `engine_config_hash` | **Public** | Field element | From the Flamingo Token. |
| `sig` | Private | Signature | The Flamingo Token signature. |

The circuit MUST enforce:

1. **Signature.** The Verifier signed the Flamingo Token.
   - Compute the [signed digest](#362-signed-digest) from the inputs.
   - Verify `sig` under `verifier_key` per [WIP-100 §3.5.1][wip-100].
2. **Request binding.** The Flamingo Token is for this request and Authenticator Provider.
   - The digest uses the public `aud`, `nonce` and `authenticator_provider_key_hash`.
   - The digest uses `has_aat * now` as the Flamingo Token's `now`.
3. **Assertion flags.** The Flamingo Token carries the public AAT sub-fields.
   - Range-check `platform`, `sec_level`, `sec_meta`, `user_presence` and `min_build_version` to their widths, and constrain `user_presence < 5`.
   - The digest uses `aat_flags = platform + 2^8 * sec_level + 2^16 * min_build_version + 2^48 * sec_meta + 2^51 * user_presence`.
4. **Optional AAT.** Without an AAT, the AAT values are zero.
   - `has_aat` is `0` or `1`, and the digest uses it.
   - When `has_aat = 0`, `authenticator_provider_key_hash`, `platform`, `sec_level`, `sec_meta`, `user_presence` and `min_build_version` MUST be `0`, as in [WIP-106 §3.7][wip-106]; `now` stays available to the embedding circuit.
5. **Engine.** The Flamingo Token names the Engine configuration that ran.
   - The digest uses the public `engine_config_hash`.
   - An embedding circuit MAY take its components as private inputs and recompute it, to constrain them.

The component returns `compared_entry_hash`. The embedding circuit MUST bind each hash its statement depends on to its own inputs (e.g. the Issuer's claim or the RP's challenge).

## 4. Trust Assumptions

The protocol assumes the isolation, measurement and attestation of AWS Nitro Enclaves are sound. If they fail, neither privacy nor integrity holds. Every party in the table below is trusted only for the listed parts, and a compromise of one only affects those parts, except AWS.

| Party | Trusted for | Not trusted for |
| --- | --- | --- |
| AWS (Nitro Enclaves) | Isolation, measurement and attestation of the enclave. | Nothing: if this fails, neither privacy nor integrity holds. |
| Engine Provider | Engine correctness: fraud detection, matching, and accurate release manifest descriptions. | Privacy: the sandbox keeps the Engine from exporting data. |
| Authenticator Provider | Verifying the Authenticator's integrity, as stated in the AAT. | — |
| Authenticator | The source and freshness of the live capture. | — |
| Host and operator | Availability only. | Privacy and integrity: they see only ciphertext, and a replay yields only a Flamingo Token with a used `nonce`. |

## 5. Reference Verification

A consumer accepts a Flamingo Token if:

1. The `signing_key_attestation`:
   - chains to the AWS Nitro Root G1 and does not have all-zero PCRs;
   - has PCR0–2 the RP accepts ([Verifiability](#37-verifiability-and-reproducible-builds));
   - attests the key that signed the Flamingo Token (`kid` is only a hint);
   - has a `timestamp` at most `MAX_ATTESTATION_AGE` old.
2. The signature verifies under that key.
3. The request matches:
   - `aud` is the RP's own;
   - `nonce` is one the RP issued, has not expired and has not been used before.
4. If `has_aat = 0`, the RP accepts requests without an AAT. Otherwise the AAT's public values pass [WIP-106 §4][wip-106]: `now`, `authenticator_provider_key_hash`, `min_build_version` and the `aat_flags` sub-fields.
5. `engine_config_hash` is the hash of a tuple the RP offered ([Engine Selection](#353-engine-selection)), from an active release manifest it verified under an active key of a trusted Engine Provider.

## 6. Rationale

1. **The Verifier interprets nothing.** Roles, frame semantics and thresholds live in the Engine and the consumer. A new capture method or credential format never changes the request or Flamingo Token.
2. **The AAT is verified in the Verifier.** [WIP-106 §3.7][wip-106] lets an attested verifier run its checks and report the public values. The Verifier already handles the media, and consumers save one signature verification. As `cdh` covers the exact `payload`, the AAT vouches for exactly the compared input.
3. **The AAT is optional.** Not every Authenticator has an Authenticator Provider that issues AATs, and requiring one would exclude them. The RP decides per request whether it accepts a Flamingo Token without one, as WIP-106 lets a circuit do with `has_aat`.
4. **Public values as claims.** The Flamingo Token carries the same public values an in-circuit AAT check would expose, so a consumer applies the same RP policy either way. Consumers read them directly instead of opening commitments; the Verifier is trusted to derive them from one request, as it is for the comparison. `build_version` stays private as WIP-106 requires; `min_build_version` takes its place.
5. **`SHA-256` over received bytes.** RPs and Issuers compute or check these hashes outside circuits, where `SHA-256` is available everywhere. They cover the bytes the Verifier received, not embeddings derived from them, which no other party could reproduce.
6. **Signature over claim values, not CBOR bytes.** The signature covers a Poseidon2 hash of the claim values, so a circuit verifies the Flamingo Token without parsing CBOR. Each claim keeps its own field element; the wider `t=16` permutation costs less than unpacking packed claims in-circuit.
7. **No Verifier time.** Most TEEs have no trusted wall clock. The Flamingo Token is bound in time by its single-use `nonce`, and `now` is only the AAT's public value, which the RP checks per [WIP-106][wip-106].
8. **Match strictness instead of scores.** A score's meaning depends on the model and the pair, so an RP cannot pick a meaningful threshold, and scores are biometric signals. An ordered strictness survives model upgrades and keeps scores out of every Flamingo Token.
9. **A separate Engine Provider signs the Engine.** Models may come from different parties, and trust in the models stays separate from trust in the capture environment. Pipelines only have meaning relative to an Engine release manifest.
10. **Engine configuration hash.** As in remote attestation ([RFC 9334](https://www.rfc-editor.org/rfc/rfc9334)), the Verifier reports a measurement and the RP appraises it against reference values, here signed release manifests. One hash gives RPs exact control over accepted configurations, keeps the individual values private, and lets circuits constrain its components.
11. **Signatures outside the Verifier.** The RP's allowlist and the Authenticator's `engine_hash` give the protection a signature check in the TEE would, so one audited Verifier image serves every Engine Provider without trusted keys in its measurement.

## 7. Alternatives Considered

1. **Running the models in a ZK circuit.** The Authenticator proves extraction and fraud detection in ZK. Rejected: proving these models is still computationally infeasible for most devices and most models, and the prover would need the model weights, while fraud detection relies on keeping them secret.
2. **MPC.** Parties jointly run the models over secret-shared inputs and weights. Rejected: it runs the models orders of magnitude slower and adds the assumption that the parties don't collude.

## 8. Security

1. **Post-quantum channel.** Biometrics never expire, so a party that records ciphertexts today, e.g. the host, must not be able to decrypt them with a future quantum computer. X-Wing combines ML-KEM-768 with X25519 and stays secure while either holds. Flamingo Token signatures are not post-quantum; a later forgery is useless because each Flamingo Token is bound to a single-use `nonce`.
2. **Authenticator integrity and missing AATs.** An AAT shows that a genuine Authenticator produced `payload`, which keeps modified or emulated Authenticators from injecting media. Without an AAT anyone can submit arbitrary media, and the verdict becomes an oracle for tuning attacks; RPs that accept `has_aat = 0` accept that risk.
3. **Unreviewed Engines.** A host may load any Engine, but an honest request reaches only the Engine whose hash the Authenticator chose, bound by `cdh`, and a Flamingo Token from another Engine carries an `engine_config_hash` no RP accepts. A leaked release key lets an attacker publish release manifests RPs and Authenticators accept until the Engine Provider marks the key `revoked`. Even a malicious Engine cannot export data directly (item 4).
4. **Closed Engine.** The Engine is not trusted with privacy. The sandbox removes its channels out, the per-request reset keeps one request's data from the next, and `debug_report` reaches only the requester and is forwarded only with the user's consent.
5. **Flamingo Token privacy.** `compared_entry_hash` of a credential entry is constant per user, so together with `aud` and `nonce` a Flamingo Token links a user to a specific RP request. Consumers MUST keep Flamingo Tokens private, e.g. as private inputs to [WIP-202][wip-202].
6. **Verifier keys.** The Verifier generates its signing key inside the TEE at boot from the hardware RNG and never exports it, so a key in a valid `signing_key_attestation` was generated by that measurement and each boot uses a new key. A key cannot be revoked; RPs stop accepting a compromised measurement, and `MAX_ATTESTATION_AGE` bounds how long its attestation stays acceptable.

## 9. Future Considerations

1. **Other TEEs.** Support for TEEs beyond AWS Nitro Enclaves, through attestation profiles that map each provider's document, root and measurement to the rules of [Attestation and Transport](#38-attestation-and-transport).

## 10. Backwards Compatibility

This WIP introduces a new interface; no existing contracts or functionality are affected.
