## 1. Abstract

This spec defines the **Flamingo Verifier** (**Verifier**), a trusted execution environment (TEE) service. It receives up to eight images or embeddings, a `pipeline` and a `match_strictness`, verifies the [WIP-106][wip-106] Authenticator Assertion Token (AAT) that vouches for them, and has a sandboxed biometric Engine check and compare them. If the Engine accepts, it signs a token over the request's policy values, the compared entries and the AAT's public values. [WIP-202][wip-202] consumes the token to prove the comparison to a Relying Party (RP) without revealing any entry.

## 2. Motivation

Comparing two embeddings is cheap. Getting an embedding anyone should believe is not.

Extraction runs a model over raw media, which is impractical in a ZK circuit. The checks that make an extracted embedding meaningful — image quality, Presentation Attack Detection, anti-fraud signals — are even worse. Many of these models need complex inputs and may rely on model obscurity.

An attested TEE keeps the inputs private from the operator and ties the result to approved code. The commitments let WIP-202 bind the processed bytes to the Issuer's and the RP's statements; the Verifier binds them to the Authenticator's. They do not establish that the live image came from a camera; that still depends on the Authenticator.

The Verifier also verifies the AAT, which removes that signature verification from the WIP-202 circuit. WIP-202 still verifies the Issuer's Credential and the account's authorization, so even a compromised Verifier cannot produce a proof without the account's authorization.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

1. The **Engine** is the sandboxed component of the Verifier that performs extraction, quality checks, Presentation Attack Detection and comparison. This spec defines none of them.
2. The Field ($F$), the hash function ($H_t$), the signature scheme (`BabyJubJub-EdDSA-Poseidon2`) and the `PublicKey` representation MUST follow [WIP-100][wip-100]. `R(d)` reads a 256-bit digest `d` as a big-endian integer modulo $p$.

### 3.1 Constants

| Constant | Value | Description |
| --- | --- | --- |
| `MAX_ENTRIES` | `8` | Entries per request. |
| `MAX_COMPARED` | `4` | Compared entries, fixed by the token layout; at most six comparisons. |
| `MAX_POLICY_ENTRIES` | `4` | Accepted pipeline entries in a [Token Verification](#310-token-verification) policy. |
| `DS_WIP_201` | `127603488023523044162070750169730750022280897185614` (`b"WORLD-ID/WIP-201/SIGN"`) | Domain separator for the token digest. |
| `MAX_ATTESTATION_AGE` | `86400` | Maximum age of a `signing_key_attestation` at `iat`, in seconds. |
| `HPKE_REQUEST_INFO` | `WORLD-ID/WIP-201/REQUEST` | HPKE `info` of a request. |
| `HPKE_RESPONSE_INFO` | `WORLD-ID/WIP-201/RESPONSE` | HPKE `info` of a response. |
| `KEYS_TAG` | `WORLD-ID/WIP-201/KEYS` | Tag of the attested key map. |
| `EAT_PROFILE` | `https://world.org/eat/flamingo/v1` | The `eat_profile` claim ([RFC 9711 §4.3.2](https://datatracker.ietf.org/doc/html/rfc9711#section-4.3.2)) of a token. |

### 3.2 Request

The request MUST be encrypted to the Verifier ([Attestation and Transport](#38-attestation-and-transport)). Its plaintext is a deterministic CBOR map:

| Field | Type | Description |
| --- | --- | --- |
| `version` | `uint` | MUST be `1`. |
| `payload` | bytes | Deterministic CBOR map of the fields below, as a byte string so the AAT commits to its exact bytes. |
| `assertion` | map | The AAT and its verification inputs ([Authenticator Assertion](#33-authenticator-assertion)). |
| `response_key` | bytes | A fresh X-Wing encapsulation key, used only for this request's response. |

| `payload` field | Type | Bounds | Description |
| --- | --- | --- | --- |
| `pipeline` | `uint` | `1..2^16` | Engine-defined pipeline, e.g. DeepFace with LightGuard. `0` is reserved. |
| `match_strictness` | `uint` | `< 2^8` | Engine-defined matching strictness within `pipeline`. |
| `meta` | bytes | ≤ 1 KiB | Request-level Engine hints, e.g. experiment flags. MUST NOT weaken `match_strictness`; anything that changes the verdict belongs in `pipeline`. |
| `entries` | array of maps | `1..=MAX_ENTRIES` | Inputs to the Engine, each `{ data, meta }`. |
| `entries[i].data` | bytes | | An encoded image or an embedding. |
| `entries[i].meta` | bytes | ≤ 256 bytes | How the Engine reads `data`, e.g. which frame of a capture it is. |
| `compare` | array of `uint` | `2..=MAX_COMPARED` distinct indices into `entries` | Ordered; the Engine compares every pair. |

1. The Verifier interprets none of the `payload` fields and forwards them to the Engine. Roles (Credential item, live frame, challenge) are fixed by `pipeline` through positions in `compare`.
2. The Verifier MUST reject a request of any other shape, exceeding a bound, or whose `compare` repeats or names an out-of-range index. It MAY impose further byte limits on `entries[].data`.

### 3.3 Authenticator Assertion

`assertion` carries the AAT and the inputs [WIP-106 §3.7][wip-106] defines for its verification:

| Field | Visibility | Type | Description |
| --- | --- | --- | --- |
| `aat` | Private | bytes | The AAT in its CWT encoding, carrying `exp`, `sec_flags` and `sig`. |
| `blind` | Private | Field element | See [WIP-106 §3.3][wip-106]. |
| `trust_anchor_key` | **Public** | `PublicKey` | The Authenticator Provider's key, chosen by the RP. |
| `aud` | **Public** | Field element | The `rpId` of the request. |
| `nonce` | **Public** | Field element | The nonce of the request. |
| `min_build_version` | **Public** | uint32 | Minimum `build_version`, chosen by the RP. |

The Authenticator forwards the RP's public values, and the RP checks them in the token ([Reference Verification](#4-reference-verification)). The Verifier computes `cdh = R(SHA-256(payload))` itself.

Before calling the Engine, the Verifier MUST perform the following checks and reject the request if any fails:

1. **Encoding**. `aat` MUST decode per [WIP-106 §3.4.1][wip-106].
2. **Verification**. Every check of [WIP-106 §3.7][wip-106] MUST hold, with `now = iat` and the `cdh` above, and the AAT's `aat_commitment` MUST equal the one the Verifier computes.

Every request MUST carry an AAT; this WIP does not use WIP-106's `has_aat = 0` case. The private values (`exp`, `sec_flags`, `sig`, `aat_commitment`, `blind` and `build_version`) MUST NOT appear in the token or the response, and `assertion` MUST NOT be passed to the Engine.

### 3.4 Response

| Variant | Contents |
| --- | --- |
| `Success` | `token` ([Token](#36-token)), `signing_key_attestation` ([Attestation and Transport](#38-attestation-and-transport)), `debug_report` |
| `Failed` | `error`, `debug_report` |

1. The response MUST be encrypted to the requester and MUST be padded to a fixed length, hiding the outcome and the report size.
2. `error` is implementation-defined and bounded in size; it comes from the Verifier or, passed through, from the Engine.
3. `debug_report` is optional Engine output outside the token. The Verifier MAY truncate or omit it. It may carry biometric-derived data, so clients MUST NOT forward it.
4. The Verifier MUST emit a token only when the Engine returns `Pass`.

### 3.5 Engine

1. Each `pipeline` defines the entry layout, how each entry's `meta` is read, and which checks run. Each `match_strictness` of a pipeline defines the match thresholds for every compared pair. Presentation Attack Detection and quality checks are fixed by `pipeline` and do not vary with `match_strictness`.
2. Within one pipeline, a higher `match_strictness` MUST be at least as strict for every compared pair. Strictness values of different pipelines are not comparable.
3. **Engine provider.** An Authenticator Provider ([WIP-106][wip-106]) provides the Engine and signs each release as `(engine_hash, engine_version, pipelines)`, where `engine_hash` is the `SHA-256` of the Engine bundle, `engine_version` a monotonic `uint32`, and `pipelines` each pipeline's `compare` layout and strictness values. The Verifier MUST pin the provider's release key in its attested measurement, and MUST refuse an Engine whose release signature fails or whose `engine_hash` differs from the received bundle.
4. The Verifier MUST pass the `payload` fields to the Engine unchanged. The Engine MUST return `Pass`, meaning every check passed and every compared pair cleared `match_strictness`, or an error, either with an optional `debug_report` and never with scores. This WIP does not specify the encoding.

#### 3.5.1 Isolation

The Engine sees raw biometrics and runs closed, injected models. The Verifier MUST give it no network access, no writable persistent storage, no process creation and no access to the Verifier's keys, and only one bounded request-response channel. See the [reference implementation's sandbox](https://github.com/worldcoin/flamingo/tree/main/verifier/sandbox-client) for one way to meet these requirements.

### 3.6 Token

A token is a CWT ([RFC 8392](https://datatracker.ietf.org/doc/html/rfc8392)) in an untagged `COSE_Sign1`, encoded as deterministic CBOR ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)).

1. The protected header MUST contain `alg` (label `1`) = `-65537` (Private Use, `BabyJubJub-EdDSA-Poseidon2`) and `kid` (label `4`) = the compressed signing public key.
2. The signature MUST be a `BabyJubJub-EdDSA-Poseidon2` signature per [WIP-100][wip-100] over the [signed digest](#362-signed-digest).

#### 3.6.1 Claims

The payload MUST contain exactly these claims, in the bytewise order of their encoded keys.

| Claim | Key | Encoded key | Value |
| --- | --- | --- | --- |
| `iat` | `6` | `06` | Time of the comparison, seconds since the Unix epoch. |
| `eat_profile` | `265` | `19 01 09` | `EAT_PROFILE`. |
| `pipeline` | `-90000` | `3a 00 01 5f 8f` | `pipeline` from the request. |
| `match_strictness` | `-90001` | `3a 00 01 5f 90` | `match_strictness` from the request. |
| `compared_entry_hash_k`, `k = 0..3` | `-90002 - k` | `3a 00 01 5f 91` … `94` | `R(SHA-256(entries[compare[k]].data))`, or `0` if `compare` has no position `k`. |
| `aud` | `-90006` | `3a 00 01 5f 95` | `aud` of the verified AAT. |
| `nonce` | `-90007` | `3a 00 01 5f 96` | `nonce` of the verified AAT. |
| `trust_anchor_key_x`, `trust_anchor_key_y` | `-90008`, `-90009` | `3a 00 01 5f 97`, `98` | Coordinates of the `trust_anchor_key` that verified the AAT. |
| `aat_flags` | `-90010` | `3a 00 01 5f 99` | `platform + 2^8 * sec_level + 2^16 * min_build_version + 2^48 * sec_meta + 2^51 * user_presence`, the [WIP-106][wip-106] `sec_flags` layout with the public `min_build_version` in place of `build_version`. |
| `engine_version` | `-90011` | `3a 00 01 5f 9a` | `engine_version` of the signed Engine release that ran. |

1. `iat`, `pipeline`, `match_strictness`, `aat_flags` and `engine_version` are CBOR uints; `iat` is a 4-byte uint (`0x1a`). All other claims except `eat_profile` are 32-byte byte strings, the canonical big-endian encoding of a field element.
2. `eat_profile` is not in the signed digest and MUST be treated as an untrusted hint.
3. `iat` MUST come from a clock covered by the attestation (e.g. the Nitro NSM), never from the host or the request. It is also the `now` of the AAT verification.

#### 3.6.2 Signed Digest

The signed message is **not** the COSE `Sig_structure`. It MUST be output element `1` of the Poseidon2 `t=16` permutation over:

```
[DS_WIP_201, iat, pipeline, match_strictness,
 compared_entry_hash_0, compared_entry_hash_1, compared_entry_hash_2, compared_entry_hash_3,
 aud, nonce, trust_anchor_key_x, trust_anchor_key_y, aat_flags, engine_version, 0, 0]
```

Two slots remain free.

### 3.7 Verifiability and Reproducible Builds

The Verifier image MUST be reproducibly built, so its measurement can be checked against source. Engines are injected at runtime and bound by their signed release ([Engine](#35-engine)) and [Isolation](#351-isolation). Multiple hardware providers MUST be supported, each with its own attestation and the same token; RPs choose the attestation roots they trust.

### 3.8 Attestation and Transport

The Verifier generates its channel key and its token signing key at boot and attests both in one document, the `signing_key_attestation`. For AWS Nitro it is the Nitro attestation document, a `COSE_Sign1` chaining to the AWS Nitro Root G1, with:

| Field | Value |
| --- | --- |
| `public_key` | The commitment to the channel's X-Wing key. |
| `user_data` | Deterministic CBOR map `{ tag: KEYS_TAG, signing_key, engine_hash, engine_version }`; `signing_key` is the token's `kid`. |
| `pcrs` | The measurement: PCR0, PCR1, PCR2, and PCR8 for a signed image. |
| `timestamp` | Time of attestation. |

1. **Request**. The Authenticator MUST verify the document before sending a request, then seal the request plaintext with HPKE ([RFC 9180](https://www.rfc-editor.org/rfc/rfc9180)) base mode, the X-Wing KEM and `info = HPKE_REQUEST_INFO`, to the committed channel key. The request is `enc || ciphertext`.
2. **Response**. The Verifier MUST seal the padded response with HPKE to `response_key` and `info = HPKE_RESPONSE_INFO`. Only the requester holds `response_key`, so the response is bound to its request; a `Success` is authenticated by its token.
3. **Replay**. The host can replay a request. That yields at most another token for the same AAT `nonce`, which the RP rejects as reused.
4. **Refresh**. The Verifier MUST re-attest so that every token has `timestamp <= iat <= timestamp + MAX_ATTESTATION_AGE` for some document of its boot.
5. **Carrying**. A proof or message that relies on a token MUST carry the token's `signing_key_attestation`, unless the consumer obtains it from the [Key Registry](#39-key-registry).

One document covers every token of a Verifier boot, so consumers MAY cache it by key. It identifies the Verifier instance, not the user.

### 3.10 Token Verification

Token verification is specified as a component for circuits (e.g. [WIP-202][wip-202]); a consumer outside a circuit MUST perform the same checks ([Reference Verification](#4-reference-verification)). The component MUST introduce these inputs.

| Input | Visibility | Type | Description |
| --- | --- | --- | --- |
| `verifier_key` | **Public** | `PublicKey` | Token signing key, checked against its `signing_key_attestation`. |
| `now` | **Public** | uint32 | Current time, in seconds since the Unix epoch. |
| `comparison_age_max` | **Public** | uint32 | Maximum age of `iat` the RP accepts. |
| `aud`, `nonce` | **Public** | Field element | The RP's request. |
| `trust_anchor_key` | **Public** | `PublicKey` | Allowlisted Authenticator Provider key. |
| `platform`, `sec_level`, `sec_meta`, `user_presence` | **Public** | uint8 | AAT sub-fields, see [WIP-106 §3.5][wip-106]. |
| `min_build_version` | **Public** | uint32 | Minimum `build_version` the RP accepts. |
| `policy` | **Public** | [(`pipeline`, `min_match_strictness`, `min_engine_version`); `MAX_POLICY_ENTRIES`] | Accepted entries; unused entries have `pipeline = 0`. |
| `iat`, `pipeline`, `match_strictness`, `engine_version` | Private | uint | From the token. |
| `compared_entry_hash` | Private | [Field element; 4] | From the token. |
| `sig` | Private | Signature | The token signature. |

The circuit MUST enforce:

1. **Signature**. Compute the [signed digest](#362-signed-digest) from the inputs and verify `sig` under `verifier_key` per [WIP-100 §3.5.1][wip-100].
2. **Freshness**. `iat`, `now` and `comparison_age_max` MUST be less than $2^{32}$. The circuit MUST enforce `iat <= now` and `now - iat <= comparison_age_max`.
3. **Request binding**. The digest MUST use the public `aud`, `nonce` and `trust_anchor_key`.
4. **Assertion flags**. The digest MUST use `aat_flags = platform + 2^8 * sec_level + 2^16 * min_build_version + 2^48 * sec_meta + 2^51 * user_presence`, with each sub-field range-checked to its width.
5. **Policy**. `pipeline`, `match_strictness` and `engine_version` MUST satisfy one `policy` entry: `pipeline` equal, `match_strictness >= min_match_strictness` and `engine_version >= min_engine_version`. `pipeline` MUST NOT be `0`.

The component returns `compared_entry_hash`. The embedding circuit MUST bind each hash its statement depends on to its own inputs (e.g. the Issuer's claim or the RP's challenge).

## 4. Reference Verification

A consumer accepts a token if:

1. The `signing_key_attestation` chains to a hardware provider root the RP accepts (e.g. the AWS Nitro Root G1), reports a measurement the RP accepts, satisfies `timestamp <= iat <= timestamp + MAX_ATTESTATION_AGE`, and its `user_data` carries `KEYS_TAG`, the token's signing key, its `engine_version`, and an `engine_hash` of an active release in the Authenticator Provider's metadata. `kid` is only a hint.
2. The signature verifies under that key.
3. `iat` is within the RP's maximum age.
4. `aud` and `nonce` equal the RP's request, and the RP rejects a reused `nonce`.
5. `trust_anchor_key` is allowlisted and active in the WIP-106 Authenticator Metadata.
6. `min_build_version`, the other `aat_flags` sub-fields, `pipeline`, `match_strictness` and `engine_version` meet RP policy.

## 5. Rationale

1. **Hashes over received bytes.** No other party ever signed an extracted embedding, so nothing could be bound to its hash.
2. **The Verifier interprets nothing.** Roles, frame semantics and thresholds live in the Engine and the consumer. A new capture method or credential format never changes the request or token.
3. **The AAT is verified in the Verifier.** [WIP-106 §3.7][wip-106] lets an attested verifier run its checks and report the public values. The Verifier already handles the media, and consumers save one signature verification. As `cdh` covers the exact `payload`, the AAT vouches for exactly the compared input.
4. **Public values as claims.** The token carries the same public values an in-circuit AAT check would expose, so a consumer applies the same RP policy either way. `build_version` stays private as WIP-106 requires; `min_build_version` takes its place.
5. **Direct claims.** Consumers read signed claims directly instead of opening commitments; the Verifier is trusted to derive them from one request, as it is for the comparison.
6. **Raw `SHA-256` entry hashes.** Issuers already sign `SHA-256` digests, e.g. in a PCP `hashes.json`, so a consumer binds to them without computing `SHA-256`.
7. **Field-element digest.** A consumer verifies the token without parsing CBOR. Claims stay unpacked: `t=16` costs about 865 ACIR opcodes against 505 for `t=8`, and leaves room for later claims.
8. **`iat` rather than `exp`.** The RP needs the comparison's age and chooses the maximum; without it a comparison is replayable forever.
9. **All pairs are compared.** Matching the live capture and the challenge separately to the Credential does not establish that they match each other.
10. **Match strictness instead of thresholds.** A score's meaning depends on the model and the pair, so an RP cannot pick a meaningful number; an ordered strictness survives model upgrades.
11. **The Authenticator Provider signs the Engine.** It already vouches for the capture environment, and pipelines only have meaning relative to an Engine release. A pinned release key turns `engine_version` into an attested statement instead of an operator's claim.
12. **No scores.** Similarity scores are biometric signals and stay out of every token.

## 6. Security

1. **Verifier trust.** The RP trusts the Verifier and its Engine for the comparison. A compromised Verifier can sign any claim values, including the AAT result, but cannot supply an account's authorization or replace the Issuer's Credential signature, which [WIP-202][wip-202] verifies.
2. **Pipelines are identifiers.** Naming a pipeline does not establish its accuracy; the RP trusts the attested Verifier to run it honestly.
3. **Live capture.** Neither the TEE nor [WIP-202][wip-202] removes trust in the Authenticator for the source and freshness of the live image.
4. **Verifier visibility.** The TEE sees the media, the AAT, `aud` and `nonce`, so it learns which RP a request is for. `blind` still hides the RP from the Authenticator Provider.
5. **Token privacy.** `compared_entry_hash` of a credential entry is constant per user, and the token carries `aud` and `nonce`. Consumers MUST keep the token and these claims private.
