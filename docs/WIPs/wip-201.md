## 1. Abstract

This spec defines the **Flamingo Verifier** (also called **Verifier** in the context of this spec): a trusted execution environment (TEE) service that receives a credential item, a live capture and optionally a challenge item, and extracts and compares their embeddings. It signs a token carrying the item commitments, pipeline commitment, comparison scores and request context.

The token is its only output. [WIP-202][wip-202] consumes it to prove the comparison to a Relying Party without revealing any item.

## 2. Motivation

Comparing two embeddings is cheap. Getting an embedding anyone should believe is not.

Extraction runs a model over raw media, which is impractical in a ZK circuit. The checks that make an extracted embedding meaningful — image quality, Presentation Attack Detection, anti-fraud signals — are even worse. Much of these models require complex inputs and advanced signals, and may even rely on model obscurity.

Running extraction and comparison in an attested Trusted Execution Environment is intended to keep the inputs private from the service operator and tie the result to approved code. The commitments let WIP-202 bind the processed bytes to the Issuer, Authenticator and RP statements. They do not establish that the live image came from a camera; that still depends on the Authenticator.

WIP-202 independently verifies the Authenticator Provider's assertion, the Issuer's Credential and the account's authorization. The assertion uses a ZK-friendly signature; platform evidence is checked by the Authenticator Provider outside the circuit. Even a compromised Verifier cannot produce a proof for a registered account without that account's authorization for the request.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

### 3.1 Inputs

A request MUST carry the RP's nonzero `nonce`, `rp_id`, `request_issued_at`, a credential item and a live capture, and MAY carry a challenge item. Absence of the challenge selects the 2-way flow. The request MUST be encrypted to the Verifier. Before sending media, the Authenticator MUST verify the Verifier's attestation and bind the encrypted channel to that attested environment. The attestation and channel protocol remain to be specified.

| Item | Supplied by |
| --- | --- |
| `credential_image` | the Authenticator, the Orb PCP's original `thumbnail.png` for WIP-202 |
| `live_image` | the Authenticator, captured at proof time |
| `challenge_image` | the RP |
| `nonce`, `rp_id`, `request_issued_at` | the RP, forwarded by the Authenticator |

The AAT, its blinding factor, PCP `hashes.json`, full Credential, account private key, account authorization signature and registry witnesses MUST NOT be sent to the Verifier. They remain with the Authenticator for local proof generation.

#### 3.1.1 Request window

The Verifier MUST require a nonzero field-element `nonce`, an unsigned 64-bit `rp_id` and a nonzero unsigned 32-bit `request_issued_at`. It MUST derive `request_expires_at = request_issued_at + REQUEST_LIFETIME_SECS`, using WIP-202's 300-second lifetime, and reject a result outside the unsigned 32-bit range. It signs the nonce, RP and deadline together with its results. The RP checks its own clock at acceptance; the Verifier needs no separate clock or lifetime policy.

### 3.2 Commitments

The Verifier MUST emit one commitment per item, over the bytes it received. It MUST NOT commit to an embedding it extracted from an image.

WIP-202 binds the credential commitment to the thumbnail digest in the Issuer-committed PCP `hashes.json`, the live commitment to the provider-signed AAT, and the challenge commitment to the RP's public input. It also verifies account authorization over the complete Verifier result. See [WIP-202 Commitments](wip-202.md#35-commitments).

### 3.3 Extraction, Quality and Presentation Attack Detection

The Verifier provider defines the extraction models, quality checks and Presentation Attack Detection. The token's `pipeline_commitment` identifies the models and full pipeline configuration used to process the request, so the RP can decide whether to accept them. The Verifier MUST NOT emit a token if its required input checks fail.

#### 3.3.1 Pipeline commitment

`pipeline_commitment` MUST be the [WIP-100][wip-100] Poseidon2 sponge over a versioned pipeline manifest, using the variable domain separator `WORLD-ID/WIP-201/PIPELINE`. The manifest MUST be encoded as deterministic CBOR, following RFC 8949 §4.2.1. It identifies the whole configured pipeline, including its branching rules, rather than one request's execution path. The same pipeline and configuration MUST produce the same commitment across requests.

The manifest MUST cover:

- Cryptographic digests of all pipeline code, model architectures and weights, including runtime-loaded artifacts. Model names or version labels alone are insufficient.
- Preprocessing, extraction, quality, Presentation Attack Detection, anti-fraud and comparison stages, their order and input roles, and the conditions under which each stage runs or is skipped. Every comparison required by §3.4 MUST run.
- Pipeline configuration, including its own check thresholds, comparison metrics, normalization and score scales.

The manifest MUST NOT contain user or device identifiers, raw assertions, request media, the nonce, request-supplied parameters or comparison results. The optional RP threshold in §3.4 is a request parameter; it does not change the pipeline commitment.

The attested Verifier code MUST compute this commitment from the pipeline's artifacts and configuration, verifying runtime-loaded artifacts against the manifest before using them. Code identified in the manifest MUST either be covered by the verified attestation measurement or have its digest verified by attested code before it runs. The Verifier MUST NOT use a caller- or operator-supplied value as the commitment. It MUST execute the described pipeline and bind its commitment to the same token as the request nonce, input commitments and scores. It MUST NOT emit a token if an executed stage or configuration is missing from, or differs from, the manifest, or if a stage ran or was skipped contrary to the stated conditions.

RPs can approve pipeline commitments in advance from their manifests and check the public commitment against that policy. This does not require fetching or processing a manifest for every proof. The commitment identifies what the Verifier attests it ran; it does not establish model accuracy or independently prove execution.

### 3.4 Comparison

The Verifier MUST compare every pair of supplied items: live against credential and, when a challenge is present, challenge against credential and live against challenge. It MUST sign a score for each pair. Scores MUST be unsigned 64-bit integers, with larger values indicating greater similarity. The provider MUST define a stable metric, normalization and score scale, shared by all three pairs, for each Verifier key, and include those definitions in every pipeline manifest whose commitment that key signs. This lets the RP choose one meaningful threshold even when it delegates pipeline selection.

A request MAY carry a minimum threshold so the Verifier can decline to emit a token for a comparison that would fail [WIP-202][wip-202] anyway. This is a convenience. The threshold that matters is the public input of [WIP-202][wip-202]; one in this request carries no guarantee.

### 3.5 Token

The output is a CWT in an untagged `COSE_Sign1`, encoded as deterministic CBOR. Its protected header MUST contain `alg` (label `1`) = `-65537` for `BabyJubJub-EdDSA-Poseidon2` and `kid` (label `4`) = the compressed signing public key. The signature MUST follow WIP-100 over the digest in §3.5.2.

#### 3.5.1 Token claims

| Claim | Key | Encoded key | Description |
| --- | --- | --- | --- |
| `nonce` | `10` | `0a` | The RP request nonce, per [RFC 9711 §4.1](https://www.rfc-editor.org/rfc/rfc9711.html#section-4.1). MUST be nonzero. |
| `eat_profile` | `265` | `19 01 09` | URI identifying the profile, as [RFC 9711](https://datatracker.ietf.org/doc/rfc9711/) §4.3.2. MUST be `https://world.org/eat/evt/v1`. |
| `credential_commitment` | `-90000` | `3a 00 01 5f 8f` | SHA-256 digest of the original `credential_image` bytes, reduced into the field as defined by WIP-202. |
| `live_commitment` | `-90001` | `3a 00 01 5f 90` | Commitment to `live_image`. |
| `challenge_commitment` | `-90002` | `3a 00 01 5f 91` | Commitment to `challenge_image`. `0` in the 2-way flow. |
| `similarity_live` | `-90003` | `3a 00 01 5f 92` | Score for live against credential. |
| `similarity_challenge` | `-90004` | `3a 00 01 5f 93` | Score for challenge against credential. `0` when `challenge_commitment` is `0`. |
| `pipeline_commitment` | `-90005` | `3a 00 01 5f 94` | Commitment to the models and full pipeline configuration for this request, per [§3.3.1](#331-pipeline-commitment). MUST be nonzero; there is no absent-pipeline value. |
| `rp_id` | `-90006` | `3a 00 01 5f 95` | RP identifier from the request. |
| `request_expires_at` | `-90007` | `3a 00 01 5f 96` | Request deadline derived in §3.1.1. |
| `similarity_live_challenge` | `-90008` | `3a 00 01 5f 97` | Score for live against challenge. `0` when `challenge_commitment` is `0`. |

The claims MUST appear in the order above, which is the bytewise lexicographic order of their encoded keys required by deterministic CBOR ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)).

The private-use keys occupy a `-90000` block, distinct from the `-70000` block [WIP-106][wip-106] uses. All are below `-65536` as the [CWT Claims registry](https://www.iana.org/assignments/cwt/cwt.xhtml) requires for private use.

Every claim value except `eat_profile` MUST be a single field element, encoded as a 32-byte CBOR byte string in canonical big-endian. `rp_id` and `request_expires_at` are private-use claims with this field encoding; they are not the registered CWT `aud` and `exp` claims. `eat_profile` is a text string and is excluded from the [signed digest](#352-signed-digest); it MUST be treated as an untrusted hint outside a circuit.

The Verifier MUST process the supplied inputs for the received nonce and sign all claims together. It MUST NOT reissue an earlier result under a new nonce. WIP-202 binds the token's nonce, RP and deadline to the RP's outstanding request, so the token needs no separate comparison timestamp or expiry policy.

The nonce binds the comparison to the request; it does not establish when the input image was captured. Capture freshness still depends on the Authenticator.

#### 3.5.2 Signed digest

The signed message is **not** the COSE `Sig_structure`. It MUST be the WIP-100 fixed-arity hash $H_{16}$ over the ten signed claim values, in deterministic CBOR map-key order ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)). The input state is:

```
[DS_WIP_201, nonce, credential_commitment, live_commitment, challenge_commitment,
 similarity_live, similarity_challenge, pipeline_commitment, rp_id, request_expires_at,
 similarity_live_challenge, 0, 0, 0, 0, 0]
```

The digest is output state element `1`.

| Constant | Value | Description |
|----------|-------|-------------|
| `DS_WIP_201` | `127603488023523044162070750169730750022280897185614` (`b"WORLD-ID/WIP-201/SIGN"`) | Domain separator for this ten-claim Verifier token digest. |

Because the digest is taken over field elements, a verifying circuit neither parses nor reconstructs CBOR. The claim encodings above are still required on the wire.

The `t=16` state holds the domain separator, ten signed claims and five zero padding elements. The claim count and order are fixed for this domain separator. WIP-202 also uses this digest as the result the account authorizes.

### 3.6 Verifiability and reproducible builds

OCI verification, reproducible builds. Models may be injected at runtime but MUST be covered by `pipeline_commitment`. The attested code must ensure models have no network access or disk persistence to exfiltrate information.

The design MUST support multiple hardware providers, with provider-specific attestation verified out of band and a common token interface for WIP-202. RPs choose which hardware providers and attestation roots they trust.

## 4. Rationale

**Commitments are over received bytes.** Committing to an extracted embedding would produce a value no other party ever signed, leaving [WIP-202][wip-202] nothing to bind it to.

**Every pair is compared.** Matching the live capture and challenge separately to the Credential does not establish that they match each other. The third score lets WIP-202 enforce that directly.

## 5. Security

The RP trusts the Verifier for the comparison pipeline. A compromised Verifier can fabricate pipeline commitments and scores. It still cannot supply a registered account's authorization over that result, forge the Authenticator Provider's assertion or replace the Issuer's Credential signature. WIP-202 verifies those independently.

The signed pipeline commitment lets an RP choose which models and pipeline it accepts, but the RP still trusts the attested Verifier to identify and execute them honestly. Identifying a model does not establish its accuracy. Neither the TEE nor WIP-202 removes trust in the Authenticator for the source and freshness of the live image. The TEE sees the media, nonce and RP identifier, but does not receive the AAT or its blinding factor.
