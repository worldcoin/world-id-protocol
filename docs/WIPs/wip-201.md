## 1. Abstract

This spec defines the **Flamingo Verifier** (**Verifier**), a trusted execution environment (TEE) service. It receives up to eight images or embeddings, a `pipeline` and a `match_strictness`, verifies the [WIP-106][wip-106] Authenticator Assertion Token (AAT) that vouches for them if one is present, and has a sandboxed biometric Engine check and compare them. If the Engine accepts, it signs a **Flamingo Token** (**token**) over the request's policy values, the compared entries and the AAT's public values, if any. [WIP-202][wip-202] consumes the token to prove the comparison to a Relying Party (RP) without revealing any entry.

## 2. Motivation

Many Proof-of-Human applications like deep fake prevention or human presence verification require A) running fraud detection models like presentation attack detection (PAD) on a set of input images and B) comparing images using embedding models, e.g., to verify that the person on a stream is the same as the one performing a liveness check on a phone.

Since biometric data is highly sensitive, ideally these images would never leave a user's local device. Running models locally has severe downsides from a security perspective, though. First, a mobile device's output is not trustworthy, e.g., a jailbroken device could report that fraud detection and embedding comparison were performed, while simply running a spoofed app that does not perform them at all. Therefore, an RP cannot be sure that the claimed checks have actually been executed. Additionally, fraud detection models' security relies on obscurity and obtaining the model weights, or even just the model architecture, opens up a wide range of attack vectors.

To achieve verifiability in a privacy-preserving way, this document introduces a general approach that runs fraud detection models and embedding models in an attested TEE. This allows users to verify that the TEE operator is not able to access any biometric data, and a signature by the TEE proves to RPs that all claimed checks have been correctly executed. The Verifier image MUST be open source and reproducibly built, so anyone can check that its attested measurement matches the source and that no raw media or embeddings leave the TEE. Fraud detection models cannot be open, so the Verifier runs them as a closed Engine inside a kernel-enforced sandbox that has no network or storage access. A signed release from the Authenticator Provider fixes which Engine runs.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

1. The **Engine** is the sandboxed component of the Verifier that performs extraction, quality checks, Presentation Attack Detection and comparison. This spec defines none of them.
2. The **Engine Provider** builds the Engine and signs its releases. It MAY be the same organization as an Authenticator Provider ([WIP-106][wip-106]).
3. The Field ($F$), the hash function ($H_t$), the signature scheme (`BabyJubJub-EdDSA-Poseidon2`) and the `PublicKey` representation MUST follow [WIP-100][wip-100]. `R(d)` reads a 256-bit digest `d` as a big-endian integer modulo $p$.

### 3.1 Constants

| Constant | Value | Description |
| --- | --- | --- |
| `MAX_ENTRIES` | `8` | Entries per request. |
| `MAX_COMPARED` | `4` | Compared entries, fixed by the token layout; at most six comparisons. |
| `MAX_POLICY_ENTRIES` | `4` | Accepted pipeline entries in a [Flamingo Token Verification](#39-flamingo-token-verification) policy. |
| `DS_WIP_201` | `127603488023523044162070750169730750022280897185614` (`b"WORLD-ID/WIP-201/SIGN"`) | Domain separator for the token digest. |
| `MAX_ATTESTATION_AGE` | `86400` | Maximum age of a `signing_key_attestation` at `iat`, in seconds. |
| `MAX_DEBUG_REPORT` | `65536` | Maximum `debug_report` size, in bytes. |
| `CHANNEL_DOMAIN` | `flamingo-verifier/matches/v2` | Domain of the request channel. |
| `CHANNEL_KEY_DOMAIN` | `pontifex/public-key-commitment/v1\0` | Domain of the channel key commitment. |
| `EAT_PROFILE` | `https://world.org/eat/flamingo/v1` | The `eat_profile` claim ([RFC 9711 §4.3.2](https://datatracker.ietf.org/doc/html/rfc9711#section-4.3.2)) of a token. |

### 3.2 Request

The request MUST be encrypted to the Verifier ([Attestation and Transport](#38-attestation-and-transport)). Its plaintext is a deterministic CBOR map:

| Field | Type | Description |
| --- | --- | --- |
| `version` | `uint` | MUST be `1`. |
| `payload` | bytes | Deterministic CBOR map of the fields below, as a byte string so the AAT commits to its exact bytes. |
| `aud` | Field element | The `rpId` of the request. |
| `nonce` | Field element | The nonce of the request. MUST NOT be `0`. |
| `assertion` | map, optional | The AAT and its verification inputs ([Authenticator Assertion](#33-authenticator-assertion)). |

| `payload` field | Type | Bounds | Description |
| --- | --- | --- | --- |
| `pipeline` | `uint` | `1..2^16` | Engine-defined pipeline. The authenticator provider may use this e.g., to select different pipelines based on the device capturing live images. |
| `match_strictness` | `uint` | `< 2^8` | Matching strictness level, defined by the Engine Provider for all pipelines. |
| `meta` | bytes | ≤ 1 KiB | Request-level Engine hints, e.g. experiment flags. MUST NOT weaken `match_strictness`; anything that changes the verdict belongs in `pipeline`. |
| `entries` | array of maps | `1..=MAX_ENTRIES` | Inputs to the Engine, each `{ data, meta }`. |
| `entries[i].data` | bytes | | An encoded image or an embedding. |
| `entries[i].meta` | bytes | ≤ 256 bytes | How the Engine reads `data`, e.g. which frame of a capture it is. |
| `compare` | array of `uint` | `2..=MAX_COMPARED` distinct indices into `entries` | Ordered; the Engine compares every pair. |
| `engine_key` | bytes | 32 bytes | [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638) `SHA-256` thumbprint of the Engine Provider release key the Authenticator requires. |

1. The Verifier interprets none of the `payload` fields and forwards them to the Engine. Roles (Credential item, live frame, challenge) are fixed by `pipeline` through positions in `compare`.
2. The Verifier MUST reject a request of any other shape, exceeding a bound, or whose `compare` repeats or names an out-of-range index. It MAY impose further byte limits on `entries[].data`.

### 3.3 Authenticator Assertion

`assertion` is OPTIONAL. Authenticators with nothing to attest to, e.g. web Authenticators, omit it. If present, it carries the AAT and the remaining inputs [WIP-106 §3.7][wip-106] defines for its verification, with `aud` and `nonce` taken from the request:

| Field | Visibility | Type | Description |
| --- | --- | --- | --- |
| `aat` | Private | bytes | The AAT in its CWT encoding, carrying `exp`, `sec_flags` and `sig`. |
| `blind` | Private | Field element | See [WIP-106 §3.3][wip-106]. |
| `authenticator_provider_key` | **Public** | `PublicKey` | The Authenticator Provider's key, chosen by the RP. |
| `min_build_version` | **Public** | uint32 | Minimum `build_version`, chosen by the RP. |

The Authenticator forwards the RP's public values, and the RP checks them in the token ([Reference Verification](#4-reference-verification)). The Verifier computes `cdh = R(SHA-256(payload))` itself.

If `assertion` is present, the Verifier MUST perform the following checks before calling the Engine and reject the request if any fails:

1. **Encoding**. `aat` MUST decode per [WIP-106 §3.4.1][wip-106].
2. **Verification**. Every check of [WIP-106 §3.7][wip-106] MUST hold, with `now = iat` and the `cdh` above, and the AAT's `aat_commitment` MUST equal the one the Verifier computes.

The Verifier MUST set `has_aat` to `1` if it verified an AAT and to `0` otherwise. With `has_aat = 0`, `authenticator_provider_key_hash` and `aat_flags` MUST be `0`, as in WIP-106's `has_aat = 0` case. The private values (`exp`, `sec_flags`, `sig`, `aat_commitment`, `blind` and `build_version`) MUST NOT appear in the token or the response, and `assertion` MUST NOT be passed to the Engine.

### 3.4 Response

| Variant | Contents |
| --- | --- |
| `Success` | `token` ([Flamingo Token](#36-flamingo-token)), `signing_key_attestation` ([Attestation and Transport](#38-attestation-and-transport)), `debug_report` |
| `Failed` | `error`, `debug_report` |

1. The response MUST be encrypted to the requester and MUST be padded to a fixed length, hiding the outcome and the report size.
2. `error` is implementation-defined and bounded in size; it comes from the Verifier or, passed through, from the Engine.
3. `debug_report` is optional Engine output outside the token. The Verifier MUST omit a report larger than `MAX_DEBUG_REPORT`. It may carry biometric-derived data: a client MUST NOT forward it without the user's explicit consent, and only to the Engine Provider. It SHOULD let the user inspect a report before forwarding it.
4. The Verifier MUST emit a token only when the Engine returns `Pass`.

### 3.5 Engine

1. Each `pipeline` defines the entry layout, how each entry's `meta` is read, and which checks run. Each pipeline sets the match thresholds that meet each `match_strictness` level. Fraud checks are fixed by `pipeline` and do not vary with `match_strictness`.
2. Each release defines the `match_strictness` levels independently of `pipeline`: every pipeline MUST support every level, a level MUST mean the same in every pipeline, and a higher level MUST be at least as strict for every compared pair. The Engine MUST reject a `match_strictness` the release does not define.
3. **Engine Provider.** The Engine Provider signs each release ([Engine Releases](#352-engine-releases)). A Verifier MAY load Engines of several Engine Providers. It MUST refuse an Engine whose release signature fails or whose `engine_hash` differs from the received bundle, and MUST reject a request unless it loaded an Engine whose release key has the thumbprint `engine_key`.
4. The Verifier MUST pass the `payload` fields to the Engine unchanged. The Engine MUST return `Pass`, meaning every check passed and every compared pair cleared `match_strictness`, or an error, either with an optional `debug_report` and never with scores. This WIP does not specify the encoding.

#### 3.5.1 Isolation

The Engine sees raw biometrics and runs closed, injected models. The Verifier MUST give it no network access, no writable persistent storage, no process creation and no access to the Verifier's keys, and only one bounded request-response channel. Each request MUST run in a fresh or reset Engine instance, so no data from one request reaches another. The Verifier MUST bound the Engine's runtime and memory and return an `error` when they are exceeded. See the [reference implementation's sandbox](https://github.com/worldcoin/flamingo/tree/main/verifier/sandbox-client) for one way to meet these requirements.

#### 3.5.2 Engine Releases

A release is a JWS ([RFC 7515](https://www.rfc-editor.org/rfc/rfc7515)) in compact serialization, signed with `ES256` by the Engine Provider's release key. Its protected header MUST contain `alg` = `ES256`, `kid` and `typ` = `world-id-engine-release`. Its payload is a JSON object:

| Field | Type | Description |
| --- | --- | --- |
| `engine_hash` | string | `SHA-256` of the Engine bundle, hex. |
| `engine_version` | integer | Monotonic release number, `< 2^32`. |
| `pipelines` | array | Per pipeline: `pipeline` (integer) and `roles` (one string per `compare` position, e.g. `"credential"`, `"live"`, `"challenge"`). |
| `match_strictness_levels` | array | Each entry: `match_strictness` (integer) and `description` (string), ascending. |

1. **Loading**. The host passes the release, the Engine bundle and the release key as a JWK. The Verifier MUST verify the release under that key and fetches nothing.
2. **Release key**. The token names the release key through `engine_key_hash`, so RPs, not the Verifier image, decide which keys they trust. Rotating a key is a metadata update.
3. **Metadata**. The Engine Provider MUST expose a JSON file over HTTPS at `https://<FQDN>/.well-known/world-id-engine.json`:

| Field | Type | Description |
| --- | --- | --- |
| `version` | integer | MUST be `1`. |
| `provider_id` | string | Stable identifier, which RPs MAY allowlist. |
| `release_keys` | array | Each entry: `jwk` (a P-256 JWK with `kid`) and `status` (`active`, `retired` or `revoked`). |
| `releases` | array | Each entry: `release` (the compact JWS) and `status` (`active`, `retired` or `revoked`). |

The Verifier never fetches the metadata. RPs check `engine_version` against it, and Authenticators read `pipelines` to lay out `compare`.

### 3.6 Flamingo Token

A token is a CWT ([RFC 8392](https://datatracker.ietf.org/doc/html/rfc8392)) in an untagged `COSE_Sign1`, encoded as deterministic CBOR ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)).

1. The protected header MUST contain `alg` (label `1`) = `-65537` (Private Use, `BabyJubJub-EdDSA-Poseidon2`) and `kid` (label `4`) = the compressed signing public key.
2. The signature MUST be a `BabyJubJub-EdDSA-Poseidon2` signature per [WIP-100][wip-100] over the [signed digest](#362-signed-digest).

#### 3.6.1 Claims

The payload MUST contain exactly these claims, in the bytewise order of their encoded keys.

| Claim | Key | Value |
| --- | --- | --- |
| `iat` | `6` | Time of the comparison, seconds since the Unix epoch. |
| `eat_profile` | `265` | `EAT_PROFILE`. |
| `pipeline` | `-90000` | `pipeline` from the request. |
| `match_strictness` | `-90001` | `match_strictness` from the request. |
| `compared_entry_hash_k`, `k = 0..3` | `-90002 - k` | `R(SHA-256(entries[compare[k]].data))`, or `0` if `compare` has no position `k`. |
| `aud` | `-90006` | `aud` from the request. |
| `nonce` | `-90007` | `nonce` from the request. |
| `authenticator_provider_key_hash` | `-90008` | [WIP-106][wip-106] hash of the `authenticator_provider_key` that verified the AAT, or `0` without an AAT. |
| `aat_flags` | `-90009` | `platform + 2^8 * sec_level + 2^16 * min_build_version + 2^48 * sec_meta + 2^51 * user_presence`, the [WIP-106][wip-106] `sec_flags` layout with the public `min_build_version` in place of `build_version`; `0` without an AAT. |
| `engine_version` | `-90010` | `engine_version` of the signed Engine release that ran. |
| `has_aat` | `-90011` | `1` if the Verifier verified an AAT, otherwise `0`. |
| `engine_key_hash` | `-90012` | `R(engine_key)`, identifying the Engine Provider release key that signed the Engine release. |

1. `iat`, `pipeline`, `match_strictness`, `aat_flags`, `engine_version` and `has_aat` are CBOR uints; `iat` is a 4-byte uint (`0x1a`). All other claims except `eat_profile` are 32-byte byte strings, the canonical big-endian encoding of a field element.
2. `eat_profile` is not in the signed digest and MUST be treated as an untrusted hint.
3. `iat` MUST come from the profile's trusted clock ([Attestation Profiles](#382-attestation-profiles)), never from the host or the request. It is also the `now` of any AAT verification.

#### 3.6.2 Signed Digest

The signed message is **not** the COSE `Sig_structure`. It MUST be output element `1` of the Poseidon2 `t=16` permutation over:

```
[DS_WIP_201, iat, pipeline, match_strictness,
 compared_entry_hash_0, compared_entry_hash_1, compared_entry_hash_2, compared_entry_hash_3,
 aud, nonce, authenticator_provider_key_hash, aat_flags, engine_version, has_aat, engine_key_hash, 0]
```

One slot remains free.

### 3.7 Verifiability and Reproducible Builds

The Verifier image MUST be reproducibly built, so its measurement can be checked against source. Engines are injected at runtime and bound by their signed release ([Engine](#35-engine)) and [Isolation](#351-isolation). Each hardware provider is an [attestation profile](#382-attestation-profiles) with the same token; RPs choose the profiles and roots they trust.

### 3.8 Attestation and Transport

The Verifier generates a channel key and a token signing key at boot and attests each in its own document. A document MUST provide, as its profile defines:

1. **Root**. A certificate chain to a hardware provider root.
2. **Measurement**. The measurement of the Verifier image.
3. **Bound key**. A key value fixed by the Verifier, as in the table below.
4. **Timestamp**. A `timestamp` in seconds since the Unix epoch, from a clock the hardware provider vouches for.
5. **Debug mode**. Whether the TEE runs in debug mode.

| Document | Bound key | Used by |
| --- | --- | --- |
| Channel attestation | `SHA-256(CHANNEL_KEY_DOMAIN \|\| channel_key)` | The Authenticator, to encrypt a request; discarded afterwards. |
| `signing_key_attestation` | The token signing key (`kid`) | Consumers, with every token. |

1. **Channel**. The Authenticator MUST verify the channel attestation before sending a request, then seal `response_key || request` to `channel_key` ([Channel Encoding](#381-channel-encoding)), where `response_key` is a fresh X-Wing encapsulation key and `request` the plaintext of [Request](#32-request).
2. **Response**. The Verifier MUST seal the padded response to `response_key`. Only the requester holds `response_key`, so the response is bound to its request; a `Success` is authenticated by its token.
3. **Replay**. The host can replay a request. That yields at most another token for the same `nonce`, which the RP rejects as reused.
4. **Refresh**. The Verifier MUST re-attest its signing key so that every token has `timestamp <= iat <= timestamp + MAX_ATTESTATION_AGE` for some `signing_key_attestation` of its boot.
5. **Carrying**. A proof or message that relies on a token MUST carry the token's `signing_key_attestation`.

The Engine needs no attestation of its own: the measured Verifier only loads signed releases ([Engine](#35-engine)) and signs `engine_version` into each token. One `signing_key_attestation` covers every token of a boot, so consumers MAY cache it by key. It identifies the Verifier instance, not the user.

#### 3.8.1 Channel Encoding

Both directions use HPKE ([RFC 9180](https://www.rfc-editor.org/rfc/rfc9180)) in base mode with the X-Wing KEM (`0x647A`), HKDF-SHA256 (`0x0001`) and ChaCha20-Poly1305 (`0x0003`). A sealed message is `header || enc || ciphertext`:

| Part | Length (bytes) | Value |
| --- | --- | --- |
| `header` | 7 | `0x02`, then the KEM, KDF and AEAD identifiers as big-endian `uint16`. It is the HPKE associated data. |
| `enc` | 1120 | The X-Wing encapsulation. |
| `ciphertext` | variable | The HPKE ciphertext. |

1. **Info**. `info` is `CHANNEL_DOMAIN || 0x00` for a request and `CHANNEL_DOMAIN || 0x01` for a response.
2. **Request plaintext**. The first 1216 bytes are `response_key`; the rest is the request.
3. **Rejection**. A recipient MUST reject any other `header`, a request shorter than 1216 bytes, or an invalid `response_key`.

#### 3.8.2 Attestation Profiles

A profile maps the document properties to one hardware provider and names the trusted clock behind `iat`. A new profile MUST define every row; one whose document lacks room for the signing key MAY bind its `SHA-256` hash instead.

| Property | AWS Nitro |
| --- | --- |
| Document | Nitro attestation document, `COSE_Sign1` |
| Root | AWS Nitro Root G1 |
| Measurement | PCR0, PCR1, PCR2, and PCR8 for a signed image |
| Bound key | `public_key` |
| Timestamp | `timestamp`, in milliseconds, divided by 1000 |
| Debug mode | All-zero PCRs |
| Trusted clock | The Nitro Secure Module (NSM) |

### 3.9 Flamingo Token Verification

Token verification is specified as a component for circuits (e.g. [WIP-202][wip-202]); a consumer outside a circuit MUST perform the same checks ([Reference Verification](#4-reference-verification)). The component MUST introduce these inputs.

| Input | Visibility | Type | Description |
| --- | --- | --- | --- |
| `verifier_key` | **Public** | `PublicKey` | Token signing key, checked against its `signing_key_attestation`. |
| `now` | **Public** | uint32 | Current time, in seconds since the Unix epoch. |
| `comparison_age_max` | **Public** | uint32 | Maximum age of `iat` the RP accepts. |
| `aud`, `nonce` | **Public** | Field element | The RP's request. |
| `has_aat` | **Public** | bool | Whether the token carries an AAT result. |
| `authenticator_provider_key_hash` | **Public** | Field element | Hash of an allowlisted Authenticator Provider key. |
| `platform`, `sec_level`, `sec_meta`, `user_presence` | **Public** | uint8 | AAT sub-fields, see [WIP-106 §3.5][wip-106]. |
| `min_build_version` | **Public** | uint32 | Minimum `build_version` the RP accepts. |
| `policy` | **Public** | [(`engine_key_hash`, `pipeline`, `min_match_strictness`, `min_engine_version`); `MAX_POLICY_ENTRIES`] | Combinations the RP accepts. An RP with fewer than `MAX_POLICY_ENTRIES` fills the rest with `pipeline = 0`, which never matches. |
| `iat`, `pipeline`, `match_strictness`, `engine_version` | Private | uint | From the token. |
| `compared_entry_hash` | Private | [Field element; 4] | From the token. |
| `engine_key_hash` | Private | Field element | From the token. |
| `sig` | Private | Signature | The token signature. |

The circuit MUST enforce:

1. **Signature**. Compute the [signed digest](#362-signed-digest) from the inputs and verify `sig` under `verifier_key` per [WIP-100 §3.5.1][wip-100].
2. **Freshness**. `iat`, `now` and `comparison_age_max` MUST be less than $2^{32}$. The circuit MUST enforce `iat <= now` and `now - iat <= comparison_age_max`.
3. **Request binding**. The digest MUST use the public `aud`, `nonce` and `authenticator_provider_key_hash`.
4. **Assertion flags**. The digest MUST use `aat_flags = platform + 2^8 * sec_level + 2^16 * min_build_version + 2^48 * sec_meta + 2^51 * user_presence`, with each sub-field range-checked to its width.
5. **Optional AAT**. `has_aat` MUST be `0` or `1` and the digest MUST use it. When `has_aat = 0`, the digest MUST use `authenticator_provider_key_hash = 0` and `aat_flags = 0`.
6. **Policy**. `engine_key_hash`, `pipeline`, `match_strictness` and `engine_version` MUST satisfy one `policy` entry: `engine_key_hash` and `pipeline` equal, `match_strictness >= min_match_strictness` and `engine_version >= min_engine_version`. `pipeline` MUST NOT be `0`.

The component returns `compared_entry_hash`. The embedding circuit MUST bind each hash its statement depends on to its own inputs (e.g. the Issuer's claim or the RP's challenge).

The proof does not reveal which `policy` entry matched.

## 4. Reference Verification

A consumer accepts a token if:

1. The `signing_key_attestation` chains to a root of a profile the RP accepts, is not in debug mode, reports a measurement the RP accepts, attests the key that signed the token and satisfies `timestamp <= iat <= timestamp + MAX_ATTESTATION_AGE`. `kid` is only a hint.
2. The signature verifies under that key.
3. `iat` is within the RP's maximum age.
4. `aud` and `nonce` equal the RP's request, and the RP rejects a reused `nonce`.
5. If `has_aat = 0`, the RP accepts requests without an AAT. Otherwise `authenticator_provider_key_hash` is the hash of a key that is allowlisted and active in the WIP-106 Authenticator Metadata, and `min_build_version` and the other `aat_flags` sub-fields meet RP policy.
6. `engine_key_hash` is `R` of the thumbprint of a `release_keys` entry of an allowlisted Engine Provider that is not `revoked`, `engine_version` is an active release signed by that key, and `pipeline`, `match_strictness` and `engine_version` meet RP policy.

## 5. Rationale

1. **The Verifier interprets nothing.** Roles, frame semantics and thresholds live in the Engine and the consumer. A new capture method or credential format never changes the request or token.
2. **The AAT is verified in the Verifier.** [WIP-106 §3.7][wip-106] lets an attested verifier run its checks and report the public values. The Verifier already handles the media, and consumers save one signature verification. As `cdh` covers the exact `payload`, the AAT vouches for exactly the compared input.
3. **The AAT is optional.** Web Authenticators have no platform to attest, and requiring an AAT would exclude them. The RP decides per request whether it accepts a token without one, as WIP-106 lets a circuit do with `has_aat`.
4. **Public values as claims.** The token carries the same public values an in-circuit AAT check would expose, so a consumer applies the same RP policy either way. Consumers read them directly instead of opening commitments; the Verifier is trusted to derive them from one request, as it is for the comparison. `build_version` stays private as WIP-106 requires; `min_build_version` takes its place.
5. **Raw `SHA-256` entry hashes over received bytes.** Issuers sign `SHA-256` digests of raw bytes, e.g. in a PCP `hashes.json`, never extracted embeddings, so a consumer binds to them without computing `SHA-256`.
6. **Signature over claim values, not CBOR bytes.** The signature covers a Poseidon2 hash of the claim values, so a circuit verifies the token without parsing CBOR. Each claim keeps its own field element; the wider `t=16` permutation costs less than unpacking packed claims in-circuit.
7. **`iat` rather than `exp`.** The RP needs the comparison's age and chooses the maximum; without it a comparison is replayable forever.
8. **All pairs are compared.** Matching the live capture and the challenge separately to the Credential does not establish that they match each other.
9. **Match strictness instead of thresholds.** A score's meaning depends on the model and the pair, so an RP cannot pick a meaningful number; an ordered strictness survives model upgrades.
10. **A separate Engine Provider signs the Engine.** Authenticators without an AAT have no Authenticator Provider, models often come from another party, and trust in the models stays separate from trust in the capture environment. Pipelines only have meaning relative to an Engine release; naming its key in the token turns `engine_version` into an attested statement instead of an operator's claim.
11. **Release keys at runtime.** One audited Verifier image serves every Engine Provider, and RPs allowlist them by `engine_key_hash` as they allowlist Authenticator Providers by `authenticator_provider_key_hash`. Pinning keys in the image would need a new measurement per provider and per rotation. `engine_key` in `payload` lets the AAT vouch for the Authenticator's choice.
12. **No scores.** Similarity scores are biometric signals and stay out of every token.

## 6. Alternatives Considered

1. **Local ZK proofs.** The Authenticator runs extraction and PAD and proves them in ZK. Rejected: proving these models on a phone is impractical, and the prover would need the model weights on the device, while PAD relies on keeping them secret.
2. **MPC.** Parties jointly run the models over secret-shared inputs and weights. Rejected: it runs the models orders of magnitude slower and adds the assumption that the parties don't collude.

## 7. Security

1. **Verifier trust.** The RP trusts the Verifier and its Engine for the comparison. A compromised Verifier can sign any claim values, including the AAT result, but cannot supply an account's authorization or replace the Issuer's Credential signature, which [WIP-202][wip-202] verifies.
2. **Pipelines are identifiers.** Naming a pipeline does not establish its accuracy; the RP trusts the attested Verifier to run it honestly.
3. **Live capture.** Neither the TEE nor [WIP-202][wip-202] removes trust in the Authenticator for the source and freshness of the live image.
4. **Verifier visibility.** The TEE sees the media, any AAT, `aud` and `nonce`, so it learns which RP a request is for. `blind` still hides the RP from the Authenticator Provider.
5. **Token privacy.** `compared_entry_hash` of a credential entry is constant per user, and the token carries `aud` and `nonce`. Consumers MUST keep the token and these claims private.
6. **Instance compromise.** A single Verifier key can not be revoked. RPs stop accepting a compromised measurement, and `MAX_ATTESTATION_AGE` bounds how long its tokens stay acceptable.

7. **Attestation coverage.** The measurement covers the Verifier image: AAT verification, `cdh` and token construction, release verification, Engine loading and the clock behind `iat`. It does not cover the host, the network or the Engine bundle, which its signed release covers. RPs MUST reject debug-mode attestations.
8. **Key binding.** The Verifier generates its signing key inside the TEE at boot from the hardware RNG and never exports it. A key in a valid `signing_key_attestation` was therefore generated by that measurement, and each boot uses a new key.
9. **Release-key compromise.** A leaked release key lets an attacker ship any Engine under a valid `engine_version`. RPs stop accepting it once the Engine Provider marks the key `revoked`.
10. **Matching oracle.** Anyone can submit arbitrary entries and learn whether they pass. An AAT limits this to genuine Authenticators, but a request without one is open to any caller.

## 8. Backwards Compatibility

This WIP introduces a new interface; no existing contracts or functionality are affected.
