## 1. Abstract

The **Flamingo Verifier** (**Verifier**) is a TEE service that:

- receives up to eight entries (images or embeddings, each with opaque metadata), up to four of them to compare, a `method` and an `assurance_level`;
- verifies the [WIP-106][wip-106] Authenticator Assertion Token (AAT) that vouches for the request;
- hands the request to a sandboxed biometric Engine that checks and compares the entries;
- when the Engine accepts, signs a token over the method, the assurance level, the compared entries and the AAT's verified public values.

The token is its only signed output. [WIP-202][wip-202] consumes it to prove the comparison to a Relying Party without revealing any entry.

## 2. Motivation

Comparing two embeddings is cheap. Getting an embedding anyone should believe is not.

Extraction runs a model over raw media, which is impractical in a ZK circuit. The checks that make an extracted embedding meaningful — image quality, Presentation Attack Detection, anti-fraud signals — are even worse. Much of these models require complex inputs and advanced signals, and may even rely on model obscurity.

Running extraction and comparison in an attested Trusted Execution Environment is intended to keep the inputs private from the service operator and tie the result to approved code. The commitments let WIP-202 bind the processed bytes to the Issuer, Authenticator and RP statements. They do not establish that the live image came from a camera; that still depends on the Authenticator.

The Verifier also verifies the Authenticator Provider's assertion ([WIP-106][wip-106]) and reports its public values, which removes that signature verification from the WIP-202 circuit. WIP-202 still independently verifies the Issuer's Credential and the account's authorization. Even a compromised Verifier cannot produce a proof for a registered account without that account's authorization for the request.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

### 3.1 Request

| Constant | Value | Description |
| --- | --- | --- |
| `MAX_ENTRIES` | `8` | Entries per request. |
| `MAX_COMPARED` | `4` | Compared entries, fixed by the token layout; at most six comparisons. |

The request MUST be encrypted to the Verifier. Its plaintext is a deterministic CBOR map of two fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `payload` | bytes | A deterministic CBOR map of the fields below; the input to the Engine. |
| `assertion` | map | The AAT and its verification inputs ([§3.1.1](#311-authenticator-assertion)). |

`payload` is carried as a byte string so the AAT can commit to its exact bytes:

| Field | Type | Bounds | Meaning |
| --- | --- | --- | --- |
| `method` | `uint` | `< 2^16` | Engine-defined algorithm, e.g. DeepFace with LightGuard. |
| `assurance_level` | `uint` | `< 2^8` | Engine-defined strictness within `method`. |
| `meta` | bytes | ≤ 1 KiB | Engine hints that do not change what is proven, e.g. experiment flags. |
| `entries` | array of `Entry` | `1..=MAX_ENTRIES` | Inputs to the Engine. |
| `compare` | array of `uint` | `2..=MAX_COMPARED` distinct indices into `entries` | Ordered; the Engine compares every pair. |

- An `Entry` is `{ data: bytes, meta: bytes }`: `data` is an encoded image or an embedding, `meta` (≤ 256 bytes) tells the Engine how to read it.
- The Verifier interprets none of the `payload` fields; it forwards them to the Engine ([§3.3](#33-engine)).
- Roles (Credential item, live frame, challenge) are fixed by `method` through positions in `compare`.
- The Verifier MUST reject a request of any other shape, exceeding a bound, or whose `compare` repeats or names an out-of-range index. It MAY impose further byte limits on `entries[].data`.

#### 3.1.1 Authenticator Assertion

`assertion` carries the AAT and the inputs [WIP-106 §3.7][wip-106] defines for its verification. The `cdh` the AAT commits to is computed by the Verifier, never supplied:

```
cdh = R(SHA-256(payload))
```

| Field | Type | WIP-106 visibility |
| --- | --- | --- |
| `aat` | bytes | The AAT in its CWT encoding, carrying the private `exp`, `sec_flags` and `sig`. |
| `blind` | Field element | Private. |
| `trust_anchor_key` | `PublicKey` | Public. |
| `aud` | Field element | Public. |
| `nonce` | Field element | Public. |
| `min_build_version` | `uint32` | Public. |

Before calling the Engine, the Verifier MUST:

- decode `aat` per [WIP-106 §3.4.1][wip-106], rejecting any other encoding;
- perform every check of [WIP-106 §3.7][wip-106], with `now = iat` and the `cdh` above, and require the AAT's `aat_commitment` to equal the one it computes;
- reject the request if any check fails.

Every request MUST carry an AAT; this WIP does not use WIP-106's `has_aat = 0` case. The private values (`exp`, `sec_flags`, `sig`, `aat_commitment`, `blind` and `build_version`) MUST NOT appear in the token or the response, and `assertion` MUST NOT be passed to the Engine.

### 3.2 Response

| Variant | Contents |
| --- | --- |
| `Success` | `token` ([§3.4](#34-token)), `signing_key_attestation`, `debug_report` |
| `Failed` | `error`, `debug_report` |

- The response MUST be encrypted to the requester and MUST be padded to a fixed length, hiding the outcome and the report size.
- `error` is implementation-defined and bounded in size. It is either the Verifier's own (e.g. a request that breaks [§3.1](#31-request)) or the Engine's, passed through.
- `debug_report` is optional bytes from the Engine, not part of the token. The Verifier MAY truncate it to fit the padded length.
- The Verifier MUST emit a token only when the Engine returns `Pass`.

### 3.3 Engine

The Engine performs extraction, quality checks, Presentation Attack Detection and comparison. This spec defines none of them.

- Each `method` defines the entry layout, how each entry's `meta` is read, and which checks run.
- Each `assurance_level` of a method defines the thresholds for every compared pair.
- Within one method, a higher `assurance_level` MUST be at least as strict on every check. Levels of different methods are not comparable.
- The Engine and its method and level definitions MUST be covered by the Verifier's attested measurement ([§3.5](#35-verifiability-and-reproducible-builds)), directly or through an attested hash of injected models and configuration.

The Verifier MUST pass the `payload` fields `method`, `assurance_level`, `meta`, `entries` and `compare` to the Engine unchanged. The Engine MUST return either `Pass`, meaning every check passed and every compared pair cleared the level, or an error. Either MAY carry a `debug_report`; neither carries scores. This WIP does not specify the encoding.

#### 3.3.1 Isolation

The Engine sees raw biometrics and may run closed or injected models. The Verifier MUST confine it:

- no network access, no writable persistent storage, no process creation;
- no access to the Verifier's signing or encryption keys;
- a single channel, the Engine request and response, both bounded in size.

See the [reference implementation's sandbox](https://github.com/worldcoin/flamingo/tree/main/verifier/sandbox-client) for one way to meet these requirements.

### 3.4 Token

- The token is a CWT in an untagged `COSE_Sign1`, encoded as deterministic CBOR.
- The protected header MUST contain `alg` (label `1`) = `-65537` (Private Use, `BabyJubJub-EdDSA-Poseidon2`) and `kid` (label `4`) = the compressed signing public key.
- The signature is `BabyJubJub-EdDSA-Poseidon2` as defined in [WIP-100][wip-100], over the [signed digest](#342-signed-digest).

#### 3.4.1 Token claims

| Claim | Key | Encoded key | Value |
| --- | --- | --- | --- |
| `iat` | `6` | `06` | Time of the comparison, seconds since the Unix epoch. |
| `eat_profile` | `265` | `19 01 09` | MUST be `https://world.org/eat/evt/v1` ([RFC 9711](https://datatracker.ietf.org/doc/rfc9711/) §4.3.2). |
| `method` | `-90000` | `3a 00 01 5f 8f` | `method` from the request. |
| `assurance_level` | `-90001` | `3a 00 01 5f 90` | `assurance_level` from the request. |
| `compared_entry_hash_k`, `k = 0..3` | `-90002 - k` | `3a 00 01 5f 91` … `94` | `R(SHA-256(entries[compare[k]].data))`, or `0` if `compare` has no position `k`. |
| `aud` | `-90006` | `3a 00 01 5f 95` | `aud` of the verified AAT. |
| `nonce` | `-90007` | `3a 00 01 5f 96` | `nonce` of the verified AAT. |
| `trust_anchor_key_x` | `-90008` | `3a 00 01 5f 97` | x coordinate of the `trust_anchor_key` that verified the AAT. |
| `trust_anchor_key_y` | `-90009` | `3a 00 01 5f 98` | y coordinate of that key. |
| `aat_flags` | `-90010` | `3a 00 01 5f 99` | `platform + 2^8 * sec_level + 2^16 * min_build_version + 2^48 * sec_meta + 2^51 * user_presence` from the verification. |

- Claims MUST appear in the order above, the bytewise order of their encoded keys ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)).
- `iat`, `method`, `assurance_level` and `aat_flags` are CBOR uints; `iat` is a 4-byte uint (`0x1a`) as in [RFC 8392](https://datatracker.ietf.org/doc/html/rfc8392#section-3.1.6).
- All other claims except `eat_profile` are 32-byte byte strings, the canonical big-endian encoding of a field element.
- `aat_flags` uses the [WIP-106][wip-106] `sec_flags` layout with the public `min_build_version` in place of the private `build_version`.
- `R(d)` reads the 256-bit digest `d` as a big-endian integer modulo $p$.
- `eat_profile` is not in the signed digest and MUST be treated as an untrusted hint.
- `iat` MUST be the time of this comparison, from a trusted clock. It is also the `now` of the AAT verification.

#### 3.4.2 Signed digest

The signed message is **not** the COSE `Sig_structure`. It MUST be output element `1` of the Poseidon2 `t=16` permutation over:

```
[DS_WIP_201, iat, method, assurance_level,
 compared_entry_hash_0, compared_entry_hash_1, compared_entry_hash_2, compared_entry_hash_3,
 aud, nonce, trust_anchor_key_x, trust_anchor_key_y, aat_flags, 0, 0, 0]
```

| Constant | Value |
| --- | --- |
| `DS_WIP_201` | `127603488023523044162070750169730750022280897185614` (`b"WORLD-ID/WIP-201/SIGN"`) |

Three slots remain free for later claims.

### 3.5 Verifiability and reproducible builds

OCI verification, reproducible builds. Models may be injected at runtime; [§3.3.1](#331-isolation) keeps them from exfiltrating information.

The design MUST support multiple hardware providers, with provider-specific attestation verified out of band and a common token interface for [WIP-202][wip-202]. RPs choose which hardware providers and attestation roots they trust.

## 4. Rationale

- **Commitments over received bytes.** A hash of an extracted embedding is a value no other party ever signed, so nothing could be bound to it.
- **The Verifier interprets nothing.** Roles, frame semantics and thresholds live in the Engine and the consumer. A new capture method or credential format never changes the request or token.
- **The AAT is verified in the Verifier.** [WIP-106 §3.7][wip-106] lets an attested verifier run its checks and report the public values. The Verifier already handles the media, and consumers lose one signature verification. Because `cdh` covers the exact `payload`, the assertion vouches for exactly the compared input.
- **Public values as claims.** The token carries the same public values an in-circuit AAT check would expose, so a consumer applies the same RP policy either way. `build_version` stays private as WIP-106 requires; `min_build_version` takes its place.
- **Direct claims.** Claims a consumer reads are signed directly, so it never opens a commitment. It need not recheck them: the Verifier is trusted to derive them from one request, as it is trusted for the comparison.
- **Raw `SHA-256` entry hashes.** Issuers already sign `SHA-256` digests, e.g. in a PCP `hashes.json`, so a consumer binds to them without computing `SHA-256`.
- **Field-element digest.** A consumer verifies the token without parsing CBOR. Claims stay unpacked: `t=16` costs about 865 ACIR opcodes against 505 for `t=8`, and leaves room for later claims.
- **`iat` rather than `exp`.** An RP needs the comparison's age. Without it, one successful comparison is replayable forever. The maximum age is the RP's choice.
- **All pairs are compared.** Matching the live capture and the challenge separately to the Credential does not establish that they match each other.
- **Assurance levels instead of thresholds.** A score's meaning depends on the model and the pair, so an RP cannot pick a meaningful number. An ordered level stays stable across model upgrades.
- **No scores.** Similarity scores are biometric signals; keeping them out of the token keeps them out of every proof.

## 5. Security

The RP trusts the Verifier and its Engine for the comparison. A compromised Verifier can sign any `method`, `assurance_level`, entry hashes and AAT result, including platform, security level and user presence. It still cannot supply a registered account's authorization over that result or replace the Issuer's Credential signature; [WIP-202][wip-202] verifies those independently.

`method` lets an RP choose which algorithm it accepts, but the RP still trusts the attested Verifier to execute it honestly. Identifying a model does not establish its accuracy. Neither the TEE nor [WIP-202][wip-202] removes trust in the Authenticator for the source and freshness of the live image. The TEE sees the media, the AAT, `aud` and `nonce`, so it learns which RP a request is for. `blind` still hides the RP from the Authenticator Provider.
