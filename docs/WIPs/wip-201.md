## 1. Abstract

This spec defines the **Flamingo Verifier** (**Verifier**): a trusted execution environment (TEE) service that receives up to eight entries (images or embeddings, each with opaque metadata), up to four of them to compare, a `method` and an `assurance_level`. It verifies the [WIP-106][wip-106] Authenticator Assertion Token (AAT) that vouches for the request, hands the entries to a sandboxed biometric Engine that checks and compares them, and, when the Engine accepts, signs a token over the method, the assurance level, the compared entries and the AAT's verified public values. The token is its only signed output; [WIP-202][wip-202] consumes it to prove the comparison to a Relying Party (RP) without revealing any entry.

## 2. Motivation

Comparing two embeddings is cheap. Getting an embedding anyone should believe is not.

Extraction runs a model over raw media, which is impractical in a ZK circuit. The checks that make an extracted embedding meaningful — image quality, Presentation Attack Detection, anti-fraud signals — are even worse. Much of these models require complex inputs and advanced signals, and may even rely on model obscurity.

Running extraction and comparison in an attested Trusted Execution Environment is intended to keep the inputs private from the service operator and tie the result to approved code. The commitments let WIP-202 bind the processed bytes to the Issuer's and the RP's statements; the Verifier binds them to the Authenticator's. They do not establish that the live image came from a camera; that still depends on the Authenticator.

The Verifier also verifies the Authenticator Provider's assertion ([WIP-106][wip-106]) and reports its public values, which removes that signature verification from the WIP-202 circuit. WIP-202 still independently verifies the Issuer's Credential and the account's authorization. Even a compromised Verifier cannot produce a proof for a registered account without that account's authorization for the request.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

1. The **Engine** is the sandboxed component of the Verifier that performs extraction, quality checks, Presentation Attack Detection and comparison. This spec defines none of them.
2. The Field ($F$), the hash function ($H_t$), the signature scheme (`BabyJubJub-EdDSA-Poseidon2`) and the `PublicKey` representation MUST follow [WIP-100][wip-100]. `R(d)` reads a 256-bit digest `d` as a big-endian integer modulo $p$.

### 3.1 Constants

| Constant | Value | Description |
| --- | --- | --- |
| `MAX_ENTRIES` | `8` | Entries per request. |
| `MAX_COMPARED` | `4` | Compared entries, fixed by the token layout; at most six comparisons. |
| `DS_WIP_201` | `127603488023523044162070750169730750022280897185614` (`b"WORLD-ID/WIP-201/SIGN"`) | Domain separator for the token digest. |
| `EAT_PROFILE` | `https://world.org/eat/flamingo/v1` | The `eat_profile` claim ([RFC 9711 §4.3.2](https://datatracker.ietf.org/doc/html/rfc9711#section-4.3.2)) of a token. |

### 3.2 Request

The request MUST be encrypted to the Verifier ([Attestation and Transport](#38-attestation-and-transport)). Its plaintext is a deterministic CBOR map:

| Field | Type | Description |
| --- | --- | --- |
| `version` | `uint` | MUST be `1`. |
| `payload` | bytes | A deterministic CBOR map of the fields below, carried as a byte string so the AAT can commit to its exact bytes. |
| `assertion` | map | The AAT and its verification inputs (see [Authenticator Assertion](#33-authenticator-assertion)). |

| `payload` field | Type | Bounds | Description |
| --- | --- | --- | --- |
| `method` | `uint` | `< 2^16` | Engine-defined algorithm, e.g. DeepFace with LightGuard. |
| `assurance_level` | `uint` | `< 2^8` | Engine-defined strictness within `method`. |
| `meta` | bytes | ≤ 1 KiB | Engine hints, e.g. experiment flags. MUST NOT weaken the level; anything that changes the verdict belongs in `method`. |
| `entries` | array of `Entry` | `1..=MAX_ENTRIES` | Inputs to the Engine. |
| `compare` | array of `uint` | `2..=MAX_COMPARED` distinct indices into `entries` | Ordered; the Engine compares every pair. |

1. An `Entry` is `{ data: bytes, meta: bytes }`. `data` is an encoded image or an embedding; `meta` (≤ 256 bytes) tells the Engine how to read it.
2. The Verifier interprets none of the `payload` fields and forwards them to the Engine. Roles (Credential item, live frame, challenge) are fixed by `method` through positions in `compare`.
3. The Verifier MUST reject a request of any other shape, exceeding a bound, or whose `compare` repeats or names an out-of-range index. It MAY impose further byte limits on `entries[].data`.

### 3.3 Authenticator Assertion

`assertion` carries the AAT and the inputs [WIP-106 §3.7][wip-106] defines for its verification:

| Field | Visibility | Type | Description |
| --- | --- | --- | --- |
| `aat` | Private | bytes | The AAT in its CWT encoding, carrying `exp`, `sec_flags` and `sig`. |
| `blind` | Private | Field element | See [WIP-106 §3.3][wip-106]. |
| `trust_anchor_key` | **Public** | `PublicKey` | The Authenticator Provider's key, chosen by the RP. |
| `aud` | **Public** | Field element | The `rpId` of the request. |
| `nonce` | **Public** | Field element | The nonce of the request. |
| `min_build_version` | **Public** | uint32 | Minimum `build_version`, chosen by the RP. |

The Authenticator forwards the RP's public values; the RP checks them in the token ([Reference Verification](#4-reference-verification)). The `cdh` the AAT commits to is computed by the Verifier, never supplied: `cdh = R(SHA-256(payload))`.

Before calling the Engine, the Verifier MUST perform the following checks and reject the request if any fails:

1. **Encoding**. `aat` MUST decode per [WIP-106 §3.4.1][wip-106].
2. **Verification**. Every check of [WIP-106 §3.7][wip-106] MUST hold, with `now = iat` and the `cdh` above, and the AAT's `aat_commitment` MUST equal the one the Verifier computes.

Every request MUST carry an AAT; this WIP does not use WIP-106's `has_aat = 0` case. The private values (`exp`, `sec_flags`, `sig`, `aat_commitment`, `blind` and `build_version`) MUST NOT appear in the token or the response, and `assertion` MUST NOT be passed to the Engine.

### 3.4 Response

| Variant | Contents |
| --- | --- |
| `Success` | `token` ([Token](#36-token)), `signing_key_attestation` (binds `kid` to the attested measurement), `debug_report` |
| `Failed` | `error`, `debug_report` |

1. The response MUST be encrypted to the requester and MUST be padded to a fixed length, hiding the outcome and the report size.
2. `error` is implementation-defined and bounded in size. It is either the Verifier's own (e.g. a malformed request) or the Engine's, passed through.
3. `debug_report` is optional bytes from the Engine, not part of the token. The Verifier MAY truncate it, and MAY omit it in production. It may carry biometric-derived data, so clients MUST NOT forward it.
4. The Verifier MUST emit a token only when the Engine returns `Pass`.

### 3.5 Engine

1. Each `method` defines the entry layout, how each entry's `meta` is read, and which checks run. Each `assurance_level` of a method defines the thresholds for every compared pair.
2. Within one method, a higher `assurance_level` MUST be at least as strict on every check. Levels of different methods are not comparable.
3. The Engine and its method and level definitions MUST be covered by the Verifier's attested measurement ([Verifiability](#37-verifiability-and-reproducible-builds)), directly or through an attested hash of injected models and configuration.
4. Each method's `compare` layout and levels MUST be published in Verifier metadata, versioned per method.
5. The Verifier MUST pass the `payload` fields to the Engine unchanged. The Engine MUST return either `Pass`, meaning every check passed and every compared pair cleared the level, or an error. Either MAY carry a `debug_report`; neither carries scores. This WIP does not specify the encoding.

#### 3.5.1 Isolation

The Engine sees raw biometrics and may run closed or injected models. The Verifier MUST confine it: no network access, no writable persistent storage and no process creation; no access to the Verifier's signing or encryption keys; and a single channel, the Engine request and response, both bounded in size. See the [reference implementation's sandbox](https://github.com/worldcoin/flamingo/tree/main/verifier/sandbox-client) for one way to meet these requirements.

### 3.6 Token

A token is a CWT ([RFC 8392](https://datatracker.ietf.org/doc/html/rfc8392)) in an untagged `COSE_Sign1`, encoded as deterministic CBOR ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)).

1. The protected header MUST contain `alg` (label `1`) with the value `-65537` (Private Use, `BabyJubJub-EdDSA-Poseidon2`) and `kid` (label `4`), the compressed signing public key.
2. The signature MUST be a `BabyJubJub-EdDSA-Poseidon2` signature per [WIP-100][wip-100] over the [signed digest](#362-signed-digest).

#### 3.6.1 Claims

The payload MUST contain exactly the following claims, in this order, the bytewise order of their encoded keys.

| Claim | Key | Encoded key | Value |
| --- | --- | --- | --- |
| `iat` | `6` | `06` | Time of the comparison, seconds since the Unix epoch. |
| `eat_profile` | `265` | `19 01 09` | `EAT_PROFILE`. |
| `method` | `-90000` | `3a 00 01 5f 8f` | `method` from the request. |
| `assurance_level` | `-90001` | `3a 00 01 5f 90` | `assurance_level` from the request. |
| `compared_entry_hash_k`, `k = 0..3` | `-90002 - k` | `3a 00 01 5f 91` … `94` | `R(SHA-256(entries[compare[k]].data))`, or `0` if `compare` has no position `k`. |
| `aud` | `-90006` | `3a 00 01 5f 95` | `aud` of the verified AAT. |
| `nonce` | `-90007` | `3a 00 01 5f 96` | `nonce` of the verified AAT. |
| `trust_anchor_key_x` | `-90008` | `3a 00 01 5f 97` | x coordinate of the `trust_anchor_key` that verified the AAT. |
| `trust_anchor_key_y` | `-90009` | `3a 00 01 5f 98` | y coordinate of that key. |
| `aat_flags` | `-90010` | `3a 00 01 5f 99` | `platform + 2^8 * sec_level + 2^16 * min_build_version + 2^48 * sec_meta + 2^51 * user_presence` from the verification. |

1. `iat`, `method`, `assurance_level` and `aat_flags` are CBOR uints; `iat` is a 4-byte uint (`0x1a`). All other claims except `eat_profile` are 32-byte byte strings, the canonical big-endian encoding of a field element.
2. `aat_flags` uses the [WIP-106][wip-106] `sec_flags` layout with the public `min_build_version` in place of the private `build_version`.
3. `eat_profile` is not in the signed digest and MUST be treated as an untrusted hint.
4. `iat` MUST be the time of this comparison, from a clock covered by the attestation (e.g. the Nitro NSM), never from the host or the request. It is also the `now` of the AAT verification.

#### 3.6.2 Signed Digest

The signed message is **not** the COSE `Sig_structure`. It MUST be output element `1` of the Poseidon2 `t=16` permutation over:

```
[DS_WIP_201, iat, method, assurance_level,
 compared_entry_hash_0, compared_entry_hash_1, compared_entry_hash_2, compared_entry_hash_3,
 aud, nonce, trust_anchor_key_x, trust_anchor_key_y, aat_flags, 0, 0, 0]
```

Three slots remain free for later claims.

### 3.7 Verifiability and Reproducible Builds

OCI verification, reproducible builds. Models may be injected at runtime; [Isolation](#351-isolation) keeps them from exfiltrating information. The design MUST support multiple hardware providers, with provider-specific attestation verified out of band and a common token interface for [WIP-202][wip-202]. RPs choose which hardware providers and attestation roots they trust.

### 3.8 Attestation and Transport

1. Before sending a request, the Authenticator MUST verify the Verifier's attestation and encrypt to the key it attests.
2. The response MUST be bound to the request it answers.

## 4. Reference Verification

A consumer accepts a token by performing the following validations:

1. The signature verifies under a Verifier key the RP allowlists, attested per [Attestation and Transport](#38-attestation-and-transport). `kid` is only a hint.
2. `iat` is within the RP's maximum age.
3. `aud` and `nonce` equal the RP's request, and the RP rejects a reused `nonce`.
4. `trust_anchor_key` is allowlisted and active in the WIP-106 Authenticator Metadata.
5. `min_build_version`, the other `aat_flags` sub-fields, `method` and `assurance_level` meet RP policy.

## 5. Rationale

1. **Commitments over received bytes.** A hash of an extracted embedding is a value no other party ever signed, so nothing could be bound to it.
2. **The Verifier interprets nothing.** Roles, frame semantics and thresholds live in the Engine and the consumer. A new capture method or credential format never changes the request or token.
3. **The AAT is verified in the Verifier.** [WIP-106 §3.7][wip-106] lets an attested verifier run its checks and report the public values. The Verifier already handles the media, and consumers lose one signature verification. Because `cdh` covers the exact `payload`, the assertion vouches for exactly the compared input.
4. **Public values as claims.** The token carries the same public values an in-circuit AAT check would expose, so a consumer applies the same RP policy either way. `build_version` stays private as WIP-106 requires; `min_build_version` takes its place.
5. **Direct claims.** Claims a consumer reads are signed directly, so it never opens a commitment. It need not recheck them: the Verifier is trusted to derive them from one request, as it is trusted for the comparison.
6. **Raw `SHA-256` entry hashes.** Issuers already sign `SHA-256` digests, e.g. in a PCP `hashes.json`, so a consumer binds to them without computing `SHA-256`.
7. **Field-element digest.** A consumer verifies the token without parsing CBOR. Claims stay unpacked: `t=16` costs about 865 ACIR opcodes against 505 for `t=8`, and leaves room for later claims.
8. **`iat` rather than `exp`.** An RP needs the comparison's age. Without it, one successful comparison is replayable forever. The maximum age is the RP's choice.
9. **All pairs are compared.** Matching the live capture and the challenge separately to the Credential does not establish that they match each other.
10. **Assurance levels instead of thresholds.** A score's meaning depends on the model and the pair, so an RP cannot pick a meaningful number. An ordered level stays stable across model upgrades.
11. **No scores.** Similarity scores are biometric signals; keeping them out of the token keeps them out of every proof.

## 6. Security

1. **Verifier trust.** The RP trusts the Verifier and its Engine for the comparison. A compromised Verifier can sign any `method`, `assurance_level`, entry hashes and AAT result, including platform, security level and user presence. It still cannot supply a registered account's authorization over that result or replace the Issuer's Credential signature; [WIP-202][wip-202] verifies those independently.
2. **Methods are identifiers.** `method` lets an RP choose which algorithm it accepts, but the RP still trusts the attested Verifier to execute it honestly. Identifying a model does not establish its accuracy.
3. **Live capture.** Neither the TEE nor [WIP-202][wip-202] removes trust in the Authenticator for the source and freshness of the live image.
4. **Verifier visibility.** The TEE sees the media, the AAT, `aud` and `nonce`, so it learns which RP a request is for. `blind` still hides the RP from the Authenticator Provider.
5. **Token privacy.** `compared_entry_hash` of a credential entry is constant per user, and the token carries `aud` and `nonce`. Consumers MUST keep the token and these claims private.
