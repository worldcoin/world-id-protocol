## 1. Abstract

This spec introduces a protocol fee that Relying Parties (RPs) pay in order to authorize proofs for specific World ID(s). Paid users (World ID holders) must provide a valid proof of the RP's payment in order to present proofs to the RP in a given billing period. During a billing period, a paid World ID can perform any number of proofs.

> [!IMPORTANT]
> **This spec is introduced as an experiment, and it applies only to select RPs and only to Proofs of Embedding Similarity ([WIP-202][wip-202])**. Other Proofs and other RPs keep their existing behavior. This spec is expected to be updated based on experimentation results, as well as leading to the introduction of billing throughout the World ID Protocol.

## 2. Motivation

World ID fees can support sustainable protocol operation. Fees are charged at the protocol level to enable decentralization.

Fees are charged to RPs receiving proofs, not individual end users making proofs, because RPs can more easily estimate the value generated by World ID and compare it to the fees charged for using World ID. It also follows that RPs usually pay fees for services they use.

Monthly per-World ID billing lets an RP budget for distinct users without paying for each repeat proof. They make it easier for RPs to trade off per-monthly-user value against fees compared to per-proof fees. Repeated Embedding Similarity comparisons motivate this design. The World ID protocol is uniquely able to support such a fee mechanism because it exposes "unique human" as a protocol primitive.

## 3. High-Level Overview

This section introduces a **non-normative** high-level description of the billing mechanism.

1. **This spec is experimentally introduced**. This means that it will apply only to a specific set of RPs and only to Embedding Similarity Proofs. This is likely to be extended in the future with a spec update.
2. An RP must pay for fees during a billing period in order to request proofs from a user.
3. Each calendar month is valid from 00:00:00 UTC+14:00 on its first day until 00:00:00 Anywhere on Earth (AoE, UTC−12:00) on the next month's first day. Periods overlap by 26 hours.
4. Billing is done through a smart contract (the “**Billing Contract**”).
5. Registration capacity is priced in USD and purchased with WLD.
5. Capacity is purchased for one RP and one billing period. Each unit permits one distinct World ID to register. *A capacity of 2 means that the RP can receive proofs from two distinct World IDs during that period.*
6. When an RP requests a proof from a user (see [ProofRequest](https://docs.rs/world-id-primitives/latest/world_id_primitives/request/struct.ProofRequest.html)), the RP’s signature authorizes usage of a capacity of at most one.
7. A user generates a Uniqueness Proof for the billing action corresponding to the current period using a valid credential. This proof results in a special type of nullifier denominated the `billingNullifier`, which is submitted once to the **Billing Contract** with the RP’s authorization to claim capacity. The Authenticator caches the nullifier and private OPRF witness for the billing period.
8. Billing for Proofs of Embedding Similarity is enforced by TEE Verifiers ([WIP-201][wip-201]) where a valid proof of payment (through a `billingNullifier`) must be presented. If a proof is not presented, the Verifier rejects the request. Furthermore, the correctness of the `billingNullifier` is asserted in the Embedding Similarity circuit ([WIP-202][wip-202]).
9. An RP may purchase or top up registration capacity for the current AoE month and the next calendar month. Current-month purchases are prorated by seconds left in the AoE month. Future months are paid in full. Capacity cannot move between RPs or periods.
10. Unused capacity receives no rebate and does not roll over.
11. Users do not pay for fees; only RPs (or an entity acting on an RP's behalf) pay.
12. Fees are set per World ID and period in the Billing Contract. The governance-controlled administrator may update the USD fee amount on-chain. Payments settle in WLD; earlier purchases remain unchanged. An oracle price is used to convert between USD and WLD.

## 4. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

The Field ($`F`$), the Curve (`BabyJubJub`), and the Hashing ($`H_t`$) definitions MUST follow the requirements of [WIP-100][wip-100].

### 4.1 Billing Contract

The Billing Contract enables the RP to purchase capacity and the registration of payment-authorized World IDs for a given RP.

1. RPs MAY purchase registration capacity through `purchaseCapacity` for the current period or the next period. Importantly anyone can purchase capacity for an RP, but each purchase belongs to its `rpId` and `periodStart`.
2. Users MAY register against that capacity through `register`. They supply their period `billingNullifier`, a Uniqueness Proof, its credential verification inputs and the RP's `RegistrationAuthorization`.
3. The following interface is normative. Implementations MUST also enforce the requirements below.

    ```solidity
    interface WorldIDBilling {
        struct BillingContext {
            uint256 chainId;
            address billingContract;
            uint64 rpId;
            uint64 periodStart;
        }

        struct RegistrationAuthorization {
            uint8 version;
            uint160 oprfKeyId;
            uint256 nonce;
            uint64 createdAt;
            uint64 expiresAt;
            bytes signature;
            bytes wip101Data;
        }

        function quotePurchase(BillingContext calldata scope, uint256 capacityAmount)
            external view returns (uint256 wldAmount);

        function purchaseCapacity(
            BillingContext calldata scope,
            uint256 capacityAmount,
            uint256 maxWldAmount
        ) external;

        function register(
            BillingContext calldata scope,
            RegistrationAuthorization calldata authorization,
            uint64 issuerSchemaId,
            uint64 expiresAtMin,
            uint256 billingNullifier,
            uint256[5] calldata proof
        ) external returns (bool success);

        function isRegistered(uint64 rpId, uint64 periodStart, uint256 billingNullifier)
            external view returns (bool);

        function getBillingPeriod(uint64 timestamp)
            external view returns (uint64 periodStart, uint64 periodEnd);
        function getFeeToken() external view returns (address);
        function setFeeToken(address feeToken) external;
        function getFeeRecipient() external view returns (address);
        function setFeeRecipient(address feeRecipient) external;
        function getUsdPerWorldID() external view returns (uint256);
        function setUsdPerWorldID(uint256 usdPerWorldID) external;
        function getMaxPriceAge() external view returns (uint64);
        function setMaxPriceAge(uint64 maxPriceAge) external;
        function getRequestLimits()
            external view returns (uint64 maxRequestAge, uint64 maxRequestLifetime);
        function setRequestLimits(uint64 maxRequestAge, uint64 maxRequestLifetime) external;
        function owner() external view returns (address);
        function paused() external view returns (bool);
        function setPaused(bool paused) external;

        event CapacityPurchased(
            uint64 indexed rpId,
            uint64 indexed periodStart,
            address indexed payer,
            uint256 capacityAmount,
            uint256 wldPaid
        );
        event Registered(
            uint64 indexed rpId,
            uint64 indexed periodStart,
            uint256 billingNullifier
        );
    }
    ```

4. The contract MUST enforce these requirements.
    - **Configuration:** The fee token is the configured WLD ERC-20 on World Chain; the fee recipient is the designated protocol fee address. The initialized proxy owner is the governance-controlled administrator. Only that owner may perform administrative operations. Address settings MUST be nonzero; the price source MUST implement §4.8. Configuration changes MUST emit events and MUST NOT alter purchased capacity, registrations, period boundaries or pinned keys. Request limits MUST agree with the OPRF nodes (§4.4).
    - **Periods:** `getBillingPeriod` returns the AoE month containing `timestamp` and its exclusive `periodEnd` (§4.2). The contract MUST reject a context for another chain or deployment and any noncanonical `periodStart`.
    - **Purchases:** `quotePurchase` and `purchaseCapacity` MUST validate the context and the current-period/next-period purchase window. `purchaseCapacity` MUST quote the prorated price (§4.8) at execution and reject `wldPaid > maxWldAmount`. It MUST add exactly `capacityAmount` to that RP and period, transfer exactly `wldPaid` from the caller to the configured fee recipient, and require the recipient's balance to increase by exactly `wldPaid`. Payment, capacity and `CapacityPurchased` MUST be atomic and protected against reentrancy.
    - **Registration:** `register` MUST require an active period under §4.2, reject a used nonce for that RP and period and verify all authorization and proof inputs under §§4.3–4.4. A new nullifier requires registrations to be unpaused and `registeredCount < capacity`; it increments the count once, records the nullifier and emits `Registered`. A valid duplicate returns `false` and consumes no further capacity, including while new registrations are paused. It still requires fresh valid authorization and consumes that authorization's nonce.
    - **Atomicity:** Both `purchaseCapacity` and `register` MUST be protected against reentrancy. `isRegistered` reports membership for the supplied RP, period and nullifier.

### 4.2 Billing Context

Every RP uses the same AoE calendar months. `periodStart` is 00:00:00 AoE on the month's first day (12:00:00 UTC). `periodEnd` is 00:00:00 AoE on the next month's first day and is exclusive. The active interval is `[periodStart - 26 hours, periodEnd)`, clipped at Unix timestamp zero. Months overlap by 26 hours. Either active context MUST be accepted. Capacity, registrations, nonces and billing actions remain separate for each period.

The Billing Contract and billing verifiers MUST reject noncanonical month identifiers. `getBillingPeriod` returns the AoE month containing `timestamp` and its exclusive end; months beginning before Unix timestamp zero MUST be rejected. Clients MUST use the selected context's active interval for registration and proof acceptance. Purchases and top-ups remain limited to the purchase window in §4.1; the overlap does not permit purchases after `periodEnd`. Any future configurable-period extension MUST expose its boundaries on-chain and preserve already purchased periods.

```solidity
uint256 billingAction = uint256(keccak256(abi.encode(
    "world-id-billing-v1",
    scope.chainId, scope.billingContract, scope.rpId, scope.periodStart
))) >> 8;
```

`billingAction: Field` is the billing OPRF input, not the `ProofRequest.action` from the RP request. The billing nullifier is `UniquenessNullifier(rpOprfKey, worldIdLeafIndex, scope.rpId, billingAction)`. `UniquenessNullifier` means the existing [Uniqueness Proof nullifier computation](https://github.com/worldcoin/world-id-protocol/blob/main/circom/client_side_proofs/oprf_nullifier.circom), using these inputs and the unblinded OPRF response under the selected key.

### 4.3 Registration Proof

Registration MUST reuse the existing [Uniqueness Proof](https://github.com/worldcoin/world-id-protocol/blob/main/docs/world-id-4-specs/README.md#uniqueness-proofs) circuit, public-input order, proving artifacts and verification key. This spec introduces no new circuit or trusted setup. The user MUST present a valid credential from a registered issuer/schema; the billing nullifier remains independent of which credential is used.

#### 4.3.1 Inputs

The billing `ProofRequest` MUST use `scope.rpId`, `billingAction` and the authorization's nonce and selected OPRF key. It MUST omit the signal and session creation, and set the minimum credential genesis issuance time to zero.

The Contract MUST construct the existing uniqueness verifier's public inputs as follows:

| Input | Value |
| --- | --- |
| `nullifier`, `action`, `rpId`, `nonce` | `billingNullifier`, `billingAction`, `scope.rpId`, `authorization.nonce`. |
| `issuerSchemaId`, `expiresAtMin` | The credential verification inputs supplied to `register`, matching the proof's request item and effective expiry minimum. |
| `signalHash`, `credentialGenesisIssuedAtMin`, `sessionId` | Zero. |
| Account root, tree depth and credential issuer public key | Root from `proof[4]`, depth from `WorldIDRegistry`, and issuer key from `CredentialSchemaIssuerRegistry`. |
| OPRF public key | The OPRF Key for the Given RP |

`proof: uint256[5]` MUST use the existing [uniqueness proof encoding](https://github.com/worldcoin/world-id-protocol/blob/main/contracts/src/core/interfaces/IWorldIDVerifier.sol): four compressed Groth16 words followed by the account Merkle root.

#### 4.3.2 Verification

All existing account, authenticator signature, OPRF, nullifier and credential constraints MUST remain enforced, including WIP-100 field, scalar and point validation. The Contract MUST validate the account root and issuer/schema against the existing registries and enforce the existing uniqueness verifier's credential expiry freshness policy.

For the first registration in a billing context, the Contract MUST resolve the RP's existing authorized OPRF key from the registries and pin its key ID and public key.

### 4.4 RP Authorization

`RegistrationAuthorization` copies the billing `ProofRequest`'s nonce, timestamps, key ID and authorization data. Its version MUST be `0x01`. The request's `rp_id`, `oprf_key_id` and `action` MUST match the context, selected key and `billingAction`.

- **EOA:** `register` MUST recover the current registered signer from an EIP-191 signature over packed `(uint8(0x01), nonce, createdAt, expiresAt, billingAction)`. Encoding uses the Solidity widths above and big-endian integers: 81 bytes total. It MUST reject invalid or noncanonical signatures and nonempty `wip101Data`.
- **WIP-101:** The signer MUST support `IWIP101` through ERC-165. `register` MUST static-call `verifyRpRequest` with the version, nonce, timestamps, `billingAction` and `wip101Data`, and accept only `0x35dbc8de`. Data MUST be at most 1024 bytes. Calls execute on chain 480; failures MUST NOT fall back to EOA recovery.
- **Freshness:** Both paths MUST enforce canonical fields, `createdAt <= now < expiresAt`, `now - createdAt <= maxRequestAge` and `expiresAt - createdAt <= maxRequestLifetime`. The `uint64` limits MUST agree with the OPRF nodes.

The [OPRF signing format](https://github.com/worldcoin/world-id-protocol/blob/316b6cf094a1bb28e7f23146bf648759fe041be6/services/oprf-node/src/auth/rp_module.rs) signs the packed message, not the SHA-256 value returned by `ProofRequest::digest_hash`. Contract authorization follows [WIP-101](https://github.com/worldcoin/world-id-protocol/blob/main/docs/WIPs/wip-101.md), including using the same action as the OPRF query.

The application's action remains separate. Sharing one authorization for application and billing actions requires an agreed protocol extension (§8); neither signature authorizes the other action. Unsigned request fields MUST NOT be treated as RP-authenticated.

### 4.5 Authenticator Cache

The Authenticator MUST:

- Cache the billing nullifier and private OPRF witness by account, `BillingContext`, OPRF key ID and public key.
- Keep OPRF witnesses, credential witnesses and query authorization inputs private, using the existing Uniqueness Proof types.
- Refresh account membership, RP authorization and credential verification inputs before generating a new registration proof.
- Expire entries at period end.
- Recover lost entries, including after switching Authenticators, through a fresh authorized query for the same World ID and BillingContext under the same pinned key. The nullifier MUST remain unchanged. An existing registration remains valid and recovery MUST NOT consume more capacity.

### 4.6 Billing Verification

Billing for the Proof of Embedding Similarity is enforced by the [WIP-201][wip-201] TEE Verifier. The sealed request to the Verifier carries `scope: BillingContext`, `billingNullifier: Field` and `request: ProofRequest`.

The TEE Verifier MUST check the RP, active period (§4.2) and application authorization. It MUST confirm finalized `billingNullifier` registration in the Contract beffore other processing.

### 4.7 Chain State

TEE Verifiers MUST:

- Cache only positive finalized registrations by `(BillingContext, billingNullifier)`; bound the cache and expire entries at period end.
- Read state through an approved provider with TLS terminating inside the enclave. The provider is trusted for state and finality.
- Any cache MUST NOT outlive the period's duration plus 24 hours of grace.

Valid cached registrations MAY serve during provider outages, subject to current authorization, credentials, trusted time and security policy. Provider failure MUST NOT fail process liveness. TEE Verifiers SHOULD implement a request-path chain reads one two-second timeout, make no retries and share concurrent lookups for the same key.

### 4.8 Fees

Fees are configured in USD per World ID per period and paid in WLD. Each unit of registration capacity permits one distinct World ID to register.

The RP approves the Billing Contract's WLD allowance, then calls `purchaseCapacity`. The contract transfers WLD from the payer to the designated protocol fee address and adds capacity atomically (§4.1). Approval alone does not pay the fee.

| Value | Type | Units |
| --- | --- | --- |
| `usdPerWorldID`, `usdPerWld` | `uint256` | USD scaled by `10^18`. |
| `TOKEN_UNIT` | `uint256` | `10^decimals` for the configured WLD token; MUST fit in `uint256`. |
| `observedAt`, `maxPriceAge` | `uint64` | Exchange-rate timestamp and maximum age, in seconds. |

`usdPerWorldID` is the full-month price. Current-month purchases and top-ups MUST be prorated by seconds left in the AoE month. Future months pay in full. Overlap adds no fee.

```
duration  = periodEnd - periodStart
remaining = periodEnd - max(block.timestamp, periodStart)
charge    = ceil(capacityAmount * usdPerWorldID * remaining * TOKEN_UNIT / (duration * usdPerWld))
```

For example, a purchase with 10 days left in a 30-day AoE month costs `10/30`, about 33.33% of the full-month price. `duration` is the AoE month's own length: 28, 29, 30 or 31 days.

Charges are in WLD base units. The contract MUST use checked USD totals and full-precision conversion.

The price source MUST be an on-chain adapter for the [Chainlink WLD/USD Data Stream](https://data.chain.link/streams/wld-usd-cexprice-streams). A report submitter obtains a signed report and submits it to the adapter. The adapter MUST verify it through the configured Chainlink verifier, require the configured feed ID, and normalize its price to USD scaled by `10^18`. It MUST expose only verified `usdPerWld` and `observedAt` values to the Billing Contract. Unverified reports MUST NOT update the stored rate.

`quotePurchase` and `purchaseCapacity` read that verified rate; a getter alone does not obtain or authenticate a report. The charge MUST NOT exceed the payer's `maxWldAmount`. Zero, future-dated, stale or unavailable prices MUST reject the purchase without affecting existing capacity. The feed ID, verifier, adapter, report format, source scale and `maxPriceAge` MUST be selected and tested before release (§8).

Unused capacity receives no refund and does not roll over. Top-ups and later parameter changes MUST NOT alter earlier purchases.

## 5. Rationale

- **Billing nullifier:** Counts one World ID across credentials without publishing its account leaf index.
- **Cached witness:** Avoids repeated billing OPRF queries.
- **Registration capacity:** One unit covers one distinct World ID for one RP and period, matching the RP's monthly user budget.
- **Overlapping months:** Capacity covers the calendar month in every time zone.
- **Prorating:** An RP that starts or tops up mid-month pays only for the time left in the AoE month.
- **No rebate or rollover:** Keeps each month's capacity and revenue independent and avoids refund or carry-forward accounting.

## 6. Security

An RP request is bearer authorization until bound to a holder. Consuming the nonce limits registrations but does not bind authorization to the intended holder.

A paid-state lookup does not prove that the caller owns the registered World ID. Therefore, the circuit needs to perform an additional verification of the OPRF evaluation.

Registrations are linkable within their billing context. Implementations MUST NOT log credentials, private witnesses or sealed payloads.

## 7. Backwards Compatibility

The billing action encoding and pinned keys MUST remain fixed for active periods. Rollout, rollback and pauses MUST preserve purchased capacity and registrations.

## 8. Experimental Release

> This section is WIP.

Before enablement:

- Select RPs, deployment addresses, the governance-controlled proxy administrator, WLD token, designated protocol fee address, initial USD price and request limits. Select the Chainlink feed, verifier, adapter, report format, scale and price-age limit (§4.8).
- Agree on signed application context and any shared application/billing authorization. OPRF nodes, WIP-101 implementations, the contract and TEEs MUST adopt the same semantics. Unsupported shared-signer and actionless flows remain disabled.

The governance-controlled proxy owner updates `usdPerWorldID` and other billing settings through the authorized on-chain setters. Changing the price does not require a node software release and MUST preserve earlier purchases.

TEE operators deploy compatible verifier images. Authenticators and RPs approve the accepted attestation measurements and keys under [WIP-201 draft](https://github.com/worldcoin/world-id-protocol/blob/wip-110/docs/WIPs/wip-201.md). The Engine Provider signs engine releases; the RP's engine policy decides which releases to accept. Operators MUST NOT treat an unsigned or unapproved release as accepted.

OPRF operators deploy compatible node software and keep pinned period keys available through period end. Clients verify OPRF proofs against the registry-authorized public keys, including the pinned key for an active billing context. Before enablement, record the operators, policy owners and contract upgrade owner and agree on compatible versions and key retention.

## 9. Rejected Alternatives

- **Per-proof charging:** Rejected for this experiment because it charges repeated comparisons and makes monthly costs less predictable. Any future per-proof scheme requires a separate proposal defining pre-purchase and expiry rules.
- **Credential-specific registration:** Charges one World ID more than once across credentials or renewals.
- **Off-chain-only billing:** Rejected for this experiment because capacity and registration would depend on a billing operator.
