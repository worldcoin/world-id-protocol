## 1. Abstract

This spec introduces a protocol fee that Relying Parties (RPs) pay in order to authorize proofs for specific World ID(s). Paid users (World ID holders) must provide a valid proof of the RP's payment in order to present proofs to the RP in a given billing period. During a billing period, a paid World ID can perform any number of proofs.

> [!IMPORTANT]
> **This spec is introduced as an experiment, and it applies only to select RPs and only to Proofs of Embedding Similarity ([WIP-202][wip-202])**. Other Proofs and other RPs keep their existing behavior. This spec is expected to be updated based on experimentation results, and may inform the billing mechanics introduced throughout the World ID Protocol. Accordingly, no organization or individual is making a commitment, promise, or obligation to develop, implement, or make available any feature, product, or functionality described in this spec, and there is no guarantee that they will ever exist or perform as described in the future.

## 2. Motivation

Fees are charged to RPs receiving proofs, not individual end users making proofs, because RPs can more easily estimate the value generated by World ID and compare it to the fees charged for using World ID. It also follows that RPs usually pay fees for services they use.

Monthly per-World ID billing lets an RP budget for distinct users without paying for each repeat proof. They make it easier for RPs to trade off per-monthly-user value against fees compared to per-proof fees. Repeated Embedding Similarity comparisons motivate this design. The World ID protocol is uniquely able to support such a fee mechanism because it exposes "unique human" as a protocol primitive.

## 3. High-Level Overview

This section introduces a **non-normative** high-level description of the billing mechanism.

1. **This spec is experimentally introduced**. This means that it will apply only to a specific set of RPs and only to Embedding Similarity Proofs. This is likely to be extended in the future with a spec update.
2. An RP must pay for fees during a billing period in order to request proofs from a user.
3. Each calendar month is valid from 00:00:00 UTC+14:00 on its first day until 00:00:00 Anywhere on Earth (AoE, UTC−12:00) on the next month's first day. Periods overlap by 26 hours.
4. Billing is done through a smart contract (the “**Billing Contract**”).
5. Registration capacity is priced in USD and purchased with WLD.
5. Capacity is purchased for one RP and one billing period. Each unit permits one distinct World ID to register. *A capacity of 2 means that the RP can receive proofs from two distinct World IDs during that period.*
6. When an RP requests a proof from a user (see [ProofRequest](https://docs.rs/world-id-primitives/latest/world_id_primitives/request/struct.ProofRequest.html)), the RP’s signature authorizes usage of a capacity of at most one.
7. A user generates a Uniqueness Proof for the billing action corresponding to the current period using a valid credential. This proof results in a special type of nullifier denominated the `billingNullifier`, which is submitted once to the **Billing Contract** with the RP’s authorization to claim capacity. The Authenticator caches the nullifier and private OPRF witness for the billing period.
8. Billing for Proofs of Embedding Similarity is enforced by TEE Verifiers ([WIP-201][wip-201]) where a valid proof of payment (through a `billingNullifier`) must be presented. If a proof is not presented, the Verifier rejects the request. Furthermore, the Embedding Similarity circuit ([WIP-202][wip-202]) proves that the `billingNullifier` belongs to the World ID making the proof.
9. An RP may purchase or top up registration capacity for the current AoE month and the next calendar month. Current-month purchases are prorated by seconds left in the AoE month. Future months are paid in full. Capacity cannot move between RPs or periods.
10. Unused capacity receives no rebate and does not roll over.
11. Users do not pay for fees; only RPs (or an entity acting on an RP's behalf) pay.
12. Fees are set per World ID and period in the Billing Contract. An administrator may update the USD fee amount on-chain. Payments settle in WLD; earlier purchases remain unchanged. An oracle price is used to convert between USD and WLD.

### 4.1 Constants

| Constant | Value | Meaning |
| --- | --- | --- |
| `CHAIN_ID` | `480` | World Chain mainnet, which hosts the production Billing Contract. |
| `WLD_TOKEN` | `0x2cFc85d8E48F8EAB294be644d9E25C3030863003` | WLD ERC-20 on World Chain (18 decimals). The production fee token. |
| `PERIOD_OVERLAP` | `93600` seconds (26 hours) | Overlap between consecutive billing periods (§4.3). |

### 4.2 Billing Contract

The Billing Contract enables the RP to purchase capacity and the registration of payment-authorized World IDs for a given RP.

1. RPs MAY purchase registration capacity through `purchaseCapacity` for the current period or the next period. Importantly anyone can purchase capacity for an RP, but each purchase belongs to its `rpId` and `periodStart`.
2. Users MAY register against that capacity through `register`. They supply their period `billingNullifier`, a Uniqueness Proof, its credential verification inputs and the RP's `RegistrationAuthorization`.
3. The following interface is normative. Implementations MUST also enforce the requirements below.

    ```solidity
    interface WorldIDBilling {
        struct BillingContext {
            uint256 chainId;
            address billingContract;
            uint64 rpId;
            uint64 periodStart;
        }

        struct RegistrationAuthorization {
            uint8 version;
            uint160 oprfKeyId;
            uint256 nonce;
            uint64 createdAt;
            uint64 expiresAt;
            bytes signature;
            bytes wip101Data;
        }

        struct Registration {
            RegistrationAuthorization authorization;
            uint64 issuerSchemaId;
            uint64 expiresAtMin;
            uint256 billingNullifier;
            uint256[5] proof;
        }

        function quotePurchase(BillingContext calldata scope, uint256 capacityAmount)
            external view returns (uint256 wldAmount);

        function purchaseCapacity(
            BillingContext calldata scope,
            uint256 capacityAmount,
            uint256 maxWldAmount
        ) external;

        function register(
            BillingContext calldata scope,
            RegistrationAuthorization calldata authorization,
            uint64 issuerSchemaId,
            uint64 expiresAtMin,
            uint256 billingNullifier,
            uint256[5] calldata proof
        ) external returns (bool success);

        function registerMany(BillingContext calldata scope, Registration[] calldata registrations)
            external returns (bool[] memory successes);

        function isRegistered(uint256 billingNullifier) external view returns (bool);
        function periods(uint64 rpId, uint64 periodStart)
            external view returns (uint256 capacity, uint256 registeredCount);
        function usedNonces(uint64 rpId, uint256 nonce) external view returns (bool);
        function getPinnedOprfKey(uint64 rpId, uint64 periodStart)
            external view returns (uint160 oprfKeyId, uint256[2] memory oprfPublicKey);

        function getBillingPeriod(uint64 timestamp)
            external view returns (uint64 periodStart, uint64 periodEnd);
        function getBillingAction(BillingContext calldata scope) external pure returns (uint256);
        function getFeeToken() external view returns (address);
        function setFeeToken(address feeToken) external;
        function getFeeRecipient() external view returns (address);
        function setFeeRecipient(address feeRecipient) external;
        function setPriceSource(address priceSource) external;
        function pricePerWorldID() external view returns (uint256);
        function setPricePerWorldID(uint256 pricePerWorldID) external;
        function maxPriceAge() external view returns (uint64);
        function setMaxPriceAge(uint64 maxPriceAge) external;
        function maxRequestAge() external view returns (uint64);
        function maxRequestLifetime() external view returns (uint64);
        function setRequestLimits(uint64 maxRequestAge, uint64 maxRequestLifetime) external;
        function owner() external view returns (address);
        function paused() external view returns (bool);
        function setPaused(bool paused) external;

        event CapacityPurchased(
            uint64 indexed rpId,
            uint64 indexed periodStart,
            address indexed payer,
            uint256 capacityAmount,
            uint256 wldPaid
        );
        event Registered(
            uint64 indexed rpId,
            uint64 indexed periodStart,
            uint256 billingNullifier
        );
        event OprfKeyPinned(
            uint64 indexed rpId,
            uint64 indexed periodStart,
            uint160 oprfKeyId
        );
    }
    ```

4. The contract MUST enforce these requirements.
    - **Configuration:** Production deployments run on `CHAIN_ID` with fee token `WLD_TOKEN` (§4.1); the fee recipient is the designated protocol fee address. The initialized proxy owner is the administrator. Only that owner may perform administrative operations. Address settings MUST be nonzero; the price source MUST implement §4.9. Configuration changes MUST emit events and MUST NOT alter purchased capacity, registrations, period boundaries or pinned keys. Request limits MUST agree with the OPRF nodes (§4.5).
    - **Periods:** `getBillingPeriod` returns the AoE month containing `timestamp` and its exclusive `periodEnd` (§4.3). The contract MUST reject a context unless `scope.chainId == block.chainid`, `scope.billingContract == address(this)` and `periodStart` is canonical (§4.3).
    - **Purchases:** `quotePurchase` and `purchaseCapacity` MUST validate the context and the current-period/next-period purchase window. `purchaseCapacity` MUST quote the prorated price (§4.9) at execution and reject `wldPaid > maxWldAmount`. It MUST add exactly `capacityAmount` to that RP and period, transfer exactly `wldPaid` from the caller to the configured fee recipient, and require the recipient's balance to increase by exactly `wldPaid`. Payment, capacity and `CapacityPurchased` MUST be atomic and protected against reentrancy.
    - **Registration:** `register` MUST require an active period under §4.3, reject a used nonce for that RP and verify all authorization and proof inputs under §§4.4–4.5. A new nullifier requires registrations to be unpaused and `registeredCount < capacity`; it increments the count once, records the nullifier and emits `Registered`. A valid duplicate returns `false` and consumes no further capacity, including while new registrations are paused. It still requires fresh valid authorization and consumes that authorization's nonce.
    - **Atomicity:** `purchaseCapacity`, `register` and `registerMany` MUST be protected against reentrancy. `registerMany` applies `register` to each entry and reverts entirely if any entry fails. `isRegistered` reports whether the nullifier is registered; `billingAction` already scopes it to one RP and period.

### 4.3 Billing Context

Every RP uses the same AoE calendar months. `periodStart` is 00:00:00 AoE on the month's first day (12:00:00 UTC). `periodEnd` is 00:00:00 AoE on the next month's first day and is exclusive. The active interval is `[periodStart - PERIOD_OVERLAP, periodEnd)`, clipped at Unix timestamp zero. Months overlap by `PERIOD_OVERLAP` (§4.1). Either active context MUST be accepted. Capacity, registrations and billing actions remain separate for each period. Nonces are consumed per RP across periods.

A `periodStart` is canonical if and only if it equals `getBillingPeriod(periodStart).periodStart`, i.e. it is 00:00:00 AoE on a month's first day. The Billing Contract and billing verifiers MUST reject a noncanonical `periodStart`. `getBillingPeriod` returns the AoE month containing `timestamp` and its exclusive end; months beginning before Unix timestamp zero MUST be rejected. Clients MUST use the selected context's active interval for registration and proof acceptance. Purchases and top-ups remain limited to the purchase window in §4.2; the overlap does not permit purchases after `periodEnd`. Any future configurable-period extension MUST expose its boundaries on-chain and preserve already purchased periods.

```solidity
uint256 billingAction = uint256(keccak256(abi.encode(
    "world-id-billing-v1",
    scope.chainId, scope.billingContract, scope.rpId, scope.periodStart
))) >> 8;
```

`billingAction: Field` is the billing OPRF input; the RP's `ProofRequest.action` MUST equal it (§4.5). The billing nullifier is `UniquenessNullifier(rpOprfKey, worldIdLeafIndex, scope.rpId, billingAction)`. `UniquenessNullifier` means the existing [Uniqueness Proof nullifier computation](https://github.com/worldcoin/world-id-protocol/blob/main/circom/client_side_proofs/oprf_nullifier.circom), using these inputs and the unblinded OPRF response under the selected key.

### 4.4 Registration Proof

Registration MUST reuse the existing [Uniqueness Proof](https://github.com/worldcoin/world-id-protocol/blob/main/docs/world-id-4-specs/README.md#uniqueness-proofs) circuit, public-input order, proving artifacts and verification key. This spec introduces no new circuit or trusted setup. The user MUST present a valid credential from a registered issuer/schema; the billing nullifier remains independent of which credential is used.

#### 4.4.1 Inputs

The Authenticator derives the billing query from the RP's request (§4.5): `scope.rpId`, the request's nonce and OPRF key, and its action, `billingAction`. The registration proof omits the signal and session creation, and sets the minimum credential genesis issuance time to zero.

The Contract MUST construct the existing uniqueness verifier's public inputs as follows:

| Input | Value |
| --- | --- |
| `nullifier`, `action`, `rpId`, `nonce` | `billingNullifier`, `billingAction`, `scope.rpId`, `authorization.nonce`. |
| `issuerSchemaId`, `expiresAtMin` | Supplied by the Authenticator to `register`. They are not matched against the RP's request; only §4.4.2 applies. |
| `signalHash`, `credentialGenesisIssuedAtMin`, `sessionId` | Zero. |
| Account root, tree depth and credential issuer public key | Root from `proof[4]`, depth `MAX_DEPTH` ([WIP-100 §5.1](https://github.com/worldcoin/world-id-protocol/blob/main/docs/WIPs/wip-100.md#51-parameters)), and issuer key from `CredentialSchemaIssuerRegistry`. |
| OPRF public key | The RP's OPRF public key pinned for the context (§4.4.2). |

`proof: uint256[5]` is the World ID Proof Envelope of [WIP-100 §3.7.2](https://github.com/worldcoin/world-id-protocol/blob/main/docs/WIPs/wip-100.md#372-world-id-proof-envelope).

#### 4.4.2 Verification

These checks apply to the Contract's `register`. TEE Verifiers check billing as in §4.7.

All existing account, authenticator signature, OPRF, nullifier and credential constraints MUST remain enforced, including WIP-100 field, scalar and point validation. The Contract MUST validate the account root and issuer/schema against the existing registries and enforce the existing uniqueness verifier's credential expiry freshness policy.

For the first registration in a billing context, the Contract MUST resolve the RP's existing authorized OPRF key from the registries and pin its key ID and public key.

### 4.5 RP Authorization

The RP's normal `ProofRequest` for the Proof of Embedding Similarity authorizes registration. The RP signs nothing extra and does not need to know whether the user is registered. An Authenticator without a cached registration for the active context (§4.6) registers with that request before proving.

`RegistrationAuthorization` copies the request's version, nonce, timestamps, OPRF key ID, signature and WIP-101 data. The request's `rp_id` and `oprf_key_id` MUST match `scope.rpId` and the context's pinned key (§4.4.2). The Contract MUST reject a version it does not support.

The request's `action` MUST equal `billingAction` for `scope` (§4.3). The RP signs the [RP signature message](https://github.com/worldcoin/world-id-protocol/blob/main/crates/primitives/src/rp.rs) with that action: `version || nonce || createdAt || expiresAt || billingAction`, 81 bytes. This is the packed message, not the SHA-256 value returned by `ProofRequest::digest_hash`.

- **Contract:** `register` MUST verify the authorization as OPRF nodes verify RP requests, with `billingAction` as the action. A registered signer without code is verified by EIP-191 recovery, and `wip101Data` MUST be empty. A signer with code MUST support `IWIP101` through ERC-165 and is verified through [WIP-101](https://github.com/worldcoin/world-id-protocol/blob/main/docs/WIPs/wip-101.md) `verifyRpRequest`, with `wip101Data` of at most 1024 bytes.
- **OPRF nodes:** Unchanged. The signed action is the queried action, `billingAction`.
- **Freshness:** The Contract MUST enforce `createdAt <= now < expiresAt`, `now - createdAt <= maxRequestAge` and `expiresAt - createdAt <= maxRequestLifetime`. The `uint64` limits MUST agree with the OPRF nodes.

Unsigned request fields MUST NOT be treated as RP-authenticated.

### 4.6 Authenticator Cache

The Authenticator SHOULD:

- Cache the billing nullifier and private OPRF witness by account, `BillingContext`, and the RP's OPRF key ID and OPRF public key.
- Keep OPRF witnesses, credential witnesses and query authorization inputs private.
- Refresh account membership, RP authorization and credential verification inputs before generating a new registration proof.
- Expire entries at period end.
- Recover lost entries, including after switching Authenticators, through a fresh authorized query for the same World ID and BillingContext under the same pinned key. The nullifier MUST remain unchanged. An existing registration remains valid and recovery MUST NOT consume more capacity.

### 4.7 Billing Verification

Billing for the Proof of Embedding Similarity is enforced by the [WIP-201][wip-201] TEE Verifier. The sealed request to the Verifier carries `scope: BillingContext`, `billingNullifier: Field` and `request: ProofRequest`.

The TEE Verifier MUST check the RP, active period (§4.3) and application authorization, and that `request.action` equals `billingAction` for `scope`. It MUST confirm finalized `billingNullifier` registration in the Contract before other processing.

The Proof of Embedding Similarity ([WIP-202][wip-202]) MUST prove that `billingNullifier` belongs to the World ID it proves. Its circuit takes `billingNullifier`, `scope.rpId`, `billingAction` and the context's pinned OPRF public key as public inputs, and the cached OPRF witness (§4.6) as private inputs. It MUST:

1. Compute the query `H_4(DS_QUERY; leaf_index, scope.rpId, billingAction)` ([WIP-100 §3.8](https://github.com/worldcoin/world-id-protocol/blob/main/docs/WIPs/wip-100.md#38-shared-constants)), using the same `leaf_index` as its Merkle inclusion proof.
2. Verify the OPRF evaluation's DLogEq proof ([WIP-100 §3.6](https://github.com/worldcoin/world-id-protocol/blob/main/docs/WIPs/wip-100.md#36-discrete-logarithm-equality-proof)) against the pinned key and the blinded query.
3. Unblind the response and constrain `billingNullifier` to the resulting `UniquenessNullifier` (§4.3).

The TEE Verifier MUST supply these public inputs itself, reading the pinned key through `getPinnedOprfKey`. The cached OPRF witness does not depend on a Merkle root, so the proof uses its own fresh root and WIP-202 Root Freshness is unchanged.

### 4.8 Chain State

TEE Verifiers MUST:

- Cache only positive finalized registrations by `(BillingContext, billingNullifier)`; bound the cache and expire entries at period end.
- Read state through an approved provider with TLS terminating inside the enclave. The provider is trusted for state and finality.
- Any cache MUST NOT outlive the period's duration plus 24 hours of grace.

Valid cached registrations MAY serve during provider outages, subject to current authorization, credentials, trusted time and security policy. Provider failure MUST NOT fail process liveness. TEE Verifiers SHOULD apply a two-second timeout to each request-path chain read, make no retries, and share concurrent lookups for the same key.

### 4.9 Fees

Fees are configured in USD per World ID per period and paid in WLD. Each unit of registration capacity permits one distinct World ID to register.

The RP approves the Billing Contract's WLD allowance, then calls `purchaseCapacity`. The contract transfers WLD from the payer to the designated protocol fee address and adds capacity atomically (§4.2). Approval alone does not pay the fee.

| Value | Type | Units |
| --- | --- | --- |
| `pricePerWorldID`, `usdPerWld` | `uint256` | USD scaled by `10^18`. |
| `TOKEN_UNIT` | `uint256` | `10^decimals` for the configured WLD token; MUST fit in `uint256`. |
| `observedAt`, `maxPriceAge` | `uint64` | Exchange-rate timestamp and maximum age, in seconds. |

`pricePerWorldID` is the full-month price. Current-month purchases and top-ups MUST be prorated by seconds left in the AoE month. Future months pay in full. Overlap adds no fee.

```
duration  = periodEnd - periodStart
remaining = periodEnd - max(block.timestamp, periodStart)
charge    = ceil(capacityAmount * pricePerWorldID * remaining * TOKEN_UNIT / (duration * usdPerWld))
```

For example, a purchase with 10 days left in a 30-day AoE month costs `10/30`, about 33.33% of the full-month price. `duration` is the AoE month's own length: 28, 29, 30 or 31 days.

Charges are in WLD base units. The contract MUST use checked USD totals and full-precision conversion.

The price source MUST be an on-chain adapter for the [Chainlink WLD/USD Data Stream](https://data.chain.link/streams/wld-usd-cexprice-streams). A report submitter obtains a signed report and submits it to the adapter. The adapter MUST verify it through the configured Chainlink verifier, require the configured feed ID, and normalize its price to USD scaled by `10^18`. It MUST expose only verified `usdPerWld` and `observedAt` values to the Billing Contract. Unverified reports MUST NOT update the stored rate.

`quotePurchase` and `purchaseCapacity` read that verified rate; a getter alone does not obtain or authenticate a report. The charge MUST NOT exceed the payer's `maxWldAmount`. Zero, future-dated, stale or unavailable prices MUST reject the purchase without affecting existing capacity. The feed ID, verifier, adapter, report format, source scale and `maxPriceAge` MUST be selected and tested before release (§8).

Unused capacity receives no refund and does not roll over. Top-ups and later parameter changes MUST NOT alter earlier purchases.

> [!WARNING]
> OPRF key rotation is not currently supported. A rotation that replaces an RP's pinned key before period end invalidates that period's `billingNullifier`s without refund, and the Contract rejects every registration for that period until it ends.

## 5. Rationale

- **Billing nullifier:** Counts one World ID across credentials without publishing its account leaf index.
- **Cached witness:** Avoids repeated billing OPRF queries.
- **Registration capacity:** One unit covers one distinct World ID for one RP and period, matching the RP's monthly user budget.
- **Overlapping months:** Capacity covers the calendar month in every time zone.
- **Prorating:** An RP that starts or tops up mid-month pays only for the time left in the AoE month.
- **No rebate or rollover:** Keeps each month's capacity and revenue independent and avoids refund or carry-forward accounting.
- **Reusing the RP request:** The RP cannot know whether a user is already registered, so its normal request must be enough to register. Setting its action to `billingAction` lets OPRF nodes and the Contract verify it unchanged.

## 6. Security

An RP request is bearer authorization until bound to a holder. Consuming the nonce limits registrations but does not bind authorization to the intended holder.

Any RP request signed with `billingAction` can authorize one registration in that context. It yields only the `billingNullifier`, never a nullifier for any other action.

A paid-state lookup alone does not prove that the prover owns the registered World ID. The Embedding Similarity circuit binds the two (§4.7).

Registrations are linkable within their billing context. Implementations MUST NOT log credentials, private witnesses or sealed payloads.

## 7. Backwards Compatibility

This spec is additive. It adds the Billing Contract and a billing check for select RPs' Proofs of Embedding Similarity. OPRF nodes, other proof types, RPs and contracts are unchanged.

The billing action encoding and pinned keys MUST remain fixed for active periods. Rollout, rollback and pauses MUST preserve purchased capacity and registrations.

## 8. Experimental Release

Before enablement:

- Select RPs, deployment addresses, the proxy administrator, designated protocol fee address, initial USD price and request limits. Select the Chainlink feed, verifier, adapter, report format, scale and price-age limit (§4.9).
- The contract and TEEs MUST adopt the billing authorization of §4.5. WIP-202 requests MUST carry `billingAction` as their action, including with a `session_id`, and WIP-202 MUST adopt the billing constraints of §4.7.

The proxy owner updates `pricePerWorldID` and other billing settings through the authorized on-chain setters. Changing the price does not require a node software release and MUST preserve earlier purchases.

TEE operators deploy compatible verifier images. Authenticators and RPs approve the accepted attestation measurements and keys under [WIP-201][wip-201]. The Engine Provider signs engine releases; the RP's engine policy decides which releases to accept. Operators MUST NOT treat an unsigned or unapproved release as accepted.

OPRF operators deploy compatible node software and keep pinned period keys available through period end. Clients verify OPRF proofs against the registry-authorized public keys, including the pinned key for an active billing context. Before enablement, record the operators, policy owners and contract upgrade owner and agree on compatible versions and key retention.

## 9. Rejected Alternatives

- **Per-proof charging:** Rejected for this experiment because it charges repeated comparisons and makes monthly costs less predictable. Any future per-proof scheme requires a separate proposal defining pre-purchase and expiry rules.
- **Credential-specific registration:** Charges one World ID more than once across credentials or renewals.
- **Off-chain-only billing:** Rejected for this experiment because capacity and registration would depend on a billing operator.
