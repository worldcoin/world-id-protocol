## 1. Abstract

This spec builds upon [WIP-109][wip-109] and describes a standalone process by which an authenticator already registered to a World ID obtains a copy of the credential vault from another registered authenticator of the same World ID.

It reuses the pairing, pairing code, key derivation and message-bridge transport of [WIP-109][wip-109], and defines the pairing URI action, the [WIP-105][wip-105] CBOR messages, signatures that bind both sides to registered keys of the same account, and how the received vault is merged.

## 2. Motivation

[WIP-109][wip-109] delivers the vault together with a registration only if the user separately approves sharing it (§3.7.3). An authenticator registered without the vault cannot generate proofs for the user's credentials until it obtains them. Likewise, a credential issued to one authenticator after another was registered reaches the other only if it is copied.

This spec defines a user-initiated, one-shot copy between two registered authenticators. Continuous synchronization of vaults is out of scope (WIP-108); this spec does not depend on it.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

Authenticator roles and keys follow [WIP-104][wip-104]. Messages MUST conform to [WIP-105][wip-105]. Where this spec applies a section of [WIP-109][wip-109], the following substitutions apply inside that section. The roles **Requesting Authenticator** and **Approving Authenticator** mean the roles defined below. "Registration", "new authenticator" and "new device" mean this sync and the **Requesting Authenticator**. A reference to another [WIP-109][wip-109] section means the section with the same number in this spec. Text about `InsertAuthenticator` or the already-registered case does not apply.

### 3.1 Terminology

The following terms apply only to this spec.

- **Requesting Authenticator**: A registered authenticator of the user's World ID, Admin or Proving, that asks for the vault.
- **Approving Authenticator**: Another registered authenticator of the same World ID, Admin or Proving, that holds a vault and sends a copy of it once the user approves.
- **Vault**: The `vault` map of [WIP-109][wip-109] §3.6.2: a `format` and the WalletKit `export_vault_for_backup` output as `data`.
- **Pubkey set**: The signing keys registered to an account, by slot (`pubkey_id`). It MAY be read from an indexer or from the `WorldIDRegistry`'s events directly, as in [WIP-109][wip-109] §3.7.2 step 2.
- **Bridge**, **Pairing Secret** and **Pairing Code**: As defined in [WIP-109][wip-109] §3.1.

### 3.2 Overview

This section is non-normative. The flow is that of [WIP-109][wip-109] §3.2 without the `InsertAuthenticator` operation. The **Requesting Authenticator** shows the Pairing URI and then the pairing code. The user scans the URI and types the code on the **Approving Authenticator**, approves and completes device verification. The **Approving Authenticator** exports its vault, signs it and returns it. The **Requesting Authenticator** verifies the signature against the account's pubkey set and merges the vault into its own.

The exchange always starts on the **Requesting Authenticator**. An **Approving Authenticator** that offers to "send credentials to another device" tells the user to start the sync on that device.

### 3.3 Pairing Secret, Pairing Code and Derived Values

The pairing secret, pairing code, code normalization, Argon2id expansion, `request_id`, `code_key` and `transport_secret` are defined in [WIP-109][wip-109] §3.3, whose §3.3.1 and §3.3.2 are replaced by §3.3.1 and §3.3.2 below. Every label `WORLD-ID/WIP-109/<purpose>` is replaced by `WORLD-ID/WIP-115/<purpose>`. For example:

```text
request_id = lowercase_hex(HKDF(pairing_secret, info = "WORLD-ID/WIP-115/REQUESTID"))
```

All requirements of [WIP-109][wip-109] §3.3 on generating, revealing and discarding these values apply.

#### 3.3.1 Sync Digest

The **Requesting Authenticator** commits to the request parameters in the Pairing URI, so the **Approving Authenticator** can detect a substituted request:

```text
sync_digest = SHA-256(
    "WORLD-ID/WIP-115/SYNC"         // ASCII
 || request_id                      // 32 bytes (the raw HKDF output)
 || leaf_index                      // 8 bytes, unsigned big-endian
 || authenticator_pubkey            // 32 bytes, WIP-100 §4 wire encoding
 || response_pubkey                 // 1216 bytes, X-Wing encapsulation key
)
```

All fields are fixed-width. Every member of `params` except `name` and `sync_sig` is covered. A future version that adds a parameter MUST add it to the digest under a new label.

#### 3.3.2 Sync Signature

The **Requesting Authenticator** proves that it holds the signing key for `authenticator_pubkey`. The digest is lowered to a field element as in [WIP-109][wip-109] §3.3.2:

```text
d_hi, d_lo = sync_digest[0..16], sync_digest[16..32]          // big-endian integers
m          = H_3(ds("WORLD-ID/WIP-115/SYNCSIG"); d_hi, d_lo)   // WIP-100 §3.3.2
sync_sig   = EdDSA-Sign(signing_key, m)                        // 64 bytes, WIP-100 §3.5.2
```

Registered signing keys are public, so this signature, not knowledge of a registered key, entitles the **Requesting Authenticator** to the vault.

#### 3.3.3 Vault Signature

The **Approving Authenticator** binds the vault to this request and to its own registered signing key:

```text
vault_digest = SHA-256(
    "WORLD-ID/WIP-115/VAULT"        // ASCII
 || sync_digest                     // 32 bytes
 || pubkey_id                       // 8 bytes, unsigned big-endian: the Approving Authenticator's slot
 || SHA-256(vault.format)           // 32 bytes, over the UTF-8 bytes of the text string
 || SHA-256(vault.data)             // 32 bytes
)
v_hi, v_lo = vault_digest[0..16], vault_digest[16..32]        // big-endian integers
m          = H_3(ds("WORLD-ID/WIP-115/VAULTSIG"); v_hi, v_lo)
vault_sig  = EdDSA-Sign(signing_key, m)                        // 64 bytes
```

### 3.4 Pairing URI

The **Requesting Authenticator** encodes the pairing in a [WIP-105][wip-105] deeplink with namespace `auth`, version `v1` and action `syncVault`:

```text
worldid://auth/v1/syncVault?s={pairing_secret}&d={sync_digest}&b={bridge_domain}
```

The parameters and all requirements of [WIP-109][wip-109] §3.4 apply, with `d` carrying `sync_digest`. This includes strict parsing, which accepts only the authority `auth` and the path `/v1/syncVault`, the bridge allowlist, the logging restrictions and the absence of an explicit expiry. Opening the URI MUST NOT imply approval.

### 3.5 Transport

[WIP-109][wip-109] §3.5 applies, with the label substitution of §3.3: the request AAD uses `WORLD-ID/WIP-115/REQUEST`, and the response AAD and HPKE `info` use `WORLD-ID/WIP-115/RESPONSE`. The message size limits and the rules on rejection, authentication order and fallback apply unchanged.

### 3.6 Messages

Requests and responses use the CBOR encoding and envelope of [WIP-109][wip-109] §3.6, including its conventions for maps, byte strings, integers and omitted optional fields.

#### 3.6.1 `worldid_auth_v1_syncVault` (Requesting → Approving)

The request MUST include `id` set to the `request_id` text string; it MUST NOT be null. The **Approving Authenticator** MUST reject a message whose `id` differs from the value it derived.

| Member | Required | Description |
| ------ | -------- | ----------- |
| `leaf_index` | REQUIRED | Index of the account the **Requesting Authenticator** is registered to, an unsigned integer from 1 to 2^30 − 1 ([WIP-109][wip-109] §3.6.2). |
| `authenticator_pubkey` | REQUIRED | The **Requesting Authenticator**'s registered signing public key in the compressed wire representation of [WIP-100 §4](wip-100.md#4-public-key-representation), as a 32-byte CBOR byte string. |
| `response_pubkey` | REQUIRED | Ephemeral X-Wing encapsulation key used to seal the response, as a 1216-byte CBOR byte string. Generated per attempt. |
| `name` | OPTIONAL | Human-readable, self-reported label. CBOR text string, at most 64 UTF-8 bytes. It is advisory and not covered by `sync_digest`; the **Approving Authenticator** MAY ignore it. |
| `sync_sig` | REQUIRED | Sync Signature (§3.3.2): the 64-byte EdDSA signature as a CBOR byte string. |

Example: sync request (byte strings abbreviated).

```text
{
  "version": "1.0",
  "id": "5c1d0e8f3a7b29c4d6e0f1a2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e6",
  "method": "worldid_auth_v1_syncVault",
  "params": {
    "leaf_index": 42,
    "authenticator_pubkey": h'119ab03f…',
    "response_pubkey": h'420044e7…',
    "name": "Chrome on MacBook",
    "sync_sig": h'8e41c0…'
  }
}
```

#### 3.6.2 Success response (Approving → Requesting)

A response with the same `id`.

| Member | Required | Description |
| ------ | -------- | ----------- |
| `pubkey_id` | REQUIRED | The **Approving Authenticator**'s slot on `leaf_index`, an unsigned integer below `NUM_KEYS` ([WIP-100][wip-100] §3.8). |
| `vault` | REQUIRED | The vault, with the format, size limit and oversize handling of [WIP-109][wip-109] §3.6.2: `format` = `"walletkit_plaintext_v1"`, and `data` of at most 1 MiB (1,048,576 bytes). If the vault would exceed this limit, the **Approving Authenticator** responds `vault_too_large` and MUST NOT truncate the vault. The **Requesting Authenticator** MUST reject a response whose `vault.data` exceeds it, without merging. |
| `vault_sig` | REQUIRED | Vault Signature (§3.3.3): the 64-byte EdDSA signature as a CBOR byte string. |

Example: successful sync response (byte strings abbreviated).

```text
{
  "version": "1.0",
  "id": "5c1d0e8f3a7b29c4d6e0f1a2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e6",
  "result": {
    "pubkey_id": 0,
    "vault": { "format": "walletkit_plaintext_v1", "data": h'53514c69746520666f726d61742033…' },
    "vault_sig": h'2b7f19…'
  }
}
```

#### 3.6.3 Error response (Approving → Requesting)

Method error responses use the request's `id`. Envelope errors and the shared `invalid_params` and `internal_error` codes follow [WIP-105][wip-105]. The table lists those shared codes and the additional codes defined by this method.

| `code` | Meaning |
| ------ | ------- |
| `invalid_params` | Missing or malformed field, a `sync_digest` that differs from the Pairing URI, or an invalid `sync_sig`. |
| `internal_error` | The **Approving Authenticator** could not complete the request for any other reason. |
| `user_rejected` | The user declined. |
| `not_authorized` | `leaf_index` is not an account of the **Approving Authenticator**, or one of the two signing keys is not registered to it. The code does not say which (§3.7.2). |
| `vault_too_large` | The vault exceeds the limit of §3.6.2. Retrying does not help until the vault is smaller. |

### 3.7 Approving Authenticator Procedure

#### 3.7.1 Receive

1. Follow [WIP-109][wip-109] §3.7.1 steps 1 to 3: parse the Pairing URI, fetch the request and authenticate it with the entered code.
2. Validate the CBOR encoding and [WIP-105][wip-105] envelope, that `method` is `worldid_auth_v1_syncVault`, `id == request_id`, and the encodings and bounds of all `params`. Recompute `sync_digest` from the params and, if it differs from the URI value, respond `invalid_params`. Verify `sync_sig` against `authenticator_pubkey`; on failure respond `invalid_params`. Ignore a `name` it does not accept, and display an accepted one only as untrusted text.

#### 3.7.2 Check account state

1. `leaf_index` MUST be an account whose vault the **Approving Authenticator** holds; otherwise respond `not_authorized`. Finding its own signing key in the pubkey set of `leaf_index` is not sufficient, because a signing key can also be registered to other accounts ([WIP-109][wip-109] §3.7.2 step 4).
2. Read the pubkey set of `leaf_index`, retrying read failures with bounded backoff. If it cannot be read, respond `internal_error`.
3. If the **Approving Authenticator**'s own signing key or `authenticator_pubkey` is not in the set, respond `not_authorized`.

The response MUST NOT reveal which check failed; the **Approving Authenticator** shows the reason only to its own user. It MUST NOT request consent or export the vault until all checks pass.

#### 3.7.3 Approve

1. The **Approving Authenticator** MUST show an explicit consent screen that at least conveys the following information:
    1. The identified authenticator will receive a copy of all credentials in the vault, including biometric data if the vault contains any.
    2. Which authenticator will receive them: any name the **Approving Authenticator** holds for that signing key, else the `name` from the request marked as unverified, else that the authenticator is unnamed. Names MUST NOT be looked up by slot alone, because slots are reused.
    3. The copy cannot be recalled. Removing that authenticator later does not delete credentials it has already received.
    4. The user should not share credentials with authenticators they don't trust.

    Approval MUST be an explicit user action and MUST NOT be pre-selected.
2. The top-level items 2 and 3 of [WIP-109][wip-109] §3.7.3 apply: a fresh device biometric or device PIN check MUST succeed before the vault is exported. If the user rejects the request or cancels device verification, respond `user_rejected`. If device verification fails or is unavailable, respond `internal_error`.

#### 3.7.4 Respond

1. Export the vault it holds for `leaf_index` after device verification succeeds. If the export fails, respond `internal_error`. Handle an oversized vault as in §3.6.2.
2. Compute `vault_sig` (§3.3.3) with its own signing key and slot.

Every response, success or error, is built, sealed, encrypted and delivered as in [WIP-109][wip-109] §3.7.5. If the response cannot be sealed to `response_pubkey`, or delivery fails after bounded retries, the **Approving Authenticator** tells the user to start again on the **Requesting Authenticator**. After sending an error, it shows the reason locally. In every case the attempt then ends.

### 3.8 Requesting Authenticator Procedure

1. The **Requesting Authenticator** MUST NOT start a sync unless it is registered to `leaf_index` with the signing key it sends as `authenticator_pubkey`.
2. Generate `pairing_secret`, `pairing_code` and the X-Wing `response_pubkey` keypair. Derive `request_id` and `transport_secret` (§3.3), compute `sync_digest` and `sync_sig`, then build the request, encode it as CBOR and encrypt it (§3.5).
3. Publish the request, display the Pairing URI, reveal the pairing code and poll as in [WIP-109][wip-109] §3.8 steps 3 and 4. On `completed`, continue with step 4 below.
4. Authenticate and decrypt the outer response, then open the HPKE seal. Validate its CBOR encoding, [WIP-105][wip-105] envelope, `id == request_id`, and the field types and bounds in §3.6 before acting on either `result` or `error`. Reject any response that fails these checks.
5. On `result`:
    1. Reject a `vault.format` it does not support.
    2. Read the pubkey set of `leaf_index`, retrying read failures with bounded backoff. Verify `vault_sig` against the signing key at slot `pubkey_id`. Reject the response if the slot is empty or the signature is invalid.
    3. Merge the vault (§3.9) and delete the session. It SHOULD tell the user whether credentials were added.
6. On `error`: show a local message for `code` and delete the session. `error.message` comes from the other device; the **Requesting Authenticator** MAY show it only as untrusted text.

A rejection in step 4 or 5, a pubkey set that cannot be read, or a failed merge ends the attempt without merging. The **Requesting Authenticator** MUST tell the user that no credentials were added and offer a new pairing. A lost response or expired session leaves nothing to reconcile and is handled the same way. Both authenticators MUST discard the pairing code, derived keys, any response private key and any plaintext copy of the vault outside their own vaults when an attempt completes, fails, expires or is cancelled.

### 3.9 Merging

The **Requesting Authenticator** MUST merge a received vault into its own vault for `leaf_index` as follows:

1. The merge adds every credential version in the received vault that is not held locally. What identifies a version is defined by the vault format; for `walletkit_plaintext_v1` it is the whole credential record, including its timestamps, credential and associated data. It MUST NOT delete, replace or modify any local credential version. A credential absent from the received vault MUST NOT be deleted locally.
2. Merging a vault whose versions are already held MUST NOT change the local vault.
3. The merge MUST be atomic: if the received vault is malformed or fails the format's structural validation, nothing is merged. The received vault is supplied by another device: the **Requesting Authenticator** MUST open it read-only and separately from its own vault, and validate it before merging.
4. These rules apply even when the local vault is empty. The **Requesting Authenticator** MUST NOT restore the received vault in place of its own.

WalletKit `merge_vault_from_backup` meets these requirements. WalletKit `import_vault_from_backup` does not: it restores into an empty vault without validating the received records. When both vaults hold different versions of the same credential, both are kept and which one is used for proofs is a local decision. Deletions do not propagate in either direction: a credential deleted on the **Approving Authenticator** remains on a **Requesting Authenticator** that already holds it, and a credential deleted on the **Requesting Authenticator** returns with the next sync that contains it.

Before using a merged credential, the **Requesting Authenticator** MUST check that its `sub` is the value derived from `leaf_index` and the credential's blinding factor, as [WIP-109][wip-109] §5 requires for imported credentials. It SHOULD run this check before merging and reject the whole vault if any credential fails it, because a later sync passes merged versions on and no sync removes them.

## 4. Rationale

- **A separate action instead of another registration.** Copying credentials changes no registry state and needs neither an Admin Authenticator nor registration consent. A dedicated action lets the consent screen describe exactly what is shared, and keeps the [WIP-109][wip-109] already-registered case limited to completing a registration.
- **Started by the Requesting Authenticator.** The response is sealed to a key that the **Requesting Authenticator** must send first, and the bridge carries exactly one request and one response, so starting from the **Approving Authenticator** would need another round trip. The code is still typed into the authenticator that releases the credentials, as in [WIP-109][wip-109]. A browser authenticator can display a QR code but usually cannot scan one.
- **Any registered authenticator may approve.** Sharing the vault changes no registry state, so it is not a management operation under [WIP-104][wip-104] §3.1. Any authenticator that holds the vault can already disclose it, so limiting approval to Admin Authenticators would constrain only compliant implementations. User approval and device verification on the **Approving Authenticator** are the controls.
- **A signature on each side.** Signing keys and their slots are public, so the **Approving Authenticator** requires `sync_sig` as proof of possession. The transport proves only that a response comes from the device the user typed the code into. Without `vault_sig`, an application that intercepts the Pairing URI and obtains the code could inject credentials that a merge never removes. Verifying `vault_sig` against the account's pubkey set is the counterpart of the on-chain check in [WIP-109][wip-109] §3.8 step 5.
- **`leaf_index` in the request.** It binds the request to one account, lets an **Approving Authenticator** that holds several World IDs export the right vault, and lets it refuse an account it does not hold (§3.7.2 step 1).
- **Additive merge.** A one-shot copy carries no ordering or deletion records. A union of versions cannot lose data and gives the same result in any order and on any retry.
- **One error for all membership failures.** Separate codes would let an attacker who obtains the code test whether the user's authenticator belongs to a guessed `leaf_index`. The **Approving Authenticator** still tells its own user the specific reason.
- **A dedicated `vault_too_large` code.** [WIP-109][wip-109] reports an oversized vault as `internal_error`, because there the vault is optional. Here the vault is the whole payload. Versions are never pruned and each merge adds the other side's history, so a vault that reaches the limit stays there, and the error must not look transient. Omitting superseded or expired versions from the export can be added in a later version.
- **Own labels.** Distinct labels in every derivation, digest and signature make a sync message unusable as a registration message and the reverse.
- **Full vault only.** Sharing selected credentials needs a vault export that can be restricted to them. It can be added in a later version.

## 5. Security

[WIP-109][wip-109] §5 applies, including the bridge, intercepted Pairing URI, code guessing, malicious QR code and malicious deeplink handler cases. In addition:

- **Requester entitlement.** The vault is sent only for the **Approving Authenticator**'s own account, and only to a holder of a signing key registered to that account. An Admin Authenticator can insert any public signing key into its own account, so a check based only on key membership would let an attacker add the user's key to the attacker's account and request the user's vault; §3.7.2 step 1 prevents this. A user who scans an attacker's URI and enters the attacker's code exposes no credentials unless the attacker also holds a registered signing key of that account. This differs from [WIP-109][wip-109], where the same mistake can register the attacker's device.
- **Compromised authenticator.** A compromised but still registered authenticator can request the vault; the user must still approve on the **Approving Authenticator** with device verification. Removing an authenticator ([WIP-104][wip-104] §3.5) stops later syncs to it, because the **Approving Authenticator** checks the current pubkey set, but copies already sent cannot be recalled. A compromised **Approving Authenticator** can send credentials that pass `vault_sig`, including versions that a local selection rule prefers over legitimate ones. The `sub` check of §3.9 limits their use. Removing them is a local action, and until then later syncs carry them to other authenticators.
- **Stale account state.** An **Approving Authenticator** that reads a lagging source can treat a just-removed authenticator as registered, and the user's approval is then the remaining control. Implementations SHOULD read the pubkey set from a source that reflects the registry's latest state, so that removals take effect promptly. An authenticator registered moments earlier may not be visible yet; the sync then fails with `not_authorized` and the user retries.
- **Replay and downgrade.** `sync_sig` and `vault_sig` bind `request_id`, `leaf_index` and `response_pubkey`, so a captured request or response is useless in another pairing. There is one method version and one vault format and no negotiation. Receivers reject unknown formats and never fall back to an unauthenticated transport ([WIP-109][wip-109] §3.5). An older vault cannot remove credentials, because merging is additive.
- **Plaintext vault.** The vault is unencrypted once the response is opened. Both authenticators discard every copy outside their own vaults when the attempt ends (§3.8).
- **Privacy.** The request reveals `leaf_index` and `authenticator_pubkey` only to holders of `transport_secret`. Both are already public in the registry, and the bridge sees neither. Because `not_authorized` does not say which check failed, a requester cannot use the **Approving Authenticator** to learn whether its user belongs to a guessed `leaf_index`.

## 6. Backwards Compatibility

There are no changes to contracts, bridge endpoints or [WIP-109][wip-109]. This spec adds a deeplink action and a method. An authenticator that implements only [WIP-109][wip-109] rejects the `syncVault` path under the strict parsing rules of [WIP-109][wip-109] §3.4 and is otherwise unaffected. The [WIP-109][wip-109] already-registered case remains available to complete a registration whose response was lost.
