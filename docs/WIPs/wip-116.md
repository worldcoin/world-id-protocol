## 1. Abstract

This spec lets a Relying Party (RP) request a session from a seed it provides instead of a session id it stores. Every Authenticator of a World ID derives the same session id for the same RP and seed. The RP can recognize a returning user from a Session Proof alone, for example to log them in, without keeping a session id per user on the client.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

### 3.1 Proof Request

The `session_id` field of a `ProofRequest` gains a fourth form:

| Wire value                  | Meaning                                                  |
| --------------------------- | -------------------------------------------------------- |
| absent / `null`             | No session                                               |
| `"create"`                  | Mint a session from a random seed                        |
| `"session_<hex>"`           | Prove an existing session                                |
| `"seed_<hex>"` (new)        | Derive the session from the given `oprf_seed`            |

`<hex>` is the 32-byte big-endian `oprf_seed`. The seed MUST have the session seed prefix (MSB `0x01`), the same as a seed generated for `"create"`.

Valid combinations:

| `proof_type` | `session_id` | Use                                                                        |
| ------------ | ------------ | -------------------------------------------------------------------------- |
| `session`    | `seed_<hex>` | Prove the seeded session                                      |
| `uniqueness` | `seed_<hex>` | Uniqueness Proof bound to the seeded session |

The RP signature message is unchanged. The seed is not signed (see §3.3).

### 3.2 RP Whitelist

1. Authenticators MUST only allow seeded requests for RPs that are explicitly whitelisted by the Authenticator Provider. The distribution of this whitelist is out of scope and up to the authenticator provider. It could e.g., distributed as part of an app release.
2. Authenticators MUST be transparent about the members of the whitelist and MUST allow users to remove RPs from the whitelist they do not trust.
3. Authenticators SHOULD allow users to manually add RPs to the whitelist.

### 3.3 Derivation of Session Commitment

1. The Authenticator derives `r` from the request's `oprf_seed` exactly as for `"create"` (session seed OPRF query, MSB `0x01`), and computes `commitment = H(DS_C, leaf_index, r)`.
2. The Authenticator MAY cache `r` per `(rp_id, oprf_seed)` and skip the seed query.
3. The response carries `session_id = (commitment, oprf_seed)` and the proof requested by `proof_type`, with `commitment` as the `id_commitment` public signal.

Because `r` depends only on `leaf_index`, `rp_id` and `oprf_seed`, all Authenticators of a World ID derive the same session id.

### 3.3 RP Verification

1. The RP MUST check that the returned `session_id.oprf_seed` equals the requested seed.
2. The RP verifies the proof against `session_id.commitment` as for any session, and identifies the user by `commitment`.

### 3.4 OPRF Nodes and Contracts

No change. OPRF Nodes already accept seed queries under both Session and Uniqueness requests. On-chain verifiers only see `commitment` and can't tell seeded sessions from random ones.

## 4. Rationale

1. **RP-provided seed instead of a fixed one.** A fixed seed is a special case. Several seeds let an RP keep separate ids per user (e.g. per tenant) at no extra risk, because `r` is scoped to `rp_id`.
2. **Sessions instead of repeated Uniqueness Proofs.** A uniqueness nullifier stays one-time use. Authenticators refuse to disclose the same nullifier twice.
3. **Seed not signed.** The RP check in §3.3 is enough, and the RP signature message stays unchanged across all RP SDKs.

## 5. Security

1. **No sybil resistance from the seed alone.** The circuit does not prove that `r` was derived from `oprf_seed`, so a modified Authenticator can produce any number of commitments. Login stays safe: a foreign commitment can't be proven and an unknown one matches no account. RPs that need one account per user MUST create the account with a `uniqueness` × `seed_<hex>` request.
2. **Tracking within an RP.** A seeded session is a stable per-RP identifier. Uniqueness Proofs bound to it are linkable to each other. This is why §3.2 requires an allowlist. Authenticators SHOULD tell the user the RP can recognize them. Ids for different RPs are unlinkable.
3. **The allowlist is enforced by Authenticators only.** It protects users from RPs. A modified Authenticator that ignores it only exposes its own user.
4. **OPRF key rotation** for an RP changes all of its seeded session ids.

## 6. Backwards Compatibility

The change is additive. Authenticators that don't implement this spec reject `"seed_<hex>"` when parsing the request.
