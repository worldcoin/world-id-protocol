> [!NOTE]
> This spec outlines a draft functionality for beta testing. Changes are expected.

## 1. Abstract

This spec adds the `embedding_similarity` proof type to the World ID proof request. With it, an RP asks for a [WIP-202][wip-202] Proof of Embedding Similarity and states the challenge, the Flamingo configurations it accepts ([WIP-201][wip-201]), its Authenticator Assertion requirements ([WIP-106][wip-106]) and its Credential policy.

## 2. Motivation

The proof request today supports uniqueness and session proofs. A WIP-202 proof needs values these proof types do not carry: the challenge, the accepted Flamingo configurations and the AAT requirements. Without a standard place for them, each integration invents its own.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

1. The proof request is the `ProofRequest` of [`world-id-primitives`](https://docs.rs/world-id-primitives/latest/world_id_primitives/request/struct.ProofRequest.html). This spec adds a proof type and fields; all other fields keep their meaning.
2. Field elements are serialized as in the existing request (e.g. `nonce`). Byte strings are lowercase hex.

### 3.1 Proof Type

`proof_type` MUST be `embedding_similarity`. Such a request:

1. MUST omit `action`; the proof has no nullifier.
2. MAY set `session_id` to an existing session, to require the same World ID as an earlier proof. It MUST NOT be `create`.
3. MUST have exactly one entry in `requests`. Its `issuer_schema_id` names the Credential, which MUST be the PoH Credential ([WIP-202 §4.1][wip-202]), and its `genesis_issued_at_min` applies as usual.
4. MUST carry the `embedding_similarity` object below.

### 3.2 `embedding_similarity` Object

| Field | Type | Description |
| --- | --- | --- |
| `challenge_hash` | Field element | `R(SHA-256(challenge))` of the challenge image ([WIP-202 §4.3][wip-202]). |
| `engine_configs` | array | The accepted Flamingo configurations, in order of preference ([WIP-201 §3.5.3][wip-201]). Each entry: `engine_hash` (hex), `pipeline` (integer) and `match_strictness` (integer). Each pipeline MUST follow the WIP-202 entry layout. |
| `aat` | object, optional | AAT requirements. Absent means the RP accepts proofs without an AAT. |
| `aat.required` | boolean | Whether the RP rejects proofs without an AAT. |
| `aat.authenticator_provider_key_hashes` | array of field elements | Accepted Authenticator Provider keys ([WIP-106 §3.2][wip-106]). |
| `aat.platforms`, `aat.sec_levels`, `aat.user_presence` | arrays of integers | Accepted values ([WIP-106 §3.5][wip-106]). An empty array accepts every value. |
| `aat.min_build_version` | integer | The RP's minimum `build_version`; `0` sets no minimum. |

### 3.3 Authenticator Behavior

1. The Authenticator MUST choose the first entry of `engine_configs` its device supports and the Verifier has loaded ([WIP-201 §3.5.3][wip-201]), and MUST verify that entry's release manifest before sending biometrics.
2. If `aat` is present, the Authenticator MUST obtain an AAT from an Authenticator Provider whose key hash is listed, and pass `aat.min_build_version` as `min_build_version` ([WIP-201 §3.3][wip-201]). If it cannot and `aat.required` is `true`, it MUST NOT generate a proof.
3. The Authenticator MUST reject a request that violates [Proof Type](#31-proof-type).

### 3.4 RP Behavior

The RP MUST verify the proof against the values of its own request ([WIP-202 §4.7][wip-202]), not against values returned by the Authenticator.

## 4. Rationale

1. **A proof type, not a request item.** The values concern the whole proof, not one Credential, so they sit next to `proof_type`.
2. **Configurations as readable tuples.** The Authenticator must see the pipeline to judge whether its device supports it; `engine_config_hash` values would hide it.
3. **Key hashes instead of keys.** They match the public value WIP-106 exposes, so the RP compares one value.

## 5. Security

1. **Unsigned fields.** The RP signature covers only `nonce`, `created_at`, `expires_at` and `action`. A party between RP and Authenticator can alter the `embedding_similarity` object. Lowering the requirements does not help it, because the RP checks the proof against its own request; pointing to an Engine does not either, because the Authenticator verifies the release manifest itself.
2. **Challenge freshness.** The RP is responsible for a `challenge_hash` that shows the party it interacts with now.

## 6. Backwards Compatibility

Authenticators that do not know `embedding_similarity` reject the request as an unknown proof type. Existing proof types are unchanged.
