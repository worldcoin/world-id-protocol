## 1. Abstract

This spec defines the **Flamingo Verifier** (also called **Verifier** in the context of this spec): a trusted execution environment (TEE) service that receives up to eight entries (images or embeddings, each with opaque metadata), a list of up to four entries to compare, a `method` and an `assurance_level`; hands them to a sandboxed biometric Engine that checks and compares them; and, when the Engine accepts, signs a token committing to the whole request and exposing the method, the assurance level and the compared entries.

The token is its only signed output. [WIP-111][wip-111] consumes it to prove the comparison to a Relying Party without revealing any item.

## 2. Motivation

Comparing two embeddings is cheap. Getting an embedding anyone should believe is not.

Extraction runs a model over raw media, which is impractical in a ZK circuit. The checks that make an extracted embedding meaningful — image quality, Presentation Attack Detection, anti-fraud signals — are even worse. Much of these models require complex inputs and advanced signals, and may even rely on model obscurity.

Running extraction and comparison in an attested Trusted Execution Environment keeps the inputs private and the execution verifiable. Committing to the raw inputs makes the result usable by a verifier who trusts neither the prover nor the prover's device.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

### 3.1 Request

The request MUST be encrypted to the Verifier. Its plaintext is a deterministic CBOR map with the following fields.

| Field | Type | Bounds | Interpreted by |
| --- | --- | --- | --- |
| `method` | `uint` | `< 2^16` | the Engine ([§3.3](#33-engine)), which defines the algorithm, e.g. DeepFace with LightGuard. The Verifier signs it without interpreting it. |
| `assurance_level` | `uint` | `< 2^8` | the Engine ([§3.3](#33-engine)). The Verifier signs it without interpreting it. |
| `meta` | bytes | ≤ 1 KiB | the Engine. Hints that do not change what is proven, e.g. experiment flags. |
| `entries` | array of `Entry` | `1..=MAX_ENTRIES` | the Engine |
| `compare` | array of `uint` | 2 to `MAX_COMPARED` distinct indices into `entries`, in order | the Engine, which compares every pair of the listed entries |

An `Entry` is a map `{ data: bytes, meta: bytes }`. `data` is an encoded image or an embedding. `meta` (≤ 256 bytes) tells the Engine how to read it, e.g. which frame of a capture it is. Both are opaque to the Verifier.

| Constant | Value | Description |
| --- | --- | --- |
| `MAX_ENTRIES` | `8` | Maximum entries per request. |
| `MAX_COMPARED` | `4` | Maximum compared entries, fixed by the token layout ([§3.4.1](#341-token-claims)). Bounds the Engine to six comparisons. |

The Verifier MUST reject a request that is not exactly this shape, that exceeds a bound, or whose `compare` repeats or names an out-of-range index. It MAY impose further byte limits on `entries[].data`.

Which entry plays which role (Credential item, live frame, challenge) is a convention between the `method` and the consuming circuit, expressed by the entries' positions in `compare`. The Verifier does not know it.

### 3.2 Response

The response MUST be encrypted to the requester and SHOULD be padded to a fixed length, so its size reveals neither the outcome nor the size of the debug report.

| Variant | Contents |
| --- | --- |
| `Success` | `token` ([§3.4](#34-token)), `signing_key_attestation`, `debug_report` |
| `Failed` | `reason`, `debug_report` |

`reason` is one of `malformed_inputs`, `input_too_large`, `rejected(validation_reason)`, `no_match`, `internal`. `validation_reason` is the Engine's reason code, passed through.

`debug_report` is optional bytes copied from the Engine. It is not part of the token. The Verifier MAY truncate it to fit the padded length.

The Verifier MUST emit a token only when the Engine returns `Pass`.

### 3.3 Engine

Extraction, quality checks, Presentation Attack Detection and comparison are delegated to an Engine inside the Verifier. The Engine defines each `method`: the entry layout it expects, how it reads each entry's `meta`, and which checks it runs. Within a method, the Engine defines what each `assurance_level` means, including the thresholds for every compared pair. This spec does not define any of them.

Within one method, a higher `assurance_level` MUST be at least as strict as a lower one on every check. Levels of different methods are not comparable. [WIP-111][wip-111] relies on this to accept a token with `method == method_expected` and `assurance_level >= assurance_level_min`.

The Engine and its method and assurance level definitions MUST be covered by the Verifier's attested measurement ([§3.5](#35-verifiability-and-reproducible-builds)), directly or through an attested hash of injected models and configuration. Otherwise a method or level means whatever the operator says it means.

The Engine interface is non-normative. The reference implementation uses the following.

| Engine request | Type |
| --- | --- |
| `protocol_version`, `request_id` | `uint32`, `uint64` |
| `method`, `assurance_level`, `meta`, `entries`, `compare` | forwarded unchanged from the request |

| Engine response | Contents |
| --- | --- |
| `Pass` | Every compared pair cleared the assurance level and every check passed. |
| `Failed` | `code` and `validation_reason` |
| `ProtocolFailure` | malformed request, message too large, unsupported version, unknown method or assurance level |

Every variant MAY carry a `debug_report`. The Engine returns no scores the Verifier signs.

### 3.4 Token

The output is a CWT `COSE_Sign1`-signed with EdDSA-Poseidon2 over BabyJubJub, encoded as deterministic CBOR, following the requirements [WIP-106][wip-106] sets for tokens of this algorithm.

The token carries two kinds of claims. `request_hash` binds the entire request. The other claims are the request fields a consuming circuit reads directly. Fields no circuit reads, such as `meta` and entries that are not compared, are bound only through `request_hash`.

The circuit does not recompute the direct claims from `request_hash`. The Verifier is trusted to derive both from the same request, as it is trusted for the comparison itself.

#### 3.4.1 Token claims

| Claim | Key | Encoded key | Description |
| --- | --- | --- | --- |
| `iat` | `6` | `06` | Time of the comparison, seconds since the Unix epoch. |
| `eat_profile` | `265` | `19 01 09` | URI identifying the profile, as [RFC 9711](https://datatracker.ietf.org/doc/rfc9711/) §4.3.2. MUST be `https://world.org/eat/evt/v1`. |
| `method` | `-90000` | `3a 00 01 5f 8f` | `method` from the request. |
| `assurance_level` | `-90001` | `3a 00 01 5f 90` | `assurance_level` from the request. |
| `request_hash` | `-90002` | `3a 00 01 5f 91` | `SHA-256` of the exact plaintext bytes the Verifier decrypted, reduced modulo $p$. |
| `compared_entry_hash_0` | `-90003` | `3a 00 01 5f 92` | `SHA-256(entries[compare[0]].data)`, reduced modulo $p$. |
| `compared_entry_hash_1` | `-90004` | `3a 00 01 5f 93` | `SHA-256(entries[compare[1]].data)`, reduced modulo $p$. |
| `compared_entry_hash_2` | `-90005` | `3a 00 01 5f 94` | `SHA-256(entries[compare[2]].data)`, reduced modulo $p$, or `0` if `compare` has fewer entries. |
| `compared_entry_hash_3` | `-90006` | `3a 00 01 5f 95` | `SHA-256(entries[compare[3]].data)`, reduced modulo $p$, or `0` if `compare` has fewer entries. |

The claims MUST appear in the order above, which is the bytewise lexicographic order of their encoded keys required by deterministic CBOR ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)).

The private-use keys occupy a `-90000` block, distinct from the `-70000` and `-80000` blocks [WIP-106][wip-106] allocates, so no World ID claim key is reused across token types. All are below `-65536` as the [CWT Claims registry](https://www.iana.org/assignments/cwt/cwt.xhtml) requires for private use.

Every claim value except `eat_profile` MUST be a single field element, encoded as a 32-byte CBOR byte string in canonical big-endian, as [WIP-106][wip-106] encodes `cdh`. `eat_profile` is a text string and is excluded from the [signed digest](#342-signed-digest); like the TAKT's, it is therefore not signature-covered and MUST be treated as an untrusted hint outside a circuit.

**Hash reduction.** A `SHA-256` digest is reduced to a field element by interpreting it as a 256-bit big-endian integer modulo $p$. A circuit holding the digest as two 128-bit halves computes the same value as `hi * 2^128 + lo` in $F$. Two distinct digests only collide if they differ by a multiple of $p$.

**Request hash.** The Authenticator computes `request_hash` over the plaintext it is about to encrypt, so both sides hash identical bytes and no canonical re-encoding is needed.

**Compared entries.** The hashes follow the order of `compare`, and the `method` fixes which position holds which role. Entry hashes are over the bytes the Verifier received and MUST NOT be over an embedding the Engine extracted. They stay raw `SHA-256` so a consumer can bind them to digests that Issuers already sign, such as a PCP `hashes.json`, without computing `SHA-256` in-circuit.

`iat` MUST be a numeric date in seconds since the Unix epoch, as defined in [RFC 8392](https://datatracker.ietf.org/doc/html/rfc8392#section-3.1.6), encoded as a 4-byte CBOR uint (`0x1a`), representable through year 2106. It MUST be the time of the comparison this token attests. A Verifier MUST NOT reuse an `iat` from an earlier comparison, and MUST NOT set it from a value supplied in the request.

`iat` rather than `exp` because an RP needs the comparison's age, which is the security-relevant quantity for proving someone is present. An expiry would only say that some lifetime chosen by the Verifier had not elapsed. Without either, a single successful comparison is replayable forever: the Authenticator can mint a fresh `aat` carrying the same `cdh` for any later request, and every other constraint in [WIP-111][wip-111] still holds.

[WIP-111][wip-111] keeps `iat` private and compares it in-circuit against an RP-supplied maximum age, so the RP learns the comparison was recent enough without learning when it happened. The operative maximum age is the RP's decision, not this spec's.

The token carries no similarity scores. The `assurance_level` is the only statement about how close the entries were, which keeps scores (themselves biometric signals) out of every proof.

#### 3.4.2 Signed digest

As with the TAKT of [WIP-106][wip-106], the signed message is **not** the COSE `Sig_structure`. It MUST be the Poseidon2 `t=16` permutation over the domain separator followed by the claim values in deterministic CBOR map-key order ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)), zero-padded:

```
[DS_EVT_V1, iat, method, assurance_level, request_hash,
 compared_entry_hash_0, compared_entry_hash_1, compared_entry_hash_2, compared_entry_hash_3,
 0, 0, 0, 0, 0, 0, 0]
```

The digest is output state element `1`.

| Constant | Value | Description |
| --- | --- | --- |
| `DS_EVT_V1` | `453338657364062333832270442605270577` (`b"WORLD_ID_EVT_V1"`) | Domain separator for the Verifier token digest. |

Because the digest is taken over field elements, a verifying circuit neither parses nor reconstructs CBOR; the CBOR encoding is the wire format only.

The state holds the domain separator and eight claims, leaving seven slots for later claims. A `t=16` permutation costs about 865 ACIR opcodes against 505 for `t=8`, which is below 1% of a consuming circuit; claims are therefore kept unpacked.

## 4. Rationale

**Commitments are over received bytes.** Committing to an extracted embedding would produce a value no other party ever signed, leaving [WIP-111][wip-111] nothing to bind it to.

**The Verifier interprets nothing.** Roles, frame semantics and thresholds live in the Engine and the consuming circuit. A new capture method or credential format changes the Engine or the circuit, never the Verifier's request or token.

**One hash for the request, direct claims for circuits.** `request_hash` can be compared with a hash an Authenticator signed ([WIP-106][wip-106] `cdh`), so a circuit can check that an Authenticator vouched for exactly the input the Verifier compared. Claims a circuit reads are signed directly, so no circuit has to open a commitment to reach them.

**Assurance levels instead of thresholds.** A score's meaning depends on the model and the compared pair, so an RP cannot pick a meaningful number. An ordered `assurance_level` stays stable across model upgrades.
