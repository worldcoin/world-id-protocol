## 1. Abstract

This spec defines the **Flamingo Verifier** (also called **Verifier** in the context of this spec): a trusted execution environment (TEE) service that receives up to four entries (images or embeddings, each with opaque metadata), a list of entries to compare, and a strictness `profile`; hands them to a biometric Engine that checks and compares them; and, when the Engine accepts, signs a token committing to every entry, the request metadata and the profile.

The token is its only signed output. [WIP-111][wip-111] consumes it to prove the comparison to a Relying Party without revealing any item.

## 2. Motivation

Comparing two embeddings is cheap. Getting an embedding anyone should believe is not.

Extraction runs a model over raw media, which is impractical in a ZK circuit. The checks that make an extracted embedding meaningful — image quality, Presentation Attack Detection, anti-fraud signals — are even worse. Much of these models require complex inputs and advanced signals, and may even rely on model obscurity.

Running extraction and comparison in an attested Trusted Execution Environment keeps the inputs private and the execution verifiable. Committing to the raw inputs makes the result usable by a verifier who trusts neither the prover nor the prover's device.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

### 3.1 Request

The request MUST be encrypted to the Verifier. Its plaintext is a deterministic CBOR map with the following fields.

| Field | Type | Bounds | Interpreted by |
| --- | --- | --- | --- |
| `profile` | `uint` | `< 2^8` | the Engine ([§3.3](#33-engine)). The Verifier signs it without interpreting it. |
| `meta` | bytes | ≤ 1 KiB | the Engine |
| `entries` | array of `Entry` | `1..=MAX_ENTRIES` | the Engine |
| `compare` | array of `uint` | 2 to `MAX_ENTRIES` distinct indices into `entries` | the Engine, which compares every pair of the listed entries |

An `Entry` is a map `{ data: bytes, meta: bytes }`. `data` is an encoded image or an embedding. `meta` (≤ 256 bytes) tells the Engine how to read it, e.g. which frame of a capture it is. Both are opaque to the Verifier.

| Constant | Value | Description |
| --- | --- | --- |
| `MAX_ENTRIES` | `4` | Fixed by the token layout ([§3.4.2](#342-signed-digest)). |

The Verifier MUST reject a request that is not exactly this shape, that exceeds a bound, or whose `compare` repeats or names an out-of-range index. It MAY impose further byte limits on `entries[].data`.

Which entry plays which role (Credential item, live frame, challenge) is a convention between the `profile` and the consuming circuit. The Verifier does not know it.

### 3.2 Response

The response MUST be encrypted to the requester and SHOULD be padded to a fixed length, so its size reveals neither the outcome nor the size of the debug report.

| Variant | Contents |
| --- | --- |
| `Success` | `token` ([§3.4](#34-token)), `signing_key_attestation`, `debug_report` |
| `Failed` | `reason`, `debug_report` |

`reason` is one of `malformed_inputs`, `input_too_large`, `rejected(validation_reason)`, `no_match`, `internal`. `validation_reason` is the Engine's reason code, passed through.

`debug_report` is optional bytes copied from the Engine. It is not signed and MUST be treated as unauthenticated. The Verifier MAY truncate it to fit the padded length.

The Verifier MUST emit a token only when the Engine returns `Pass`.

### 3.3 Engine

Extraction, quality checks, Presentation Attack Detection and comparison are delegated to an Engine inside the Verifier. The Engine defines what each `profile` means, including the thresholds for every compared pair. This spec does not define any of them.

A higher `profile` MUST be at least as strict as a lower one on every check. [WIP-111][wip-111] relies on this to accept any token with `profile >= profile_min`.

The Engine and its profile definitions MUST be covered by the Verifier's attested measurement ([§3.5](#35-verifiability-and-reproducible-builds)), directly or through an attested hash of injected models and configuration. Otherwise a profile means whatever the operator says it means.

The Engine interface is non-normative. The reference implementation uses the following.

| Engine request | Type |
| --- | --- |
| `protocol_version`, `request_id` | `uint32`, `uint64` |
| `profile`, `meta`, `entries`, `compare` | forwarded unchanged from the request |

| Engine response | Contents |
| --- | --- |
| `Pass` | Every compared pair cleared the profile and every check passed. |
| `Failed` | `code` and `validation_reason` |
| `ProtocolFailure` | malformed request, message too large, unsupported version, unknown profile |

Every variant MAY carry a `debug_report`. The Engine returns no scores the Verifier signs.

### 3.4 Token

The output is a CWT `COSE_Sign1`-signed with EdDSA-Poseidon2 over BabyJubJub, encoded as deterministic CBOR, following the requirements [WIP-106][wip-106] sets for tokens of this algorithm.

#### 3.4.1 Token claims

| Claim | Key | Encoded key | Description |
| --- | --- | --- | --- |
| `iat` | `6` | `06` | Time of the comparison, seconds since the Unix epoch. |
| `eat_profile` | `265` | `19 01 09` | URI identifying the profile, as [RFC 9711](https://datatracker.ietf.org/doc/rfc9711/) §4.3.2. MUST be `https://world.org/eat/evt/v1`. |
| `selector` | `-90000` | `3a 00 01 5f 8f` | `profile + compare_mask * 2^8`. |
| `meta_commitment` | `-90001` | `3a 00 01 5f 90` | `SHA-256(meta)` reduced modulo $p$. |
| `entry_commitment_0` | `-90002` | `3a 00 01 5f 91` | Commitment to `entries[0]`. |
| `entry_commitment_1` | `-90003` | `3a 00 01 5f 92` | Commitment to `entries[1]`, or `0` if absent. |
| `entry_commitment_2` | `-90004` | `3a 00 01 5f 93` | Commitment to `entries[2]`, or `0` if absent. |
| `entry_commitment_3` | `-90005` | `3a 00 01 5f 94` | Commitment to `entries[3]`, or `0` if absent. |

The claims MUST appear in the order above, which is the bytewise lexicographic order of their encoded keys required by deterministic CBOR ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)).

The private-use keys occupy a `-90000` block, distinct from the `-70000` and `-80000` blocks [WIP-106][wip-106] allocates, so no World ID claim key is reused across token types. All are below `-65536` as the [CWT Claims registry](https://www.iana.org/assignments/cwt/cwt.xhtml) requires for private use.

Every claim value except `eat_profile` MUST be a single field element, encoded as a 32-byte CBOR byte string in canonical big-endian, as [WIP-106][wip-106] encodes `cdh`. `eat_profile` is a text string and is excluded from the [signed digest](#342-signed-digest); like the TAKT's, it is therefore not signature-covered and MUST be treated as an untrusted hint outside a circuit.

**Selector.** `compare_mask` has bit `i` set exactly when entry `i` is listed in `compare`, so `compare_mask < 2^MAX_ENTRIES`. Bits for absent entries MUST be `0`. Both halves are range-checked by the consumer, which keeps the packing injective.

**Entry commitment.** For `entries[i]`:

```
entry_commitment_i = H_4(DS_EVT_ENTRY_V1; sha_hi, sha_lo, meta_hash)
```

`sha_hi` and `sha_lo` are the high and low 128-bit big-endian halves of `SHA-256(entries[i].data)`, and `meta_hash` is `SHA-256(entries[i].meta)` reduced modulo $p$. `H_4` is as defined in [WIP-100][wip-100].

The commitment is over the bytes the Verifier received. It MUST NOT be over an embedding the Engine extracted. The raw SHA-256 is kept inside so a consumer can bind it to digests that Issuers already sign, such as a PCP `hashes.json`, without computing SHA-256 in-circuit.

`meta_commitment` and each `meta_hash` bind the Engine's interpretation to the token. Without them a mislabelled frame or a different request mode would produce an identical token.

`iat` MUST be a numeric date in seconds since the Unix epoch, as defined in [RFC 8392](https://datatracker.ietf.org/doc/html/rfc8392#section-3.1.6), encoded as a 4-byte CBOR uint (`0x1a`), representable through year 2106. It MUST be the time of the comparison this token attests. A Verifier MUST NOT reuse an `iat` from an earlier comparison, and MUST NOT set it from a value supplied in the request.

`iat` rather than `exp` because an RP needs the comparison's age, which is the security-relevant quantity for proving someone is present. An expiry would only say that some lifetime chosen by the Verifier had not elapsed. Without either, a single successful comparison is replayable forever: the Authenticator can mint a fresh `aat` carrying the same `cdh` for any later request, and every other constraint in [WIP-111][wip-111] still holds.

[WIP-111][wip-111] keeps `iat` private and compares it in-circuit against an RP-supplied maximum age, so the RP learns the comparison was recent enough without learning when it happened. The operative maximum age is the RP's decision, not this spec's.

The token carries no similarity scores. The `profile` is the only statement about how close the entries were, which keeps scores (themselves biometric signals) out of every proof.

#### 3.4.2 Signed digest

As with the TAKT of [WIP-106][wip-106], the signed message is **not** the COSE `Sig_structure`. It MUST be the Poseidon2 `t=8` permutation over the domain separator followed by the claim values in deterministic CBOR map-key order ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)):

```
[DS_EVT_V1, iat, selector, meta_commitment, entry_commitment_0, entry_commitment_1, entry_commitment_2, entry_commitment_3]
```

The digest is output state element `1`.

| Constant | Value | Description |
| --- | --- | --- |
| `DS_EVT_V1` | `453338657364062333832270442605270577` (`b"WORLD_ID_EVT_V1"`) | Domain separator for the Verifier token digest. |
| `DS_EVT_ENTRY_V1` | `127603488023589505565657392769732680071060662474289` (`b"WORLD_ID_EVT_ENTRY_V1"`) | Domain separator for entry commitments. |

Because the digest is taken over field elements, a verifying circuit neither parses nor reconstructs CBOR; the CBOR encoding is the wire format only.

The `t=8` state is full. `MAX_ENTRIES` is `4` for this reason; a fifth entry would require a wider permutation and would change every digest.

## 4. Rationale

**Commitments are over received bytes.** Committing to an extracted embedding would produce a value no other party ever signed, leaving [WIP-111][wip-111] nothing to bind it to.

**The Verifier interprets nothing.** Roles, frame semantics and thresholds live in the Engine and the consuming circuit. A new capture method or credential format changes the Engine or the circuit, never the Verifier's request or token.

**Profiles instead of thresholds.** A score's meaning depends on the model and the compared pair, so an RP cannot pick a meaningful number. An ordered `profile` stays stable across model upgrades.
