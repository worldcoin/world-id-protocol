## Abstract

This spec defines a standard JSON wire format for World ID authenticators to communicate with each other. It defines a versioned message envelope, message identifiers, reply correlation, encoding and validation rules.

## Motivation

World ID supports authenticators from different providers and on different platforms. These authenticators need a shared wire format so that application protocols can be implemented independently of a particular transport.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

### Message Envelope

Every inter-authenticator message MUST be a UTF-8 encoded JSON object with the following members:

| Member | Required | Description |
|--------|----------|-------------|
| `version` | REQUIRED | Wire format version. This spec defines version `1`. |
| `id` | REQUIRED | Message identifier encoded as a canonical lowercase UUIDv4 as defined in [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562). |
| `type` | REQUIRED | Namespaced application message type in the form `<protocol>.v<version>.<message>`. Additional message segments MAY follow. |
| `in_reply_to` | OPTIONAL | The `id` of the message to which this message replies. It MUST be omitted for the first message of an exchange. |
| `payload` | REQUIRED | A JSON object whose schema is defined by the specification that owns `type`. |

For example:

```json
{
  "version": 1,
  "id": "7a1c2e77-46d8-4d14-b852-ca3f4bb28eb2",
  "type": "auth.v1.register",
  "payload": {
    "registration_id": "7ecb8475e581443ca67a0868ce3638d1"
  }
}
```

### JSON Schema

The following [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12) schema is normative for the message envelope. Specifications defining a message type MUST further constrain `type` and `payload`.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "WIP-105 Authenticator Message",
  "type": "object",
  "required": [
    "version",
    "id",
    "type",
    "payload"
  ],
  "properties": {
    "version": {
      "const": 1
    },
    "id": {
      "$ref": "#/$defs/message_id"
    },
    "type": {
      "type": "string",
      "pattern": "^[a-z][a-z0-9_]*\\.v[1-9][0-9]*(?:\\.[a-z][a-z0-9_]*)+$"
    },
    "in_reply_to": {
      "$ref": "#/$defs/message_id"
    },
    "payload": {
      "type": "object"
    }
  },
  "additionalProperties": false,
  "$defs": {
    "message_id": {
      "type": "string",
      "format": "uuid",
      "pattern": "^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$"
    }
  }
}
```

### Encoding and Validation

1. Implementations MUST reject JSON containing duplicate member names.
2. Implementations MUST reject envelope members not defined by the selected `version`. New envelope members require a new wire format version.
3. An implementation receiving an unsupported `version` or unknown `type` MUST NOT process its `payload`.

4. An implementation MUST process a given `id` at most once within the lifetime of the application protocol. Receiving the same `id` again MUST NOT repeat an approval, signature or other side effect.

When a message needs to be hashed or signed, it MUST first be serialized using the [JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785) defined in RFC 8785. The specification requiring the hash or signature MUST define its domain separator and identify the exact object being canonicalized.

### Application Protocol

An application protocol defines a set of message types, payload schemas & rules on how the messages are processed.

Protocols SHOULD define messages types in a namespaced form `<protocol>.<version>.<message>`. For example `auth.v1.register`.

### Transport Requirements

A transport protocol is a mechanism for exchanging the messages between authenticators. The transport protocol MUST provide a bidirectional, ordered channel for communication. The transport protocol MUST be secure & end-to-end encrypted using ephemeral locally generated keys. The transport protocol MUST NOT use authenticator keys to encrypt or sign messages.
