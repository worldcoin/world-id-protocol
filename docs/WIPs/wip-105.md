## 1. Abstract

This spec defines a standard JSON wire format for World ID authenticators to communicate with each other. Messages MUST be JSON-RPC 2.0 objects, and the `method` field MUST use underscore-separated `camelCase` segments prefixed with `worldid`. The `params`, `result` and `error` semantics of individual methods are defined by the protocols that use this format.

It also defines the `worldid://` deeplink format: a scheme, a namespace, a version and an action, followed by action-specific query parameters.

## 2. Motivation

World ID supports authenticators from different providers and on different platforms. These authenticators need a shared message and deeplink format so that application protocols can be implemented independently of a particular transport.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

### 3.1 JSON-RPC 2.0

Messages exchanged between authenticators MUST be JSON objects conforming to the [JSON-RPC 2.0 specification](https://www.jsonrpc.org/specification).

### 3.2 Methods

The `method` field MUST consist of `camelCase` segments joined by underscores `_`. The first segment MUST be `worldid`. For example `worldid_auth_v1_register`.

The `method`, `params`, `result` and `error` fields MUST be defined in a WIP. This spec does not introduce specific methods.

### 3.3 Deeplinks

Deeplinks MUST be URIs ([RFC 3986](https://www.rfc-editor.org/rfc/rfc3986)) of the form:

```plain text
worldid://{namespace}/{version}/{action}?{parameters}
```

The scheme MUST be `worldid`. `namespace` is the protocol area, `version` is `v` followed by a positive integer, and `action` is the operation the deeplink starts. For example `worldid://auth/v1/register`.

Authenticators SHOULD register the `worldid` scheme with the operating system where the platform allows.

The `namespace`, `version`, `action` and parameters of a deeplink MUST be defined in a WIP. This spec does not introduce specific deeplinks.

## 4. Backwards Compatibility

This WIP defines a new message format and deeplink format. It does not modify existing protocol behavior, contracts or stored data, and implementations that do not exchange authenticator messages are unaffected. Existing `worldid` URIs that are not defined by a WIP are not affected.
