## 1. Abstract

This spec defines a CBOR wire format for World ID authenticators to exchange requests, responses and notifications. The `method` field MUST use underscore-separated `camelCase` segments prefixed with `worldid`. Other WIPs define the methods and their payloads.

It also defines `worldid://` deeplinks, which SHOULD follow a namespace, version and action structure. The details of individual deeplinks are defined by the protocols that use them.

## 2. Motivation

World ID supports authenticators from different providers and on different platforms. A shared message and deeplink format lets them communicate over different transports.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

### 3.1 Message format

#### 3.1.1 Encoding

Messages MUST be encoded using CBOR ([RFC 8949](https://www.rfc-editor.org/rfc/rfc8949.html)). Each transport message MUST contain exactly one CBOR map: a request, response or notification. Receivers MUST reject trailing bytes and check the whole message against the encoding rules below before executing the request.

The transport defines message boundaries, routing, authentication and encryption.

Envelope field names are case-sensitive CBOR text strings. Binary payloads MUST use CBOR byte strings. Each method's defining WIP specifies its parameter and result schemas.

Messages MUST follow the core deterministic encoding requirements of [RFC 8949 §4.2.1](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2.1). In particular, strings, arrays and maps MUST use definite lengths; receivers MUST reject indefinite-length items. If an application value has more than one CBOR representation, its method schema MUST specify which to use, following [RFC 8949 §4.2.2](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2.2).

Receivers MUST reject any message that contains a map with duplicate keys, as defined by [RFC 8949 §5.6.1](https://www.rfc-editor.org/rfc/rfc8949.html#section-5.6.1).

Each transport specification MUST set a maximum encoded message size and define what happens when it is exceeded. Implementations MUST limit nesting depth and resource use, and check lengths before allocating memory. Receivers MAY drop messages that exceed these limits or fail transport authentication without replying.

#### 3.1.2 Requests and notifications

Either peer MAY send a request. For each request, the sender is the caller and the receiver is the responder.

A notification is a valid request without an `id` field. The responder MUST NOT reply to a valid notification, even if execution fails, the method is unknown or its arguments are invalid. A malformed request without an `id` is not a notification.

A request is a map with these fields:

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `version` | Yes | Text string | MUST be `"1.0"`, the envelope version defined by this WIP. |
| `method` | Yes | Text string | Method name following §3.2. |
| `params` | No | Array or map | Arguments in the order defined by the method, or a map using the method's exact parameter names. |
| `id` | No | Text string, integer or null | ID used to match the response to the request. Omit for notifications. |

Callers SHOULD use non-null IDs. They MUST NOT reuse an ID while waiting for the response to that ID from the same peer in the same session. Integer and text IDs are distinct: `1` and `"1"` are different IDs.

For a valid request with an `id`, the responder MUST return one response with the same ID value and type, even if the ID is null.

Omitting `params` means no arguments were supplied. If present, `params` MUST be an array or map, not null. Unknown envelope fields MUST be ignored. Requests MUST NOT contain `result` or `error`.

#### 3.1.3 Responses

A response is a map containing `version: "1.0"`, `id` (a text string, integer or null), and exactly one of `result` or `error`. Responses MUST NOT contain `method` or `params`. Unknown envelope fields MUST be ignored.

A successful response MUST contain `result`, which MAY be any CBOR value, including null or a byte string. A failed response MUST contain an `error` map with these fields:

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `code` | Yes | Integer | Machine-readable failure code. |
| `message` | Yes | Text string | Short human-readable explanation. |
| `data` | No | Any CBOR value | Additional details defined by the method or error code. |

Unknown fields in the error map MUST be ignored. Callers MUST match responses to requests by `id`, not arrival order. They MUST NOT reply to invalid or unmatched responses, or accept them as successful results. Implementations SHOULD report these as local protocol errors.

#### 3.1.4 Errors

The following error codes are shared by all methods:

| Code | Meaning |
| --- | --- |
| `-32700` | The message does not follow the CBOR encoding rules in §3.1.1. |
| `-32600` | The request is malformed, or its envelope version is unsupported. |
| `-32601` | The requested method is not available. |
| `-32602` | The arguments do not match the method's parameter schema. |
| `-32603` | The responder could not complete the call because of an internal error. |
| `-32099` through `-32000` | Implementation-defined responder failures. |

The range `-32768` through `-32000` is reserved for protocol errors. Codes in that range not assigned above are reserved for future versions. Method-specific errors MUST use codes outside that range and MUST be defined by the method's WIP.

Whether to reply to a parse error is transport-defined. If a parse error response is sent, it MUST use `id: null`. For an invalid request, the responder MUST copy its ID if it can read a single, unambiguous text string, integer or null ID; otherwise it MUST use null. Error responses MUST use `version: "1.0"`. Responders MUST NOT send errors in reply to notifications or responses.

#### 3.1.5 Examples

These examples show CBOR diagnostic notation. `h'0102ff'` represents the three bytes `01 02 ff`.

Request with an inline binary argument:

```text
{
  "version": "1.0",
  "method": "worldid_example_v1_process",
  "params": {"payload": h'0102ff'},
  "id": "request-1"
}
```

Successful response with an inline binary result:

```text
{"version": "1.0", "result": h'0304', "id": "request-1"}
```

Failure response:

```text
{
  "version": "1.0",
  "error": {"code": -32602, "message": "Unexpected payload length"},
  "id": "request-1"
}
```

Notification (no response, including on failure):

```text
{"version": "1.0", "method": "worldid_example_v1_process", "params": {"payload": h'0102ff'}}
```

### 3.2 Methods

The `method` field MUST consist of `camelCase` segments joined by underscores `_`. The first segment MUST be `worldid`. For example `worldid_auth_v1_register`.

The `method`, `params`, `result` and `error` fields MUST be defined in a WIP. This spec does not introduce specific methods.

### 3.3 Deeplinks

Deeplinks MUST be URIs ([RFC 3986](https://www.rfc-editor.org/rfc/rfc3986)) with the scheme `worldid`. They SHOULD have the form:

```plain text
worldid://{namespace}/{version}/{action}?{parameters}
```

`namespace` is the protocol area, `version` is `v` followed by a positive integer, and `action` is the operation the deeplink starts. For example `worldid://auth/v1/register`.

Authenticators SHOULD register the `worldid` scheme with the operating system where the platform allows.

Deeplinks MUST be defined in a WIP. This spec does not introduce specific deeplinks.

## 4. Backwards Compatibility

This WIP defines a new message format and deeplink format. It does not modify existing protocol behavior, contracts or stored data, and implementations that do not exchange authenticator messages are unaffected. Existing `worldid` URIs that are not defined by a WIP are not affected.
