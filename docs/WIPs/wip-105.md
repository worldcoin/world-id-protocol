## 1. Abstract

This spec defines a standard JSON wire format for World ID authenticators to communicate with each other. Messages MUST be JSON-RPC 2.0 objects, and the `method` field MUST use underscore-separated `camelCase` segments prefixed with `worldid`. The `params`, `result` and `error` semantics of individual methods are defined by the protocols that use this format.

It also defines the `worldid://` deeplink format that one authenticator uses to start an exchange with another, e.g. through a QR code. A deeplink consists of a scheme, a namespace, a version and an action, followed by action-specific query parameters.

## 2. Motivation

World ID supports authenticators from different providers and on different platforms. These authenticators need a shared wire format so that application protocols can be implemented independently of a particular transport, and a shared deeplink format so that any authenticator can open a link or scan a QR code produced by another.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

### 3.1 JSON-RPC 2.0

Messages exchanged between authenticators MUST be JSON objects conforming to the [JSON-RPC 2.0 specification](https://www.jsonrpc.org/specification).

### 3.2 Methods

The `method` field MUST consist of `camelCase` segments joined by underscores `_`. The first segment MUST be `worldid`. For example `worldid_auth_v1_register`.

The `method`, `params`, `result` and `error` fields MUST be defined in a WIP. This spec does not introduce specific methods.

### 3.3 Deeplinks

A deeplink is a URI ([RFC 3986](https://www.rfc-editor.org/rfc/rfc3986)) that the user carries from one authenticator to another, by opening a link or scanning a QR code, to start an exchange. A deeplink MUST have the form:

```plain text
worldid://{namespace}/{version}/{action}?{parameters}
```

| Component    | Description                                                                                          |
| ------------ | ---------------------------------------------------------------------------------------------------- |
| Scheme       | `worldid`, in lowercase.                                                                             |
| `namespace`  | The protocol area, carried as the URI authority. For example `auth` for authenticator management.    |
| `version`    | `v` followed by a positive decimal integer without leading zeros. For example `v1`.                  |
| `action`     | The operation the deeplink starts. For example `register`.                                           |
| `parameters` | The query: `name=value` pairs joined by `&`. Omitted together with the `?` if the action has none.   |

- `namespace` and `action` MUST consist of lowercase ASCII letters and digits, and MUST start with a letter.
- A deeplink MUST NOT contain userinfo, a port, a fragment, or path segments other than `version` and `action`.
- Parameter names and values are percent-encoded as defined in [RFC 3986 §2.1](https://www.rfc-editor.org/rfc/rfc3986#section-2.1) and decoded exactly once. Binary values SHOULD use unpadded base64url ([RFC 4648 §5](https://www.rfc-editor.org/rfc/rfc4648#section-5)), which needs no percent-encoding.
- A QR code MUST encode the deeplink verbatim.

The `namespace`, `version` and `action` of a deeplink MUST be defined in a WIP, together with its parameters, their encodings and which of them are required. This spec does not introduce specific deeplinks.

- A deeplink that starts a JSON-RPC exchange SHOULD use the segments of the method it starts. For example, `worldid://auth/v1/register` starts `worldid_auth_v1_register`.
- A change that existing parsers cannot handle, including a new parameter, MUST use a new `version`.
- An authenticator MUST reject a deeplink that does not match this format, has an unknown `namespace`, `version` or `action`, or has unknown, missing or duplicated parameters.
- Opening a deeplink MUST NOT by itself authorize an action. An action that requires user consent still requires it when started from a deeplink.

## 4. Security

- **Scheme ownership.** Any application can register the `worldid` URI scheme, so the operating system can deliver a deeplink to an application other than the intended authenticator. Anyone who sees a QR code also learns its deeplink. A WIP that places a secret in a deeplink MUST account for both.

## 5. Backwards Compatibility

This WIP defines a new message format and deeplink format. It does not modify existing protocol behavior, contracts or stored data, and implementations that do not exchange authenticator messages are unaffected. Existing `worldid` URIs that are not defined by a WIP are not affected.
