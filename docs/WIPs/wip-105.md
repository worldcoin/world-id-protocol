## 1. Abstract

This spec defines a CBOR wire format for World ID authenticators to exchange requests, responses and notifications, including binary payloads. The `method` field MUST use underscore-separated `camelCase` segments prefixed with `worldid`. Individual protocols define their methods and payload schemas using this envelope.

It also defines `worldid://` deeplinks, which SHOULD follow a namespace, version and action structure. The details of individual deeplinks are defined by the protocols that use them.

## 2. Motivation

World ID supports authenticators from different providers and on different platforms. These authenticators need a shared message and deeplink format so that application protocols can be implemented independently of a particular transport. Native byte strings allow binary payloads to travel inside messages without base64 expansion or a separate download.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

### 3.1 Message format

#### 3.1.1 Encoding

Messages MUST be encoded using CBOR ([RFC 8949](https://www.rfc-editor.org/rfc/rfc8949.html)). Each transport message MUST contain exactly one CBOR data item: a request or response map, or a batch array as defined below. Trailing bytes MUST be rejected. Receivers MUST validate the entire encoded item against this encoding profile before executing any request it contains. The transport defines message boundaries, routing, authentication and encryption; this WIP does not define a transport.

Envelope field names are case-sensitive CBOR text strings. Binary payloads MUST use CBOR byte strings. Each method's defining WIP specifies its parameter and result schemas.

Messages MUST follow the core deterministic encoding requirements of [RFC 8949 §4.2.1](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2.1). In particular, strings, arrays and maps MUST use definite lengths; receivers MUST reject indefinite-length items. Method schemas MUST resolve alternative representations of the same application value where needed for deterministic encoding, as described in [RFC 8949 §4.2.2](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2.2).

Transport specifications MUST define maximum encoded message size and behavior when that limit is exceeded. Implementations MUST also bound nesting depth and resource use before allocating from untrusted lengths. Resource-limit or transport-authentication failures MAY terminate delivery without a message-level response.

#### 3.1.2 Requests and notifications

Either peer MAY initiate a request. The sender is the caller and the receiving peer is the responder for that request. A request is a map with these fields:

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `version` | Yes | Text string | MUST be `"1.0"`, the envelope version defined by this WIP. |
| `method` | Yes | Text string | Method name conforming to §3.2. |
| `params` | No | Array or map | Positional arguments in the method's defined order, or named arguments with exactly matching names. |
| `id` | No | Text string, integer or null | Correlation identifier. Absence makes the request a notification. |

Callers SHOULD use non-null IDs and MUST NOT reuse an ID while a request with that ID is outstanding to the same peer in the same session. Integer and text IDs are distinct: `1` and `"1"` do not identify the same request. The envelope version is independent of the method version in §3.2.

For a valid request containing `id`, the responder MUST return one response with the same ID value and type, including when the ID is null. A notification has no `id` field. The responder MUST NOT reply to a valid notification, even if execution fails, the method is unknown or its arguments are invalid. An invalid request envelope is not a notification merely because it lacks `id`.

Omitted `params` means no arguments were supplied. A present `params` MUST be an array or map; null is not a substitute for omission. Unknown envelope fields MUST be ignored. Requests MUST NOT contain `result` or `error`.

#### 3.1.3 Responses

A response is a map containing `version: "1.0"`, `id` (a text string, integer or null), and exactly one of `result` or `error`. Responses MUST NOT contain `method` or `params`. Unknown envelope fields MUST be ignored.

On success, `result` MUST be present and MAY contain any CBOR value, including null or a byte string. On failure, `error` MUST be present and MUST be a map with the following fields:

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `code` | Yes | Integer | Machine-readable failure code. |
| `message` | Yes | Text string | Short human-readable explanation. |
| `data` | No | Any CBOR value | Additional details defined by the method or error code. |

Unknown fields in the error map MUST be ignored. Callers MUST correlate responses using `id`, not arrival order. Invalid responses or responses with no matching outstanding request MUST NOT trigger another response or be accepted as a successful result; implementations SHOULD surface them as protocol errors locally.

#### 3.1.4 Errors

The following codes define envelope-level failures:

| Code | Meaning |
| --- | --- |
| `-32700` | The message cannot be decoded as exactly one CBOR item in the encoding profile of §3.1.1. |
| `-32600` | The decoded item is not a valid request envelope or batch, including an unsupported envelope version. |
| `-32601` | The requested method is not available. |
| `-32602` | The arguments do not satisfy the method's parameter schema. |
| `-32603` | An internal failure prevented the responder from completing the call. |
| `-32099` through `-32000` | Implementation-defined responder failures. |

The range `-32768` through `-32000` is reserved for protocol errors. Codes in that range not assigned above are reserved for future versions. Method-specific errors MUST use codes outside that range and MUST be defined by the method's WIP.

For a parse error, the error response MUST have `id: null`. For an invalid request, the responder MUST copy `id` if it can unambiguously recover a text string, integer or null ID; otherwise it MUST use null. Error responses MUST use `version: "1.0"`. These rules do not override notification suppression or the rule against responding to responses.

A transport MUST define how to distinguish inbound requests from responses when decoding fails, and when a reply can be delivered. If a message cannot be classified, or no reply route is available, the receiver MUST discard it without replying and SHOULD surface the failure locally. This prevents error-response loops and allows transports whose reply routing is carried inside the payload.

#### 3.1.5 Batches

A caller MAY send a non-empty array of requests and notifications as one message. The responder MAY process its entries concurrently and in any order. A batch is not atomic and does not imply execution ordering.

After processing the batch, the responder MUST return an array containing one response for each entry requiring a response. Invalid request entries, including nested batch arrays, produce `-32600` errors. An entry identified as a response MUST NOT be answered, even in a request batch; it is handled as a local protocol error. Notifications produce no response entries. If every entry is a notification, the responder MUST send no response, rather than an empty array. Response entries MAY appear in any order.

An empty request batch produces a single `-32600` response map with `id: null`, not an array. An undecodable request batch produces a single `-32700` response map with `id: null`; no entries from that message are executed. Each batch MUST contain only requests and notifications, or only responses; peers MUST NOT mix the two directions in one batch.

#### 3.1.6 Examples

The following use CBOR diagnostic notation, not the bytes sent on the wire. `h'0102ff'` represents the three bytes `01 02 ff`. The illustrative method and its payload are not introduced by this WIP.

Request with an inline binary argument:

```text
{
  "version": "1.0",
  "method": "worldid_example_v1_process",
  "params": {"payload": h'0102ff'},
  "id": "request-1"
}
```

Successful response with an inline binary result:

```text
{"version": "1.0", "result": h'0304', "id": "request-1"}
```

Failure response:

```text
{
  "version": "1.0",
  "error": {"code": -32602, "message": "Unexpected payload length"},
  "id": "request-1"
}
```

Notification (no response, including on failure):

```text
{"version": "1.0", "method": "worldid_example_v1_process", "params": {"payload": h'0102ff'}}
```

### 3.2 Methods

The `method` field MUST consist of `camelCase` segments joined by underscores `_`. The first segment MUST be `worldid`. For example `worldid_auth_v1_register`.

The `method`, `params`, `result` and `error` fields MUST be defined in a WIP. This spec does not introduce specific methods.

### 3.3 Deeplinks

Deeplinks MUST be URIs ([RFC 3986](https://www.rfc-editor.org/rfc/rfc3986)) with the scheme `worldid`. They SHOULD have the form:

```plain text
worldid://{namespace}/{version}/{action}?{parameters}
```

`namespace` is the protocol area, `version` is `v` followed by a positive integer, and `action` is the operation the deeplink starts. For example `worldid://auth/v1/register`.

Authenticators SHOULD register the `worldid` scheme with the operating system where the platform allows.

Deeplinks MUST be defined in a WIP. This spec does not introduce specific deeplinks.

## 4. Backwards Compatibility

This WIP defines a new message format and deeplink format. It does not modify existing protocol behavior, contracts or stored data, and implementations that do not exchange authenticator messages are unaffected. Existing `worldid` URIs that are not defined by a WIP are not affected.
