## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).


### Field

Unless otherwise noted, all circuits MUST be arithmetised over $F_q$, the scalar field of BN254, which is also the base field of [BabyJubJub](https://docs.iden3.io/publications/pdfs/Baby-Jubjub.pdf). All arithmetic MUST be done over $F_q$, except where a scalar of the BabyJubJub group is required, in which case arithmetic MUST be done over $F_r$, BabyJubJub's own scalar field.

- $F_q$ (or `Fq`) is the prime field of order

  $q = 21888242871839275222246405745257275088548364400416034343698204186575808495617$

- $F_r$ (or `Fr`) is the prime field of order $\ell$, the order of the large prime-order subgroup of BabyJubJub (see [Curve](#curve)), where

  $\ell = 2736030358979909402780800718157159386076813972158567259200215660948447373041$

### Curve

BabyJubJub is used in its twisted Edwards form $E$, defined over $F_q$ by

$$a x^2 + y^2 = 1 + d x^2 y^2, \qquad a = 168700,\ d = 168696$$

All group operations — key generation, [signatures](#signatures) and scalar multiplication — MUST use this form. The group has cofactor $h = 8$, a large prime-order subgroup of order $\ell$, and total order

$$n = h \cdot \ell = 21888242871839275222246405745257275088614511777268538073601725287587578984328$$

The base point of the Protocol is the generator $G$ of the prime-order subgroup:

$$G = \left(5299619240641551281634865583518297030282874472190772894086521144482721001553,\ 16950150798460657717958625567821834550301663161624707787222815936182638968203\right)$$

### Hashing

Unless otherwise noted, hashing is done via a Poseidon2 permutation over $F_q$. $P_t$ denotes the Poseidon2 **permutation** on $F_q^t$ with the $x^5$ S-box and the round counts below; it is a permutation, not a hash. The hash constructions built from it are defined in the subsections that follow.

| $t$ | $R_F$ (external rounds) | $R_P$ (internal rounds) |
| --- | ----------------------- | ----------------------- |
| 2   | 8                       | 56                      |
| 3   | 8                       | 56                      |
| 4   | 8                       | 56                      |
| 8   | 8                       | 57                      |
| 16  | 8                       | 57                      |

Round constants and the external/internal matrices MUST be those produced for BN254 at the given $t$ by the reference [Poseidon2 parameter generation script](https://github.com/HorizenLabs/poseidon2/blob/main/poseidon2_rust_params.sage). Widths not listed above MUST NOT be used.

#### Domain separators

A domain separator `ds` is the $F_q$ element derived from an ASCII label by big-endian octet-string-to-integer conversion, reduced mod $q$. Labels MUST be at most 31 bytes, so that distinct labels cannot collide under the reduction.

Each label MUST be bound to exactly one (construction, $t$, $k$) triple. For example, `EdDSA Signature` is allocated to the [challenge hash](#signatures) at $t = 8$, $k = 5$, giving

$$\texttt{ds}_{\texttt{EdDSA Signature}} = 360302137480307891234917541314130533$$

#### Fixed-arity hash $H_t$

For a domain separator `ds` and inputs $m_1, \dots, m_k$ with $k \le t - 1$:

$$H_t(\texttt{ds}; m_1, \dots, m_k) := P_t([\texttt{ds}, m_1, \dots, m_k, 0, \dots, 0])[1]$$

That is, `ds` occupies the capacity element at state index `0`, the inputs occupy state indices `1..k`, any remaining state elements are zero, and the digest is state element **`1`** of the permutation output.

$k$ MUST be constant for a given `ds`. The zero padding is not length-encoded, so $H_t(\texttt{ds}; m_1)$ and $H_t(\texttt{ds}; m_1, 0)$ are the same digest; binding $k$ to `ds` is what prevents cross-arity collisions. A construction whose input count varies at runtime MUST NOT use $H_t$.

#### Variable-length hash $H_\text{var}$

Byte strings of unbounded length MUST be hashed with a SAFE-style $P_{16}$ sponge: rate 15 over state indices `0..14`, capacity at index **`15`**, squeezing from index **`0`** — the opposite convention to $H_t$. The capacity is initialised with a SHA3-256 tag over the domain separator label and the input length, so unlike $H_t$ this construction is length-encoded.

### Signatures

The default signature scheme for the World ID Protocol is an Edwards-curve Digital Signature Algorithm (EdDSA) over the twisted Edwards form $E$ of BabyJubJub, referred to as **`BabyJubJub-EdDSA-Poseidon2`**.

It follows the structure of [RFC-8032](https://datatracker.ietf.org/doc/html/rfc8032) but is **not** an RFC 8032 ciphersuite: RFC 8032 defines only Ed25519 and Ed448, each with a fixed curve and a fixed hash function, and this scheme replaces both.

1. `BabyJubJub-EdDSA-Poseidon2` uses:
    1. $F_q$ as its finite field;
    2. $E$ as its elliptic curve;
    3. the base point $G$ as defined in [Curve](#curve), of prime order $\ell$;
    4. Poseidon2 as its challenge hash, as defined in [Hashing](#hashing);
    5. BLAKE3 in XOF mode for secret scalar derivation and for deterministic nonce derivation. Implementations MUST NOT substitute Poseidon2 here, nor SHA-512 as RFC 8032 would prescribe.
2. **Message**. Messages are elements of $F_q$. A message not natively encodable in $F_q$ MUST first be hashed to $F_q$ with a construction from [Hashing](#hashing).
3. **Canonical Scalar**. All `s` scalars MUST fulfill $s < \ell$ to prevent signature malleability (i.e. a reduced scalar).
4. **$R$ on curve**. $R$ must be a point satisfying the BabyJubJub curve equation because addition is only complete for on-curve points. The point is NOT REQUIRED to lie in the prime-order subgroup.
5. **Challenge**. $c = H_8(\texttt{ds}_{\texttt{EdDSA Signature}}; R_x, R_y, A_x, A_y, \mathtt{message})$, where $A$ is the signer's public key. $c$ MAY be used as a full-field scalar without reduction, since reduction mod $\ell$ is a no-op on the prime-order subgroup in which $A$ is required to lie.
6. **Cofactored verification equation**. The signature MUST meet the cofactored verification equation $[h]\left(sG - R - cA\right) = \mathcal{O}$, with $h = 8$. See [Chalkias, K. et al.](https://eprint.iacr.org/2020/1244.pdf). Cofactorless verification MUST NOT be used; the two accept different sets of signatures.

## Public Key Representation

The `PublicKey` type is introduced to represent public keys of arbitrary elliptic curves. Two representations are defined and MUST NOT be conflated:

1. **In-circuit**: an affine point, i.e. a structure with two `Field` elements $(x, y)$. Both coordinates MUST be carried explicitly; a circuit MUST NOT decompress a point.
2. **Wire**: a compressed point of 32 bytes, holding $y$ as a canonical little-endian $F_q$ element with the sign of $x$ in the most significant bit of the final byte. The sign bit is set when $x > -x$, comparing canonical integer representatives.

Decompression recovers $x$ from $y$ via the curve equation and selects the root indicated by the sign bit. Deserialisation MUST reject a non-canonical $y$, i.e. one that is not less than $q$.

This compressed encoding is not the iden3 BabyJubJub packing, and the two are not interchangeable.

## Merkle Inclusion Proof

The protocol uses Merkle Tree to store membership

Nodes MUST be combined with the Davies–Meyer compression function

$$\mathrm{Compress}(l, r) := P_2([l, r])[0] + l$$

$t = 2$ leaves no state element free for a capacity, so $\mathrm{Compress}$ carries no domain separator and is the one exception to [Domain separators](#domain-separators). A Merkle tree requires only collision resistance from its compression function, and the fixed tree depth excludes cross-level second preimages. $\mathrm{Compress}$ MUST NOT be used elsewhere.
