## 1. Abstract

This spec introduces a new ZK circuit ("Ownership Proof") to the World ID Protocol that allows a user to prove they own a specific registered leaf without revealing their `leaf_index` or any private key material to the verifier. The circuit takes a domain-separated commitment over `(leaf_index, commitment_blinder)` for a given `commitment_type`, and proves that the user controls a secret key registered in the `WorldIDRegistry` for that leaf, without exposing the `commitment_blinder` value (e.g. a credential blinding factor) as a public input. The initial use case is Issuer Authentication, where a user proves ownership of a credential `sub` to an Issuer for operations like re-issuance, renewal, or deletion.

## 2. Motivation

There are use cases that require users to prove ownership for their World ID and a specific commitment. At the time of writing there is a well-known use case for Issuer Authentication.

### 2.1 Issuer Authentication

Issuers may require users to authenticate with their World ID. Some examples of such use cases:
- **Re-issuance**. Allowing the user to get a new copy of their credential due to loss.
- **Status information**. Providing the user with information on their current enrollment state.
- **Cancellation/deletion/unregistration**. Allowing the user to unregister, delete or cancel their existing credential.

For the cases above, Issuers need to know the legitimate owner of a Credential is requesting the operation. Issuers do not know the user's `leaf_index` by design, so a mechanism to authenticate based on the Credential's [subject](https://docs.rs/world-id-primitives/latest/world_id_primitives/credential/struct.Credential.html#structfield.sub) (`sub`) is required.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

The terms [Authenticator](https://docs.rs/world-id-core/latest/world_id_core/struct.Authenticator.html), Issuer and [Credential](https://docs.rs/world-id-primitives/latest/world_id_primitives/credential/struct.Credential.html) are as defined in the World ID Protocol.

This specification introduces a new circuit to the Protocol: **"Ownership Proof"**. The Ownership Proof is a new circuit which allows users to prove _ownership_ (as defined below) using a specific commitment.

A **non-normative high-level description** of what the circuit proves:
> 1. It proves the user's `leaf_index` hashed with a `commitment_blinder` for a specific `commitment_type` produces an `expected_commitment`. _An example, is the Credential's blinded `sub`_.
> 2. It proves the user's `leaf_index` is validly registered in the `WorldIDRegistry` and the user can produce a signature with a secret key ($sk$) registered as an authenticator for the particular `leaf_index`.
> 3. It proves the user authorized the operation through a signature with a registered authenticator secret key and that such operation is only valid for a specific `nonce` and `context` provided.

The Ownership Proof circuit MUST introduce the following inputs. The circuit MUST NOT introduce any additional public inputs which are not specified in this or a future spec.

| Input               | Visibility | Type  | Description                                 |
|---------------------|------------|-------|---------------------------------------------|
| `expected_commitment` | **Public** | Field element | The expected output of the hashed commitment (e.g. the `sub` of a credential)            |
| `merkle_root`         | **Public** | Field element | The root hash of the Merkle tree used for inclusion (representing the `WorldIDRegistry`) |
| `nonce`         | **Public** | Field element | One-time use value to prevent replays. See [Nonce](#33-nonce) section. |
| `context`       | **Public** | Field element | A verifier-supplied context for which the proof is valid. |
| `commitment_type` | **Public** | Field element | The commitment-type number: `WIP-103-<NNN>` has `commitment_type = NNN` as an integer (so `WIP-103-001` is `commitment_type = 1`). MUST NOT be `0`. See [Commitment Types](#4-commitment-types). |
| `user_pk`       | Private | [PublicKey; NUM_KEYS] | The list of authenticator public keys registered in the `WorldIDRegistry`. |
| `pk_index`           | Private | Field element | The index in `user_pk` of the key used for signature. |
| `sig_s`            | Private | Field element | The `s` component from the EdDSA signature on the message (see constraints). |
| `sig_r`            | Private | [Field element; 2] | The `r` component from the EdDSA signature on the message (see constraints). |
| `leaf_index`         | Private | Field element | The index of the user's World ID in the `WorldIDRegistry`. |
| `siblings`           | Private | [Field element; MAX_DEPTH] | The sequence of all siblings from the `leaf_index` to the `merkle_root` . |
| `commitment_blinder` | Private | Field element | The blinding value that is hashed with the `leaf_index` to output the `expected_commitment`. The provenance of the value depends on the specific commitment type (see [Commitment Types](#4-commitment-types)). |

For the inputs above, a `PublicKey` is as defined in the [WIP-100][wip-100] spec (_an EdDSA public key represented as its coordinate points $(x,y)$ with each coordinate being a Field element_). _For reference, `user_pk`, `pk_index`, `leaf_index` (named `mt_index`), `siblings` introduce the same constraints that the Nullifier Proof circuit._

The ordered public inputs MUST be `[merkle_root, nonce, expected_commitment, context, commitment_type]`. The `WorldIDRegistry` tree depth is fixed at 30 by [WIP-100][wip-100].

### 3.1 Circuit constants

The Field ($F$), the Curve (`BabyJubJub`), and the Hashing ($H_t$) definitions MUST follow the requirements of [WIP-100][wip-100]. For example, in this spec `H_3` refers to the hash constructed from a Poseidon2 permutation of 3-elements.

| Constant | Value | Description |
|----------|-------|-------------|
| `NUM_KEYS` | `7` | Length of the authenticator public key list. Fixed by the Nullifier Proof circuit and the `WorldIDRegistry`. |
| `MAX_DEPTH` | `30` | For reference, defined in [WIP-100][wip-100]. Maximum supported `WorldIDRegistry` Merkle tree depth; also the length of `siblings`. |
| `MERKLE_LEAF_DS` | `105702839725298824521994315` (`b"World ID PK"`) | Domain separator for the authenticator key list commitment. |
| `DS_EDDSA` | `360302137480307891234917541314130533` (`b"EdDSA Signature"`) | For reference, defined in [WIP-100][wip-100]. Domain separator for the EdDSA challenge hash. |
| `DS_CREDENTIAL_SUB` | `87492525752134038588518953` (`b"H_CS(id, r)"`) | For reference, defined in [WIP-100][wip-100]. |
| `DS_WIP_103` | `127603488023523044162070750169730677966885882513230` (`b"WORLD-ID/WIP-103/SIGN"`) | Domain separator for the Ownership Proof signed message. MUST NOT be reused outside of the Ownership Proof signed-message construction. |
| `DS_WIP_103_COMMITMENT` | `8362622191109606222205468683123469711237815630071417172` (`b"WORLD-ID/WIP-103/COMMIT"`) | Domain separator allocated to `H_4` with `k = 3` for the Ownership Proof commitment. MUST NOT be reused elsewhere. |

### 3.2 Circuit constraints

The Ownership Proof circuit MUST implement the following constraints (order is not relevant):

1. **Expected commitment**. Compute the commitment according to `commitment_type`:
   - If `commitment_type = 1` ([WIP-103-001](#41-wip-103-001-issuer-authentication)), the commitment is `H_3(DS_CREDENTIAL_SUB; leaf_index, commitment_blinder)`. This is the Credential `sub` from [WIP-100][wip-100], kept unchanged so existing credentials remain provable.
   - Otherwise, the commitment is `H_4(DS_WIP_103_COMMITMENT; commitment_type, leaf_index, commitment_blinder)`.

   The computed commitment MUST equal `expected_commitment`. The circuit MUST NOT restrict `commitment_type` to an allowlist beyond `commitment_type != 0`, and in both branches the capacity element is a fixed constant, never a prover- or verifier-supplied value. _Non-normative note: a circuit can compute both hashes and select by `commitment_type == 1`._
2. **Authorization message**. Compute `message = H_4(DS_WIP_103, expected_commitment, nonce, context)`. Constraint 3 verifies the Authenticator's signature over it, which authorizes the particular `nonce` and `context`.
3. **World ID Authentication**. The circuit MUST enforce [WIP-100 World ID Authentication](wip-100.md#61-world-id-authentication) over `message`, with `user_pk`, `pk_index`, `leaf_index`, `siblings` and `(sig_r, sig_s)` as its inputs. This selects `pk = user_pk[pk_index]` with `pk_index < NUM_KEYS`, rejects the neutral element $O = (0,1)$ used for inactive slots, proves inclusion of the `MERKLE_LEAF_DS` key-set commitment at `leaf_index` under `merkle_root` with `0 < leaf_index < 2^30`, and verifies the signature.
4. **Leaf-index binding.** The `leaf_index` hashed into the commitment in constraint 1 and the `leaf_index` of constraint 3 MUST be the same witness. The circuit MUST NOT accept two independent values. This binding is **essential**, otherwise the circuit is only proving the prover knows the `sk` of **some** leaf, not the one being proven in the `expected_commitment`.
5. **Verifier-supplied input validation**. The `nonce`, `context` and `commitment_type` MUST NOT equal `0`. These are usually intended as sentinel values and could surface an incorrect use of them.

### 3.3 Nonce

The nonce is a security mechanism to prevent replay attacks. Recipients of an **Ownership Proof** (also called "verifiers" in this spec) are responsible for its generation and verification.
1. **Provenance**. Verifiers MUST generate and provide the nonce. Authenticators MUST NOT generate nonces.
2. **Single Use**. Verifiers MUST enforce that a nonce may only be used one time. Verifiers MUST invalidate any nonce after first use.
3. **Entropy**. Verifiers MUST generate the nonce from a uniformly random distribution using a CSPRNG over the whole field $F$.
4. **Expiration**. Nonces MUST have a defined TTL and not be valid after expiration. Verifiers MAY define the mechanism to accomplish this.
5. The `0` element is NOT a valid nonce.

### 3.4 Context

The `context` is the mechanism by which a verifier binds a specific proof to a specific requested operation. The verifier MUST constrain the use of Ownership Proofs to specific operations and assign such operations with a unique context. For example, renewing a credential and deleting a credential are two different contexts. The verifier MUST provide the `context` when requesting a proof and MUST verify the provided `context` is valid for the explicit operation being executed. 

It is RECOMMENDED that Verifiers use contexts shorter than 31 bytes or use a hash function to avoid collisions.

The `0` element is NOT a valid context.

### 3.5 Verification requirements
1. **Enrollment**. Verifiers SHOULD verify a Proof of Ownership when enrolling a `sub` (i.e. seeing it for the first time). This recommendation depends on what enrollment does at the Verifier. For example, providing an invalid `sub` for ordinary credential issuance only yields an unusable credential. In any case, an unverified `sub` MUST NOT authorize any operation by itself.
2. **Root Freshness**. Verifiers MUST check that the provided public input `merkle_root` is valid and non-expired. Verifiers MAY check `WorldIDRegistry.isValidRoot(merkle_root)` on every verification or cache a valid result until the root's actual expiration (e.g. from `WorldIDRegistryV2.getRootExpiration`). The configured `getRootValidityWindow()` is not the root's remaining lifetime and MUST NOT, by itself, determine the cache duration. A `getRootExpiration` result of `0` denotes the latest root, not an unlimited cache lifetime. Cache access MUST NOT extend the expiration.
3. **Proving System**. Ownership Proofs MUST use the [ProveKit](https://github.com/worldfnd/provekit) proving system. Verifiers MUST NOT use verification artifacts supplied by the prover.
4. **Commitment Type**. Verifiers MUST check that the `commitment_type` public input equals the commitment type they serve (see [Commitment Types](#4-commitment-types)), and MUST reject the proof otherwise. This check MUST be an exact equality comparison against a single configured value, never a range check or a comparison against a prover-supplied value.

## 4. Commitment Types

1. **Commitment-type numbering**. Commitment-type identifiers are `WIP-103-<NNN>`, with `commitment_type = NNN` as an integer (for example, `WIP-103-001` has `commitment_type = 1` and `WIP-103-002` has `commitment_type = 2`). Numbers are allocated by the WIP that defines the commitment type, and MUST be unique and never reused. Every commitment type other than [WIP-103-001](#41-wip-103-001-issuer-authentication) uses the shared `H_4(DS_WIP_103_COMMITMENT; commitment_type, leaf_index, commitment_blinder)` commitment and MUST NOT define its own commitment construction or domain separator; doing so would require a new circuit. Because all new commitment types share the WIP-103-only `DS_WIP_103_COMMITMENT` separator in the capacity slot and differ only in the hashed `commitment_type` input, their commitments are domain-separated from every other protocol hash, such as `DS_SESSION_COMMITMENT` or `DS_CREDENTIAL_SUB`, and from each other.
2. **New commitment types**. Each new commitment type MUST be specified in its own WIP referencing WIP-103 and MUST define:
   1. The commitment-type identifier `WIP-103-<NNN>` and its `commitment_type` value.
   2. **Commitment semantics:** what `expected_commitment` identifies, and how the Verifier comes to know and associate it with a subject *before* accepting a proof (for example, received at issuance or enrollment over an authenticated channel). If the Verifier can first learn the commitment from the proof itself, the WIP MUST say so and treat it as trust-on-first-use. A first-seen commitment only proves that the prover owns *some* registered leaf.
   3. **Blinder provenance:** how `commitment_blinder` is generated, stored or re-derived, and recovered. It MUST be high-entropy; unless the WIP specifies otherwise, it SHOULD be generated uniformly from a CSPRNG over $F$. The WIP MUST also state whether the commitment survives World ID Recovery.
   4. **Verifier and operations:** who verifies, the `context` value assigned to each operation, and any nonce requirements beyond [§3.3](#33-nonce).
   5. **Use conditions:** when an Authenticator may generate the proof, to which Verifier it may be sent, and how the commitment type prevents the Verifier from using the proof as an oracle (compare [§7](#7-security) item 3).
   6. **Uniqueness:** whether the commitment type needs a single commitment per World ID, and if so how it is enforced outside this circuit (see [§7](#7-security) item 6).
   7. **Privacy:** what the commitment links, within and across Verifiers.
   8. **Test vectors:** a valid witness and the commitment-type-specific rejection cases, in the format of [Appendix A](#appendix-a-normative-test-vectors).
3. **Authenticator enforcement**. Authenticators MUST restrict Ownership Proofs to the commitment types defined in this spec or a referencing WIP. Authenticators MUST refuse unknown `commitment_type` values and MUST enforce the use conditions of the applicable commitment type.
4. **Verifier enforcement**. Verifiers MUST check that the `commitment_type` public input matches their expected commitment type (see [Verification requirements](#35-verification-requirements)).

Please note that after **World ID Recovery**, a Proof of Ownership can still be used to prove a `sub`, as the original `leafIndex` is preserved.

### 4.1 WIP-103-001: Issuer Authentication
- **Use case**: Authenticating to an Issuer where the Issuer has a `sub` as identifier.
- **`commitment_type`**: `1`. The commitment is the Credential `sub`, `H_3(DS_CREDENTIAL_SUB; leaf_index, commitment_blinder)`.
- **`commitment_blinder` value**: The credential's blinding factor as stored (or re-derived) by the Authenticator.
- **Use conditions**: Can only be used to prove ownership with the specific Issuer for which the `sub` was generated. The Authenticator MUST ensure this proof is only provided to the Issuer it corresponds. The Authenticator knows this from the blinding factor used as the `commitment_blinder` input. Furthermore, providing this proof MUST come from a user initiated action and SHALL NOT be requested by Issuers. Acceptable examples include: when a user requests a Credential re-issuance, when a user requests a Credential renewal, when a user requests a Credential deletion.
- **Verification**: Issuers MUST ensure the `expected_commitment` public input of the circuit matches the expected identifier (i.e. Credential's `sub`) and that the `commitment_type` public input equals `1`.


## 5. Rationale
A keen observer would notice the Ownership Proof circuit is very similar to the Query Proof circuit. Using this circuit is not an option because the verifying party would need to learn the `commitment_blinder` being verified to ensure the hash validity (it's a public input). For example, an Issuer does not need to learn the credential blinding factor, which would defeat the purpose of the blinding factor because the `leaf_index` could be easily brute forced.

`commitment_type` is a public input hashed in the rate, not the capacity, so new commitment types can be added in future WIPs without modifying the circuit or regenerating proving and verification artifacts, while the capacity of every commitment hash remains a fixed constant as [WIP-100 §3.3.2](wip-100.md#332-fixed-arity-hash-h_t) requires. The alternative of placing a per-commitment-type domain separator in the capacity was rejected because it allows the prover to influence the capacity element. [WIP-103-001](#41-wip-103-001-issuer-authentication) keeps `H_3(DS_CREDENTIAL_SUB; leaf_index, commitment_blinder)` for compatibility with the existing Credential `sub`. `commitment_type` does not need to be hashed directly into the authorization message `H_4(DS_WIP_103, expected_commitment, nonce, context)`: the Authenticator signs `expected_commitment`, Constraint 1 binds `commitment_type` into `expected_commitment`, as a hashed input or, for `commitment_type = 1`, through the choice of construction (assuming second-preimage resistance of both constructions), and the verifier independently checks that the `commitment_type` public input equals its expected commitment-type value.


## 6. Reference Verification
An Issuer will be able to know a specific user is the legitimate owner of a `sub` by performing the following validations:
1. Ensuring the received zero-knowledge proof verifies according to [Proving system](#35-verification-requirements).
2. The root hash satisfies [Root freshness](#35-verification-requirements) at verification time.
3. The `expected_commitment` public input matches the expected `sub` being verified. This value MAY also be used for lookups when the `sub` is not known in advance.
4. The `nonce` public input is one the Issuer itself generated, has not expired, and has not been used before. The nonce MUST be invalidated at this point. See [Nonce](#33-nonce).
5. The `context` public input is the context the Issuer assigns to the operation it is about to execute. A proof carrying any other context MUST be rejected, even if every other check passes. See [Context](#34-context).
6. The `commitment_type` public input equals `1` (see [Commitment Types](#4-commitment-types)). A proof carrying any other `commitment_type` MUST be rejected, even if every other check passes.

Validations 4, 5, and 6 are what make the proof unreplayable, single-purpose, and bound to the intended commitment type. The circuit binds `nonce` and `context` into the signature and `commitment_type` into the signed commitment, but it cannot know which values the verifier intended, so a verifier that accepts the values supplied alongside the proof without comparing them to its own gains no replay, cross-context, or cross-commitment-type protection.

## 7. Security

1. **`commitment_blinder` is never revealed.** Unlike the Query Proof circuit, the `commitment_blinder` value is a private input. For Issuer Authentication (WIP-103-001), this means the credential blinding factor is never exposed to the Issuer. If it were, the Issuer could brute-force the `leaf_index` (the domain of possible values is small) and break the unlinkability property of the blinding factor.
2. **Domain and commitment-type separation prevent cross-context replay.** Every commitment hash keeps a fixed constant in the capacity slot (`DS_CREDENTIAL_SUB` for `commitment_type = 1` and `DS_WIP_103_COMMITMENT` for all other commitment types), and for `commitment_type != 1` hashes `commitment_type` as an ordinary rate input into the signed `expected_commitment`. For `commitment_type = 1`, `commitment_type` selects the `sub` construction instead of being hashed. Moving a proof between commitment types therefore requires a second preimage of the fixed `expected_commitment`, within or across the two commitment constructions. This separates WIP-103 commitments from every other protocol hash (such as `DS_SESSION_COMMITMENT`) and separates distinct WIP-103 commitment types from one another without exposing the capacity element to prover control. Because the circuit does not enforce an allowlist beyond `commitment_type != 0`, Authenticators MUST refuse unknown `commitment_type` values and enforce use conditions, and Verifiers MUST check that `commitment_type` equals the single configured constant for the commitment type they serve. A proof generated for one commitment type cannot be replayed in another.
3. **Authenticator-gated usage.** Authenticators MUST restrict generation of Ownership Proofs to user-initiated actions for the defined commitment types. Issuers SHALL NOT be able to request this proof; the Authenticator must initiate it. This prevents an Issuer from using the proof as an oracle to test whether a given `sub` belongs to a particular user.
4. **Nonce and context are bound into the signed message.** The signature verified by the circuit is over `nonce`, `context` and `expected_commitment`, not only over the bare commitment. This means every Ownership Proof requires a fresh signature from the authenticator signing key for that specific `(nonce, context)` tuple (in addition to the `expected_commitment`), anchoring proof generation to an active signing event by the Authenticator.
5. For note, proofs for the same `expected_commitment` (e.g. the same `sub`) are linkable because they use the same public input. This is intended as the `expected_commitment` is what its getting proven. This proof however prevents cross-verifier linking as the `commitment_blinder` differs.
6. **Blinder provenance is not constrained.** The circuit treats `commitment_blinder` as a free private witness and does not check how it was derived (for WIP-103-001, it does not check that it is the OPRF-derived credential blinding factor). Consequently, one World ID can produce valid proofs for any number of distinct commitments under the same `commitment_type`; binding to a specific commitment rests on the Verifier already knowing it, and on the preimage resistance of the commitment hash. The Ownership Proof does not provide one-commitment-per-account uniqueness, so commitment types that need it MUST obtain it elsewhere and state how (see [§4](#4-commitment-types)).

## 8. Backwards Compatibility

This World Improvement Proposal (WIP) introduces a new interface; no existing contracts are affected.

Adopting the [WIP-100 Circuit Components](wip-100.md#6-circuit-components) removed the public `depth` input and added the `leaf_index != 0` constraint, and adding the `commitment_type` public input appended it to the ordered public inputs. These changes alter the circuit's public inputs and its proving and verification artifacts, so provers and verifiers MUST upgrade together.
