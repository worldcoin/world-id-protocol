## 1. Abstract

This spec introduces the **Authenticator Assertion Token (AAT)**: a short-lived statement, signed by an Authenticator Provider, about the integrity of the environment in which a single World ID Proof is generated. The Authenticator Provider checks platform integrity evidence (e.g. Apple App Attest) for every request and signs the result with a `BabyJubJub-EdDSA-Poseidon2` key. The AAT is verified confidentially, typically inside a ZK circuit, bound to the Relying Party's request through a blinded commitment, so the Authenticator Provider doesn't need to learn which Relying Party the proof is for.

## 2. Motivation

Some use cases need information beyond the World ID Proof about where it was generated, typically when the Authenticator provides inputs the proof cannot verify itself (e.g. a live selfie compared in a ZK circuit). Relying Parties then need to know that a genuine Authenticator on a genuine device produced the proof.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

1. The definition of an Authenticator Provider is explicitly introduced into the Protocol. An **Authenticator Provider** is the publishing entity (e.g. a software company) of an [Authenticator](https://github.com/worldcoin/world-id-protocol/tree/main/docs/world-id-4-specs#definitions) client.
2. An Authenticator Provider MAY opt in to issuing AATs. An AAT is a statement **only** from the Authenticator Provider. Each Relying Party (RP) decides which Authenticator Providers and which security properties it accepts.
3. The Field ($F$), the Curve (`BabyJubJub`), the hash function ($H_t$), the signature scheme (`BabyJubJub-EdDSA-Poseidon2`) and the `PublicKey` representation MUST follow [WIP-100][wip-100].
4. An AAT MUST only be verified where it stays confidential, e.g. as a private input to a ZK circuit or inside a TEE. Authenticator Providers and Authenticators MUST NOT share AATs raw with any other party. A verifier MUST NOT disclose `req`, `exp` or `sig`.

### 3.1 Constants

| Constant | Value | Description |
|----------|-------|-------------|
| `DS_AAT` | `498451125091886891258088867850510460821031698772` (`b"WORLD-ID/WIP-106/AAT"`) | Domain separator for the AAT digest, allocated to $H_4$ with $k = 3$. |
| `DS_REQ` | `498451125091886891258088867850510460821032813905` (`b"WORLD-ID/WIP-106/REQ"`) | Domain separator for the request commitment, allocated to $H_8$ with $k = 5$. |
| `MAX_AAT_LIFETIME` | `1800` | Maximum remaining lifetime `exp - now` of an AAT, in seconds. |
| `EAT_PROFILE` | `https://world.org/eat/aat/v1` | The `eat_profile` claim ([RFC 9711 §4.3.2](https://datatracker.ietf.org/doc/html/rfc9711#section-4.3.2)) of an AAT. |

### 3.2 Trust Anchor Key

1. An Authenticator Provider that issues AATs MUST have a `trust_anchor_key`, the key that signs its AATs. The `trust_anchor_key` MUST be a `BabyJubJub-EdDSA-Poseidon2` key pair generated randomly.
2. The `trust_anchor_key` is identified by its `kid`, which MUST be the compressed wire encoding of its public key as specified in [WIP-100 §4][wip-100].
3. A `trust_anchor_key` MUST be published in the [Authenticator Metadata](#38-authenticator-metadata), with `not_before` and `not_after`, at least 24 hours before it signs its first AAT, so RPs with cached metadata recognize it.
4. A `trust_anchor_key` MUST NOT sign AATs for more than 180 days (`not_after - not_before <= 15552000`). Authenticator Providers SHOULD rotate keys every 90 days.
5. To rotate, an Authenticator Provider MUST publish the next key per item 3 before the current key's `not_after`, and MUST keep the outgoing key published for at least `MAX_AAT_LIFETIME` after its last AAT.
6. The `trust_anchor_key` private key SHOULD be generated and used only inside hardware-protected key storage (e.g. an HSM or a TEE), and SHOULD NOT be exportable.
7. On suspected compromise, the Authenticator Provider MUST mark the key `revoked` immediately.

### 3.3 Request Commitment

The Authenticator binds an AAT to a single request through the request commitment `req`:

`req = H_8(DS_REQ; aud, nonce, cdh, presence, blind)`

| Value | Description |
|-------|-------------|
| `aud` | The `rpId` of the [ProofRequest](https://docs.rs/world-id-primitives/latest/world_id_primitives/request/struct.ProofRequest.html). |
| `nonce` | The `nonce` of the ProofRequest. |
| `cdh` | Client data hash. A commitment set by the Authenticator to bind the AAT to its upstream use (e.g. a user's `leaf_index`). `0` is the nil value. |
| `presence` | The user presence value set by the Authenticator (see [User Presence](#331-user-presence)). |
| `blind` | A blinding factor, generated by the Authenticator. MUST be a random element of $F$, fresh for every request. |

The Authenticator MUST send only `req` to the Authenticator Provider, never `aud`, `nonce`, `cdh`, `presence` or `blind`.

#### 3.3.1 User Presence

`presence` is an assertion by the Authenticator about the user during the request. It is covered by the platform integrity evidence and the AAT signature through `req`, but the Authenticator Provider does not see it and the Protocol does not verify it.

| Value | Meaning |
|-------|---------|
| 0 | Undetermined |
| 1 | User is not present |
| 2 | User is present, verified by a liveness or biometric check during this request |
| 3 | User was present within the last 7 days |
| 4 | User was present within the last 30 days |

1. Values `5` to `7` are reserved and MUST be rejected.
2. The Authenticator MUST set `presence` only from checks it performed itself.
3. Values are identifiers, not an order. RPs SHOULD allowlist the exact values they accept.

### 3.4 Authenticator Assertion Token

An AAT consists of the following values and a signature over them.

| Value | Type | Description |
|-------|------|-------------|
| `exp` | uint32 | Expiration time, in seconds since the Unix epoch. |
| `req` | Field element | The request commitment (see [Request Commitment](#33-request-commitment)). |
| `sec_flags` | uint51 | Packed security attributes (see [Security Flags](#35-security-flags)). |
| `sig` | Signature | `BabyJubJub-EdDSA-Poseidon2` signature by the `trust_anchor_key` over `message`. |

The signed message is:

`message = H_4(DS_AAT; exp, req, sec_flags)`

`sig` MUST follow [WIP-100 §3.5][wip-100], including its encoding.

#### 3.4.1 Encoding

An AAT is transported as a CBOR Web Token ([RFC 8392](https://datatracker.ietf.org/doc/html/rfc8392)): an untagged `COSE_Sign1` ([RFC 9052](https://datatracker.ietf.org/doc/rfc9052/)) in deterministic CBOR ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)).

1. The protected header MUST contain only `alg` (label `1`) with the value `-65537`. The unprotected header MUST be empty or contain only the `kid` (label `4`) of the `trust_anchor_key`, as an untrusted hint.
2. The payload MUST contain exactly the following claims, in this order. `nonce` and `eat_profile` are the Entity Attestation Token claims of [RFC 9711](https://datatracker.ietf.org/doc/rfc9711/).

| Claim | Key | Value type | Value length (bytes) |
|-------|-----|------------|----------------------|
| `exp` | 4 | uint, in $[2^{16}, 2^{32})$ | 4 |
| `nonce` | 10 | bstr: `req` as a canonical big-endian field element | 32 |
| `eat_profile` | 265 | tstr: `EAT_PROFILE` | 28 |
| `sec_flags` | -70000 | bstr, big-endian | 8 |

With CBOR headers the payload is always 89 bytes. `sig` is 64 bytes and the `kid`, if present, 32 bytes.

3. The signature field MUST carry `sig`.
4. The algorithm `-65537` (Private Use) is allocated to `BabyJubJub-EdDSA-Poseidon2` over an AAT. It does not sign the `Sig_structure` bytes ([RFC 9052 §4.4](https://datatracker.ietf.org/doc/html/rfc9052#section-4.4)). Instead it decodes `exp`, `req` and `sec_flags` from the claims and signs `message`. The CWT bytes MUST be exactly the encoding above, and verifiers MUST reject any other encoding.
5. An AAT is a syntactically valid CWT, but its signature is not over the CBOR bytes. Generic COSE/CWT libraries can decode an AAT but cannot verify it; only verifiers implementing algorithm `-65537` as defined here can.

### 3.5 Security Flags

`sec_flags` packs the following sub-fields (LSB-first). Bits 51 and above MUST be `0`.

| Bits | Sub-field | Description |
|------|-----------|-------------|
| 0-7 | `platform` | Platform of the Authenticator. |
| 8-15 | `sec_level` | Class of integrity evidence the Authenticator Provider verified for this request. |
| 16-47 | `build_version` | Monotonic version of the Authenticator build that produced the evidence. |
| 48-50 | `sec_meta` | 3-bit bitmask, provider-defined. `000` is the nil value. The meaning of each bit MUST be published in the [Authenticator Metadata](#38-authenticator-metadata). |

The `platform` enum:

| Key | Value |
|-----|-------|
| 0 | Unspecified |
| 2 | iOS |
| 4 | Android |
| 6 | Web browser |

The `sec_level` enum. Values are identifiers, not a trust ranking; RPs SHOULD allowlist the exact values they accept.

| Key | Value | Example evidence |
|-----|-------|------------------|
| 0 | Unspecified | None |
| 1 | Hardware-bound key, attested by the platform manufacturer to belong to a genuine app on a genuine device | Apple App Attest; Android Key Attestation (TEE or StrongBox) |
| 3 | Platform integrity verdict, without a hardware-bound key | Google Play Integrity |
| 5 | Internally verified. The Authenticator Provider MUST guarantee only authorized parties (e.g. internal developers) obtain this level | Provider-internal |
| 10 | User-bound credential, no environment integrity | WebAuthn passkey; browser-held key |

### 3.6 Issuance

For every AAT, the Authenticator Provider:

1. MUST verify platform integrity evidence whose challenge commits to `req` before signing (e.g. an App Attest assertion with `clientDataHash = SHA-256(req)`).
2. MUST set `sec_flags` according to the evidence verified for this request, and MUST NOT set a `sec_level` the evidence does not support.
3. MUST set `exp` such that `exp - now <= MAX_AAT_LIFETIME` at issuance.
4. MUST set `build_version` from the evidence where the platform attests it (e.g. Play Integrity `versionCode`), and otherwise from the Authenticator's report.
5. MUST NOT retain a link between a device identifier and an issuance time beyond what abuse prevention requires.
6. SHOULD rate-limit issuance per device.

### 3.7 Verification

AAT verification is specified below as a component embedded in other circuits (e.g. the Nullifier Proof). A verifier outside a circuit MUST perform the same checks, treat the **Public** values as its reported output and keep the **Private** values confidential. The component MUST introduce the following inputs.

| Input | Visibility | Type | Description |
|-------|------------|------|-------------|
| `trust_anchor_key` | **Public** | `PublicKey` | The Authenticator Provider's key, supplied by the RP. |
| `now` | **Public** | uint32 | Current time, in seconds since the Unix epoch. |
| `aud` | **Public** | Field element | The `rpId` of the request. |
| `nonce` | **Public** | Field element | The nonce of the request. |
| `platform` | **Public** | uint8 | See [Security Flags](#35-security-flags). |
| `sec_level` | **Public** | uint8 | See [Security Flags](#35-security-flags). |
| `sec_meta` | **Public** | uint3 | See [Security Flags](#35-security-flags). |
| `presence` | **Public** | uint3 | See [User Presence](#331-user-presence). |
| `min_build_version` | **Public** | uint32 | Minimum `build_version` the RP accepts. |
| `exp` | Private | uint32 | From the AAT. |
| `sec_flags` | Private | uint51 | From the AAT. |
| `sig` | Private | Signature | From the AAT. |
| `cdh` | Private | Field element | See [Request Commitment](#33-request-commitment). |
| `blind` | Private | Field element | See [Request Commitment](#33-request-commitment). |

The circuit MUST implement the following constraints:

1. **Request binding**. Compute `req = H_8(DS_REQ; aud, nonce, cdh, presence, blind)` from the public `aud`, `nonce` and `presence` inputs and the private `cdh` and `blind`. The `aud`, `nonce` and `presence` hashed here MUST be the same values as the public inputs, and this `req` MUST be the one used in `message`. The circuit embedding the AAT MUST constrain `cdh` to its own inputs (e.g. recompute it from the `leaf_index` it proves), otherwise the AAT is not bound to its upstream use.
2. **Signature**. Compute `message` as in [Authenticator Assertion Token](#34-authenticator-assertion-token) and verify `sig` over it under `trust_anchor_key` per [WIP-100 §3.5.1][wip-100].
3. **Freshness**. `exp` and `now` MUST be less than $2^{32}$. The circuit MUST enforce `now < exp` and `exp - now <= MAX_AAT_LIFETIME`, as comparisons over the full field $F$.
4. **Security flags**. `sec_flags` MUST be less than $2^{51}$ and MUST equal `platform + 2^8 * sec_level + 2^16 * build_version + 2^48 * sec_meta`, with each sub-field range-checked to its width.
5. **Nonce**. `nonce` MUST NOT equal `0`.
6. **Presence**. `presence` MUST be less than `5`.
7. **Build version**. `build_version >= min_build_version`, as a comparison over the full field $F$. `build_version` MUST remain private.

A circuit MAY make AAT verification optional through a public boolean input `has_aat`. When `has_aat = 0`, constraints 1-4, 6 and 7 MUST NOT be enforced and `platform`, `sec_level`, `sec_meta` and `presence` MUST equal `0`.

`exp` MUST remain private: its exact value would let the Authenticator Provider link a proof to the AAT it issued.

### 3.8 Authenticator Metadata

1. Each Authenticator Provider MUST expose a JSON metadata file over HTTPS at `https://<FQDN>/.well-known/world-id-authenticator.json`.
2. The file MUST include:

| Field | Type | Description |
|-------|------|-------------|
| `version` | integer | Schema version of this file. |
| `provider_id` | string | Stable identifier RPs allowlist. |
| `trust_anchor_keys` | array | Each entry: `kid` (hex), `x`, `y` (hex, the in-circuit `PublicKey`), `status` (`active`, `retired` or `revoked`), `not_before` and `not_after` (seconds since the Unix epoch). |
| `sec_meta` | object | Meaning of each `sec_meta` bit (see item 3). |

3. `sec_meta` is keyed by bit index (`"0"`, `"1"`, `"2"`). Each value is an object with `name` (string) and `description` (string). A bit without an entry is undefined, and the Authenticator Provider MUST NOT set it.
4. `trust_anchor_key` `status` values:
    - `active`: the key signs AATs.
    - `retired`: the key no longer signs AATs (e.g. after rotation). AATs it signed remain valid until they expire. Authenticator Providers MAY remove a retired key `MAX_AAT_LIFETIME` after its last AAT.
    - `revoked`: the key must no longer be trusted (e.g. it was compromised). RPs MUST reject every AAT signed by it.

## 4. Reference Verification

An RP accepts an AAT-carrying proof by performing the following validations, on the proof's public inputs or on the values a verifier outside a circuit reports:

1. `trust_anchor_key` belongs to an allowlisted Authenticator Provider, is `active` or `retired` (never `revoked`), and `now` is within its validity window.
2. `now` is within 5 minutes of the RP's local time (RECOMMENDED; RPs MAY be stricter).
3. `aud` is the RP's own `rpId`, and `nonce` is one the RP issued, has not expired and has not been used before.
4. `platform`, `sec_level`, `sec_meta` and `presence` match values the RP allowlists.
5. `min_build_version` is the RP's own minimum.

## 5. Rationale

1. **A single provider-signed token.** Verifying device-bound platform signatures (ECDSA P-256 over SHA-256) in-circuit dominates proving cost on mobile devices. Having the Authenticator Provider verify the platform evidence off-circuit reduces in-circuit verification to a single EdDSA signature over a Poseidon2 digest.
2. **Blinded request commitment.** The Authenticator Provider must bind its signature to the request, but must not learn the RP or be able to link the proof back to the device. `blind` makes `req` hiding, and the AAT stays a private input.
3. **CWT for transport only.** The AAT is carried as a CWT, but its signature is over `message` rather than the CBOR bytes, so circuits verify it without parsing or hashing CBOR. Generic COSE libraries do not implement the private-use algorithm.
4. **Presence in the request commitment.** Only the Authenticator observes user presence checks, so it sets `presence`. Placing it in `req` covers it with the platform integrity evidence and the AAT signature without disclosing it to the Authenticator Provider.
5. **Verifiers outside a circuit.** Some use cases already rely on a TEE that the RP trusts for other checks. Verifying the AAT there adds no new trust assumption and removes its cost from the circuit. Privacy is preserved as long as the verifier keeps `req`, `exp` and `sig` confidential, which a TEE enforces through attestation even when the Authenticator Provider operates it. The circuit form in [Verification](#37-verification) stays the reference, so verification can move back into circuits as proving on mobile devices gets cheaper.

## 6. Alternatives Considered

1. **Device-signed AAT with a provider-signed key token.** The Authenticator Provider attests a device-bound P-256 key once, and the device signs each AAT. Rejected: verifying P-256 ECDSA over SHA-256 in-circuit is too expensive for proving on mobile devices.
2. **Device-signed AAT with a ZK-friendly key.** As above, but with a BabyJubJub device key. Rejected: platforms can not hold such keys in secure hardware, so a device owner can extract the key and sign assertions from any environment.
3. **Pre-fetched AATs.** Authenticators obtain AATs ahead of requests to decouple issuance from proof timing. Rejected: an AAT would no longer attest the environment of a specific request, and `cdh` values that commit to per-request data can not be known in advance.

## 7. Security

1. **Assertions are Authenticator Provider statements.** The Protocol verifies only that an AAT was signed by a `trust_anchor_key`. It does not and can not verify the claims: `sec_flags` reflects only what the Authenticator Provider verified, and `presence` only what the Authenticator asserts. RPs MUST base their trust on the Authenticator Providers they allowlist.
2. **Issuance visibility.** The Authenticator Provider observes every AAT issuance (device and time), but not the RP or the request. Issuance and proof times remain correlatable; short lifetimes limit this.
3. **Trust anchor compromise.** A leaked `trust_anchor_key` lets an attacker mint AATs with arbitrary `sec_flags`. Revocation is through the [Authenticator Metadata](#38-authenticator-metadata); AATs themselves are not revocable and rely on short lifetimes.
4. **Web environments.** Browsers offer no remote attestation of the running code. Evidence from web Authenticators proves possession of a user credential only, hence `sec_level = 10`.
5. **User presence.** `presence` is only as trustworthy as the Authenticator that sets it. Use cases that need stronger guarantees SHOULD verify a signed statement from the check itself (e.g. a TEE face verifier) in-circuit.
6. **Availability.** AAT issuance requires the Authenticator Provider to be online. Proofs without an AAT remain valid; RPs decide whether to accept them.
