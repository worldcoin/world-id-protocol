## 1. Abstract

This spec introduces the **Authenticator Assertion Token (AAT)**: a short-lived statement, signed by an Authenticator Provider, about the integrity of the environment in which a single World ID Proof is generated. The Authenticator Provider checks platform integrity evidence (e.g. Apple App Attest) for every request and signs the result with a `BabyJubJub-EdDSA-Poseidon2` key. The AAT is verified inside a ZK circuit, bound to the Relying Party's request through a blinded commitment, so the Authenticator Provider never learns which Relying Party the proof is for.

## 2. Motivation

Some use cases need information beyond the World ID Proof about where it was generated, typically when the Authenticator provides inputs the proof cannot verify itself (e.g. a live selfie compared in a ZK circuit). Relying Parties then need to know that a genuine Authenticator on a genuine device produced the proof.

Verifying device-bound platform signatures (ECDSA P-256 over SHA-256) inside a circuit dominates proving cost on mobile devices. Having the Authenticator Provider verify the platform evidence off-circuit and sign a ZK-friendly token reduces in-circuit verification to a single EdDSA signature over a Poseidon2 digest.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

1. An **Authenticator Provider** is the publishing entity (e.g. a software company) of an [Authenticator](https://github.com/worldcoin/world-id-protocol/tree/main/docs/world-id-4-specs#definitions) client.
2. An Authenticator Provider MAY opt in to issuing AATs. An AAT is a statement **only** from the Authenticator Provider. Each Relying Party (RP) decides which Authenticator Providers and which security properties it accepts.
3. The Field ($F$), the Curve (`BabyJubJub`), the Hashing ($H_t$), the signature scheme (`BabyJubJub-EdDSA-Poseidon2`) and the `PublicKey` representation MUST follow [WIP-100][wip-100].
4. An AAT MUST only be used as a private input to a ZK circuit.

### 3.1 Constants

| Constant | Value | Description |
|----------|-------|-------------|
| `DS_AAT` | `412198274779845851431252` (`b"WIP106 AAT"`) | Domain separator for the AAT digest, allocated to $H_4$ with $k = 3$. |
| `DS_REQ` | `1770378109647059536643285678650228` (`b"WIP106 Request"`) | Domain separator for the request commitment, allocated to $H_8$ with $k = 4$. |
| `MAX_AAT_LIFETIME` | `1800` | Maximum remaining lifetime `exp - now` of an AAT, in seconds. |
| `EAT_PROFILE` | `https://world.org/eat/aat/v1` | The `eat_profile` claim of an AAT. |

### 3.2 Trust Anchor Key

1. An Authenticator Provider that issues AATs MUST have a `trust_anchor_key`: a `BabyJubJub-EdDSA-Poseidon2` key pair generated with a CSPRNG.
2. The `trust_anchor_key` is identified by its `kid`, the compressed wire encoding of its public key ([WIP-100 §4][wip-100]).

### 3.3 Request Commitment

The Authenticator binds an AAT to a single request through the request commitment `req`:

`req = H_8(DS_REQ; aud, nonce, cdh, blind)`

| Value | Description |
|-------|-------------|
| `aud` | The `rpId` of the [ProofRequest](https://docs.rs/world-id-primitives/latest/world_id_primitives/request/struct.ProofRequest.html). |
| `nonce` | The `nonce` of the ProofRequest. |
| `cdh` | Client data hash. A commitment set by the Authenticator to bind the AAT to its upstream use (e.g. a user's `leaf_index`). The circuit embedding the AAT defines how `cdh` is computed and verified. `0` is the nil value. |
| `blind` | A blinding factor. MUST be generated with a CSPRNG, uniformly distributed over $F$, and fresh for every request. |

The Authenticator MUST send only `req` to the Authenticator Provider, never `aud`, `nonce`, `cdh` or `blind`.

### 3.4 Authenticator Assertion Token

An AAT consists of the following values and a signature over them.

| Value | Type | Description |
|-------|------|-------------|
| `exp` | uint32 | Expiration time, in seconds since the Unix epoch. |
| `req` | Field element | The request commitment (see [Request Commitment](#33-request-commitment)). |
| `sec_flags` | uint20 | Packed security attributes (see [Security Flags](#35-security-flags)). |
| `sig` | Signature | `BabyJubJub-EdDSA-Poseidon2` signature by the `trust_anchor_key` over `message`. |

The signed message is:

`message = H_4(DS_AAT; exp, req, sec_flags)`

`sig` MUST follow [WIP-100 §3.5][wip-100], including its encoding.

#### 3.4.1 Encoding

An AAT is transported as a CBOR Web Token ([RFC 8392](https://datatracker.ietf.org/doc/html/rfc8392)): an untagged `COSE_Sign1` ([RFC 9052](https://datatracker.ietf.org/doc/rfc9052/)) in deterministic CBOR ([RFC 8949 §4.2.1](https://datatracker.ietf.org/doc/html/rfc8949#section-4.2.1)).

1. The protected header MUST contain only `alg` (label `1`) with the value `-65537`. The unprotected header MUST be empty or contain only the `kid` (label `4`) of the `trust_anchor_key`, as an untrusted hint.
2. The payload MUST contain exactly the following claims, in this order:

| Claim | Key | Value type |
|-------|-----|------------|
| `exp` | 4 | uint, in $[2^{16}, 2^{32})$ so that it encodes in 4 bytes |
| `nonce` | 10 | 32-byte bstr: `req` as a canonical big-endian field element |
| `eat_profile` | 265 | tstr: `EAT_PROFILE` |
| `sec_flags` | -70000 | 4-byte bstr, big-endian |

3. The signature field MUST carry `sig`.
4. The algorithm `-65537` (Private Use) is allocated to `BabyJubJub-EdDSA-Poseidon2` over an AAT: the `Sig_structure` ([RFC 9052 §4.4](https://datatracker.ietf.org/doc/html/rfc9052#section-4.4), empty `external_aad`) MUST be exactly the encoding above, and the signature is computed over `message` from its claim values. Verifiers MUST reject any other `Sig_structure`. As the encoding is canonical, signing `message` is equivalent to signing the `Sig_structure`.

### 3.5 Security Flags

`sec_flags` packs the following sub-fields (LSB-first). Bits 20 and above MUST be `0`.

| Bits | Sub-field | Description |
|------|-----------|-------------|
| 0-7 | `platform` | Platform of the Authenticator. |
| 8-15 | `sec_level` | Class of integrity evidence the Authenticator Provider verified for this request. |
| 16-19 | `sec_meta` | 4-bit bitmask, provider-defined. `0000` is the nil value. The meaning of each bit MUST be published in the [Authenticator Metadata](#38-authenticator-metadata). |

The `platform` enum:

| Key | Value |
|-----|-------|
| 0 | Unspecified |
| 2 | iOS |
| 4 | Android |
| 6 | Web browser |

The `sec_level` enum. Values are identifiers, not a trust ranking; RPs SHOULD allowlist the exact values they accept.

| Key | Value | Example evidence |
|-----|-------|------------------|
| 0 | Unspecified | None |
| 1 | Hardware-bound key, attested by the platform manufacturer to belong to a genuine app on a genuine device | Apple App Attest; Android Key Attestation (TEE or StrongBox) |
| 3 | Platform integrity verdict, without a hardware-bound key | Google Play Integrity |
| 5 | Internally verified. The Authenticator Provider MUST guarantee only authorized parties (e.g. internal developers) obtain this level | Provider-internal |
| 10 | User-bound credential, no environment integrity | WebAuthn passkey; browser-held key |

### 3.6 Issuance

For every AAT, the Authenticator Provider:

1. MUST verify platform integrity evidence whose challenge commits to `req` before signing (e.g. an App Attest assertion with `clientDataHash = SHA-256(req)`).
2. MUST set `sec_flags` according to the evidence verified for this request, and MUST NOT set a `sec_level` the evidence does not support.
3. MUST set `exp` such that `exp - now <= MAX_AAT_LIFETIME` at issuance.
4. MUST NOT sign an AAT for a `req` it has signed before.

### 3.7 Verification

AAT verification is a component embedded in other circuits (e.g. the Nullifier Proof). It MUST introduce the following inputs.

| Input | Visibility | Type | Description |
|-------|------------|------|-------------|
| `trust_anchor_key` | **Public** | `PublicKey` | The Authenticator Provider's key, supplied by the RP. |
| `now` | **Public** | uint32 | Current time, in seconds since the Unix epoch. |
| `aud` | **Public** | Field element | The `rpId` of the request. |
| `nonce` | **Public** | Field element | The nonce of the request. |
| `platform` | **Public** | uint8 | See [Security Flags](#35-security-flags). |
| `sec_level` | **Public** | uint8 | See [Security Flags](#35-security-flags). |
| `sec_meta` | **Public** | uint4 | See [Security Flags](#35-security-flags). |
| `exp` | Private | uint32 | From the AAT. |
| `sec_flags` | Private | uint20 | From the AAT. |
| `sig` | Private | Signature | From the AAT. |
| `cdh` | Private | Field element | See [Request Commitment](#33-request-commitment). |
| `blind` | Private | Field element | See [Request Commitment](#33-request-commitment). |

The circuit MUST implement the following constraints:

1. **Request commitment**. Compute `req` as in [Request Commitment](#33-request-commitment).
2. **Signature**. Compute `message` as in [Authenticator Assertion Token](#34-authenticator-assertion-token) and verify `sig` over it under `trust_anchor_key` per [WIP-100 §3.5.1][wip-100].
3. **Freshness**. `exp` and `now` MUST be less than $2^{32}$. The circuit MUST enforce `now < exp` and `exp - now <= MAX_AAT_LIFETIME`, as comparisons over the full field $F$.
4. **Security flags**. `sec_flags` MUST be less than $2^{20}$ and MUST equal `platform + 2^8 * sec_level + 2^16 * sec_meta`, with each sub-field range-checked to its width.
5. **Nonce**. `nonce` MUST NOT equal `0`.

A circuit MAY make AAT verification optional through a public boolean input `has_aat`. When `has_aat = 0`, constraints 1-4 MUST NOT be enforced and `platform`, `sec_level` and `sec_meta` MUST equal `0`.

`exp` MUST remain private: its exact value would let the Authenticator Provider link a proof to the AAT it issued.

### 3.8 Authenticator Metadata

1. Each Authenticator Provider MUST expose a JSON metadata file over HTTPS at `https://<FQDN>/.well-known/world-id-authenticator`.
2. The file MUST include:

| Field | Type | Description |
|-------|------|-------------|
| `version` | integer | Schema version of this file. |
| `provider_id` | string | Stable identifier RPs allowlist. |
| `trust_anchor_keys` | array | Each entry: `kid` (hex), `x`, `y` (hex, the in-circuit `PublicKey`), `status` (`active`, `retired` or `revoked`), and optional `not_before`, `not_after` (seconds since the Unix epoch). |
| `sec_meta` | object | Meaning of each `sec_meta` bit. |

3. To rotate, a Provider MUST publish the new key as `active` before the outgoing key stops issuing. A key that must no longer be trusted MUST be marked `revoked`.

## 4. Reference Verification

An RP accepts an AAT-carrying proof by performing the following validations:

1. The proof verifies with the correct verifying key.
2. `trust_anchor_key` belongs to an allowlisted Authenticator Provider, is `active`, and is within its validity window.
3. `now` is within 5 minutes of the RP's local time (RECOMMENDED; RPs MAY be stricter).
4. `aud` is the RP's own `rpId`, and `nonce` is one the RP issued, has not expired and has not been used before.
5. `platform`, `sec_level` and `sec_meta` match values the RP allowlists.

## 5. Rationale

1. **A single provider-signed token.** Verifying P-256 ECDSA and SHA-256 in-circuit made up ~94% of the cost of an earlier two-token design (~49k ACIR opcodes, ~13s proving on a low-end Android device). Moving that verification to the Authenticator Provider leaves one Poseidon2-native signature in the circuit.
2. **Blinded request commitment.** The Authenticator Provider must bind its signature to the request, but must not learn the RP or be able to link the proof back to the device. `blind` makes `req` hiding, and the AAT stays a private input.
3. **CWT for transport only.** The AAT is carried as a CWT, but its signature is over `message` rather than the CBOR bytes, so circuits verify it without parsing or hashing CBOR. Generic COSE libraries do not implement the private-use algorithm.
4. **No user presence claim.** An Authenticator Provider cannot observe user presence checks run on the device, so any presence flag would be an unverified claim of the Authenticator. Use cases that need presence SHOULD verify a signed statement from the check itself (e.g. a TEE face verifier) in-circuit.

## 6. Security

1. **Issuance visibility.** The Authenticator Provider observes every AAT issuance (device and time), but not the RP or the request. Issuance and proof times remain correlatable; short lifetimes limit this.
2. **Trust anchor compromise.** A leaked `trust_anchor_key` lets an attacker mint AATs with arbitrary `sec_flags`. Revocation is through the [Authenticator Metadata](#38-authenticator-metadata); AATs themselves are not revocable and rely on short lifetimes.
3. **Web environments.** Browsers offer no remote attestation of the running code. Evidence from web Authenticators proves possession of a user credential only, hence `sec_level = 10`.
4. **Availability.** AAT issuance requires the Authenticator Provider to be online. Proofs without an AAT remain valid; RPs decide whether to accept them.
