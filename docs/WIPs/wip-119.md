## 1. Abstract

This WIP defines how a Relying Party (RP) publishes its name, logo, and static action labels for World ID 4.0 approval screens. The Authenticator resolves metadata through the domain in `RpRegistry` and verifies that the domain authorizes the RP before displaying its branding. An RP can request proofs without publishing metadata.

## 2. Motivation

An approval screen should tell the user which RP the proof will be scoped to and, when available, what action it covers. Today the Developer Portal's [proof-context endpoint][portal] provides app branding and action descriptions. RP-hosted metadata lets independent Authenticators render the approval screen without a Portal lookup or centralized review of RP names and logos.

## 3. Specification

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be interpreted as described in [BCP 14][bcp14] when they appear in all capitals.

### 3.1 Discovery

1. The Authenticator MUST read the on-chain `RelyingParty` record for the proof request's `rp_id` from the configured `RpRegistry` for that request's protocol deployment. A protocol deployment is identified by its chain ID and `RpRegistry` address.
2. The Authenticator MUST use only the record's `unverifiedWellKnownDomain` to select the metadata host. The value MUST be a fully qualified DNS hostname. Normalize ASCII case and remove a single trailing dot before validation and use. Internationalized domains MUST be registered in ASCII A-label form. A scheme, port, path, userinfo, query, fragment, or IP literal makes the value unusable.
3. The Authenticator resolves `https://<host>/.well-known/world-id.json`. The endpoint MUST serve the file as UTF-8 JSON with HTTP status 200 and media type `application/json`. The Authenticator MUST treat a redirect from that URL as unavailable.
4. Before displaying any metadata, the Authenticator MUST match the document's top-level chain ID and registry address to the configured deployment and find the request's RP ID in `rps`. A valid version 1 document for a different deployment or without the requested RP ID is an explicit mismatch. This includes an empty `rps` array.
5. Normal proof request and RP authorization checks still apply. The Authenticator MUST use the metadata for the exact RP ID and deployment that the proof will be scoped to. The domain binding authorizes use of the RP's branding for that proof scope.

### 3.2 Metadata document

The top-level object MUST include the following fields.

| Field | Type | Description |
| --- | --- | --- |
| `version` | integer | Metadata version. Value `1`. |
| `chain_id` | string | Chain ID as a positive decimal string without leading zeros. |
| `registry_address` | string | `RpRegistry` contract address as `0x` followed by 40 lowercase hexadecimal digits. |
| `rps` | array | RP entries for the specified deployment. |

Each file covers one deployment. An RP using separate production and staging deployments can publish a file on a separate hostname for each deployment and register those hostnames in the corresponding registries.

Each element of `rps` MUST be an object with `rp_id` and `name`. It MAY also include `logo_path` and `actions`.

| Field | Type | Description |
| --- | --- | --- |
| `rp_id` | string | RP ID as `rp_` followed by 16 lowercase hexadecimal digits. |
| `name` | string | RP display name as non-empty plain text. |
| `logo_path` | string | Origin-relative path to a PNG logo on the metadata host. |
| `actions` | object | Map from canonical action field elements to non-empty plain-text labels for static uniqueness actions. |

- The document MUST contain at most one entry per RP ID. Duplicate JSON member names and duplicate RP IDs make the document invalid.
- The Authenticator MUST ignore unknown fields in version 1 and treat an unsupported version as unavailable.
- The Authenticator MUST validate the document structure, deployment fields, and RP IDs before checking the binding. A missing or invalid display field in a matching entry affects only that field.
- A `logo_path` MUST start with one `/` and resolve to the exact metadata origin. It MUST contain no query, fragment, or backslash.
- The Authenticator MUST accept only a successfully decoded PNG served as `image/png` from that path and MUST treat redirects as an unavailable logo.
- The Authenticator MUST enforce resource limits on the decoded JSON body, the logo download, and the decoded image.

This example uses an illustrative registry address and shows two RPs on one domain.

```json
{
  "version": 1,
  "chain_id": "480",
  "registry_address": "0x1111111111111111111111111111111111111111",
  "rps": [
    {
      "rp_id": "rp_000000000000002a",
      "name": "Example Product",
      "logo_path": "/assets/product.png",
      "actions": {
        "0x001237952bcfc3b8a21418a332e1a7d05a7cc2b46c3e6f97956c66819bb8bc9e": "Use this product"
      }
    },
    {
      "rp_id": "rp_000000000000002b",
      "name": "Example Community"
    }
  ]
}
```

### 3.3 Static action labels

An action key MUST be the canonical encoding of a field element in [WIP-100][wip100]'s native field as `0x` followed by 64 lowercase hexadecimal digits, representing 32 big-endian bytes. To display a static action label, the Authenticator MUST verify the authorization covering the uniqueness action and select the label keyed by the exact field element the proof will use. The legacy v1 EOA signature covers this field element. If the Authenticator cannot verify the action before prompting, it MUST omit the label. A key outside the field or an invalid label is ignored.

For an IDKit string action, the RP derives the key from the action identifier by taking Keccak-256 of its UTF-8 bytes, interpreting the digest as a big-endian integer, and shifting it right by eight bits. The example uses `use-product` as the identifier and “Use this product” as the display label. An RP supplying a field element directly publishes that exact value as the key. Keeping the display label separate lets an RP publish metadata for an existing action and revise its wording without changing the action's uniqueness scope.

Session-only requests use the Authenticator's session prompt. Templates, per-request descriptions, and labels for other proof types are out of scope for version 1.

### 3.4 Approval screen

#### Presentations

- **Branded presentation.** When the domain binding is verified, the Authenticator MUST show the verified hostname alongside the usable name, logo, and action label. It MUST describe the RP as the party the proof is for and use a placeholder for an absent or unusable logo. It MUST tell the user that the RP supplies its own branding and ask them to check the hostname. A domain match MUST NOT be presented as World endorsement. An example warning is “This app supplies its own name and logo. Check that the website matches the one you intended to use.”
- **Generic presentation.** When metadata is unavailable, the Authenticator MUST show a generic app name and placeholder logo and omit RP branding, hostnames, and RP-supplied action descriptions. It MUST allow approval if the request otherwise passes the applicable checks. Unavailable metadata includes a missing or invalid domain configuration, an unreachable or missing endpoint, a redirect, an invalid document, and an unsupported version.
- **Explicit mismatch.** The Authenticator MUST block approval, omit the branding and approval action, and explain that the website did not authorize this RP for the current deployment.

#### Hostname and RP content

- In the branded presentation, the Authenticator MUST prominently show the full verified hostname in an Authenticator-owned, clearly labeled field before approval. It MUST render the normalized ASCII hostname from §3.1 left to right, including any internationalized labels in A-label form. The hostname MAY wrap and MUST remain available in full without truncation or ellipsis.
- The Authenticator MUST render the RP name and action label as plain text and isolate their text direction from the surrounding UI. It MUST omit any name or label containing a character with the Unicode `Bidi_Control` property, a Unicode control character (general category `Cc`), or a line or paragraph separator (general categories `Zl` and `Zp`). Text in right-to-left scripts can be rendered within the isolated field. [Unicode Bidirectional Algorithm][bidi]
- The Authenticator MUST constrain RP-provided text and logos to their own display areas. RP content MUST NOT obscure or reorder the hostname, proof details, warning, or approval controls, or push them outside the approval view. Authenticator-owned information and controls MUST remain distinguishable from RP content.
- If the name is omitted, the verified hostname identifies the proof's RP. If the label is omitted, the Authenticator MUST use the normal proof prompt for the available RP identity and omit the raw action field element from user-facing copy.

#### Proof details

- In both presentations, the Authenticator MUST describe the proof type, any credential information that will be disclosed, and whether approval creates or uses a session, where applicable. It MUST derive this information from the operation the user is approving and limit claims of RP authorization to fields covered by the authenticated request context.
- If the proof's deployment, RP ID, or action changes after the prompt is shown, the Authenticator MUST obtain approval for the updated operation.

For the example in §3.2, the prompt can say “Generate a World ID uniqueness proof for Example Product,” show `example.com` in a separate website field, and display “Use this product” as the RP's action label. A proof for Example Community can still show its name and hostname when the requested action has no matching label.

## 4. Security and privacy

- **Unilateral domain claims.** A malicious RP can set its registry domain to another RP's website. A valid file authorizing only the other RP yields an explicit mismatch. If the file is unavailable, the claiming RP can only receive the generic presentation. An authorization for the same numeric RP ID on another chain or registry also yields a mismatch.
- **Signer scope.** RPs SHOULD use a dedicated signer for each RP ID. The registry permits signer reuse. The legacy v1 EOA signature covers the nonce, timestamps, and action when present. It leaves the RP ID and the rest of the request body outside the signature. [WIP-101][wip101] likewise leaves the RP ID implicit in the signer contract. Claiming that a specific RP initiated the request requires evidence that authenticates the request for that RP ID.
- **Lookalike branding.** A domain operator can publish a misleading name, logo, or action label on its own site. The verified hostname gives the user a way to check the RP against the site they intended to use. The label describes the action in the RP's own words.
- **Metadata fetch privacy.** Fetching metadata or logos during an approval flow can reveal the user's IP address and the timing of the request to the RP before the user approves. A fetch intermediary may also be able to associate the user with the RP. How to mitigate this exposure is an implementation concern outside the scope of this WIP.
- **Change of control.** A domain transfer or compromise can change the branding served for any RP that still references it. RP managers can update the hostname through the registry. Cached metadata can delay when users see changes made at the origin.

## 5. Backwards compatibility

This WIP uses the existing `unverifiedWellKnownDomain` field and leaves the proof request, proof response, and proof verification formats intact. RPs can adopt the metadata format by publishing the file and setting the registered hostname without changing their RP ID or action values. An Authenticator implementing this WIP can handle otherwise valid requests for RPs without published metadata using the generic presentation.

This WIP defines a standalone alternative to the Developer Portal's proof-context lookup. Migration of existing Portal registrations and retirement of that lookup are outside the scope of this WIP.
