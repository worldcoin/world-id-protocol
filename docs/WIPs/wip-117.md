## 1. Abstract

This spec builds on [WIP-116](wip-116.md) and introduces the `bound_uniqueness` proof type: a Uniqueness Proof bound to a session. For a seeded session, an Authenticator that already disclosed the nullifier returns a Session Proof for the same session instead. An RP can then use one request both for a user's first proof and for every later authentication.

## 2. Motivation

RPs that want one account per user and want to recognize that user later need a Uniqueness Proof and a Session Proof from the same World ID. Today a `uniqueness` request with `session_id: "create"` returns a Uniqueness Proof whose `id_commitment` public signal commits to a new session. The circuit proves that both belong to the same leaf. This binding has no proof type of its own: a session in a `uniqueness` request quietly turns it into a bound proof.

A dedicated `bound_uniqueness` proof type makes binding an explicit request. `uniqueness` never carries a session, each proof type maps to one verifier entry point, and Authenticators can tell the user that the proof links the session to the nullifier.

With seeded sessions ([WIP-116](wip-116.md)), the RP also doesn't know before the request whether a user is new. Either new users need a second request for the Uniqueness Proof, or returning users get `nullifier_replayed` and need a second request for a Session Proof. Only the Authenticator knows whether it already disclosed the nullifier, so `bound_uniqueness` lets it choose. If it hasn't disclosed the nullifier yet, it returns a Uniqueness Proof bound to the session. Otherwise it returns a Session Proof for the same session. The RP sends one request and gets back either a new registration or an authentication, and no nullifier is disclosed twice.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

### 3.1 Proof Request

`proof_type` gains the value `"bound_uniqueness"`. A `bound_uniqueness` request MUST carry an `action` (MSB `0x00`) and a `session_id` of `"create"` or `"seed_<hex>"` ([WIP-116](wip-116.md)).

It replaces the `uniqueness` × `"create"` and `uniqueness` × `"seed_<hex>"` combinations, so `uniqueness` requests no longer carry a session.

The proof type does not map to a single OPRF prefix, because the nullifier query depends on the outcome (§3.2). Its encoding MUST NOT reuse an OPRF prefix value.

### 3.2 Authenticator

1. If the Authenticator has not disclosed the nullifier for `(rp_id, action)` before, it returns a Uniqueness Proof bound to the session: response items carry `nullifier`, and `id_commitment` is a public signal of each proof.
2. If it has disclosed the nullifier before:
    - with `"seed_<hex>"`, it MUST return a Session Proof for the seeded session: response items carry `session_nullifier`.
    - with `"create"`, it MUST fail with `nullifier_replayed`.
3. The Authenticator SHOULD decide before running the uniqueness nullifier query, e.g. by recording disclosures per `(rp_id, action)`, so the fallback doesn't cost an extra OPRF query.

All items in one response MUST be of the same kind. The response always carries `session_id`.

### 3.3 RP Verification

| Response item       | RP action                                                                                                                                                                                                  |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `nullifier`         | Verify the proof against `id_commitment`. Unknown nullifier: store the account under `nullifier` and `id_commitment`. Known nullifier: authenticate if `id_commitment` matches the account, otherwise reject. |
| `session_nullifier` | Verify the Session Proof. Authenticate if `id_commitment` matches an account, otherwise reject.                                                                                                             |

A known nullifier with a new `id_commitment` can come from a modified Authenticator (see [WIP-116](wip-116.md) §4), so the RP MUST NOT add it as a second account.

## 4. Rationale

1. **New proof type instead of reusing `uniqueness`.** The response item kind depends on the Authenticator's local state. A separate type keeps `uniqueness` and `session` returning one fixed kind.
2. **No fallback for `"create"`.** The fallback would have to return the session from the first proof. Any RP could then recognize a user it holds no state for, which [WIP-116](wip-116.md) only allows for whitelisted RPs.

## 5. Security

1. **Disclosure state.** A Session Proof tells the RP the nullifier was disclosed on this device, the same information `nullifier_replayed` gives today.
2. **Nullifiers are not one-time across devices.** A new Authenticator has no disclosure record and returns the Uniqueness Proof again. RPs MUST handle a known nullifier as in §3.3.
3. **Lockout.** If the first Uniqueness Proof never reached the RP, the Authenticator falls back to a Session Proof the RP can't match. The user can't register from that Authenticator until its disclosure record expires.

## 6. Backwards Compatibility

Breaking: `uniqueness` × `"create"` is removed. Authenticators that don't implement this spec reject `"bound_uniqueness"` when parsing the request. Verifier contracts need no changes: bound proofs verify as today's session-bound Uniqueness Proofs and fallbacks as Session Proofs.
