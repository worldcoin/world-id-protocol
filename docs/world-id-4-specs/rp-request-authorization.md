# RP request authorization

`ProofRequest` version 1 uses EIP-712 to bind an RP's authorization to the complete semantic request.

## EIP-712 domain

The domain is:

- `name`: `World ID RP Request`
- `version`: `1`
- `chainId`: the chain containing the RP registry
- `verifyingContract`: the RP registry proxy address

The chain and registry bindings prevent a signature from being replayed against a different deployment. OPRF nodes obtain both values from their configured registry provider; clients must not supply them as unsigned request metadata.

## Public authorization

EOA-backed RPs sign the following typed data. Contract-backed RPs receive this same struct as the `intent` argument of [WIP-101](../WIPs/wip-101.md)'s `verifyRpRequest` — not a parallel copy of it — so the authorization a contract validates is byte-for-byte the one an EOA signs.

```solidity
struct RpRequest {
    uint8 requestVersion;
    uint64 rpId;
    uint160 oprfKeyId;
    uint256 nonce;
    uint64 createdAt;
    uint64 expiresAt;
    uint8 proofType;
    uint8 sessionMode;
    uint8 actionKind;
    uint256 action;
    bytes32 existingSessionSeedAuthorization;
    bytes32 detailsHash;
}
```

These fields authorize what an OPRF node is allowed to compute:

- `requestVersion` identifies the request schema. Its only supported value is `1`.
- `rpId` prevents replay between RPs that use the same signer.
- `oprfKeyId` is checked against the key derived from the RP registry, preventing an unsigned key substitution.
- `nonce`, `createdAt`, and `expiresAt` provide replay and lifetime bounds.
- `proofType`, `sessionMode`, and the optional `action` authorize an exact operation matrix rather than merely authenticating a timestamp.
- `existingSessionSeedAuthorization` authorizes rederivation of one exact existing session seed without disclosing that seed to nodes processing the other operations in the request.
- `detailsHash` binds the private request body without sending it to OPRF nodes.

`actionKind` is `0` when `action` is absent and `1` when it is present. An absent action is encoded as zero, but is distinct from a present zero action. `proofType` is `0` for uniqueness and `2` for session. `sessionMode` is `0` for none, `1` for create, and `2` for existing.

OPRF nodes enforce the following matrix:

| Proof type | Session mode | Authorized OPRF operations |
| --- | --- | --- |
| Uniqueness | None | The exact signed uniqueness action |
| Uniqueness | Create | The exact signed uniqueness action and one fresh session-seed derivation |
| Session | Create | One fresh session-seed derivation and randomized session actions |
| Session | Existing | Rederivation of the exact committed session seed and randomized session actions |

Any other combination is invalid. In particular, an ordinary uniqueness request cannot be reused to create a session.

## Private details commitment

`detailsHash` is the EIP-712 struct hash of `RpRequestDetails`:

```solidity
struct RpRequestDetails {
    bytes32 requestSalt;
    string requestId;
    bytes32 sessionRefHash;
    bytes32 requestItemsHash;
    bytes32 constraintsHash;
}
```

The RP MUST supply a fresh, unpredictable, non-zero 32-byte `request_salt`. It is sent to the Authenticator with the proof request but is not forwarded to OPRF nodes. Salting prevents a node from guessing a low-entropy private request body from `detailsHash`.

The nested hashes commit to:

- the exact request ID;
- the session-reference variant and, for an existing session, both its commitment and OPRF seed;
- the ordered proof-request items, including each identifier, issuer-schema ID, signal presence and full Keccak-256 signal hash, effective minimum genesis timestamp, and effective minimum expiration timestamp;
- the complete ordered constraint tree, including `all`, `any`, or `enumerate` operators, leaf-vs-expression tags, and every referenced identifier.

Optional fields are normalized to their protocol meaning before hashing: an absent `genesisIssuedAtMin` is zero, and an absent `expiresAtMin` is the request's `createdAt`. Explicit presence tags distinguish values where absence has different semantics, such as the signal and action.

The request signature, query proof, Merkle root, and values generated by the Authenticator for a new session are not part of the private details commitment. They are either the authorization itself, independently verified by the nodes, or unavailable when the RP signs. Their permitted behavior is instead constrained by the signed public operation matrix.

For an existing session, the Authenticator discloses a request-specific opening only to a node call that rederives the seed. The node verifies:

```text
existingSessionSeedAuthorization =
    hash(SessionSeedAuthorization(opening, requestedOprfSeed))
```

The full existing session reference remains bound inside `detailsHash`; ordinary session-action calls expose neither it nor the salt.

The same public authorization is necessarily attached to each OPRF operation belonging to one proof request, so a node can correlate those operations as one short-lived request. With a fresh salt and nonce, the authorization itself does not create a stable handle across requests. An existing session's OPRF seed is still visible to nodes when its blinding factor is explicitly rederived, so repeated rederivations remain linkable as the same RP session; caching the blinding factor avoids that call, and ordinary session-action calls do not expose the seed. Strict unlinkability even between operations in one composite request would require separate domain-separated capabilities, independent nonces, and unlinkable transport; that is a larger protocol mode than one RP request signature.

## Rollout

This is an in-place replacement of the unreleased request authorization format, not a parallel version. Clients, OPRF nodes, and WIP-101 contracts must roll out together: legacy signatures and the former WIP-101 calldata shape are no longer accepted. A rollback therefore requires rolling back all three components to the previous commit as one coordinated change.
